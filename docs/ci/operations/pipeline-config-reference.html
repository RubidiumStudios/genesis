Genesis v3 pipeline configuration reference

Operators' reference sheet for the repository-level and environment-level pipeline keys. Describes Genesis 3.2.0 pipeline build 3d2fcd89. Dated 2026-11-13. Every key, default and allowed value is taken from the schema and validation code of that build.

How to set the keys

  • Repository keys live under pipeline: in .genesis/config, which must be configuration version 3. The file is generated. Change it only with genesis config --set <key> <value> and genesis config --unset <key>, never by hand.
  • --set and --unset repeat, so several keys can change in one run. --set-from-file <key> <file> sets a key from a file (a collection is read as YAML or JSON). Bare arguments only read: genesis config pipeline.provider.type.
  • The command validates the configuration it would write and writes nothing if that configuration does not load. Set keys that depend on each other in the same run, and set pipeline.enabled last.
  • A pipeline section on a version 2 file is refused. Migrate with genesis config --set version 3; the pipeline keys can be set in the same run.
  • With --set, a boolean given as false, no, off, 0 or an empty string is false, and any other text is true.
  • Environment keys live in the environment's own YAML file, under genesis.pipeline. Edit the file and commit it on the control branch (or on a feature branch merged into it).
  • The block is read merged through the environment's file hierarchy, so a key in a shared file is inherited by every environment beneath it, and the nearer file wins.
  • The pipeline's shape is read from control. The pipeline section and every environment's keys take effect from the control branch, committed and pushed. genesis pipeline-apply runs from control, in step with the remote. The previews (genesis pipeline-describe, genesis pipeline-graph, genesis pipeline-apply --dry-run) read the working tree.
  • pipeline.source_control.repository, uri and control_branch are read from the working tree's own .genesis/config, because they say where control is.
  • Validation runs at configuration load, for every command. The checks beyond the schema run only when pipeline.enabled is true. A key the schema does not declare is refused by name.
genesis config --set pipeline.provider.type concourse --set pipeline.provider.url https://ci.example.com --set pipeline.provider.team main
genesis config --set pipeline.source_control.auth.type ssh --set pipeline.source_control.auth.path git
genesis config --unset pipeline.provider.public
genesis config --set pipeline.enabled true

Checks made at load, beyond the schema

These run for every command once pipeline.enabled is true. A refusal about an environment key names the key, the environment, and the file that sets it.

  • deployment_type must be a git ref component.
  • Every shape key must resolve from the environment's own files.
  • A key gated by a capability is refused where the provider does not declare it: genesis.pipeline.manual (optional_git_triggers) and genesis.pipeline.redeploy_cron (scheduled_jobs).
  • genesis.pipeline.redeploy_cron is refused when pipeline.redeploy.enabled is false.
  • manifest_store must be exodus, and every environment's Genesis floor must be 3.1.0 or later.
  • Every environment with a genesis.pipeline block must resolve genesis.exodus_mount to pipeline.exodus_mount.
  • The override file, .genesis/pipeline-overrides-<provider type>.yml, must be a YAML map. See the next section.
  • Every environment file must parse as YAML.
  • genesis.pipeline.prior_env must name an environment of the pipeline, and the chain must not form a cycle. This is checked where the topology is read from control.
  • genesis.pipeline.track_bosh_configs is refused on an OCFP environment that manages its own cloud configs.

Extending the pipeline with an override file

For a change to the compiled pipeline that no configuration key expresses: an extra resource, job or group, or a different value on something Genesis emits.

  • One file per provider type, beside .genesis/config: .genesis/pipeline-overrides-<provider type>.yml. Under Concourse that is .genesis/pipeline-overrides-concourse.yml. There is no key for it in the pipeline section and no override directory. The manual provider emits no pipeline, so it reads none.
  • How it is applied. After the pipeline is compiled, the file is merged over it with spruce merge, as written. Maps merge key by key. A list entry that has a name merges into the emitted entry of that name, and an entry with a new name is added. spruce's operators can be used.
  • When it takes effect. At genesis pipeline-apply, so run the apply after changing the file. genesis pipeline-apply --dry-run prints the pipeline with the override merged, and is where the names Genesis emits can be read.
  • Where it lives. In the repository, committed on control with the rest of the pipeline's definition.
  • What is checked. At load the file must be a YAML map. A merge that fails refuses the apply and sets nothing.
  • Migrating from v2. Anything a ci.yml carried outside its pipeline: key, which v2 merged over the generated pipeline, moves to this file.
# .genesis/pipeline-overrides-concourse.yml
resources:
- name: nightly          # a new name, so it is added
  type: time
  source: {interval: 24h}
jobs:
- name: nightly-report   # a new job beside the emitted ones
  plan:
  - get: nightly
    trigger: true

Secrets the pipeline expects in the vault

Under Concourse, each vault reference in .genesis/config is compiled to ((path.key)), which Concourse resolves from its secrets store. A secret <name> is looked for at <path_prefix>/<team>/<pipeline>/<name>, then <path_prefix>/<team>/<name>, then <path_prefix>/<shared_path>/<name>, which is /concourse/shared/<name> by default and is skipped where shared_path is "". <path_prefix> is pipeline.provider.secrets_store.path_prefix (default /concourse), <team> is pipeline.provider.team, and <pipeline> is pipeline.name or else deployment_type. genesis pipeline-apply checks every reference and refuses when one is missing, unless --missing-secrets-ok is given.

How a reference is written. The form differs by key. A credential block's path, and pipeline.shuttle.auth written as a path, take a secret path with no key. A credential block's component keys, the shuttle's two among them, and pipeline.source_control.api_token take <path>:<key>, and nothing else in this build: a value written as ((path.key)) is wrapped a second time and does not resolve. From build 94e35c72 on, those keys take either form, and a value that starts with (( is written into the pipeline as given. pipeline.notifications.slack.webhook takes either in both. The pipeline.locker keys are written into the pipeline as given, so a secret there is named as ((path.key)). Every path is relative to the store, as <name> above, and is compiled unquoted, so a path holding a dot does not resolve.

The reference in pipeline.notifications.slack.webhookthe key named in the referenceThe Slack webhook URL.
<path_prefix>/<team>/<pipeline>/webhooktokenOnly with pipeline.provider.git.webhooks. genesis pipeline-apply generates it, or keeps the one in place.
<path_prefix>/<team>/<pipeline>/bosh/<bosh_env>url, ca_cert, client, client_secretOnly for a director whose BOSH configs an environment tracks. genesis pipeline-apply copies them from the director's exodus record.

Genesis itself writes the pipeline's applied record at <pipeline.exodus_mount>_pipelines/<deployment_type>, for example /secret/exodus/_pipelines/bosh. It is not set by hand.

Worked examples

Both examples use the deployment type bosh and a chain of three environments, lab, then staging, then prod. Each shows the pipeline: block as it stands in .genesis/config once set with genesis config --set, and the matching fragment of each environment file on control. Outside the block, the load also needs version: 3, manifest_store: exodus (the default), a Genesis floor of 3.1.0 or later, and the repository's vault in secrets_provider, shown beneath each block. In either example, source_control.repository can be left out where the clone's remotes settle which repository the pipeline lives in; the manual provider requires nothing beyond the lines shown.

Manual provider

pipeline:
  enabled: true
  provider:
    type: manual
secrets_provider:            # genesis secrets-provider <target>
  url: https://vault.example.com
# lab.yml
genesis:
  env: lab

# staging.yml
genesis:
  env: staging
  pipeline:
    prior_env: lab

# prod.yml
genesis:
  env: prod
  pipeline:
    prior_env: staging

Under the manual provider, genesis.pipeline.manual and genesis.pipeline.redeploy_cron are refused, and no pipeline.provider key other than type is accepted.

Concourse provider

pipeline:
  enabled: true
  provider:
    type: concourse
    url:  https://ci.example.com
    team: main
  source_control:
    repository: example-org/bosh-deployments
    auth:
      type: ssh
      path: git              # holds private_key
    identity:                # optional
      name:  Genesis CI
      email: ci@example.com
  vault:                     # the vault itself is secrets_provider's
    auth:
      type: approle
      path: vault/approle    # holds role_id, secret_id
  locker:
    url: https://locker.example.com
  shuttle:
    backend: s3
    bucket:  genesis-pipelines
    auth:    shuttle         # holds access_key_id, secret_access_key
secrets_provider:            # genesis secrets-provider <target>
  url: https://vault.example.com

Concourse environment fragments

# lab.yml
genesis:
  env: lab
  pipeline:
    manual: false   # deploys when its branch moves

# staging.yml
genesis:
  env: staging
  pipeline:
    prior_env: lab
    manual: false

# prod.yml
genesis:
  env: prod
  pipeline:
    prior_env: staging   # waits for a person

An environment that says nothing of manual waits for a person, as prod does here.

Required by the schema: secrets_provider.url (set with genesis secrets-provider, and under the manual provider too), provider.url, provider.team, source_control.auth, vault.auth, locker.url, shuttle.backend, shuttle.bucket. The other lines are optional.

With require_pr: true on an environment, also set pipeline.source_control.api_token: the clone credential here is ssh.
