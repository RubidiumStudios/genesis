Pipeline Migration: v2 to v3

Genesis operator guide · applies to Genesis 3.2.x and later, moving a deployment repository from a v2 pipeline (ci.yml, genesis repipe) to a v3 pipeline configuration on the Concourse provider with a GitHub-hosted repository · audience: operators migrating a repository's pipeline · companions: Pipeline Accounts and Permissions and New Pipeline: Expected First Runs

1. Summary

A v3 pipeline is generated from .genesis/config and the environment files, and set with genesis pipeline-apply. It replaces the v2 model, in which every job watched the default branch through path filters, with branch propagation:

  • Changes are committed to one branch, control.
  • A propagate job delivers each change to a branch per environment, <env>/<type>, once the environment before it has deployed it.
  • Each environment's deploy reads its own branch.

Nothing migrates automatically. This guide is the cutover by hand:

  • the order to do it in (section 3);
  • where every ci.yml setting goes (sections 4 and 5);
  • the secrets the new pipeline reads, and where (section 6);
  • what was renamed (section 7);
  • what tools outside the pipeline must change (section 8);
  • what behaves differently (section 9);
  • what isn't available yet (section 10).
Genesis never retires the v2 pipeline. Pause it before you start, and apply v3 paused beside it under a different name where the names would collide. Deleting the v2 pipeline is your decision, made by hand once v3 has proved itself.

2. Before you start

  • Genesis 3.2.x embedded in the deployment root (genesis embed). Every pipeline task runs the root's own .genesis/bin/genesis, and the compile refuses without it.
  • A task image with git 2.34.1 or later. The default is genesiscommunity/concourse:latest.
  • A safe other than 1.26.0, on your machine and in the task image. That one release exports secrets in a form Genesis doesn't read, and Genesis refuses its output by name. Use 1.26.1 or later. The deployment vault's mount can be KV version 1 or 2.
  • Manifests kept in exodus (manifest_store: exodus), and every kit at 3.1.0 or later. The load refuses older ones.
  • Names that are valid git ref components for every environment and for the deployment type, because each becomes a branch name.
  • One exodus mount. Every environment's genesis.exodus_mount must resolve to the pipeline's pipeline.exodus_mount (default /secret/exodus/).
  • The services v3 requires, which v2 left optional:
    • a locker: locks are mandatory, with no opt-out;
    • an S3 bucket for the shuttle, which carries deployment events and redeploy requests.
  • The accounts in Pipeline Accounts and Permissions:
    • an automation account for GitHub;
    • an AppRole on the deployment vault;
    • your own admin GitHub token for the apply.

3. The cutover

  1. Pause the v2 pipeline. Pause every job, or the whole pipeline with fly -t <target> pause-pipeline -p <v2-name>. Once a v3 Genesis is embedded, a v2 task fails: the commands its tasks ran are retired. Leave it paused; don't destroy it yet.
  2. Make control. Cut it from the current default branch, keeping its history, and make it the repository's default branch on GitHub: 
    git switch -c control origin/<default-branch>
git push -u origin control
    History isn't carried into the deployment branches. Each deployment branch's first delivery is a single commit squashing control's applicable files. The branch must be named control: a different name, through pipeline.source_control.control_branch, isn't supported yet.
  3. Clear old environment-named branches. Delete a branch named for an environment alone (lab), or rename it to the new form (git branch -m lab lab/<type>). Every clone then runs git fetch --prune once.
  4. Write the configuration on control, with genesis config only. .genesis/config is generated, so don't edit it by hand. The order matters: 
    genesis config --set version 3
genesis config --set pipeline.name <name>        # see the callout below
genesis config --set pipeline.provider.type concourse
...                                              # section 4; enabled still false
genesis config --set pipeline.enabled true       # last
git rm ci.yml
    One genesis config run can't both unset and set the same key; use two runs. Then add the genesis.pipeline keys to the environment files (section 5), and commit.
  5. Publish the secrets the pipeline will read (section 6), at the team scope of Concourse's vault.
  6. Preview. Each of these reads your working tree, says in a banner how it differs from control on the remote, and changes nothing:
    • genesis pipeline-describe and genesis pipeline-graph show the environments and their order;
    • genesis pipeline-apply --dry-run prints the pipeline and runs the secret check;
    • genesis pipeline-diff compares the pipeline with the one Concourse has.
  7. Push control; the apply refuses a control the remote doesn't have.
  8. Apply, paused: 
    GITHUB_AUTH_TOKEN=<your admin token> genesis pipeline-apply --paused
    The apply does five things:
    • creates each <env>/<type> branch;
    • sets the branch rulesets;
    • writes the webhook token and the director credentials it owns (section 6);
    • checks every other secret;
    • records what it applied, and sets the pipeline, paused.
    Run the apply and any push as separate commands, and check the apply's exit status before you push.
  9. Review, then unpause the new pipeline in Concourse. Expect what New Pipeline: Expected First Runs describes:
    • propagate makes each environment's first delivery;
    • deploys run in order, a manual environment's when you start it;
    • each redeploy-<env> fails its first run on purpose;
    • a chained deploy stays pending until its predecessor has deployed once.
  10. Retire v2 when you're ready. Once every environment has deployed through v3, destroy the v2 pipeline by hand (fly -t <target> destroy-pipeline -p <v2-name>), and remove any GitHub webhook that pointed at it.
Pipeline names. pipeline.name defaults to the deployment type. If it would equal the v2 pipeline's name, choose another, for example <type>-v3. Applying v3 under the v2 name would overwrite the v2 pipeline, which this cutover forbids.

  • pipeline.provider.secrets_store, where Concourse's vault is not the repository's (section 6).
  • pipeline.provider.pipeline_state_after_apply, insecure, min_fly_version, fly_bin_path.
  • pipeline.provider.group_commits, which only accepts true.

5. Environment settings: layouts to genesis.pipeline

Each environment's place in the pipeline lives in its own file, under genesis.pipeline. These keys are read merged, so one set in a site file applies to every environment beneath it. They must resolve from the files alone: no (( vault )) or credhub values.

v2 layoutv3, in the environment file
A -> Bin B's file: genesis.pipeline.prior_env: A
auto <pattern>, for the environments it matchedgenesis.pipeline.manual: false
every environment the auto pattern did not matchnothing: an environment waits for a person unless it says manual: false
tagged: truegenesis.pipeline.provider.tag: <worker tag> (a string or a list); the environment's own name keeps the old effect
Manual is still the default. In v2 an environment was manual unless an auto pattern matched it. In v3 it's manual unless its file sets manual: false. Miss this, and a tier that deployed on its own waits for a person to press its button, which is the safe way to be wrong.

Other per-environment keys:

  • require_pr: deliveries arrive as a pull request into the environment's branch, which a reviewer approves and merges.
  • track_bosh_configs: watch the director's configs (section 9); Classic environments only.
  • track_additional_files: replaces required_files.
  • track_dependencies, redeploy_cron: accepted, but nothing acts on them yet (section 10).
  • The director is genesis.bosh_env, as before. It also names the director's lock.

Retired keys are refused naming their replacement. This covers locks, status_signal, signal_prefix, required_files, redeploy, redeploy_cron_start and redeploy_cron_stop. The per-environment notifications override loads but is not honoured yet, so leave it unset.

6. Secrets

The pipeline carries no secret. Each is a Concourse variable, ((path.key)), which Concourse resolves from its own vault in this order:

<path_prefix>/<team>/<pipeline>/<path>   then   <path_prefix>/<team>/<path>   then   <path_prefix>/<shared_path>/<path>

path_prefix is /concourse and shared_path is shared, so the third place is /concourse/shared, unless pipeline.provider.secrets_store says otherwise. That block also names Concourse's vault by URL where it isn't the repository's own.

The shared path must match Concourse's own. shared is what the Genesis Concourse kit sets --vault-shared-path to. Genesis can't read the server's setting, so on a Concourse run with another shared path, set shared_path to it, and on one run with none, set shared_path: "". Otherwise the apply's check reports a secret found where Concourse never looks.

The inventory below is every secret a v3 pipeline can read. The path in each row is the one you name in .genesis/config; Concourse looks for it under the scopes above.

How a secret is named

  • A credential block (source_control.auth, vault.auth, registry.auth, shuttle.auth) names a path, and each of its keys is read from that path under its own name. The shuttle's may be written as the path alone.
  • One value (api_token, the Slack webhook, or one key of a credential block stored under another name) is written as <path>:<key>, or in Concourse's own form, ((path.key)). The two mean the same.
  • The locker's keys are written into the pipeline as given, so its password is written only in Concourse's form.
  • Keys v2 stored under other names can stay. Name each where it is held, in place of the path: 
    pipeline.shuttle.auth.access_key_id      management-bucket:aws_access_key_id
pipeline.shuttle.auth.secret_access_key  management-bucket:aws_secret_access_key
pipeline.vault.auth.role_id              <path>:approle_id
    Each is set with genesis config --set <key> <value>.
  • The apply's secret check. Before it sets anything, pipeline-apply looks every reference up where Concourse would and reports it as found, missing, or unverified (when it can't read the store). It never prints a value. A missing reference refuses the apply unless you give --missing-secrets-ok.
  • Access the apply needs. The operator running it needs write access to the pipeline scope, and read access to the tracked directors' exodus records in the deployment vault.
  • Silence safe set when you publish a secret by hand, because it echoes the value:
safe -T <concourse-vault> set concourse/<team>/github token="$(pbpaste)" >/dev/null 2>&1; echo "rc=$?"

A v2 webhook secret shared by every git resource is replaced by the pipeline's own token. A v2 pipeline's per-director credentials are no longer referenced except through the apply's copy.

8. Tools outside the pipeline

  • Redeploy requests. Anything that asked for a redeploy by writing to a v2 shuttle path, such as another pipeline or a secret-rotation job, now writes to the shuttle bucket at <env>-<type>/redeploy. Readers of deployment events read <env>-<type>/deployed and /redeployed.
  • Pipeline overrides and scripts keyed to v2 names (<env>-<type> jobs, -changes, -cache, git) match nothing in v3. Rename them using section 7.
  • GitHub webhooks. The apply manages only the hook that calls its own pipeline. Remove a v2 pipeline's hook by hand when you retire it.
  • Commands.
    • genesis repipe (and genesis push), genesis graph and genesis describe are retired in 3.2. Each refuses, whatever it is given, and names its replacement: pipeline-apply, pipeline-graph and pipeline-describe. Update any script that calls them.
    • The commands a v2 task ran (ci-pipeline-deploy, ci-show-changes, ci-generate-cache) are retired.
  • Deploying by hand. While the pipeline is enabled, genesis <env> deploy and propagate refuse at a terminal without --force, since a hand deploy takes none of the pipeline's locks. --dry-run is always allowed.
  • Scripts that read an exit status. A Genesis command that fails no longer exits 1 for everything. Section 9 lists the codes; a wrapper that tests for exactly 1 needs changing.
  • An older Genesis against the same director. Don't run one while 3.2 deploys there; section 9 says why, under the network claims lock.

9. What behaves differently

  • Delivery by branch.
    • You commit to control. propagate delivers each control commit to every environment it touches.
    • A delivery mirrors the environment's files: its hierarchy, .genesis/config, kits, ops/, the embedded Genesis, and its track_additional_files.
    • A deploy reads its own branch's tip and writes nothing back to git. Manifests live in exodus.
  • Holds.
    • A change waits until the environment before it has deployed it.
    • A control commit with a Genesis-Stage: <reason> trailer is held until it's released.
    • Every environment starts uncertified and holds those after it until it deploys once through the pipeline. Nothing deployed before the migration counts.
  • Pull request environments.
    • With require_pr, each delivery opens or updates pr/<env>/<type> as one commit, merged by rebase only.
    • A reviewer needs Write and must not be the automation account.
    • One Slack message per run lists the pull requests.
    • A merge waits for the branch's next poll.
  • Manual environments. Their deploy never triggers on its own. Their notify job posts what deploying would change, and a deploy started by hand names who started it.
  • Locks are always on.
    • A deploy or redeploy holds its own deployment's lock.
    • A director's deploy also holds that director's lock against the deployments on it.
    • A lost worker can strand a lock; release it with the locker's own tools.
  • Redeploys. redeploy-<env> runs deploy --redeploy on request, by its button or from the shuttle queue. Nothing triggers it automatically yet.
  • BOSH config tracking only notifies.
    • One check per director and config type, and one Slack notice per director when a config changes.
    • The first check after an apply sends one notice.
    • It triggers no deploy or redeploy.
    • An OCFP environment, which uploads its own configs, refuses the key.
  • Worker tags go only on the steps that need an environment's network: its deploy, redeploy and notify tasks, and its director's config checks. Untagged workers must reach GitHub, the vault, the locker, S3, Slack and Concourse itself.
  • Webhooks. With webhooks on, a push to control is checked at once, and propagate asks Concourse to check each branch it pushes. Other moves wait for the poll. GitHub allows twenty push hooks per repository.
  • The apply is repeatable. It reports each write as new, changed or already in place.
  • Previews read your working tree; the apply reads control.
    • pipeline-describe, pipeline-graph, pipeline-diff and pipeline-apply --dry-run read the working tree, so a change can be checked before it is committed. A banner lists every way the tree differs from control on the remote, and --from <ref> previews a commit instead.
    • A real apply runs only from control, committed and pushed.
  • Slack messages begin with an emoji naming their kind and link to their build.
  • Build logs are private unless pipeline.provider.public is set.
  • Removing an environment.
    • Deleting an environment's file from control leaves its branch, its ruleset, any open pull request and its vault records behind. pipeline-apply lists each such environment as an orphan, with what it left.
    • pipeline-apply --cleanup-orphans removes those traces, after asking. It removes nothing where it couldn't read an orphan's vault records, since they are among the traces.
    • Neither tears the deployment down. Where an orphan is still deployed, the apply says so: restore its file from its branch and run genesis <env> terminate.
  • The network claims lock. A deploy that writes a director's network claims takes a lock in the vault, which 3.2 keeps in a secret of its own. An older Genesis keeps it elsewhere and doesn't see the new one. 3.2 refuses while an older Genesis holds a fresh lock, but the reverse isn't true, so don't run an older Genesis against a director while 3.2 deploys there.

When the vault can't be read

Genesis reads records from the vault to decide what to do: what an environment last deployed, whether a hold stands, what the pipeline was applied from. In 3.2 a read that fails is never taken for a record that isn't there.

  • A command stops on a record it couldn't read, names the path and what the vault said, and says what it had done by then. A deploy stops before it deploys. A secrets command stops before it changes anything.
  • A report keeps the row. pipeline-status prints every environment, puts the reason on the row it couldn't read, and exits non-zero. A propagate run fails that one environment, holds those after it, and delivers to the rest.
  • The exit status names the cause, so a wrapper can tell what to do next:
ExitCauseWhat helps
77The vault refused the read: the token has no access to the path, or has expired.Authenticate again, or have the policy extended. A retry alone does not.
69The vault gave no usable answer: sealed, unreachable, or an answer Genesis couldn't read.A retry, once the vault answers.
65The record was read and isn't a valid one, or the repository's state is not what the command needs.Look at what the message names, and repair it.
78The configuration is wrong or incomplete.Fix the configuration.
75A fault the next run may clear, such as a failed push.Run it again.
130You declined, or interrupted it.

A propagate run with more than one failed environment exits the most serious of their causes, in the order 78, 77, 65, 69, 75. In pipeline-status --json, a row that couldn't be read carries the same code as exit_code, beside its error.

10. Not available yet

  • Automatic redeploys:
    • on a schedule (redeploy_cron loads but schedules nothing);
    • when a dependency deploys (track_dependencies is recorded only);
    • when a stemcell or a director's config changes.
  • Automatic kit and Genesis updates (v2's update-genesis-assets).
  • Errands and tasks run after a deploy.
  • A director's deploy refreshing the credential copies of the pipelines that track it. Until then, re-run pipeline-apply after a director's credentials rotate.
  • A watcher that checks a deployment branch when a pull request merges, instead of waiting for the poll.
  • The apply using the pipeline's own GitHub token for the hook. It uses yours.
  • A per-environment polling interval, and per-environment notification settings.

11. Checklist

  1. v2 pipeline paused.
  2. control cut from the default branch, pushed, and made GitHub's default.
  3. Old environment-named branches deleted or renamed.
  4. genesis config: version 3, the pipeline block (section 4), pipeline.enabled true last.
  5. ci.yml removed.
  6. Environment files: prior_env, manual: false on every formerly auto environment, tags, and tracking (section 5).
  7. Genesis 3.2.x embedded.
  8. Secrets published at the team scope, with v2 key names changed where needed (section 6).
  9. Locker TLS settled: nothing to set where v2 relied on its default, or skip_ssl_validation: false with ca_cert where the locker is to be verified (section 4).
  10. safe is not 1.26.0, on your machine and in the task image.
  11. pipeline.name differs from the v2 pipeline's.
  12. Previews clean, and pipeline-apply --dry-run finding every secret.
  13. control pushed.
  14. genesis pipeline-apply --paused run with an admin GITHUB_AUTH_TOKEN, and its exit status checked.
  15. The new pipeline reviewed and unpaused, and its first runs as Expected First Runs describes.
  16. Tools outside the pipeline updated (section 8).
  17. When every environment has deployed through v3: the v2 pipeline destroyed and its webhook removed, by hand.
