Pipeline Accounts and Permissions

Genesis operator guide · applies to Genesis 3.2.x and later with a v3 pipeline configuration on the Concourse provider and a GitHub-hosted deployment repository · audience: operators setting up a deployment repository's pipeline, and the repository and vault owners who grant it access

1. Summary

A pipeline acts on four systems: the GitHub repository, the deployment vault, Concourse, and the services Concourse talks to on its behalf (the shuttle's object store, the locker, Slack). Each needs an identity with just enough access, and each identity's secret is stored where Concourse can resolve it. This guide lists every identity, where its credential lives, and the GitHub and vault permissions it needs, and it says what to do where a client will not let the pipeline's people set branch rules themselves.

The pipeline acts on GitHub as an automation account. Everything the pipeline does on GitHub should use a dedicated automation (machine) account, never an operator's personal account. That covers cloning and pushing over HTTPS, and opening and reading pull requests. This is the common and recommended practice, for four reasons:
  • The pipeline keeps working when a person leaves or changes role.
  • Its pushes and pull requests are attributed to the pipeline, not to a person.
  • Its access can be scoped to the repositories it serves.
  • Where an environment sets genesis.pipeline.require_pr, GitHub does not let the author of a pull request approve it. A pull request opened with a person's own token cannot be approved by that person, so there it is a requirement, not a preference.
Operators keep their own logins for what they run at a terminal, such as genesis pipeline-apply.

3. Where credentials are stored

The pipeline carries no secret. .genesis/config names each one by a vault reference, and the compiled pipeline turns that into a Concourse variable, ((path.key)), which Concourse resolves from its own credential store at run time. That store is the vault Concourse is configured with, which is usually not the deployment vault. Concourse looks a variable up under the team's path, first per pipeline, then per team, and then under a shared path where the Concourse administrator has configured one:

Where Concourse's store is not the repository's own vault, pipeline.provider.secrets_store in .genesis/config names it by URL, with its path_prefix and, where the Concourse administrator configured one, its shared_path; each operator reaches it through their own safe target for that URL. Publish the credentials the pipelines share, such as the locker's, the shuttle's and the AppRole, at the team scope, <path_prefix>/<team>/. A shared path works too, where the Concourse administrator has configured one, but the team scope is the recommendation. Before it sets anything, genesis pipeline-apply looks up every reference the compiled pipeline uses where Concourse would, reports each as found, missing or unverified, and refuses on a missing one unless given --missing-secrets-ok.

With HTTPS auth, the clone credential's password is a GitHub token, and propagate uses it to open pull requests too, so api_token is not needed. It must then carry the pull request permissions in section 4, and it must belong to the automation account. With SSH auth, api_token is required wherever an environment sets require_pr, because GitHub's API takes no SSH key, and genesis pipeline-apply refuses to compile the pipeline without it.

When storing a secret with safe, silence both of its output streams, since safe set echoes the value:

safe -T <concourse-vault> set concourse/main/github token="$(pbpaste)" >/dev/null 2>&1; echo "rc=$?"

A rotated credential needs nothing reapplied: Concourse reads it again at the next build that uses it. A token that expires stops propagation with a 401 from GitHub, naming the host.

  • Fine-grained tokens are created under the resource owner of the repository, the organization, not the person's own account, with Only select repositories naming the deployment repository. Where the organization requires approval, a new token answers as though the repository did not exist (HTTP 404) until an owner approves it under the organization's Settings → Personal access tokens → Pending requests.
  • The operator's GitHub token is read from GITHUB_AUTH_TOKEN in their shell when they run genesis pipeline-apply. Where that is not set, the apply uses the automation account's token, the one pipeline.source_control.api_token names, reading it from the secrets store where Concourse would and saying which path it came from, never its value. That token then needs the operator's rights above as well as its own, so a site that wants no admin token in the store leaves it with pull requests alone and gives the apply one in the shell. With neither, the apply does everything else and says skipped the branch protection, because GITHUB_AUTH_TOKEN is not set, and why the store gave none. With a token that lacks admin, it warns, names each branch it could not protect and the rules it needed, and carries on. With webhooks on and a token that lacks Webhooks, it reports the hook unverified and prints the URL to configure by hand, the token named but not shown; past GitHub's twenty push hooks per repository it reports GitHub's refusal, and the branches' fallback poll does the work. The operator's own vault access must also let them write concourse/<team>/<pipeline>/webhook, where the apply keeps the token, and concourse/<team>/<pipeline>/bosh/*, where it copies each tracked director's credentials, and read those directors' exodus records in the deployment vault.
  • Other rules in the repository must not stop the pipeline's own pushes. A repository-wide or organization ruleset that requires pull requests on every branch, or restricts who may push, will refuse the clone credential's pushes to deployment branches and to pr/ branches unless the automation account or deploy key is on its bypass list.
  • The automation account's token is best created as a fine-grained token by the automation account itself, under the organization, so its access ends with the account rather than with a person. Where the organization uses a GitHub App for automation instead, the App's installation token serves the same role.

5. The branch rules the apply sets

One GitHub ruleset per branch, named genesis-<branch>, active, targeting that branch alone. A re-run of the apply sends nothing where the rules it would send already stand, and replaces a ruleset of that name, rather than adding another, where they differ. After a replacement, check that any bypass list an owner added is still in place.

BranchRules
controlblock force pushes; require linear history; and, where pipeline.source_control.control_requires_pr is true, require a pull request with one approving review, merged by squash or rebase
each deployment branch, <env>/<type>block force pushes; require linear history
a deployment branch whose environment sets require_pras above, and require a pull request with one approving review, merged by rebase only, so the marker in each commit survives the merge

The pull request rule keeps an approval standing across the rebuild a later propagate pushes (it does not dismiss stale reviews), and it requires no code owner review, no approval of the last push and no resolution of threads.

6. Where the operator may not set branch rules

Some clients do not allow the people who run the pipeline to administer the repository. The pipeline still works without its branch rules, but nothing on GitHub then stops a force push to control or a deployment branch, or a merge into a pull request environment's branch without review. Have a repository owner set them by hand:

  1. Run the apply without admin, either without GITHUB_AUTH_TOKEN or with a token that lacks Administration. It applies everything else, and with a token it lists, per branch, the rules it could not set.
  2. Send the owner the branch list and section 5's rules for each. For each branch, the owner opens the repository's Settings → Rules → Rulesets → New ruleset → New branch ruleset, names it genesis-<branch>, sets Enforcement status to Active, adds the branch as a target by its full name, and enables Block force pushes and Require linear history; and for a pull request branch, Require a pull request before merging with 1 required approval and Allowed merge methods set to Rebase (Squash and Rebase for control).
  3. Use exactly those names, so a later apply run by someone with admin recognises the rulesets as its own and replaces them rather than adding a second set beside them.

Branches are added by the apply when an environment is added, and an environment that later sets require_pr needs its pull request rule added, so the owner's step repeats with those changes.

7. Vault permissions

The pipeline's tasks log in to the deployment vault with the AppRole. Its policy needs, on a KV v2 mount named secret:

path "secret/data/*"                       { capabilities = ["read", "list"] }
path "secret/metadata/*"                   { capabilities = ["read", "list"] }
path "secret/data/<secrets base>/*"        { capabilities = ["create", "read", "update", "list"] }
path "secret/data/exodus/*"                { capabilities = ["create", "read", "update", "delete", "list"] }
path "secret/metadata/exodus/*"            { capabilities = ["read", "delete", "list"] }
  • Read everywhere the manifests read secrets from.
  • Create and update under each environment's secrets base, because a pipeline deploy generates missing secrets and rotates expiring ones (deploy -F). A secret only a person can supply is never written; the deploy refuses and names it.
  • Full access under exodus, where each deploy writes its record and replaces older ones; delete on the metadata is what lets it prune.

Store the AppRole's role_id and a secret_id in Concourse's vault at the path pipeline.vault.auth names. A new secret_id is needed only where the role was recreated or its secret id expired; a policy change takes effect at the next login. The operator's own vault login writes the applied record during pipeline-apply.

8. Setup checklist

  1. Create or choose the automation account, a machine account rather than a person's; give it Write on the repository; create its fine-grained token (section 4) and have an owner approve it if required.
  2. Create the clone credential: a deploy key with write access, or the automation account's HTTPS token. Not an operator's personal token.
  3. Create the AppRole and its policy on the deployment vault (section 7).
  4. Store every credential in Concourse's vault at the paths section 3 lists.
  5. Set the matching keys in .genesis/config, commit and push control.
  6. Run genesis pipeline-apply with an admin token in GITHUB_AUTH_TOKEN, or without one and follow section 6.
  7. Check the rulesets under the repository's Settings → Rules, and that reviewers can approve a pull request the pipeline opens.
