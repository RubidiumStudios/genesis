New Pipeline: Expected First Runs

Genesis operator note · applies to Genesis 3.2.x and later with a v3 pipeline configuration on the Concourse provider · audience: operators publishing a deployment repository's pipeline with genesis pipeline-apply

1. Summary

Until each environment has deployed once through a newly published pipeline, two of the pipeline's jobs behave in ways that look like faults and are not. Both clear by themselves after that first deploy.

The redeploy. A published pipeline has a redeploy-<env> job for every environment, beside its deploy-<env> job. A redeploy deploys again exactly the commit that last deployed successfully, which is how secrets, configs or stemcells changed outside git reach a running deployment without new content from propagation.

The first redeploy runs on its own when the pipeline is published. Each redeploy-<env> job starts once, by itself, as soon as Concourse first checks the job's request queue. No one pressed anything.
That run fails, and so does every redeploy until the environment has deployed once through the pipeline. A redeploy refuses unless the last successful deploy was made with Genesis 3.2.x or later from the environment's own deployment branch, which is what a pipeline deploy does. Nothing is deployed, nothing on the director changes, and the refusal says why.

After one successful deploy of an environment from its deployment branch, through the pipeline's deploy-<env> job, including an environment set to genesis.pipeline.manual whose deploy is started by hand, that environment's redeploy works. Sections 2 to 4 explain this. They apply only where the pipeline has redeploy jobs: pipeline.redeploy.enabled: false in .genesis/config emits none, and then there is no first redeploy to expect.

The chained deploy. An environment that names another as its genesis.pipeline.prior_env follows it: it takes only what its predecessor has deployed.

A chained environment's deploy waits until its predecessor has deployed once through the pipeline. Until then, deploy-<env> for the follower does not start, even when pressed: its build stays pending. Nothing fails, and nothing is deployed.

Section 5 explains this.

2. Why the first redeploy runs

The redeploy job is triggered by a request queue, a shuttle resource named redeploy_<env>-<type>, so that the job's own button, and in time other pipelines and the CLI, can ask for a redeploy. Concourse runs a job only when every resource it reads has a version, so the queue is given a starting version (its seed) to keep the button usable before anyone has written a request. Concourse starts a build whenever a triggering resource shows a version the job has not run on yet, and the seed is such a version. So the first check after publishing runs the job once.

This is a property of how Concourse schedules jobs, not a choice made per environment, and it cannot be turned off without losing the redeploy's trigger. The run is made harmless instead, by the refusal in section 3.

3. Why the redeploy refuses

A redeploy takes the commit named in the environment's last successful deploy record and checks it out. It stands only on a recorded commit that is on the environment's deployment branch, <env>/<type>, and refuses everything else, because anything else is not a redeploy of what that branch delivered. On a newly published pipeline every environment is in one of two states, and both refuse:

3.1 No deploy recorded

The environment has never deployed successfully, or its newest record names no commit, which an older record format can.

Refusing to target the deployed commit for <env>.

No successful deploy recorded in /secret/exodus/<env>/<type>/deployments
names a commit, so there is nothing on <env>/<type> to deploy again, and
its tip may carry content that has never been deployed.

3.2 Last deployed before the pipeline

The last deploy ran from the repository's old branch, which is every environment migrating to the pipeline. The commit may still exist elsewhere in the repository; it is refused all the same, because it is not on the deployment branch.

Refusing to target the deployed commit for <env>.

The deployed commit <sha>, named by /secret/exodus/<env>/<type>/deployments,
is not on <env>/<type>: it was deployed from another branch, before this
pipeline delivered to <env>/<type>, or the branch has been rewritten since,
and only a commit on the deployment branch can be stood on.

Both exit with code 78 (configuration). The deploy branch's tip is never used in their place, since it may carry changes that have not been deployed yet, and deploying them is the deploy-<env> job's work, not the redeploy's.

Where Slack is configured, the failure posts as usual, with a link to the build:

<pipeline>: Concourse redeploy of <env>-<type> failed (redeploy-<env> #1)

The run takes and releases the environment's deployment locks like any redeploy, so a deploy started at the same moment waits for it, briefly, and then proceeds.

4. What to do

4.1 After publishing

Nothing. Expect one failed redeploy-<env> build per environment, numbered #1, and leave it. Open it only to confirm the refusal is one of the two in section 3; any other failure is a real problem and should be read as one.

4.2 Enable the redeploy for an environment

  1. Deploy the environment through the pipeline once, with its deploy-<env> job. For an environment set to genesis.pipeline.manual: true, that is pressing the job's button after its notify-<env> job has posted the pending changes. The deploy records the deployment-branch commit it stood on.
  2. Confirm the record, without deploying anything. This reads the environment as deployed and refuses with the messages of section 3 if the record is not yet usable: 
    genesis <env> info --as-deployed
  3. From then on, redeploy-<env>'s button redeploys that commit.

The same holds for a deploy with Genesis 3.2.x or later run by hand while standing on the environment's deployment branch, since it records that branch's commit too. A deploy made from any other branch does not count.

5. A chained deploy waits for its predecessor

When an environment sets genesis.pipeline.prior_env, its predecessor's deploy job draws a line to its own deploy job in the pipeline view, left to right in the order changes travel. The line is the <prior>-<type>_deployed event: the predecessor's deploy-<prior> writes it on success, and the follower's deploy-<env> reads it with passed: [deploy-<prior>]. Concourse draws a line between two jobs only for passed.

The same passed is also a rule Concourse enforces: the follower's deploy runs only on an event that came out of a successful deploy-<prior> build. A new pipeline's event resource holds only its starting version, its seed, which no deploy wrote. So until the predecessor has deployed once through the pipeline, the follower's deploy has no input it may use, and a build of it, pressed or triggered, stays pending, waiting for a suitable set of input versions. It does not fail, and it starts on its own, without another press, once the predecessor's deploy succeeds.

This only matches what the chain already means. Propagation holds the follower's changes until its predecessor has deployed them, and reports the follower as held, awaiting deployment meanwhile, so in ordinary use there is nothing for the follower to deploy before its predecessor has deployed.

Two things are not affected:

  • propagate, which also reads the predecessor's _deployed, to deliver the follower's changes when the predecessor deploys. It reads it without passed, so a new pipeline's first propagation, which the predecessor's first deploy depends on, never waits.
  • redeploy-<env> for the follower, which reads no event of its predecessor. It is governed by sections 2 to 4.

5.1 What to do

Deploy the predecessor through the pipeline first, as section 4.2 describes. The follower's pending deploy, if one was pressed, then starts.

Where the follower must deploy before its predecessor ever has, deploy it by hand with Genesis 3.2.x or later, standing on its deployment branch <env>/<type>. The pipeline's deploy job cannot do it, by design.

6. Caveats

Changing the shuttle settings starts a redeploy again, and makes a chained deploy wait again. Concourse treats a resource whose settings changed as a new resource, with a new seed and none of the old one's history. After a change to pipeline.shuttle (bucket, endpoint, credentials) is applied, and after the shuttle credentials are rotated in the vault Concourse reads them from, since Concourse compares the settings with the credentials filled in:
  • expect each redeploy-<env> job to run once more. For an environment that has already deployed through the pipeline that run is a real redeploy of its deployed commit, and it succeeds.
  • expect each chained environment's deploy to wait again, as in section 5, until its predecessor next deploys through the pipeline.
  • expect propagate to run once. It delivers whatever is due, and nothing where nothing is.
Pause the redeploy jobs first if a redeploy is unwanted: 
fly -t <target> pause-job -j <pipeline>/redeploy-<env>

Re-running genesis pipeline-apply with no change, or with changes to anything other than the shuttle, does none of this: each event resource keeps its versions.
