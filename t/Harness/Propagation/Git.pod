=head1 NAME

Harness::Propagation::Git - the Service::Git test subclass with a step counter

=head1 SYNOPSIS

  my $git = fault_git($h);
  fail_on($git, 'checkout_file', 3);
  skip_on($git, 'push', 1);
  my @steps = step_log($git);

=head1 DESCRIPTION

Fault injection is the technique in which the harness makes a chosen git step
fail partway and the row then asserts the invariants hold.  This subclass
counts each intercepted step, appends it to a log, and dies where the plan
arms it, delegating to C<Service::Git> otherwise.

A plan entry can carry an action instead of a death.  The wrapper runs that
command at the armed call and then delegates as it always would, so the step
itself still happens.  That is how C<move_on_r_at> has a teammate move a
branch on R in the middle of a run, at the step the row names, rather than
before it, where the run's own refresh would absorb the move and no push
would ever be rejected.

A plan entry can also carry a skip, which C<skip_on> arms.  The wrapper
returns at the armed call without delegating, so the step is reported in the
log and its write never lands, and the run carries on as though the write had
gone through.  A fault cannot make that shape, because a death is not a
silence, and the rows that weigh a write reported and never made need the
silence rather than the death.

The plan and the log are files named by the environment rather than fields on
an object, because the rows run whole commands and a spawned C<genesis> child
builds its own handle.  The child loads this module through C<PERL5OPT> and
C<import> makes C<< Service::Git->new >> answer with a subclass instance.  No
file under C<lib/> changes.

C<Service::Git> caches one instance per repository and answers every later
caller with it, whatever class that caller asked for, so C<fault_git>
re-blesses the cached instance rather than building a second one.  A row that
read a copy before it armed a fault still meets the fault.

=head1 STEPS

C<checkout>, C<checkout_file>, C<add>, C<rm>, C<commit>, C<create_branch>,
C<fetch_branch>, C<fetch_branches>, C<push>, C<delete_remote_branch>, and
C<reset_working_tree>.

Some of these steps call others, and the wrappers catch the inner call as
readily as the outer one.  C<< $git->commit($message, @files) >> stages the
files by calling C<add> itself, so a row that commits with files sees
C<commit> and then C<add> in the log, and the C<add> counter moves as well.
A row that arms C<add> arms that inner call too.

=cut
