=head1 NAME

Genesis::Top - Root-directory context object for Genesis deployment repositories

=head1 SYNOPSIS

    use Genesis::Top;

    # Open an existing deployment repository
    my $top = Genesis::Top->new('/path/to/cf-deployments');

    # Open with a specific vault target for this session
    my $top = Genesis::Top->new('/path/to/cf-deployments', vault => 'prod-vault');

    # Create a new deployment repository
    my $top = Genesis::Top->create('/repos', 'cf');

    # Common operations
    my $env  = $top->load_env('us-east-prod');
    my $kit  = $top->local_kit_version('cf', '2.3.0');
    my $type = $top->type;   # Returns: 'cf'

    # Check vault connectivity
    if ($top->has_vault) {
        my $v = $top->vault;
        printf "Using vault: %s\n", $v->name;
    }

=head1 DESCRIPTION

Several interactions with Genesis have to take place in the context of a
I<root> directory. Often this is a C<something-deployments> git repository.

C<Genesis::Top> abstracts operations on that root directory so that other
parts of the codebase can stop worrying about file paths and instead carry
around a C<Top> context object which handles those concerns for them.

A C<Top> object manages:

=over 4

=item * The repository root path and file operations relative to it

=item * The configuration stored in C<.genesis/config>

=item * Connectivity to the Vault secrets provider

=item * Kit discovery, download, and version resolution

=item * Environment loading and creation

=back

Inherits from L<Genesis::Base>, which provides memoization helpers
(C<_memoize>, C<_set_memo>, C<_clear_memo>, C<_get_memo>).

=head1 CONSTANTS

=head2 DEFAULT_CONTROL_BRANCH

The branch a branch-based pipeline treats as authoritative when
C<pipeline.source_control.control_branch> is not configured. Read through
L</control_branch> rather than directly.

=head2 DEFAULT_PR_PREFIX

The prefix a pull request branch carries when
C<pipeline.source_control.pr_prefix> is not configured. Read through
L</pr_prefix> rather than directly.

=head1 METHODS

=head2 new

    my $top = Genesis::Top->new;

Opens an existing Genesis deployment repository. With no arguments, opens
the current directory. When the first argument is an odd-length list element
(i.e., a plain scalar followed by pairs), it is taken as C<$root>; otherwise
C<$root> defaults to C<'.'>.

As a side effect, sets C<$ENV{GENESIS_ROOT}> to the absolute path of the
repository, and sets C<$ENV{GENESIS_TARGET_VAULT}> and C<$ENV{SAFE_TARGET}>
to the vault name when a vault is successfully connected.

B<Parameters:>

=over 4

=item C<$root>

B<(optional)> Path to the root of an existing Genesis deployment repository.
Defaults to C<'.'> when the argument list has an even number of elements.

=item C<vault>

B<(optional)> Name or URL of a safe target to use for this session only.
Overrides the vault stored in the repository configuration without saving
the change.

=item C<no_vault>

B<(optional)> When true, disables vault connectivity entirely for this
object. Intended for test contexts.

=item C<materialised_tree>

B<(optional)> When true, says the repository is a tree written out of a
commit rather than a working checkout. Such a tree carries no vault of its
own and cannot answer the repository questions the configuration checks ask,
such as whether an enabled pipeline sits in a git checkout with a remote
behind it, so vault attachment and configuration validation are both skipped
and C<$ENV{GENESIS_TARGET_VAULT}> and C<$ENV{SAFE_TARGET}> are left alone.
C<$ENV{GENESIS_ROOT}> is still set, as it is for any other Top, so a caller
that must leave the process as it found it localises that one itself.  The
caller that materialised the tree has already had those answers from the
repository it is running in.  L<Genesis::Env/propagation_files_at> is the
reader this exists for.

It also marks the object as already being its own shape: L</_shape> and
L</pipeline_topology> answer for such a tree's own files rather than reading
control out of it, since a tree written out of one control commit has
nothing further to read and reading it that way is what stops a read of
control from reading control again.

=item C<repair_config>

B<(optional)> When true, L</config> reads a version 2 or 3 configuration
without refusing it. The schema is installed and its defaults filled, as
for any load, and the version is recorded for L</_current_config_schema>,
but nothing the file carries is refused: no unknown key, no retired key,
no pipeline section in a version 2 file, and none of the checks that follow
the schema. C<genesis config> is the caller, because a configuration every
other command refuses is the one an operator most needs it for, and it
judges the configuration it would write instead. A version 1 or
unsupported version loads as it would without the option.

=back

B<Returns:> A new C<Genesis::Top> object.

B<Errors:>

=over 4

=item *

C<"'$root' is not a Genesis deployment repository"> - raised when the
specified path does not contain a valid C<.genesis/config> file.

=back

B<Examples:>

    # Open current directory as a Genesis Top object
    my $top = Genesis::Top->new;
    # Returns: Genesis::Top object for the current directory

=head2 create

    my $top = Genesis::Top->create($path, $name, %opts);

Creates a new Genesis deployment repository under C<$path>. Strips a
trailing C<-deployments?> suffix from C<$name> before use. The repository
directory is created as C<$path/$dir> where C<$dir> defaults to
C<$name> (or C<$name-deployments> when the legacy suffix is enabled in the
Genesis RC configuration).

The method writes C<.genesis/config>, creates the C<.genesis/> directory
hierarchy, creates the local kits directory (when C<kits_path> is supplied),
and generates a C<README.md>.
On failure the partially-created directory is removed and the error is
re-thrown.

Sets C<$ENV{GENESIS_ROOT}> as a side effect (inherited from C<_build>).

B<Parameters:>

=over 4

=item C<$path>

B<(required)> Parent directory under which the new repository directory is
created.

=item C<$name>

B<(required)> Deployment type name (e.g., C<'cf'>, C<'bosh'>, C<'vault'>).
A trailing C<-deployments?> suffix is stripped automatically. Must match
C</^[a-z][a-z0-9_-]+$/> after stripping.

=item C<directory>

B<(optional)> Override the final directory name. Defaults to C<$name> or
C<$name-deployments>.

=item C<vault>

B<(optional)> Safe target name or URL to record as the secrets provider.

=item C<no_vault>

B<(optional)> When true, skips vault configuration. Raises an error if
C<$ENV{GENESIS_COMMAND}> is set (i.e., running in a real genesis session,
not a test).

=item C<kits_path>

B<(optional)> Path to the directory where compiled kits are stored.
Humanized relative to the repository root when possible, otherwise stored
as an absolute path (with C<~> substituted for the home directory prefix).

=item C<creator_version>, C<updater_version>, C<minimum_version>, C<manifest_store>

B<(optional)> Override the corresponding config keys written to
C<.genesis/config>.

=back

B<Returns:> A new C<Genesis::Top> object pointing at the newly created
repository.

B<Errors:>

=over 4

=item *

C<"Invalid Genesis deployment repository name '$name'"> - raised when
C<$name> (after stripping the suffix) does not match C</^[a-z][a-z0-9_-]+$/>.

=item *

C<"Repository directory name must only contain alpha-numeric characters, periods, hyphens and underscores">
- raised when the resolved directory name contains illegal characters.

=item *

C<"Cannot create new deployments repository `$dir': already exists!"> -
raised when the target path already exists.

=item *

C<"no_vault option can only be used in test contexts"> - raised when
C<no_vault> is passed but C<$ENV{GENESIS_COMMAND}> is set.

=back

B<Examples:>

    # Create a new CF deployment repository
    my $top = Genesis::Top->create('/repos', 'cf');
    # Creates /repos/cf-deployments (with legacy suffix enabled)
    # or /repos/cf (without)

    # Create with a specific directory name
    my $top = Genesis::Top->create('/repos', 'cf',
        directory => 'cloud-foundry',
    );

=head2 search_for_repo_path

    my ($root, $path) = Genesis::Top->search_for_repo_path($deployment, %opts);
    my @paths         = Genesis::Top->search_for_repo_path($deployment, all_paths => 1);

Searches for a deployment repository whose directory name matches
C<$deployment> within the configured deployment roots (from
C<$HOME/.genesis/config>, plus the current and parent directories). Applies
glob-pattern matching - anchoring with C<^> and C<$> is supported.

Search roots are checked in order: the current directory (C<@current>),
the parent directory (C<@parent>), and then each named root from the
C<deployment_roots_map> configuration key. Within each root, BOSH
repositories are sorted first, then other types alphabetically.

When exactly one match is found it is returned immediately. When multiple
matches are found and the process is running in a controlling terminal, an
interactive prompt (via C<prompt_for_choice>) is presented to the user.
When not in a controlling terminal and more than one match exists, an error
is raised listing all matches unless C<all_paths> is set.

B<Parameters:>

=over 4

=item C<$deployment>

B<(required)> Deployment name or glob pattern to match against repository
directory names. The pattern is automatically wrapped with C<*...*> wildcards
unless anchored with C<^> or C<$>.

=item C<all_paths>

B<(optional)> When true, returns all matching C<[$label, $path]> pairs as a
list rather than prompting for selection.

=back

B<Returns:>

In normal mode: a two-element list C<($deployment_root, $path)> where
C<$deployment_root> is the parent directory of the matched repository and
C<$path> is the full path to the repository.

When C<all_paths> is true: a list of C<[$label, $path]> array references,
one per match.

B<Errors:>

=over 4

=item *

C<"Invalid option specified to search_for_repo_path: %s"> - raised (via
C<bug()>) when an unrecognized option key is passed. C<%s> is replaced by
the unrecognized key name.

=item *

C<"No deployment repositories found matching #C{%s}"> - raised when no
matching repository exists anywhere in the search roots. C<%s> is replaced
by the C<@:$deployment> label.

=item *

C<"Ambiguous deployment repository name: #C{%s} matches multiple paths:\n  -#\@{_}%s\n\nPlease refine your match criteria.">
- raised when multiple matches are found and the process is not in a
controlling terminal (and C<all_paths> is not set). C<%s> is the label and
the indented path list respectively.

=item *

C<"No deployment repository path selected."> - raised when the user chooses
the "None of these" option from the interactive prompt.

=back

B<Examples:>

    # Locate the cf deployments repository
    my ($root, $path) = Genesis::Top->search_for_repo_path('cf');
    # Returns: ('/srv/deployments', '/srv/deployments/cf-deployments')

    # Get all matching paths without prompting
    my @all = Genesis::Top->search_for_repo_path('*vault*', all_paths => 1);

=head2 is_repo

    my $bool = Genesis::Top->is_repo($path);

Returns true when C<$path> looks like a valid Genesis deployment repository:
it must have a C<.genesis/> directory, a C<.genesis/config> file, and that
file must contain the string C<deployment_type:>, or carry C<type:> at the
start of a line, the oldest version 1 key for it, which the version 1
upgrade reads as its fallback (T399). A C<type:> nested under another key
does not count.

B<Parameters:>

=over 4

=item C<$path>

B<(required)> Path to test.

=back

B<Returns:> A true value when C<$path> is a Genesis deployment repository,
false otherwise.

B<Examples:>

    if (Genesis::Top->is_repo('/srv/cf-deployments')) {
        my $top = Genesis::Top->new('/srv/cf-deployments');
    }
    # Returns: 1 when path is a Genesis repo, '' otherwise

=head2 kit_provider

    my $provider = $top->kit_provider;

Returns the kit provider configured for this repository. The result is
memoized after the first call. The provider is constructed from the
C<kit_provider> hash in C<.genesis/config>, or defaults to a
C<Genesis::Kit::Provider::GenesisCommunity> instance when that key is absent.

B<Returns:> A C<Genesis::Kit::Provider> subclass instance.

B<Examples:>

    my $provider = $top->kit_provider;
    my @names = $provider->kit_names;

=head2 set_kit_provider

    my $err = $top->set_kit_provider(%opts);

Initializes a new kit provider from C<%opts> and updates the repository
configuration. If the new provider is a
C<Genesis::Kit::Provider::GenesisCommunity> instance, the C<kit_provider>
key is cleared from the config (restoring the default). Otherwise the
provider configuration is written and saved.

Both branches (GenesisCommunity and custom provider) set C<updater_version>
(when the config file exists on disk), judge the result with
L</_validate_config_to_save>, and save the config to disk only if the
next load would accept it. A refusal leaves the file as it was and comes
back as the returned error.

B<Parameters:>

=over 4

=item C<%opts>

Options forwarded to C<< Genesis::Kit::Provider->init >>. See
L<Genesis::Kit::Provider> for accepted keys.

=back

B<Returns:> The value of C<$@> after the eval block - an empty string on
success, or the error message if initialization failed.

B<Examples:>

    my $err = $top->set_kit_provider(type => 'github',
        organization => 'my-org');
    # Returns: '' on success, error string on failure
    die $err if $err;

=head2 vault

    my $vault = $top->vault(%opts);

Returns the C<Service::Vault> object for this repository's secrets provider.
The result is memoized after the first successful call; options passed on
subsequent calls are ignored.

Resolution order:

=over 4

=item 1.

If C<$ENV{GENESIS_NO_VAULT}> is set, returns a C<Service::Vault::None>
instance immediately.

=item 2.

If running inside a Genesis callback and C<$ENV{GENESIS_TARGET_VAULT}> is
set, re-binds to the inherited vault via C<Service::Vault::Remote->rebind()>.

=item 3.

If the repository config has a C<secrets_provider> block, attaches to that
vault URL using C<Service::Vault::Remote->attach(...)>. Falls back to
C<Service::Vault::None> when attachment fails and C<no_vault> is set.

=item 4.

Otherwise, uses C<< Service::Vault->default >> (whatever C<safe> is currently
targeting) and connects and validates it.

=back

B<Parameters:>

=over 4

=item C<silent>

B<(optional)> Passed to C<< Service::Vault::Remote->attach >> and to
C<< $vault->connect_and_validate >> to suppress output. Only consulted on
the first call (before memoization).

=item C<no_vault>

B<(optional)> When true and attachment to the configured URL fails, returns
a C<Service::Vault::None> instead of raising an error. Only consulted on the
first call.

=back

B<Returns:> A C<Service::Vault> subclass object (C<Remote> or C<None>).

B<Examples:>

    my $vault = $top->vault;
    printf "Vault: %s at %s\n", $vault->name, $vault->url;
    # Returns: a Service::Vault::Remote or Service::Vault::None object

    # Allow no-vault mode silently
    my $vault = $top->vault(silent => 1, no_vault => 1);
    # Returns: Service::Vault::None when no vault is reachable

=head2 repo_vault

    my $result = $top->repo_vault;

Returns the repository's configured vault object when C<has_vault()> is true,
or the system default vault otherwise. Builds a C<Service::Vault::Remote>
from the C<secrets_provider> config, mirroring the attach logic in C<vault()>
but without memoization or session options.

B<Returns:> A C<Service::Vault::Remote> object when a vault is configured;
C<< Service::Vault->default >> otherwise.

=head2 has_vault

    my $bool = $top->has_vault;

Returns true when the repository configuration contains a non-empty
C<secrets_provider> hash.

B<Returns:> True when a vault is configured, false otherwise.

B<Examples:>

    if ($top->has_vault) {
        my $v = $top->vault;
        printf "Configured vault: %s\n", $v->name;
    }

=head2 set_vault

    $top->set_vault(%opts);

Sets the secrets provider for this repository, either interactively or by
target name. Unless C<session_only> is set, the new vault configuration is
persisted to C<.genesis/config>.

B<Parameters:>

=over 4

=item C<interactive>

B<(optional)> When true, presents an interactive safe-target selection
prompt. Ignores the C<target> option.

=item C<target>

B<(optional)> Name or URL of the safe target to use. Exactly one candidate
vault must match; otherwise an error string is returned without raising.

=item C<clear>

B<(optional)> When true, removes the vault configuration entirely (clears
C<secrets_provider> from config). B<Note:> the clear operation does not call
C<< config->save() >>, so the change is not persisted to disk.

=item C<vault>

B<(optional)> A vault object to set directly.  Any C<Service::Vault>, which
is a C<Service::Vault::Remote> or a C<Service::Vault::Local>, since a local
vault serves a read as a remote one does.  A C<Service::Vault::None> is not
one of them and is refused, because it is the absence of a vault rather than
a vault.

=item C<session_only>

B<(optional)> When true, updates the in-memory vault reference but does not
write C<.genesis/config>.

=back

B<Returns:> An error string (C<"#R{[Error]} ..."> formatted) when the target
lookup fails; nothing (C<undef>) on success.

B<Errors:>

=over 4

=item *

C<"Invalid call to Genesis::Top->set_vault"> - raised via C<bug()> when none
of C<interactive>, C<target>, C<clear>, or a C<vault> that is a
C<Service::Vault> is provided.

=item *

Any refusal L</_validate_config_to_save> makes, at
C<Genesis::Exit::CONFIG>, when the configuration it would save -- the new
C<secrets_provider>, or its removal -- is one the next load would refuse.
Nothing is saved. Unless C<session_only> is given, both setting and
clearing are judged this way.

=back

B<Examples:>

    # Set vault by target name, session only
    $top->set_vault(target => 'prod-vault', session_only => 1);
    # Returns: undef on success

    # Set vault interactively and save to config
    $top->set_vault(interactive => 1);
    # Returns: undef on success

    # Clear vault configuration
    $top->set_vault(clear => 1);
    # Returns: undef on success

=head2 vault_status

    my %status = $top->vault_status;

Returns a hash of status information about the repository's configured vault.
Returns an empty list when C<has_vault()> is false.

The returned hash includes the raw C<secrets_provider> fields from config,
augmented with:

=over 4

=item C<security>

A display string: empty string for verified HTTPS, C<"#Y{(noverify)}"> for
unverified HTTPS, or C<"#Y{(insecure)}"> for plain HTTP.

=item C<alias>

The local safe target alias when exactly one alias maps to the vault URL.

=item C<alias_error>

Set when zero or more than one local aliases map to the vault URL.

=item C<status>

Connectivity status string. Contains a C<safe target> command hint when no
alias is found, a de-duplication hint when multiple aliases exist, or the
result of C<< $vault->status >> when a single alias is found.

=back

B<Returns:> A flat key-value list suitable for assignment to a C<%hash>.
Returns an empty list when C<has_vault()> is false.

B<Examples:>

    my %info = $top->vault_status;
    if (%info) {
        printf "URL:    %s\n", $info{url};
        printf "Status: %s\n", $info{status};
    }

=head2 git

    my $git = $top->git;

The handle on the repository this deployment root lives in. It is the one
handle every caller of the repository shares, since L<Service::Git> keeps one
per root and answers a path it has resolved before from memory, so a reader
holding a Top asks here rather than building one from a path.

B<It installs the resolver for the pipeline's remote on the handle>
(L<Service::Git/pipeline_remote_resolver>), so the remote is resolved, and
judged, by whatever first uses it, a fetch, a push, a refresh of control,
rather than when the configuration loads (D118, noted 2026-10-15). The
resolver answers the remote L</_source_control> resolves, and nothing where
this file does not enable a pipeline, so outside a pipeline a remote
operation that names no remote is refused as before. It holds the Top
weakly, because the handle is shared and outlives any one Top. A handle
built from a path with L<Service::Git/new> instead has no resolver, so a
pipeline command takes its handle from here.

B<Parameters:> None.

B<Returns:> The L<Service::Git> handle.

B<Errors:> What L<Service::Git/new> raises for a directory under no git
control.

B<Examples:>

    my $git = $top->git;
    $git->fetch_branches([$top->control_branch]);
    # fetches from the pipeline's remote

=head2 deployment_slug_for

    my $slug = $top->deployment_slug_for($env_name);

The deployment slug for an environment name, which is C<< <env>/<type> >>.

This is the one identity a deployment has. The deployment branch, the vault
path under the exodus mount, and the BOSH deployment name are three
renderings of it, so composing any of them anywhere else is how they drift.

The argument is a name as a string and never a C<Genesis::Env>, deliberately,
so that a caller holding only a name composes the slug without loading an
environment.

B<Parameters:> The environment's name, as a string.

B<Returns:> The slug, such as C<qa/bosh>.

B<Errors:>

=over 4

=item *

C<"deployment_slug_for expects an environment name, got a %s"> - raised (via
C<bug()>) when the argument is a reference rather than a name, with C<%s>
replaced by the kind of reference it was handed.

=item *

=head2 pr_branch_for

    my $branch = $top->pr_branch_for($env_name);
    my $branch = $top->pr_branch_for($env_name, envs => \@names);

The pull request branch for an environment name, which is L</pr_prefix>
joined onto its slug.

The prefix is configuration rather than a caller's choice, so no caller
passes one.

The join can produce a name another branch already owns, and that is refused
here rather than in each caller, so this is the one place a pull request
branch is named and the one place the collision is caught. Both the prefix
and the deployment type append, so the type cancels on both sides and the
comparison is against the composed branch names.

The names that comparison is made against are the caller's to pass where it
already holds them. L</pipeline_env_names> memoises nothing and builds the
whole topology, which walks every environment file, so a run asking about
each of its pull request environments in turn paid for one entire topology
per ask. A caller with a topology in hand passes its environment names
through C<envs> instead, and the answer is the same either way.

B<Parameters:>

=over 4

=item C<$env_name>

The environment's name, as a string.

=item C<envs>

Optional. The environment names to compare the composed branch against, as
an arrayref. Defaults to L</pipeline_env_names>, which builds a topology of
its own.

=back

B<Returns:> The branch name, such as C<pr/qa/bosh>.

B<Errors:>

=over 4

=item *

C<"The pull request branch for ... would be ..., which is the deployment
branch of the environment ..."> - raised when the joined name is a branch
some environment already owns, which needs an environment whose name is the
prefix followed by another environment's name. With the prefix C<pr-> and
the environments C<lab> and C<pr-lab>, the pull request branch for C<lab>
and the deployment branch for C<pr-lab> are both C<pr-lab/bosh>.

=item *

C<"The pull request branch for ... would be ..., which is the control
branch."> - raised when the joined name is the control branch itself.

=item *

C<"deployment_slug_for expects an environment name, got a %s"> and
C<"deployment_slug_for called without an environment name"> - raised (via
C<bug()>) when the argument is a reference or is missing, because the name is
passed straight into L</deployment_slug_for> before anything is joined onto
it.

=back

Both refusals exit C<Genesis::Exit::CONFIG> and name the branch they
would have collided with, and both are answered by changing
C<pipeline.source_control.pr_prefix>.

B<Examples:>

    my $branch = $top->pr_branch_for('qa');
    # returns 'pr/qa/bosh' under the default prefix

    my $branch = $top->pr_branch_for('qa', envs => ['qa', 'prod']);
    # the same answer, with no topology built to reach it

    # with pr_prefix 'pr-' and an environment named pr-lab
    my $branch = $top->pr_branch_for('lab');
    # exits Genesis::Exit::CONFIG, naming pr-lab/bosh

=head2 pr_branch_problems

=head2 source_control_resolved

drifted away from what git says is visible rather than silent.

C<derived>, because git was never asked. The explicit tier is read with
C<Genesis::Config::is_set> rather than with C<get>, the way

C<control_branch> and C<pr_prefix> in for every repository and a filled

B<Errors:> None of the clone's: they are reported in the remote row. It

B<Examples:>

=head2 applied_record

=head2 pipeline_staleness

    my $changes = $top->pipeline_staleness($git);

The environments whose pipeline no longer matches what is on control.

This is the one home of the comparison. The propagate pre-flight, the deploy
pre-flight, and C<pipeline-status> all ask it, because three copies of a
comparison drift three ways.

It reads three things. The applied commit comes from L</applied_record>. A
path diff between that commit and the commit L</_shape> resolved covers
C<.genesis/config> and every file of each environment's hierarchy, which is
what the pipeline's definition is made of. And each environment's compiled
dependency set is compared with the set its last deploy recorded reading.

The roster it walks, and the environment files it compares, both come from
L</_shape> -- control as C<R> held it when the command started, under D112
-- rather than from the working tree the caller is standing in. That matters
to one caller. The propagate pre-flight and C<pipeline-status> stand on
control, so for them the shape and the tree in front of them say the same
thing, but the deploy stands on a deployment branch, which carries one
environment's hierarchy and no sibling's. Read from that tree the roster
would be a list of one, and an environment added to control since the apply
would be invisible to every deploy, which is the case this comparison exists
to catch.

Both halves are read off the one shape, at the one commit it resolved to and
kept as C<< $self->{__shape_commit} >>: the diff's far side is that commit
and the roster is that shape's own L</pipeline_topology>. They can never
disagree about which commit "control" meant, because neither asks git a
second time. A clone with a remote for control compares against the
remote-tracking ref -- a local commit on control not yet pushed is not part
of what this reads as control -- and a clone with no remote compares against
the local branch instead; see L</_control_commit> for which of the two applies.
Control moving again after the command started is not seen here; the next
command opens a fresh L</_shape> and reads it anew.

The environment files come from C<potential_environment_files>, which is pure
name derivation and touches no disk, so a defining path that exists only on
control is compared rather than skipped. What that gives up is explicitly
inherited files, which are named inside file contents and so need a tree to
be found at all.

A repository with no pipeline reports nothing, and it answers before the
applied record's address is composed. The deploy pre-flight asks this on
every deploy, and addressing that record where there is no pipeline reaches
the refusal in L</_pipeline_exodus_mount>, which would stop an ordinary
deploy with a sentence about a pipeline the operator does not have.

A repository C<pipeline-apply> has never run against also reports nothing,
because there is no commit to be stale against. So does a repository whose
shape is itself -- a deployment root not under git at all, or a clone whose
control ref cannot be found anywhere -- which is a question about control
the caller's own control check has already asked. A control that carries no
root for this deployment type resolves to L</_no_pipeline_shape> instead,
whose empty topology leaves nothing to iterate and so answers nothing here
too.

B<Parameters:> A C<Service::Git> for the repository.

B<Returns:> An arrayref of hashrefs, each with C<env> and C<reason>, where
the reason is C<configuration-changed> or C<dependencies-changed>.

B<Errors:>

=over 4

=item *

C<< "Cannot diff <commit> against <commit> in <root>: <reason>. Fetch the
missing commit or branch, then try again." >> - raised (via
C<Service::Git::diff_names>) when git cannot take the path diff, because the
applied commit or the commit L</_shape> resolved is not in the local
repository. A clean answer there would be a wrong answer, so the query
refuses instead.

=back

B<Examples:>

    my $changes = $top->pipeline_staleness($git);
    # returns [] where the pipeline is current

    my $changes = $top->pipeline_staleness($git);
    # returns [{env => 'staging', reason => 'configuration-changed'}]
    # for a deploy standing on qa/bosh, which carries no staging.yml

=head2 pipeline_topology

    my $topo = $top->pipeline_topology();

The single answer to "what environments are in this pipeline, and in
what order".

Until this existed the question had two implementations that agreed only
by coincidence: C<pipeline_env_names> globbed F<*.yml> through
L</envs>, while
C<Genesis::CI::Compiler::ASTBuilder::build_from_env_files> walked the
same directory building a DAG.  The latter was private and called from
four places in C<Genesis::Commands::Pipelines>, each repeating the same
edge-collection and breadth-first ordering.  Everything reading pipeline
membership now comes through here.

Membership is every environment C<Genesis::Top::has_env> accepts,
whether or not it declares a C<genesis.pipeline> block -- an environment
with no pipeline metadata still has a branch, still appears in
C<pipeline-status>, and still needs preparing.

Reads through L</_shape>. Where control can be resolved, this delegates to
the topology L</_shape> built for control's own tree, so under D112 the
roster is control's declaration rather than whatever the branch in front of
the command happens to carry -- a deploy standing on one deployment branch
still sees every sibling environment control knows about. A tree that is its
own shape -- a deployment root not under git at all, a clone whose control
ref cannot be found anywhere, or a materialised tree opened over one commit
-- answers through L</_topology_here> instead: a materialised tree's answer
is cached the first time, since such a tree's files cannot change, while a
live checkout with no resolvable control is read fresh on every call, since
its files can.

B<Parameters:> None.  The environment directory is the root of whichever
tree answers -- L</_shape>'s, where control could be resolved.

B<Returns:> A hashref:

=over 4

=item C<nodes>

Hashref of environment name to its C<genesis.pipeline> data.

=item C<edges>

Arrayref of C<< {from => ..., to => ...} >>, derived from C<prior_env>.

=item C<children>

Hashref of environment name to the arrayref of environments downstream
of it.

=item C<parent_of>

Hashref of environment name to the environment it follows.

=item C<order>

Arrayref of names, breadth-first from the roots.  Siblings are sorted by
name so the order is stable across runs -- callers print it and tests
compare against it.

=back

Every field is empty when CI is not configured, or when no environment
files are found, so callers may iterate without checking first.

B<Errors:> None.  Deciding that an empty topology is fatal belongs to
the caller: C<pipeline-status> and C<propagate> bail on it, while
C<pipeline_env_names> returns an empty list.

B<Examples:>

    my $topo = $top->pipeline_topology();
    for my $env (@{$topo->{order}}) {
        printf "%s (after %s)\n", $env, $topo->{parent_of}{$env} // 'control';
    }
    # mgmt (after control)
    # lab (after mgmt)
    # qa (after lab)

    # Roots are the environments with no parent
    my @roots = grep {!$topo->{parent_of}{$_}} @{$topo->{order}};

    # Called from a clone standing on the qa deployment branch, which
    # carries only qa/bosh.yml, this still lists every sibling, because
    # the roster comes from control rather than from qa's own tree.
    my $topo = $top->pipeline_topology();
    # {order => ['mgmt', 'lab', 'qa'], ...}

=head2 fetch_pipeline_envs

    my $result = $top->fetch_pipeline_envs($git);
    my $result = $top->fetch_pipeline_envs($git, command => 'qa deploy',
                                                 action  => 'deploy',
                                                 outcome => 'Nothing was deployed.');

Refreshes the control branch and every deployment branch of the pipeline in
one round trip, so credentials are prompted once.  Control is always in the
list.  Returns the refresh result, whose C<created> list names the local refs
that had to be made from the remote and whose C<fetched> and C<absent> lists
name the rest.  Returns C<undef> when the repository has no pipeline or no
remote.

The names it asks for are deployment branches rather than environment names,
composed through L</branch_for>, because the branch is what the remote holds
and an environment name is not a ref on it.

Every pipeline command calls this before its first read of a branch, and no
command may skip it.  C<genesis pipeline-status> is the one exception, and it
reads without refreshing only under its own C<--no-refresh>, which marks every
answer that depends on the remote as unverifiable.

B<Parameters:>

=over 4

=item C<$git>

A C<Service::Git> for the repository.

=item C<%opts>

=over 4

=item C<command>

Names the command in a refusal, as in C<run genesis qa deploy>.  Defaults to
C<propagate>.

=item C<action>

Replaces the whole "run C<genesis E<lt>commandE<gt>>" phrase, for a command
that says something else.  The deploy passes C<deploy>, so its refusal opens
"Refusing to deploy".

=item C<outcome>

The closing sentence of a refusal, which says what was not done.  Defaults to
C<Nothing was written.>

=back

=back

B<Returns:> The refresh result, carrying C<ok>, C<kind>, C<fetched>,
C<created>, and C<absent>.  C<undef> where the repository declares no
pipeline, which leaves nothing to refresh.  The remote is
L</source_control_remote>, which a pipeline repository always resolves, since
the load refuses one that cannot derive it.

B<Errors:>

An unreachable remote, a rejected credential, or a failed request is fatal
here and exits C<TEMPFAIL>, because every command that calls this refreshes
unconditionally and a retry is what fixes it.  The refusal names the remote,
says which of the three kinds it was, quotes git's own message, and closes
with the caller's C<outcome>.  Only C<genesis pipeline-status> reads without
refreshing, and it says so in every cell that depends on the remote.

B<Examples:>

    my $result = $top->fetch_pipeline_envs($git, command => 'propagate');
    # every branch refreshed; $result->{created} names any local ref
    # this refresh had to make from the remote

    my $result = $top->fetch_pipeline_envs($git);
    # returns undef in a repository that declares no pipeline

    $top->fetch_pipeline_envs($git, action  => 'deploy',
                                    outcome => 'Nothing was deployed.');
    # with the remote unreachable, exits TEMPFAIL saying
    # "Refusing to deploy. ... Nothing was deployed."

=head2 repository_identity

    my $identity = Genesis::Top::repository_identity($text);

The repository a value names, as its host, owner and repo, or C<undef> where
it names none. A repository is one identity however it is written (D118):
C<owner/repo>, which means github.com, an https URL, or either ssh form, the
scp-like C<git@host:owner/repo> or C<ssh://git@host/owner/repo>. A C<.git>
suffix and a trailing slash are dropped, a userinfo or port in the URL is
passed over, and the host is lowercased; owner and repo keep their spelling,
which the API and the messages use, and L</_identity_key> folds them for
comparison. It is public because the CI compiler composes the clone URL from
it, through L<Genesis::CI::ProviderCompiler/git_uri>.

Any host parses the same way as github.com, GitHub Enterprise included,
because a GitHub-compatible host need not carry "github" in its name (D118).
Whether a host speaks GitHub's API is a question for the API, not for its
name. A filesystem path or a C<file://> URL carries no host and answers
C<undef>.

Plain function, not a method.

B<Parameters:>

=over 4

=item C<$text>

The configured C<repository>, or a remote's fetch URL. An undefined or empty
value answers C<undef>.

=back

B<Returns:> A hashref of C<host>, C<owner> and C<repo>, or C<undef>.

B<Errors:> None.

B<Examples:>

    my $identity = repository_identity('git@github.com:team/bosh.git');
    # returns {host => 'github.com', owner => 'team', repo => 'bosh'}

    my $identity = repository_identity('team/bosh');
    # returns the same

    my $identity = repository_identity('https://github.example.com/team/bosh');
    # returns {host => 'github.example.com', owner => 'team', repo => 'bosh'}

    my $identity = repository_identity('https://git.example.com/team/bosh.git');
    # returns {host => 'git.example.com', owner => 'team', repo => 'bosh'}

    my $identity = repository_identity('/srv/git/bosh.git');
    # returns undef -- a path names no repository

=head2 _shape

    my $shape = $top->_shape();

The C<Genesis::Top> the pipeline's shape is read from.

Every key that says what the pipeline is -- L</pipeline_enabled>,
L</pipeline_provider_type>, L</recreate_on_deploy>, L</control_requires_pr>,
L</pr_prefix>, L</pipeline_name>, L</pipeline_section>, and
L</pipeline_topology> -- reads through here rather than off L</config>
directly, because under D112 the shape is control's fact: what control held
as C<R> when the command started, not what the tree in front of the command
happens to carry. The keys that say where control is -- L</control_branch>
and the C<pipeline.source_control> block -- are read from the tree in front
of the command instead, because control cannot be found without them first.

Resolved once per C<Genesis::Top> and kept, through L</_read_shape>, so every
shape key one command asks is one read of control, and every caller within
that command sees the same commit however long the command runs. A
materialised tree, already opened over one commit, is its own shape: reading
control out of a tree that already is one commit of control is what would
let a read of control read control again.

Control is the remote-tracking ref where the clone has one, and the local
control branch where it has no remote. The tree is written out of git once
per commit the ref resolves to and kept on this C<Genesis::Top>. A tree the
command cannot read control out of at all -- a directory that is no git
checkout, or a clone with no control branch anywhere -- reads its own files,
and the refusals that concern control are asked where they always were.

Control moving on the remote after this resolves is not seen by the command
that already resolved it. The next command opens a new C<Genesis::Top> and
reads control anew.

B<Parameters:> None.

B<Returns:> C<$self> for a materialised tree. Otherwise, the C<Genesis::Top>
L</_read_shape> resolved, which may also be C<$self> where control could not
be read from at all.

A preview that has called L</read_shape_from_worktree> reads the tree in front
of it here instead, and never reaches control.

B<Errors:> Whatever L</_read_shape> raises propagates, and a shape whose tree
fails the configuration checks is refused through L</_refuse_invalid_shape>
at C<CONFIG> (D112, noted 2026-10-16), so no command that acts takes an
unreadable control as one with no pipeline.

B<Examples:>

    my $enabled = $top->_shape->config->get('pipeline.enabled');
    # reads control's pipeline.enabled, not the tree in front of the command

=head2 _read_shape

    my $shape = $top->_read_shape();

Resolves control as C<R> holds it when the command starts and writes its
tree out once, so L</_shape> can keep the answer for the rest of the
command.

Where this deployment root is not under git at all, there is nothing to read
control from, so this returns C<$self> and the shape is the tree in front of
the command. Where the root is under git but L</_control_commit> finds no ref
for L</control_branch> anywhere -- no local branch and no remote-tracking one
-- this returns C<$self> for the same reason: a clone with no control ref has
no fact to read but its own. Where control has a ref but carries no
deployment root of this type at all, L</_topology_at> answers nothing and
this returns L</_no_pipeline_shape> instead of the branch in front of the
command, so a repository control does not carry a pipeline for is not
reported as having one merely because the local branch is.

Opening the materialised tree through L</_topology_at> sets C<GENESIS_ROOT>
to it, so the read is localised around this call and leaves the command's
own repository's environment as it found it.

The commit the shape was read at is kept on C<< $self->{__shape_commit} >>,
so L</pipeline_staleness>, which needs the commit as well as the tree, does
not resolve L</_control_commit> a second time.

The tree a commit writes out is the same for every command that reads it, so
it is kept for the life of the process under the deployment root and the
commit. A later command in the same process, such as another C<Genesis::Top>
a command builds for the same root, resolves control in one git call and, at
the same commit, reads nothing more. A command that finds control moved
resolves the new commit and writes that tree out.

B<Parameters:> None.

B<Returns:> A C<Genesis::Top>: a materialised tree at control's commit, or
C<$self> where there is no control to read from, or L</_no_pipeline_shape>
where control carries no root for this deployment type.

B<Errors:>

=over 4

=item *

Whatever L</_topology_at> raises when it cannot read or unpack control's
tree -- C<< "Failed to read the deployment root at <ref>" >> and
C<< "Failed to write out the deployment root at <ref>" >> -- propagates
uncaught.

=back

B<Examples:>

    my $shape = $top->_read_shape();
    # a materialised Top over control's tree, or $self for a root git
    # knows nothing about

The resolution itself is L</_control_shape>'s; this records the commit as the
shape's and hands the tree back.

=head2 _control_commit

The commit control stands at.

=head2 _resolve_remote

    my $resolved = $top->_resolve_remote($control);

The remote this clone's pipeline lives on, found by the repository it points
at rather than by its name, since a remote's name and protocol are each
cloner's own (D118).

=over 4

=item *

The clone's own pin, C<genesis.remote> in its C<.git/config>, is read before
the match and wins, unchecked against the repository, through
L</_pinned_remote>. One set only in the user's or the system's configuration
is ignored, with the warning L</_warn_outside_pin> gives.

=item *

A clone with one remote uses it whatever its URL, unless that URL names a
repository other than the configured C<repository>. A filesystem path or a
C<file://> URL names none, and stands.

=item *

Among several remotes, the ones naming the repository are kept: the
configured C<repository>, or else the one repository all of them agree on.
Remotes naming more than one repository with none configured are refused,
because a clone of a fork tracks the fork and choosing by tracking would
publish there. Where several remotes name the repository, control's upstream
chooses between them, and otherwise they are refused.

=back

It answers a refusal rather than raising one, because L</_control_commit>
asks it before the configuration is validated, and in repositories with no
pipeline at all. L</_source_control> raises the refusal at C<CONFIG>. Read
from the tree in front of the command, because it says where control is
(D112). The remotes are read through the Top's shared handle, L</git>, and the
answer is kept on the Top.

B<Parameters:>

=over 4

=item C<$control>

The control branch's name.

=back

B<Returns:> A hashref of C<remote>, C<identity> (the repository, or C<undef>
for a single remote that names none), and C<how> (C<pinned>, C<only> or
C<matched>); or a hashref of C<refusal> alone, carrying the words.

B<Errors:> None of its own; see L</_remote_refusal> for the refusals it
answers with. A pin set only outside the clone is reported as a warning.

B<Examples:>

    my $resolved = $top->_resolve_remote('control');
    # returns {remote => 'upstream', how => 'matched',
    #          identity => {host => 'github.com', owner => 'org', repo => 'repo'}}
    # where upstream points at org/repo and origin at a fork

=head2 _topology_at

    my ($topology, $at) = $top->_topology_at($git, 'control');

The pipeline's environments as one ref holds them, and the C<Genesis::Top>
they were read through.

The deployment root's configuration and environment files are read out of
the ref's objects in one git process, L<Service::Git/read_blobs>, and written
byte for byte into a scratch tree with the root's own prefix taken off each
path, and a C<Genesis::Top> is opened over that tree as
a materialised one, so what comes back is what L</pipeline_topology> would
answer for a clone standing on that ref. Nothing else under the root is
written out: no kit hook runs against this tree, so the kit source would be
extraction paid for and never read.

The dev kit's own declaration, F<dev/kit.yml>, is written out too where the
ref carries one, alongside C<.genesis/config> and the environment files.
Without it, an environment file at that ref naming the dev kit and no
version -- valid only where a dev kit exists -- would drop out of the
topology the moment it was read through here, even though the ref itself
holds the dev kit that makes it valid.

L</_read_shape> is the only caller, and it reads C<$self>'s shape through the
C<Genesis::Top> that comes back, so the scratch directory is held on that
object rather than taken down when this returns. It passes the commit
L</_control_commit> resolved rather than a branch name, so the tree it writes
out never moves under the caller mid-command. The ref is an argument rather
than a fixed name so that a later caller can ask the same question of
another one.

Opening a C<Genesis::Top> sets C<GENESIS_ROOT>, so the caller localises the
environment around this call and around the reads it makes afterwards.

B<Parameters:> A C<Service::Git> for the repository, and the ref to read.

B<Returns:> The topology and the C<Genesis::Top>, or the empty list where the
ref carries no deployment root.  Where the tree's configuration fails the
checks, L</_config_problems> words the failures onto the Top's
C<__config_problems> and the topology is C<undef>, because a tree the load
would refuse is never walked (D112, noted 2026-10-16).

B<Errors:>

=over 4

=item *

C<< "Cannot read <ref> ..." >> - raised at C<DATAERR> by
L<Service::Git/read_blobs> when git cannot resolve the ref or read its
objects.

=item *

What C<mkfile_or_fail> raises when a file cannot be written into the scratch
tree.

=back

B<Examples:>

    my ($topology, $at) = $top->_topology_at($git, $top->control_branch);
    # returns control's whole roster, whatever branch this clone is on

=head2 _strongbox_for_config

    my $sb = $top->_strongbox_for_config($vault);

Decides what to record for C<secrets_provider.strongbox> when writing the
provider block, given the vault the block is being written from.

Every write path rebuilds the whole block, so an edit that only meant to
change the alias and URL also rewrites Strongbox from whatever the vault
object happens to carry. While safe defaulted Strongbox on, a vault always
carried a value and this was invisible. Since safe made it opt-in, a target
that never stated the flag reports nothing -- and re-pointing a deployment
would silently record Strongbox as disabled for a vault that runs one, with
no prompt and no mention in the output.

So an unstated flag is not treated as a statement that Strongbox is off.
When the vault has no value, whatever the repository already records is kept,
on the grounds that it was written when something did know. When nothing is
recorded either, nothing is written, and the absent key means unstated.

B<Parameters:>

=over 4

=item $vault

The vault whose settings are being recorded. Its C<strongbox> may be
C<undef>.

=back

B<Returns:> C<Genesis::Config::TRUE> or C<Genesis::Config::FALSE> when the
vault states a value; otherwise the currently recorded value, which is
C<undef> when the repository has none. Callers must omit the C<strongbox>
key entirely when this returns C<undef>.

B<Errors:> None.

B<Examples:>

    # Vault states enabled
    $top->_strongbox_for_config($vault);
    # Returns: Genesis::Config::TRUE

    # Vault says nothing, repository records enabled
    $top->_strongbox_for_config($vault);
    # Returns: the recorded true value, preserved

    # Vault says nothing, repository records nothing
    $top->_strongbox_for_config($vault);
    # Returns: undef -- caller writes no strongbox key

=item C<$path>

The file to inspect.

=back

=head2 _repo_config_schema_v2

    my $schema = $top->_repo_config_schema_v2();

The schema describing a version 2 repository config: which keys exist, their
types, which are required, and what each is for.

Used to validate a loaded config and to drive the upgrade from version 1.

It declares one key a version 2 repository never wrote, which is
C<pipeline>, with the gate under it and nothing else. L</_validate_config>
injects that gate at default priority once a version 2 config has loaded,
so that downstream readers meet one shape whichever version is on disk,
and nothing clears the defaults between one validation and the next, so a
schema that did not declare the injection would report it as a key nobody
wrote and refuse every write the repository can make.

The key is declared for the injection and refused when anybody writes it.
Declaring a key is also what makes it writable, so L</_validate_config>
refuses a C<pipeline> section that the operator wrote or set on a version 2
repository, naming the migration to version 3, and the injection is filed
at default priority so the refusal never trips on the loader's own fill.

B<Parameters:> None.

B<Returns:> The schema as a hashref, keyed by config field.

B<Examples:>

    my $schema = $top->_repo_config_schema_v2();
    # returns { deployment_type => { type => 'string', required => 1, ... }, ... }

=head2 _validate_config

    $self->_validate_config

Validates the configuration in memory against the schema its C<version>
selects. L</config> calls it on the first load, so every command validates
whether or not it is a pipeline command, and every writer calls it again,
through L</_validate_config_to_save>, on the result it is about to save.

B<It judges every time it is asked, and reads the version off the
configuration in memory.> There is no "already validated" guard: an
earlier one marked the load done before validating, and turned every
writer's check, and the version 1 upgrade's, into a no-op that returned
at once. Reading the version off the configuration rather than off the
file is what lets a writer that sets C<version> be judged by the rules of
the version it writes. What a judgement records -- the version, and the
legacy F<ci.yml> flag -- is recorded afresh each time, because a writer's
judgement is of a different result. A Top over a materialised tree is
never judged, and answers C<1>.

A version 1 configuration is upgraded to v2, interactively or
automatically according to the RC settings; see L</_upgrade_config_to_v2>.
The C<version> field is classified before it is compared, as an integer or
as a release semver: repositories written before the dedicated
C<genesis_version> field put the Genesis release (such as C<2.7.1>) in
C<version>, and they are treated as version 1. Comparing such a string
with C<==> would warn, which is why the shape is checked first. The
upgraded configuration is then judged as the version 2 configuration it
now is.

A version 3 configuration is validated against L</_repo_config_schema>,
which carries the C<pipeline> section and declares each retired key so it is
refused naming what replaced it, so C<genesis E<lt>envE<gt> deploy> and
C<genesis propagate> meet the same refusal in the same words. The checks a
declarative schema cannot state follow in L</_validate_pipeline_config>, and
then each registered section handler's C<validate_config_section>.

B<Every problem is refused at once> (T411). The schema's problems and every
check's are gathered, through L</_refuse_config> and L</_refuse_config_text>,
and refused together at C<Genesis::Exit::CONFIG> under one heading, so an
operator does not meet one class of problem per run. Where the schema has
already failed, a check that dies over the shape it refused is set aside, the
schema's refusal standing for it. An environment file that does not parse is
still refused on the spot, because every check after it reads that file.

A version 2 configuration is first refused if it carries a C<pipeline>
section of its own, through L</_refuse_v2_pipeline>. That comes B<before
the schema>, so the operator hears where the section belongs and how to
get there rather than that the keys under it were never declared, and
before the injection below puts a pipeline default there itself. It is
then validated against L</_repo_config_schema_v2>, and has a version 3
shaped C<pipeline> gate injected at default priority, so that downstream
readers meet one shape whichever version is on disk. The injection is
never saved, and the version 2 schema declares the key it fills so that a
later validation does not report it as a key nobody wrote.

This method does not itself refuse a stale F<ci.yml>; it records what it
found, and two other places act on the record. It sets the flag that
L</has_legacy_ci_yml> reports, for a version 2 configuration beside a
F<ci.yml> whose first significant key is C<pipeline:>, and for a version 3
one that enables no pipeline. C<Genesis::Commands::_gate_pipeline_on_legacy_ci_yml>
reads it to error for every pipeline command, naming the migration; other
commands run. An environment file named F<ci.yml>, which starts with
C<kit:> or C<genesis:>, does not trip it. And where a F<ci.yml> sits
beside a version 3 configuration that already enables a pipeline, it warns
that the file is a stale leftover and lets the command through, once per
run for each F<ci.yml>, however many Tops the run opens or judgements it
makes (T397). That check
reads C<pipeline.enabled> off L</config> directly rather than through
L</pipeline_enabled>'s shape, because the question is about the F<ci.yml>
sitting beside this file, not about what control declares.

On a Top opened with C<repair_config>, a version 2 or 3 configuration is
read through L</_check_config> rather than validated, and nothing the file
carries is refused or warned about: the retired-key refusal, the version 2
pipeline refusal, and everything after the version 3 schema are skipped.
The version is still recorded and the version 2 gate still injected.

B<Returns:> C<1> on success. Raises on invalid or unsupported config versions.

B<Errors:>

=over 4

=item *

C<"This repository's configuration is version 1, and a preview writes nothing, so it is not upgraded here.  ...">
- raised at C<Genesis::Exit::CONFIG> when a v1 config is loaded by a preview
(a command whose registration declares C<preview>, or C<--dry-run> where it
names that option), because the upgrade rewrites the file. It names
C<genesis config> as a command that upgrades it, and leaves the file as it was
(T408).

=item *

C<"Genesis deployment repo v1 configuration is not supported, and cannot update automatically.  ...">
- raised at C<Genesis::Exit::CONFIG> when a v1 config is detected, no
controlling terminal is available, and automatic upgrade is disabled. It names
the two ways the upgrade runs: from a terminal, or with
C<automatic_config_upgrade: yes> in F<~/.genesis/config> (T390).

=item *

C<"Genesis deployment repo configuration version %s is not supported">
- raised at C<Genesis::Exit::CONFIG> when the version is not 1, 2, 3, or a
recognized semver string. The C<%s> is the literal version value from the
config file.

=back

B<Examples:>

    $self->_validate_config;
    # Returns: 1 on success; raises on invalid schema

=head2 _validate_config_to_save

    $self->_validate_config_to_save;
    $self->config->save;

Judges what a writer is about to save. Every writer of
F<.genesis/config> -- C<genesis config>, L</set_vault>,
L</set_kit_provider>, L</create> -- calls it once, on its final result,
immediately before it saves, and saves only if it returns (D28). Nothing
is judged while the writer is still applying its changes, so a run may
pass through states the load would refuse.

B<It is the load's own judgement, not a list of the writer's.> It runs
L</_validate_config> on the configuration in memory, with repair mode
turned off, so a check added to the load reaches every writer. The
writers' checks used to be a hand-kept subset of the load's, and
C<genesis config> could save a file the next command refused.

It drops what the load worked out from the configuration it loaded:
L</_source_control> keeps its answer, and an answer about the loaded
configuration is not an answer about the one being saved. Nothing has
been written yet, so the schema's refusal names "the configuration this
run would write" and says the file is left as it was. Every other check the
load makes refuses through L</_refuse_config> or L</_refuse_config_text>,
so its refusal says the same during a save (T403).

B<Parameters:> None.

B<Returns:> C<1> when the result would load.

B<Errors:> Every refusal L</_validate_config> makes, at
C<Genesis::Exit::CONFIG>, with the schema's refusal worded as
C<"Configuration validation failed for the configuration this run would
write (%s is left as it was):%s">.

B<Examples:>

    $top->config->set('pipeline.enabled', 1);
    $top->_validate_config_to_save;   # refuses if the next load would
    $top->config->save;

=head2 _refuse_config

    $self->_refuse_config(@problems) if @problems;

Refuses a load check's problems, one bullet each, as "Configuration
validation failed for" what is being judged: the file on disk at load, and
during L</_validate_config_to_save> the configuration the run would write,
which says the file is left as it was (T403). A check that names the file on
disk when a save is refused reads as a file the operator has to repair.

During a judgement by L</_validate_config>, it and L</_refuse_config_text>
add their problems to the judgement's list rather than refusing, and the list
is refused once at the end (T411).

B<Parameters:> The problems, each a sentence.

B<Returns:> Never.

B<Errors:> Always bails at C<Genesis::Exit::CONFIG>.

B<Examples:>

    $self->_refuse_config("#R{genesis.pipeline.manual} in #C{qa}: ...");
    # Configuration validation failed for the configuration this run would
    # write (.genesis/config is left as it was):
    #  - genesis.pipeline.manual in qa: ...

=head2 _upgrade_config_to_v2

    $self->_upgrade_config_to_v2($config_version, $upgrade_automatically)

Constructs a new v2 configuration from the existing v1/semver config,
shows a diff, and (depending on C<$upgrade_automatically> and the presence of
a controlling terminal) prompts the user for confirmation before saving.

B<The candidate is judged before anything is shown, asked or saved> (D28),
against L</_repo_config_schema_v2> through L<Genesis::Config/problems>.
What the v1 file carried, such as C<kit_provider>, is copied over as it
was found, so this is where a value the version 2 schema does not allow
is caught; the refusal lists each problem. The judgement had been a
recursive call to L</_validate_config> that a since-removed guard turned
into a no-op, so an invalid v2 file was saved without a word.

Modifies the object in-place: replaces C<$self-E<gt>{__config}> with the new
v2 config object, then calls C<< $self->config->replace($old_config) >>
on success. L</_validate_config> then judges the saved result as the
version 2 configuration it now is.

B<Parameters:>

=over 4

=item C<$config_version>

The raw version string from the existing config.

=item C<$upgrade_automatically>

One of C<'no'>, C<'yes'>, or C<'silent'>. When C<'no'>, prompts the user.
When C<'silent'>, upgrades without any output. When any other truthy value,
upgrades with informational output but without prompting.

=back

B<Returns:> Nothing on success; raises on failure.

B<Errors:>

=over 4

=item *

C<"Cannot upgrade Genesis deployment repo v1 configuration to v2.  Manual intervention required:%s">
- raised at C<Genesis::Exit::CONFIG> when the candidate v2 config fails
validation, followed by a bullet for each problem. Nothing is saved.

=item *

C<"Genesis deployment repo configuration upgrade to v2 aborted"> - raised
when the user answers no to the upgrade confirmation prompt.

=back

B<Examples:>

    $self->_upgrade_config_to_v2('1.0.0', 'silent');
    # Returns: nothing on success; rewrites .genesis/config to v2 format

=head2 _repo_config_schema

    $self->_repo_config_schema

Returns the version 3 configuration schema, which is the version 2 schema with
C<version> pinned to C<"3"> and the C<pipeline> section added. The section is
built by L</_pipeline_config_schema>, so its whole shape is stated in one
place.

Nothing in the schema is assembled out of the configuration's own values.
The one block whose shape depends on a value is C<pipeline.provider>,
which is declared as a C<custom_struct> on its own C<type> and dispatched
during the walk, so the provider that owns the block's shape is also the
one that validates it.

The section is named C<pipeline> while the C<Genesis::CI> code namespace is
deliberately left where it is, because the compiler genuinely is CI. There is
no C<pipeline.repo.root>, because the git prefix already locates the
deployment root. There are no compatibility aliases either, so a key written
under its old C<ci.> spelling is refused by name rather than moved onto its
replacement, and that is safe because the version 3 schema is unreleased.

Every version 2 key is inherited unchanged:

=over 4

=item C<deployment_type> - required string

=item C<creator_version> - required; semver, C<"(development)">, or C<"Unknown">

=item C<updater_version> - optional semver or C<"(development)">

=item C<minimum_version> - optional semver

=item C<manifest_store> - optional enum: C<repository>, C<hybrid>, C<exodus>; default C<exodus>

=item C<kits_path> - optional string; default C<$GENESIS_ROOT/.genesis/kits>

=item C<kit_provider> - optional hash with sub-keys C<type>, C<organization>, C<label>, C<tls>, C<domain>

=item C<secrets_provider> - optional hash with sub-keys C<url> (required), C<insecure>, C<strongbox>, C<namespace>, C<alias>

C<strongbox> deliberately has B<no schema default>. An absent key means no
one has stated the setting, which is a third state rather than a synonym for
enabled. Defaulting it would re-create on read the ambiguity the writer goes
to some trouble to avoid -- see L</_strongbox_for_config>.

=item C<deployment_change_reason_required_size> - optional number; default C<0>

=item C<user_provided_bosh_creds> - optional enum: C<ignore>, C<allow>, C<require>; default C<ignore>

=item C<allow_oversized_secrets> - optional boolean

=item C<confirm_release_overrides> - optional enum: C<always>, C<outdated>, C<never>

=back

B<Returns:> A hash reference.

=head2 _pipeline_config_schema

    $self->_pipeline_config_schema

Returns the C<pipeline> block of the version 3 schema, in the shape
C<< $self->config->validate() >> consumes. Every key the pipeline reads is
declared here, so C<Genesis::Config> refuses an undeclared key by name as the
configuration loads, for every command rather than only for the pipeline ones.
The schema is the contract, and there are no compatibility aliases, because
the v3 schema is unreleased.

The block declares C<enabled>, which is the gate and defaults to false, the
C<provider> block, which is optional even once the gate is on and whose keys
the provider named by C<pipeline.provider.type> declares, and C<name>, which
is the pipeline's own label in its provider and falls back to the deployment
type.

The C<provider> block is declared as a C<custom_struct> on its own C<type>,
so the field that decides the block's shape is named where the block is
declared and nothing reads that field raw to build a schema out of it. The
provider that owns the shape therefore owns validating it: C<Genesis::Config>
matches the written type against the map L</_provider_module_map> builds and
hands the block to that provider's class. The discriminator's default is
C<manual>, declared under C<discriminator_default> beside the map.

The C<provider> block itself defaults to an empty hash so that the type's own
default still applies when the operator writes no provider block at all,
since validation walks into a block that is present and nowhere else. A
section that is enabled with no provider block is therefore a manual pipeline
rather than no pipeline, which is why the provider block is not required
beside an enabled gate.

C<exodus_mount> is the one vault mount every pipeline record lives under, the
applied record included, so it is the pipeline's own key rather than one
recovered from an environment (D116).

C<pipeline.provider.output_layout> is C<single> or C<multiple>, and a
provider offers it by declaring it, which one that cannot emit several
files does not, so the key is undeclared under such a provider and is
refused by name like any other. It decides the override file's name: the
single form is C<.genesis/pipeline-overrides-E<lt>providerE<gt>.yml>, and
the multiple form is one file per emitted output, named by that output's
base name without its extension. The name follows the effective choice
and not the capability.

The block also declares C<source_control>, which is what the pipeline needs
to know about the repository, in three tiers. C<remote>, C<uri>, and
C<repository> are derived from git with an explicit override; C<control_branch>,
C<pr_prefix>, and C<control_requires_pr> are defaulted; and C<auth> and
C<identity> are required wherever an automation has to clone and commit
unattended, which is what L</_automated_provider_configured> decides.  The
block itself is required there too, since a predicate on a key inside an
absent block is never asked (T385); under the manual provider it may be left
out, every key it would hold being derived or defaulted. Two
things take no key at all. The deployment root is a fact of the checkout,
read from the git prefix, and the branch a command runs from is runtime
state, so it is checked rather than configured. L</_source_control> resolves
the tiers.

Four more blocks complete the section. C<shuttle> is the object store behind
every deployment's request queue and its C<_ran> event, and it is required
wherever an automation has to do the work unattended, which is again what
L</_automated_provider_configured> decides. Its C<backend> is C<s3>, the one
store the shuttle resource has, and never a directory, because a directory
on one worker cannot trigger across pipelines.

The shuttle is declared on that backend rather than flat, so the backend
declares the keys it reads and any other is refused by name.
L<Genesis::CI::Shuttle::S3> declares C<bucket>, which is required, C<region>,
C<endpoint>, and C<auth>, and the resource C<image> and C<image_tag> with
their defaults. A shuttle block written with no backend, or another, is
refused as an unknown backend naming C<s3>, the map being what the value is
checked against.

C<vault> is the vault a pipeline task writes exodus through. Its C<url> is
required, and C<namespace>, C<auth>, and C<options> are optional. It is
required under an automated provider for the same reason the shuttle is,
because a task nobody is watching cannot be asked where to write.

C<locker> is the locker the two deploy locks use. The block declares the
locker and its credentials and says nothing about either lock, so how a
pipeline takes them is settled where the pipeline is compiled rather than
here. Its C<url> is required, C<username>, C<password>, and C<ca_cert> are
optional, and C<skip_ssl_validation> defaults to false. It is required under
an automated provider as well.

C<notifications> is optional under every provider. Its C<style> is the
repository default rendering and defaults to C<default>, and C<slack> and
C<email> carry whatever entries the notifier reads. An environment overrides
the style through its own C<genesis.pipeline.notifications> block, which
L</_pipeline_env_keys_schema> declares.

The section also carries C<pipeline.name>, which is the pipeline's label
in its provider and nothing more. It composes no branch, since the branch
is the deployment slug, so it is deliberately not validated as a git ref
component and keeps whatever character set its provider allows.

C<pipeline.recreate_on_deploy> is C<never>, C<redeploy-only>, or
C<always>, defaulting to C<never>. It and C<pipeline.provider.group_commits>
are repository-wide and refused per environment, because a key that
changes how a deployment progresses has to be uniform or the earlier
environments stop rehearsing the later ones.

B<Returns:> A hash reference.

=head2 _current_config_schema

and L</_repo_config_schema_v2> for anything older.

B<The version is read off the configuration as it stands, not off the

refused by name when the result is judged by L</_validate_config>.

=head2 _provider_module_map

=head2 _pipeline_env_keys_schema

    my $schema = $top->_pipeline_env_keys_schema();

Returns the declared shape of an environment file's C<genesis.pipeline>
block, in the shape C<< Genesis::Config::validate >> consumes. Validation
runs once per environment against that environment's merged parameters,
never against the leaf file alone, because an inherited key is absent from

B<Returns:> A hash reference.

=head2 _source_control

    my $sc = $top->_source_control();

L</_source_control_found>'s values, with what the clone could not give
raised at C<Genesis::Exit::CONFIG>. This is the clone's judgement (D118,
noted 2026-10-15): it runs where the remote is first used, through
L</source_control_remote> or the git handle's resolver, and never at load.
The file's own rules for these keys -- that C<repository> parses, that
C<control_branch> and C<pr_prefix> are not empty -- are the schema's
(L</_repository_rule>, L</_control_branch_rule>, L</_pr_prefix_rule>), and
are judged at load and before every save.

B<Returns:> The hash reference L</_source_control_found> answers, without a
C<refusal>.

B<Errors:>

=over 4

=item *

C<"pipeline is enabled, but ... is not a git checkout"> - raised when the
deployment repository is not under git at all, which leaves the derivations
with nothing to read.

=item *

C<"This clone has no git remote ..."> - raised when the clone has no remote
at all, and C<"genesis.remote names ..., which is not a remote of this
clone"> - raised when the clone's own pin names a remote it lacks.

=item *

C<"No remote of this clone points at ...">, C<"This clone's remotes point at
more than one repository ...">, and C<"Remotes ... all point at ..."> -
raised when L</_resolve_remote> cannot settle the remote, as
L</_remote_refusal> words each case.

=item *

C<"pipeline.source_control.repository could not be derived"> - raised when
the remote's URL carries no GitHub C<owner/repo> pair and no override names
one. There is no exception under the manual provider.

=back

B<Examples:>

    my $sc = $top->_source_control;
    # returns {remote => 'origin', uri => 'git@github.com:team/bosh.git',
    #          repository => 'team/bosh', control_branch => 'control',
    #          pr_prefix => 'pr/',
    #          identity => {host => 'github.com', owner => 'team',
    #                       repo => 'bosh'}}

=head2 _source_control_found

    my $sc = $top->_source_control_found;

The source-control values, and what the clone could not give, without
refusing anything. Its keys are C<remote>, C<remote_how>, C<uri>,
C<repository>, C<identity>, C<control_branch> and C<pr_prefix>, and
C<refusal> where the clone could not give the remote or the repository: the
sentence L</_source_control> refuses with. The answer is resolved once and
kept, refusal and all.

Precedence is explicit over derived over default. The remote is
L</_resolve_remote>'s answer, the clone's own pin or the clone's remote that
points at the repository; it is never the first C<git remote>, which is
alphabetical order. The repository is the one written in the configuration,
as C<owner/repo> or as a URL, or else the repository the resolved remote
points at, or the C<owner/repo> its URL carries, on any host; either way it
is read through L</repository_identity> and its identity kept beside it. A
written repository is identified even where the clone has no remote or no
git at all, which is what lets a dry run and the describe report go on
without one. The remote is set on L</git>'s shared handle as its
L<Service::Git/pipeline_remote>, so every remote operation on the
repository takes it without being told.

C<pr_prefix> is read off the configuration being judged, not through
L</pr_prefix>, which answers control's value under D112, because reading
control here would make every command in a pipeline repository pay for a
read of control. The url is asked of git only where C<repository> was not
configured, since the repository is the one value derived from the url and
asking costs a fork; so a configured repository is the only way C<uri> comes
back undef. The git checkout is asked about before the handle is built,
because the handle's constructor refuses the path with a message about the
path, and what an operator who turned a pipeline on needs to hear is what a
pipeline needs a repository for.

B<Parameters:> None.

B<Returns:> The hash reference described above.

B<Errors:> None of its own.

B<Examples:>

    my $sc = $top->_source_control_found;
    # in a clone with no remote, and repository: org/repo written:
    # {repository => 'org/repo', identity => {...}, control_branch => 'control',
    #  pr_prefix => 'pr/', refusal => "This clone has no git remote, ..."}

    # key is unset

    $top->_validate_one_exodus_mount;
    # exits CONFIG (78) where prod resolves /other/exodus/ and
    # pipeline.exodus_mount is unset, so /secret/exodus/

=head2 _pipeline_exodus_mount

    my $mount = $top->_pipeline_exodus_mount();

The one exodus mount every pipeline record lives under, which is what
L</applied_record_path> hangs the pipeline's own record under.

It is C<pipeline.exodus_mount> from C<.genesis/config>, defaulting to
C</secret/exodus/>, the pipeline's own key under D116. No environment is
loaded to learn it, so a command standing on a deployment branch, which
carries only its own environment's file, can address every pipeline record.
It is read whether or not C<pipeline.enabled> is true, because a disowned
repository is precisely one whose key is off while the record still stands,
and the refusal that exists to find that record has to address it. The value
comes back normalised to one leading and one trailing slash, as an
environment's C<exodus_mount> is, so a caller appends to it directly.

B<Limitations:> the key is read from the configuration in front of the
command. D112 moves every key that says what the pipeline is onto control's
copy, and this read moves with them when that reader lands.

B<Parameters:> None.

B<Returns:> The mount, as a string ending in a slash.

B<Errors:> None.

B<Examples:>

    my $mount = $top->_pipeline_exodus_mount;
    # returns '/secret/exodus/' where the key is unset

    my $mount = $top->_pipeline_exodus_mount;
    # returns '/secret/other/' where the key is 'secret/other'

=head2 _validate_pipeline_config

    $top->_validate_pipeline_config();

Runs the checks on the pipeline section that a declarative schema cannot
state. It is called from L</_validate_config> for every command, straight
after C<< Genesis::Config::validate >>, so that a repository meets the same
refusal in the same words whichever command loaded it.

A section that is off is left alone. Otherwise the checks run in this
order. Both halves of the deployment slug are checked as git ref components
by L</_validate_slug_components>, first, because they name the branches
everything else here is about. Then every key that shapes the pipeline is
checked by L</_validate_shape_values> to have resolved from the
environment's own files, before anything reads the shape. The source
control is not resolved here: whether the clone is a git checkout with a
remote that points at the repository is asked where the remote is first
used (L</_source_control>), and the file's own rules for those keys are the
schema's (D118, noted 2026-10-15). The configured
provider's own rules are not among the checks here: the provider block
declares the type that decides it, so C<Genesis::Config::validate> has
already dispatched the block to that provider and gathered what it said with
every other error. Then come the capability gates of
L</_validate_capability_gates>, before the environment blocks are read for
their shape, because a key with no ability behind it is a fact about the
provider rather than about how the operator wrote the block; then the
manifest store and the kit floors of L</_validate_manifest_store>, a fact
about the pipeline as a whole; and then the one exodus mount of
L</_validate_one_exodus_mount>, which comes after the store because the
mount is where that store keeps the pipeline's applied record. Then the
provider's override files are checked by L</_validate_override_files>
(T389), so a bad one is refused before the pipeline is built. Last, every
environment the deployment root holds has its C<genesis.pipeline> block
checked, read merged through L</_merged_env_params>; a file whose C<genesis>
key is not a hash carries no block to check, and is left to whatever reads
the environment itself. The refusals
themselves belong to L</_validate_slug_components>, to
L</_validate_shape_values>,
to L</_validate_capability_gates>, to
L</_validate_manifest_store>, to L</_validate_one_exodus_mount>, to
L</_validate_override_files>, and to L</_validate_env_pipeline_block>.

B<Returns:> 1.

=head2 _validate_override_files

    $top->_validate_override_files();

Checks every override file the configured provider would merge over its
emitted pipeline: each F<.genesis/pipeline-overrides-E<lt>typeE<gt>.yml>, and
under the multi-file form each
F<.genesis/pipeline-overrides-E<lt>typeE<gt>-E<lt>fileE<gt>.yml>, as the
compiler's C<override_file_names> names them (D27, D67). Each must parse as
YAML and be a map, which is what the compile's C<spruce merge> needs, so a bad
one is refused at load rather than after the pipeline is built (T389). A file
named for another provider is not this pipeline's and is not read. The files
are read from the deployment root, where the compiler reads them.

B<Parameters:> None.

B<Returns:> 1.

B<Errors:> Bails at C<CONFIG>, one bullet per file, naming a file that does
not parse with the parser's first line, and a file that parses to something
other than a map.

B<Examples:>

    $top->_validate_override_files;
    # Configuration validation failed for .genesis/config:
    #  - .genesis/pipeline-overrides-concourse.yml must be a map, merged over
    #    the emitted pipeline

=head2 _validate_shape_values

    $top->_validate_shape_values();

Refuses, at C<Genesis::Exit::CONFIG>, a key that shapes the pipeline whose
value still contains C<((> after the environment's merge: C<genesis.bosh_env>
and the eight keys of the C<genesis.pipeline> block, C<prior_env>,
C<require_pr>, C<manual>, C<redeploy_cron>, C<notifications>,
C<track_dependencies>, C<track_additional_files> and C<track_bosh_configs>,
searched through any list or hash a value holds.

Each environment's shape is read through L</_merged_env_params>, a merge of
its own files with vault unreachable (D117), so a C<grab>, a C<concat> or a
C<||> default the files resolve has already been resolved, and what still
holds C<((> is one of three things: a credhub or BOSH variable, which no
shape key may carry since none holds sensitive data; a vault value, directly
or through any reference to one, which would let the pipeline's gating
change without a commit; or a reference those files do not resolve, a value
only Genesis or the kit supplies among them. Each is checked on every
environment L</_env_file_names> holds, so a value a site file sets is
refused on every environment that inherits it, and the refusal names the
nearest file in that environment's hierarchy that sets the key, found by
reading the hierarchy's files one at a time on the way to a refusal.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Configuration validation failed for ..."> - one bullet per environment
and key, naming the key, the environment, the value as it stands after the
merge, and the file that sets the key.

=back

B<Examples:>

    $top->_validate_shape_values;
    # returns 1 where prior_env is (( concat meta.site "-lab" )) and
    # meta.site is set

    $top->_validate_shape_values;
    # exits CONFIG (78) where prior_env is (( concat "c-" meta.value "-lab" ))
    # and meta.value is a (( vault )), naming c-(( vault "..." ))-lab

=head2 _file_setting

    my $file = $top->_file_setting('us-east-qa', 'genesis.pipeline.manual');

The nearest file in an environment's hierarchy that sets a key, read one file
at a time from the leaf up, as the path relative to the deployment root, or
C<undef> when no file sets it. A refusal of an inherited key names the
environment that inherits it, and the operator edits the file this answers,
so L</_validate_shape_values>, L</_validate_capability_gates> and
L</_validate_env_pipeline_block> name both (T405).

B<Parameters:> The environment name and the dotted key.

B<Returns:> The file, or C<undef>.

B<Errors:> None of its own; a file that does not parse is read as setting
nothing.

B<Examples:>

    $top->_file_setting('us-east-qa', 'genesis.pipeline.manual');   # 'us.yml'

=head2 _validate_prior_env_graph

    $top->_validate_prior_env_graph();

Refuses, at C<Genesis::Exit::CONFIG>, a C<genesis.pipeline.prior_env> graph
that is not well formed: a predecessor that is no environment of this
pipeline, and a chain of predecessors that comes back on itself, an
environment that follows itself included.

The topology orders the environments from the ones that follow nothing, so
an environment in a cycle is never reached, and one whose predecessor is no
environment becomes a root that nothing holds; left to the topology, both
would be dropped or ungated without a word. The edges come from each
environment's merged files through L</_merged_env_params>. Each chain is
followed from every environment, and a cycle is named once, from its
alphabetically first member.

It runs where the shape is built, from L</_topology_here>, on the shape's own
tree, rather than at configuration load: a deployment branch carries one
environment's hierarchy, so the tree in front of a deploy never holds the
predecessor it names, and only the shape's tree holds every environment.
Every command that uses the graph reads the shape first, so a malformed
graph still refuses before anything acts. D77's dependency-cycle exception
concerns C<track_dependencies>, another key, and is untouched.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Configuration validation failed for ..."> - one bullet per environment
whose predecessor is no environment, naming both, and one per cycle, naming
each environment in it and the one it follows.

=back

B<Examples:>

    $top->_validate_prior_env_graph;
    # returns 1 where qa follows lab and prod follows qa

    $top->_validate_prior_env_graph;
    # exits CONFIG (78) where lab follows prod, prod follows qa, and qa
    # follows lab

=head2 _validate_capability_gates

    $top->_validate_capability_gates();

Refuses, at C<Genesis::Exit::CONFIG>, any configuration key whose provider
capability is false, naming both the key and the capability.

A capability is what a provider is able to do and a key is the operator's
choice inside that ability, so a key with no ability behind it cannot mean
anything. Three of the six capabilities gate a key. C<optional_git_triggers>
gates C<genesis.pipeline.manual>, C<scheduled_jobs> gates
C<genesis.pipeline.redeploy_cron>, and C<per_commit_runs> gates
C<pipeline.provider.group_commits>. C<deployment_locks> and
C<cross_pipeline_events> are structural and gate nothing configurable.

C<multi_file_output> gates nothing here either. A key that only some
providers offer is declared by those providers rather than gated centrally,
so the provider that can emit several files declares
C<pipeline.provider.output_layout> in its own fragment and the one that
cannot declares nothing at all. Under such a provider the key is simply not
a key, and an operator who writes it is refused by name as the configuration
loads, before any gate is read.

Every provider declares its abilities, so every gate here has a declaration
to read and nothing asks whether a provider has a compiler class. The manual
provider declares all six false, which is why a key it gates is refused
rather than quietly accepted. Each declaration is checked against the six
names through L<Genesis::CI::Provider/declared_capabilities> before any gate
reads it.

The type is read as C<pipeline.provider.type>, defaulting to C<manual>,
directly off L</config> rather than through L</pipeline_provider_type>'s
shape, because validation checks the configuration in front of it and not
what control declares; the default matches the accessor's. The declaration
comes from the class
L<Genesis::CI::ProviderRegistry/provider_class> names for it, which is the
class the provider block was already dispatched to.

The one repository-wide key is read for what the operator actually wrote,
through C<< Genesis::Config::is_set >> rather than C<< has >>, because a
value the schema filled from a provider's own default is nobody's choice
and cannot be what a refusal is about. The two per-environment keys are
read out of each environment's merged C<genesis.pipeline> block, where no
default is ever applied. The gates that will fire are sorted by where their
key lives before anything is read, so the environment files are walked once
rather than once per capability. Every gate that fires is gathered before the
refusal is raised.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Configuration validation failed for ..."> - raised when at least one
configured key is gated on a capability the provider does not declare. Each
one is listed under it, naming the key, the provider, and the capability,
and the environment as well where the key lives in an environment file.

=item *

C<"CI provider ... declares the capabilities ..."> - raised through
L<Genesis::CI::Provider/declared_capabilities> when the provider class
answers anything but exactly the six names, which is a bug in that class
rather than anything an operator wrote.

=item *

C<"Failed to load CI provider ..."> - raised through
L<Genesis::CI::ProviderRegistry/provider_class> when the registry names a
class whose file will not compile. It exits 1 and carries the compiler's error
uncut. An operator meets this at the dispatch inside
C<Genesis::Config::validate> instead, which loads the same class first and
refuses at C<Genesis::Exit::CONFIG> with the backtrace cut away, in the
terms every configuration refusal carries.

=back

B<Examples:>

    $top->_validate_capability_gates;
    # returns 1 where every configured key has its capability behind it

    $top->_validate_capability_gates;
    # exits CONFIG (78) where an environment sets genesis.pipeline.manual
    # under a provider that declares optional_git_triggers false

=head2 _validate_manifest_store

    $top->_validate_manifest_store();

Refuses, at C<Genesis::Exit::CONFIG>, a C<manifest_store> that is not
C<exodus>, and any environment whose effective Genesis floor is below
3.1.0 or is not declared at all. It does not read C<pipeline.enabled>
itself, because L</_validate_pipeline_config> is its only caller and has
already returned where the section is off, so everything below is said of
a repository whose pipeline is known to be on.

The key is read with no fallback of its own, because the schema declares
the default and a second one here would read an explicit null as C<exodus>
instead of refusing it by name. The case where nothing supplies a value is a
configuration that has not met the version 2 schema yet, which is a version 1
file on its way through L</_upgrade_config_to_v2>.

Under a pipeline the deploy must not be a git writer on a deployment
branch, because the propagation writer already advances it. The certified
commit and the applied, hold and proposed records live in exodus, so the
store cannot be anything else, and the refusal is permanent rather than a
limit the MVP lifts later.

The check sits here rather than in the compiler's validator, which is
where a deploy would never meet it. That gap is what let an environment on
an old kit keep both writers on the branch, because a kit whose Genesis
floor is below 3.1.0 is forced onto the repository store at run time
whatever the configuration says, since earlier versions cannot update the
exodus deployment audit data.

The floor compared is the effective one, which is the higher of the
repository's own C<minimum_version> and the environment's merged
C<genesis.min_version>, or C<genesis.minimum_version>, the same pair
C<< Genesis::Env::effective_minimum_version >> takes the maximum of.
Reading the environment's line alone would refuse a repository whose own
floor already lifts it, over a number no deploy would ever honour. Each
environment is read merged through L</_merged_env_params> and refused by
name, with the remedy of raising the kit's floor rather than changing the
store's value.

An environment where neither line is written declares nothing, and that
resolves to C<0.0.0> rather than to no opinion, so the run time serves it
out of the repository store exactly as it serves a declared 3.0.0. It is
therefore refused too, in its own words, because the remedy there is to
write a floor down rather than to raise one. A newly written environment
file omits the minimum version whenever Genesis is a development build,
so this is a case an operator meets rather than a theoretical one.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"manifest_store: ... cannot be used under a pipeline"> - raised when the
repository's pipeline is enabled and its store is C<repository> or
C<hybrid>, naming the value that was configured.

=item *

C<"The environment ... declares no minimum Genesis version"> - raised when
neither the environment's merged C<genesis.min_version>, nor its
C<genesis.minimum_version>, nor the repository's C<minimum_version> is
written, naming the environment and both keys that would settle it.

=item *

C<"The environment ... has a Genesis floor below 3.1.0"> - raised when an
environment's effective floor, the higher of its own merged
C<genesis.min_version>, or C<genesis.minimum_version>, and the
repository's C<minimum_version>, is older than 3.1.0, naming the
environment and carrying the remedy. The remedy names the key as well as
the kit, because the loop reads the floor out of the merged environment
parameters and the repository's own setting, and those are usually
written from the kit but need not be.

=back

B<Examples:>

    $top->_validate_manifest_store;
    # returns 1 where the store is exodus and every kit floor is 3.1.0 or later

    $top->_validate_manifest_store;
    # exits CONFIG (78) where .genesis/config says manifest_store: hybrid

=head2 _merged_env_params

    my $params = $top->_merged_env_params('us-east-prod');

Returns an environment's merged parameters as a hash reference, loaded from
its file hierarchy with the nearer file winning. It is the load-time form of
the read every C<genesis.pipeline.*> key gets: an inherited key is absent
from the leaf file, so a leaf-only read answers wrongly and says nothing
about it.

The read is the environment's own: a bare C<Genesis::Env>, its
C<vaultless_environment> manifest, which is spruce's adaptive merge over the
hierarchy C<actual_environment_files> gives, the name-based ancestors and any
C<genesis.inherits>, with vault unreachable to it
(L<Genesis::Env::Manifest::VaultlessEnvironment>). Spruce's merge operators,
C<(( append ))>, C<(( prune ))> and the rest, apply exactly as they do when
the environment is deployed; a value operator the files resolve, a C<grab> or
a C<concat>, is resolved; and a C<(( vault ))> comes back as its own text, in
its place and in every value built from it, as does anything else that
resolves nowhere here. No kit is needed, which is what lets the check run as
the configuration loads, and the manifest is cached for the process under the
environment's signature.

An operator written in spruce's C<(( op(args) ))> call form is refused first,
in its own words, by L<Genesis::Env/_refuse_operator_call_form>. A file in
the hierarchy that will not merge is refused rather than skipped:
a key can live anywhere in the hierarchy, so a file nobody can read is a key
nobody can see. The refusal names the files by name alone, because listing
the hierarchy in full parses every file for what it inherits and would fall
over the same file again. It is refused on the spot even while the load is
gathering its problems into one refusal (T411), because every check after it
reads the parameters this answers.

The answer is also kept on the object, one entry per environment name, so
the five call sites that walk every environment are handed the same hash.

Nothing invalidates that memo and nothing wants to yet. All five callers run
from L</_validate_pipeline_config>, which L</config> runs once behind its own
memo, so no environment file is written between the first read and the last.
L</_validate_env_pipeline_block> is the only one that writes into what it was
handed, and it copies the top level before it does. A caller added after an
environment file is written would need an invalidator.

B<Parameters:>

=over 4

=item C<$env_name>

The environment's name, which is also the stem of its leaf file.

=back

B<Returns:> A hash reference of the merged parameters.

B<Errors:>

=over 4

=item *

C<"Invalid environment name ...">, from L<Genesis::Env/bare>, when handed a
name the naming rules refuse, which no caller walking L</_env_file_names>
ever does.

=item *

C<"An environment file could not be read as YAML."> - raised at
C<Genesis::Exit::CONFIG>, naming the hierarchy's files on the lines below and
carrying what the merge said, when a file in the hierarchy will not merge.

=back

B<Examples:>

    my $params = $top->_merged_env_params('us-east-prod');
    # returns the merge of us.yml, us-east.yml, and us-east-prod.yml,
    # with the nearest file winning

=head2 _env_file_names

    my @names = $top->_env_file_names();

Returns the environment names the deployment root holds, sorted: the stems
of its top-level C<.yml> files that declare a C<genesis.env> equal to their
own name, found off the text by L<Genesis::Env/declared_env_names> with no
parse, under a name the environment naming rules accept, the same filter
L</envs> applies. A name the rules refuse is no environment, so it is left
out rather than refused, and no branch is ever composed from it.

An ancestor is not one. Its keys are checked where they take effect, on each
environment whose merged hierarchy carries them, so a site file is never
refused as though it were an environment of its own. Anything else at the
root, a legacy C<ci.yml> among them, is never read. Only plain files are
counted: a directory whose own name ends in C<.yml> is not an environment
file however much it looks like one.

B<Returns:> A sorted list of names, empty where the root holds no
environment files.

=head2 _validate_env_pipeline_block

    $top->_validate_env_pipeline_block('us-east-prod', $block);

Checks one environment's C<genesis.pipeline> block against
L</_pipeline_env_keys_schema>, and refuses it by name where it does not fit.

The block is validated through a throw-away in-memory C<Genesis::Config>, so
the types, the defaults, the required flags, and the unknown-key refusal are
the ones the repository configuration already gets and there is no second
validator to keep in step with the first. A block that is not a hash at all
is handed over as it stands, so the answer is the declaration's own refusal
rather than a Perl error. A bare string written where one of the three list
keys is declared is normalised to a one-element list first, because an
operator may still write a single entry, and nothing is split on the way,
since a crontab expression carries commas of its own.

Two shapes the declaration cannot state are checked beside it. A
C<track_dependencies> entry is a deployment type at this environment or an
C<< <env>/<type> >> pair elsewhere, and C<track_bosh_configs> is a boolean or
a list of config type names.

Each refused key that the environment inherits rather than writes itself is
followed by C<(set in E<lt>fileE<gt>)>, the file L</_file_setting> answers, as
is each key L</_validate_capability_gates> refuses (T405).

Those checks read the block as the operator wrote it, taken before the
validator runs. Each list key declares C<envsplit>, and C<Genesis::Config>
answers a value that is not a list by splitting it as though it came from the
environment, which turns a mapping into the address of a reference. A mapping
written where a list belongs is therefore refused outright, before any entry
of it is read. The copy taken is shallow, which is enough while all three list
keys are lists of strings and nothing between the copy and the checks writes
through it; a key that grows a nested subtype would need a deep copy.

A refusal the validator raises that carries no bullets to pick apart is
reported by its first line, so an C<eval> that failed never leaves the block
looking valid and a multi-line failure does not read ragged under a bullet
of its own. The caught text is taken before anything else is called, because
the readers that pick it apart run evals of their own and would clear it.

B<Parameters:>

=over 4

=item C<$env_name>

The environment the block belongs to, which the refusal names.

=item C<$block>

Hash reference of the merged C<genesis.pipeline> block.

=back

B<Returns:> 1.

B<Errors:>

=over 4

=item *

Each fault is a problem of the load's one refusal, through L</_refuse_config>,
worded C<< genesis.pipeline.<key> in <env>: ... >> as the capability gate
words its own (T411), and refused at C<Genesis::Exit::CONFIG>. The faults are
the schema's own refusals with their keys named as the environment file spells them, the
shape refusals above, and C<"genesis.pipeline.<key>: expected a list of
strings"> where a mapping was written in a list's place.

=back

B<Examples:>

    $top->_validate_env_pipeline_block('us-east-prod', {manual => 1});
    # returns 1

    $top->_validate_env_pipeline_block('us-east-prod', {manual => 'maybe'});
    # exits CONFIG: genesis.pipeline.manual: expected a boolean

=head2 _first_errors

    my @errors = _first_errors($@);

The bullet lines out of a caught C<< Genesis::Config::validate >> refusal.
That refusal arrives already formatted and wrapped to the terminal, so the
text is split on the bullet the formatter itself uses, each error is passed
through L<Genesis/without_backtrace>, and the heading above the first bullet is
dropped. The
bullet is asked for rather than assumed, because which glyph it is depends on
what the terminal can render.

Each error's C<pipeline.> prefix is rewritten to C<genesis.pipeline.>, so the
key is named the way the environment file spells it rather than the way the
throw-away configuration was built. The rewrite is anchored to the head of
the folded line, because it is for the key the error opens with, and a value
of the operator's that happens to carry the word is not a key.

That is also what cuts each error at the first C<< at <file> line <n> >>
behind it. Under C<Carp::Always> the backtrace is folded into the bullet it
was raised under, and without the cut a developer reads the stack appended to
the error.

Plain function, not a method.

B<Parameters:>

=over 4

=item C<$caught>

The caught text, normally C<$@>. An undefined or empty value answers an empty
list.

=back

B<Returns:> A list of one-line error strings, empty where the text carries no
bullet at all, which is the caller's cue to report the caught text as it
stands.

B<Examples:>

    my @errors = _first_errors($@);
    # returns ('genesis.pipeline.manual: expected a boolean, not maybe')
