=head1 NAME

Genesis::Top - Root-directory context object for Genesis deployment repositories

=head1 SYNOPSIS

    use Genesis::Top;

    # Open an existing deployment repository
    my $top = Genesis::Top->new('/path/to/cf-deployments');

    # Open with a specific vault target for this session
    my $top = Genesis::Top->new('/path/to/cf-deployments', vault => 'prod-vault');

    # Create a new deployment repository
    my $top = Genesis::Top->create('/repos', 'cf');

    # Common operations
    my $env  = $top->load_env('us-east-prod');
    my $kit  = $top->local_kit_version('cf', '2.3.0');
    my $type = $top->type;   # Returns: 'cf'

    # Check vault connectivity
    if ($top->has_vault) {
        my $v = $top->vault;
        printf "Using vault: %s\n", $v->name;
    }

=head1 DESCRIPTION

Several interactions with Genesis have to take place in the context of a
I<root> directory. Often this is a C<something-deployments> git repository.

C<Genesis::Top> abstracts operations on that root directory so that other
parts of the codebase can stop worrying about file paths and instead carry
around a C<Top> context object which handles those concerns for them.

A C<Top> object manages:

=over 4

=item * The repository root path and file operations relative to it

=item * The configuration stored in C<.genesis/config>

=item * Connectivity to the Vault secrets provider

=item * Kit discovery, download, and version resolution

=item * Environment loading and creation

=back

Inherits from L<Genesis::Base>, which provides memoization helpers
(C<_memoize>, C<_set_memo>, C<_clear_memo>, C<_get_memo>).

=head1 CONSTANTS

=head2 DEFAULT_CONTROL_BRANCH

The branch a branch-based pipeline treats as authoritative when
C<pipeline.source_control.control_branch> is not configured. Read through
L</control_branch> rather than directly.

=head2 DEFAULT_PR_PREFIX

The prefix a pull request branch carries when
C<pipeline.source_control.pr_prefix> is not configured. Read through
L</pr_prefix> rather than directly.

=head2 PROPAGATE_NO_BRANCH_EXIT

The exit status C<genesis propagate> uses when it refuses to run because
an environment in scope has no branch anywhere.

B<It exists so a refusal can be told apart from a breakage.> C<deploy>
runs C<propagate> as a subprocess and sees only an exit status. Reporting
a raw non-zero code sends the operator debugging, when a missing branch
is a known condition one flag from resolution. C<Genesis::Env> matches on
this value to say so plainly, and treats every other non-zero status as
an unexpected failure. See
L<Genesis::Commands::Pipelines/_authorize_branch_creation>.

Values below 9 are avoided because the shell and Perl already ascribe
meaning to them; a distinctive value keeps the match unambiguous.

=head1 METHODS

=head2 new

    my $top = Genesis::Top->new;

Opens an existing Genesis deployment repository. With no arguments, opens
the current directory. When the first argument is an odd-length list element
(i.e., a plain scalar followed by pairs), it is taken as C<$root>; otherwise
C<$root> defaults to C<'.'>.

As a side effect, sets C<$ENV{GENESIS_ROOT}> to the absolute path of the
repository, and sets C<$ENV{GENESIS_TARGET_VAULT}> and C<$ENV{SAFE_TARGET}>
to the vault name when a vault is successfully connected.

B<Parameters:>

=over 4

=item C<$root>

B<(optional)> Path to the root of an existing Genesis deployment repository.
Defaults to C<'.'> when the argument list has an even number of elements.

=item C<vault>

B<(optional)> Name or URL of a safe target to use for this session only.
Overrides the vault stored in the repository configuration without saving
the change.

=item C<no_vault>

B<(optional)> When true, disables vault connectivity entirely for this
object. Intended for test contexts.

=back

B<Returns:> A new C<Genesis::Top> object.

B<Errors:>

=over 4

=item *

C<"'$root' is not a Genesis deployment repository"> - raised when the
specified path does not contain a valid C<.genesis/config> file.

=back

B<Examples:>

    # Open current directory as a Genesis Top object
    my $top = Genesis::Top->new;
    # Returns: Genesis::Top object for the current directory

=head2 create

    my $top = Genesis::Top->create($path, $name, %opts);

Creates a new Genesis deployment repository under C<$path>. Strips a
trailing C<-deployments?> suffix from C<$name> before use. The repository
directory is created as C<$path/$dir> where C<$dir> defaults to
C<$name> (or C<$name-deployments> when the legacy suffix is enabled in the
Genesis RC configuration).

The method writes C<.genesis/config>, creates the C<.genesis/> directory
hierarchy, creates the local kits directory (when C<kits_path> is supplied),
and generates a C<README.md>.
On failure the partially-created directory is removed and the error is
re-thrown.

Sets C<$ENV{GENESIS_ROOT}> as a side effect (inherited from C<_build>).

B<Parameters:>

=over 4

=item C<$path>

B<(required)> Parent directory under which the new repository directory is
created.

=item C<$name>

B<(required)> Deployment type name (e.g., C<'cf'>, C<'bosh'>, C<'vault'>).
A trailing C<-deployments?> suffix is stripped automatically. Must match
C</^[a-z][a-z0-9_-]+$/> after stripping.

=item C<directory>

B<(optional)> Override the final directory name. Defaults to C<$name> or
C<$name-deployments>.

=item C<vault>

B<(optional)> Safe target name or URL to record as the secrets provider.

=item C<no_vault>

B<(optional)> When true, skips vault configuration. Raises an error if
C<$ENV{GENESIS_COMMAND}> is set (i.e., running in a real genesis session,
not a test).

=item C<kits_path>

B<(optional)> Path to the directory where compiled kits are stored.
Humanized relative to the repository root when possible, otherwise stored
as an absolute path (with C<~> substituted for the home directory prefix).

=item C<creator_version>, C<updater_version>, C<minimum_version>, C<manifest_store>

B<(optional)> Override the corresponding config keys written to
C<.genesis/config>.

=back

B<Returns:> A new C<Genesis::Top> object pointing at the newly created
repository.

B<Errors:>

=over 4

=item *

C<"Invalid Genesis deployment repository name '$name'"> - raised when
C<$name> (after stripping the suffix) does not match C</^[a-z][a-z0-9_-]+$/>.

=item *

C<"Repository directory name must only contain alpha-numeric characters, periods, hyphens and underscores">
- raised when the resolved directory name contains illegal characters.

=item *

C<"Cannot create new deployments repository `$dir': already exists!"> -
raised when the target path already exists.

=item *

C<"no_vault option can only be used in test contexts"> - raised when
C<no_vault> is passed but C<$ENV{GENESIS_COMMAND}> is set.

=back

B<Examples:>

    # Create a new CF deployment repository
    my $top = Genesis::Top->create('/repos', 'cf');
    # Creates /repos/cf-deployments (with legacy suffix enabled)
    # or /repos/cf (without)

    # Create with a specific directory name
    my $top = Genesis::Top->create('/repos', 'cf',
        directory => 'cloud-foundry',
    );

=head2 search_for_repo_path

    my ($root, $path) = Genesis::Top->search_for_repo_path($deployment, %opts);
    my @paths         = Genesis::Top->search_for_repo_path($deployment, all_paths => 1);

Searches for a deployment repository whose directory name matches
C<$deployment> within the configured deployment roots (from
C<$HOME/.genesis/config>, plus the current and parent directories). Applies
glob-pattern matching - anchoring with C<^> and C<$> is supported.

Search roots are checked in order: the current directory (C<@current>),
the parent directory (C<@parent>), and then each named root from the
C<deployment_roots_map> configuration key. Within each root, BOSH
repositories are sorted first, then other types alphabetically.

When exactly one match is found it is returned immediately. When multiple
matches are found and the process is running in a controlling terminal, an
interactive prompt (via C<prompt_for_choice>) is presented to the user.
When not in a controlling terminal and more than one match exists, an error
is raised listing all matches unless C<all_paths> is set.

B<Parameters:>

=over 4

=item C<$deployment>

B<(required)> Deployment name or glob pattern to match against repository
directory names. The pattern is automatically wrapped with C<*...*> wildcards
unless anchored with C<^> or C<$>.

=item C<all_paths>

B<(optional)> When true, returns all matching C<[$label, $path]> pairs as a
list rather than prompting for selection.

=back

B<Returns:>

In normal mode: a two-element list C<($deployment_root, $path)> where
C<$deployment_root> is the parent directory of the matched repository and
C<$path> is the full path to the repository.

When C<all_paths> is true: a list of C<[$label, $path]> array references,
one per match.

B<Errors:>

=over 4

=item *

C<"Invalid option specified to search_for_repo_path: %s"> - raised (via
C<bug()>) when an unrecognized option key is passed. C<%s> is replaced by
the unrecognized key name.

=item *

C<"No deployment repositories found matching #C{%s}"> - raised when no
matching repository exists anywhere in the search roots. C<%s> is replaced
by the C<@:$deployment> label.

=item *

C<"Ambiguous deployment repository name: #C{%s} matches multiple paths:\n  -#\@{_}%s\n\nPlease refine your match criteria.">
- raised when multiple matches are found and the process is not in a
controlling terminal (and C<all_paths> is not set). C<%s> is the label and
the indented path list respectively.

=item *

C<"No deployment repository path selected."> - raised when the user chooses
the "None of these" option from the interactive prompt.

=back

B<Examples:>

    # Locate the cf deployments repository
    my ($root, $path) = Genesis::Top->search_for_repo_path('cf');
    # Returns: ('/srv/deployments', '/srv/deployments/cf-deployments')

    # Get all matching paths without prompting
    my @all = Genesis::Top->search_for_repo_path('*vault*', all_paths => 1);

B<Parameters:>

=over 4

=item C<$path>

=back

B<Examples:>

=head2 kit_provider

    my $provider = $top->kit_provider;

Returns the kit provider configured for this repository. The result is
memoized after the first call. The provider is constructed from the
C<kit_provider> hash in C<.genesis/config>, or defaults to a
C<Genesis::Kit::Provider::GenesisCommunity> instance when that key is absent.

B<Returns:> A C<Genesis::Kit::Provider> subclass instance.

B<Examples:>

    my $provider = $top->kit_provider;
    my @names = $provider->kit_names;

=head2 set_kit_provider

    my $err = $top->set_kit_provider(%opts);

Initializes a new kit provider from C<%opts> and updates the repository
configuration. If the new provider is a
C<Genesis::Kit::Provider::GenesisCommunity> instance, the C<kit_provider>
key is cleared from the config (restoring the default). Otherwise the
provider configuration is written and saved.

Both branches (GenesisCommunity and custom provider) set C<updater_version>
(when the config file exists on disk), call C<_validate_config()>, and save
the config to disk.

B<Parameters:>

=over 4

=item C<%opts>

Options forwarded to C<< Genesis::Kit::Provider->init >>. See
L<Genesis::Kit::Provider> for accepted keys.

=back

B<Returns:> The value of C<$@> after the eval block - an empty string on
success, or the error message if initialization failed.

B<Examples:>

    my $err = $top->set_kit_provider(type => 'github',
        organization => 'my-org');
    # Returns: '' on success, error string on failure
    die $err if $err;

=head2 vault

    my $vault = $top->vault(%opts);

Returns the C<Service::Vault> object for this repository's secrets provider.
The result is memoized after the first successful call; options passed on
subsequent calls are ignored.

Resolution order:

=over 4

=item 1.

If C<$ENV{GENESIS_NO_VAULT}> is set, returns a C<Service::Vault::None>
instance immediately.

=item 2.

If running inside a Genesis callback and C<$ENV{GENESIS_TARGET_VAULT}> is
set, re-binds to the inherited vault via C<Service::Vault::Remote->rebind()>.

=item 3.

If the repository config has a C<secrets_provider> block, attaches to that
vault URL using C<Service::Vault::Remote->attach(...)>. Falls back to
C<Service::Vault::None> when attachment fails and C<no_vault> is set.

=item 4.

Otherwise, uses C<< Service::Vault->default >> (whatever C<safe> is currently
targeting) and connects and validates it.

=back

B<Parameters:>

=over 4

=item C<silent>

B<(optional)> Passed to C<< Service::Vault::Remote->attach >> and to
C<< $vault->connect_and_validate >> to suppress output. Only consulted on
the first call (before memoization).

=item C<no_vault>

B<(optional)> When true and attachment to the configured URL fails, returns
a C<Service::Vault::None> instead of raising an error. Only consulted on the
first call.

=back

B<Returns:> A C<Service::Vault> subclass object (C<Remote> or C<None>).

B<Examples:>

    my $vault = $top->vault;
    printf "Vault: %s at %s\n", $vault->name, $vault->url;
    # Returns: a Service::Vault::Remote or Service::Vault::None object

    # Allow no-vault mode silently
    my $vault = $top->vault(silent => 1, no_vault => 1);
    # Returns: Service::Vault::None when no vault is reachable

=head2 repo_vault

    my $result = $top->repo_vault;

Returns the repository's configured vault object when C<has_vault()> is true,
or the system default vault otherwise. Builds a C<Service::Vault::Remote>
from the C<secrets_provider> config, mirroring the attach logic in C<vault()>
but without memoization or session options.

B<Returns:> A C<Service::Vault::Remote> object when a vault is configured;
C<< Service::Vault->default >> otherwise.

=head2 has_vault

    my $bool = $top->has_vault;

Returns true when the repository configuration contains a non-empty
C<secrets_provider> hash.

B<Returns:> True when a vault is configured, false otherwise.

B<Examples:>

    if ($top->has_vault) {
        my $v = $top->vault;
        printf "Configured vault: %s\n", $v->name;
    }

=head2 set_vault

    $top->set_vault(%opts);

Sets the secrets provider for this repository, either interactively or by
target name. Unless C<session_only> is set, the new vault configuration is
persisted to C<.genesis/config>.

B<Parameters:>

=over 4

=item C<interactive>

B<(optional)> When true, presents an interactive safe-target selection
prompt. Ignores the C<target> option.

=item C<target>

B<(optional)> Name or URL of the safe target to use. Exactly one candidate
vault must match; otherwise an error string is returned without raising.

=item C<clear>

B<(optional)> When true, removes the vault configuration entirely (clears
C<secrets_provider> from config). B<Note:> the clear operation does not call
C<< config->save() >>, so the change is not persisted to disk.

=item C<vault>

B<(optional)> A C<Service::Vault::Remote> object to set directly.

=item C<session_only>

B<(optional)> When true, updates the in-memory vault reference but does not
write C<.genesis/config>.

=back

B<Returns:> An error string (C<"#R{[Error]} ..."> formatted) when the target
lookup fails; nothing (C<undef>) on success.

B<Errors:>

=over 4

=item *

C<"Invalid call to Genesis::Top->set_vault"> - raised via C<bug()> when none
of C<interactive>, C<target>, C<clear>, or a C<vault> object reference is
provided.

=back

B<Examples:>

    # Set vault by target name, session only
    $top->set_vault(target => 'prod-vault', session_only => 1);
    # Returns: undef on success

    # Set vault interactively and save to config
    $top->set_vault(interactive => 1);
    # Returns: undef on success

    # Clear vault configuration
    $top->set_vault(clear => 1);
    # Returns: undef on success

=head2 vault_status

    my %status = $top->vault_status;

Returns a hash of status information about the repository's configured vault.
Returns an empty list when C<has_vault()> is false.

The returned hash includes the raw C<secrets_provider> fields from config,
augmented with:

=over 4

=item C<security>

A display string: empty string for verified HTTPS, C<"#Y{(noverify)}"> for
unverified HTTPS, or C<"#Y{(insecure)}"> for plain HTTP.

=item C<alias>

The local safe target alias when exactly one alias maps to the vault URL.

=item C<alias_error>

Set when zero or more than one local aliases map to the vault URL.

=item C<status>

Connectivity status string. Contains a C<safe target> command hint when no
alias is found, a de-duplication hint when multiple aliases exist, or the
result of C<< $vault->status >> when a single alias is found.

=back

B<Returns:> A flat key-value list suitable for assignment to a C<%hash>.
Returns an empty list when C<has_vault()> is false.

B<Examples:>

    my %info = $top->vault_status;
    if (%info) {
        printf "URL:    %s\n", $info{url};
        printf "Status: %s\n", $info{status};
    }

=head2 deployment_slug_for

    my $slug = $top->deployment_slug_for($env_name);

The deployment slug for an environment name, which is C<< <env>/<type> >>.

This is the one identity a deployment has. The deployment branch, the vault
path under the exodus mount, and the BOSH deployment name are three
renderings of it, so composing any of them anywhere else is how they drift.

The argument is a name as a string and never a C<Genesis::Env>, deliberately,
so that a caller holding only a name composes the slug without loading an
environment.

B<Parameters:> The environment's name, as a string.

B<Returns:> The slug, such as C<qa/bosh>.

B<Errors:>

=over 4

=item *

C<"deployment_slug_for expects an environment name, got a %s"> - raised (via
C<bug()>) when the argument is a reference rather than a name, with C<%s>
replaced by the kind of reference it was handed.

=item *

C<"deployment_slug_for called without an environment name"> - raised (via
C<bug()>) when the argument is missing or empty.

=back

B<Examples:>

    my $slug = $top->deployment_slug_for('qa');
    # returns 'qa/bosh' in a repository whose deployment_type is bosh

=head2 branch_for

    my $branch = $top->branch_for($env_name);

The deployment branch for an environment name, which is its slug.

B<Parameters:> The environment's name, as a string.

B<Returns:> The branch name, such as C<qa/bosh>.

B<Errors:>

=over 4

=item *

C<"deployment_slug_for expects an environment name, got a %s"> - raised (via
C<bug()>) when the argument is a reference, because the name is passed
straight into L</deployment_slug_for>.

=item *

C<"deployment_slug_for called without an environment name"> - raised (via
C<bug()>) when the argument is missing or empty, for the same reason.

=back

B<Examples:>

    my $branch = $top->branch_for('qa');
    # returns 'qa/bosh'

=head2 pr_branch_for

    my $branch = $top->pr_branch_for($env_name);

The pull request branch for an environment name, which is L</pr_prefix>
joined onto its slug.

There is no second argument, because the prefix is configuration rather than
a caller's choice.

The join can produce a name another branch already owns, and that is refused
here rather than in each caller, so this is the one place a pull request
branch is named and the one place the collision is caught. Both the prefix
and the deployment type append, so the type cancels on both sides and the
comparison is against the composed branch names.

B<Parameters:> The environment's name, as a string.

B<Returns:> The branch name, such as C<pr/qa/bosh>.

B<Errors:>

=over 4

=item *

C<"The pull request branch for ... would be ..., which is the deployment
branch of the environment ..."> - raised when the joined name is a branch
some environment already owns, which needs an environment whose name is the
prefix followed by another environment's name. With the prefix C<pr-> and
the environments C<lab> and C<pr-lab>, the pull request branch for C<lab>
and the deployment branch for C<pr-lab> are both C<pr-lab/bosh>.

=item *

C<"The pull request branch for ... would be ..., which is the control
branch."> - raised when the joined name is the control branch itself.

=item *

C<"deployment_slug_for expects an environment name, got a %s"> and
C<"deployment_slug_for called without an environment name"> - raised (via
C<bug()>) when the argument is a reference or is missing, because the name is
passed straight into L</deployment_slug_for> before anything is joined onto
it.

=back

Both refusals exit C<Genesis::Exit::CONFIG> and name the branch they
would have collided with, and both are answered by changing
C<pipeline.source_control.pr_prefix>.

B<Examples:>

    my $branch = $top->pr_branch_for('qa');
    # returns 'pr/qa/bosh' under the default prefix

    # with pr_prefix 'pr-' and an environment named pr-lab

=head2 pipeline_staleness

    my $changes = $top->pipeline_staleness($git);

The environments whose pipeline no longer matches what is on control.

This is the one home of the comparison. The propagate pre-flight, the deploy
pre-flight, and C<pipeline-status> all ask it, because three copies of a
comparison drift three ways.

It reads three things. The applied commit comes from L</applied_record>. A
path diff between that commit and the control branch covers
C<.genesis/config> and every file of each environment's hierarchy, which is
what the pipeline's definition is made of. And each environment's compiled
dependency set is compared with the set its last deploy recorded reading.

A repository C<pipeline-apply> has never run against reports nothing, because
there is no commit to be stale against.

A repository with no pipeline reports nothing as well, and it answers before
the applied record's address is composed. The deploy pre-flight asks this on
every deploy, and addressing that record where there is no pipeline reaches
the refusal in L</_pipeline_exodus_mount>, which would stop an ordinary
deploy with a sentence about a pipeline the operator does not have.

B<Parameters:> A C<Service::Git> for the repository.

B<Returns:> An arrayref of hashrefs, each with C<env> and C<reason>, where
the reason is C<configuration-changed> or C<dependencies-changed>.

B<Errors:>

=over 4

=item *

C<< "Cannot compare <commit> against <branch>" >> - raised (via
C<Service::Git::diff_names>) when git cannot take the path diff, because the
applied commit is not in the local repository or the control branch has no
local ref. A clean answer there would be a wrong answer, so the query
refuses instead.

=back

B<Examples:>

    my $changes = $top->pipeline_staleness($git);
    # returns [] where the pipeline is current

    my @names = $top->pipeline_env_names();
    # returns ('prod', 'sandbox', 'staging')

    my @names = $top->pipeline_env_names();

=head2 pipeline_topology

    my $topo = $top->pipeline_topology();

The single answer to "what environments are in this pipeline, and in
what order".

Until this existed the question had two implementations that agreed only
by coincidence: C<pipeline_env_names> globbed F<*.yml> through
L</envs>, while
C<Genesis::CI::Compiler::ASTBuilder::_build_from_env_files> walked the
same directory building a DAG.  The latter was private and called from
four places in C<Genesis::Commands::Pipelines>, each repeating the same
edge-collection and breadth-first ordering.  Everything reading pipeline
membership now comes through here.

Membership is every environment C<Genesis::Top::has_env> accepts,
whether or not it declares a C<genesis.pipeline> block -- an environment
with no pipeline metadata still has a branch, still appears in
C<pipeline-status>, and still needs preparing.

B<Parameters:> None.  The environment directory is always the
repository root.

B<Returns:> A hashref:

=over 4

=item C<nodes>

Hashref of environment name to its C<genesis.pipeline> data.

=item C<edges>

Arrayref of C<< {from => ..., to => ...} >>, derived from C<prior_env>.

=item C<children>

Hashref of environment name to the arrayref of environments downstream
of it.

=item C<parent_of>

Hashref of environment name to the environment it follows.

=item C<order>

Arrayref of names, breadth-first from the roots.  Siblings are sorted by
name so the order is stable across runs -- callers print it and tests
compare against it.

=back

Every field is empty when CI is not configured, or when no environment
files are found, so callers may iterate without checking first.

B<Errors:> None.  Deciding that an empty topology is fatal belongs to
the caller: C<pipeline-status> and C<propagate> bail on it, while
C<pipeline_env_names> returns an empty list.

B<Examples:>

    my $topo = $top->pipeline_topology();
    for my $env (@{$topo->{order}}) {
        printf "%s (after %s)\n", $env, $topo->{parent_of}{$env} // 'control';
    }
    # mgmt (after control)
    # lab (after mgmt)
    # qa (after lab)

    # Roots are the environments with no parent
    my @roots = grep {!$topo->{parent_of}{$_}} @{$topo->{order}};

=head2 fetch_pipeline_envs

=item C<%opts>

=over 4

=item C<include_control>

Also fetch the control branch.

=back

=back

B<Returns:> 1 on success or when there was nothing to do.

B<Errors:>

=over 4

=item *

C<"Failed to reach #C{%s} when fetching pipeline env branches."> -- raised

=head2 _strongbox_for_config

    my $sb = $top->_strongbox_for_config($vault);

Decides what to record for C<secrets_provider.strongbox> when writing the
provider block, given the vault the block is being written from.

Every write path rebuilds the whole block, so an edit that only meant to
change the alias and URL also rewrites Strongbox from whatever the vault
object happens to carry. While safe defaulted Strongbox on, a vault always
carried a value and this was invisible. Since safe made it opt-in, a target
that never stated the flag reports nothing -- and re-pointing a deployment
would silently record Strongbox as disabled for a vault that runs one, with
no prompt and no mention in the output.

So an unstated flag is not treated as a statement that Strongbox is off.
When the vault has no value, whatever the repository already records is kept,
on the grounds that it was written when something did know. When nothing is
recorded either, nothing is written, and the absent key means unstated.

B<Parameters:>

=over 4

=item $vault

The vault whose settings are being recorded. Its C<strongbox> may be
C<undef>.

=back

B<Returns:> C<Genesis::Config::TRUE> or C<Genesis::Config::FALSE> when the
vault states a value; otherwise the currently recorded value, which is
C<undef> when the repository has none. Callers must omit the C<strongbox>
key entirely when this returns C<undef>.

B<Errors:> None.

B<Examples:>

    # Vault states enabled
    $top->_strongbox_for_config($vault);
    # Returns: Genesis::Config::TRUE

    # Vault says nothing, repository records enabled
    $top->_strongbox_for_config($vault);
    # Returns: the recorded true value, preserved

    # Vault says nothing, repository records nothing
    $top->_strongbox_for_config($vault);
    # Returns: undef -- caller writes no strongbox key

=head2 _validate_config

    $self->_validate_config

and runs on the first access to L</config>, so every command validates
whether or not it is a pipeline command.

C<"Genesis deployment repo v1 configuration is not supported, and cannot update automatically.  Manual intervention required.">

C<"Genesis deployment repo configuration version %s is not supported">

=head2 _repo_config_schema

    $self->_repo_config_schema

Returns the version 3 configuration schema, which is the version 2 schema with
C<version> pinned to C<"3"> and the C<pipeline> section added. The section is
built by L</_pipeline_config_schema>, so its whole shape is stated in one
place.

The section is named C<pipeline> while the C<Genesis::CI> code namespace is
deliberately left where it is, because the compiler genuinely is CI. There is
no C<pipeline.repo.root>, because the git prefix already locates the
deployment root. There are no compatibility aliases either, so a key written
under its old C<ci.> spelling is refused by name rather than moved onto its
replacement, and that is safe because the version 3 schema is unreleased.

Every version 2 key is inherited unchanged:

=over 4

=item C<deployment_type> - required string

=item C<creator_version> - required; semver, C<"(development)">, or C<"Unknown">

=item C<updater_version> - optional semver or C<"(development)">

=item C<minimum_version> - optional semver

=item C<manifest_store> - optional enum: C<repository>, C<hybrid>, C<exodus>; default C<exodus>

=item C<kits_path> - optional string; default C<$GENESIS_ROOT/.genesis/kits>

=item C<kit_provider> - optional hash with sub-keys C<type>, C<organization>, C<label>, C<tls>, C<domain>

=item C<secrets_provider> - optional hash with sub-keys C<url> (required), C<insecure>, C<strongbox>, C<namespace>, C<alias>

C<strongbox> deliberately has B<no schema default>. An absent key means no
one has stated the setting, which is a third state rather than a synonym for
enabled. Defaulting it would re-create on read the ambiguity the writer goes
to some trouble to avoid -- see L</_strongbox_for_config>.

=item C<deployment_change_reason_required_size> - optional number; default C<0>

=item C<user_provided_bosh_creds> - optional enum: C<ignore>, C<allow>, C<require>; default C<ignore>

=item C<allow_oversized_secrets> - optional boolean

=item C<confirm_release_overrides> - optional enum: C<always>, C<outdated>, C<never>

=back

B<Returns:> A hash reference.

=head2 _pipeline_config_schema

    $self->_pipeline_config_schema

Returns the C<pipeline> block of the version 3 schema, in the shape
C<< $self->config->validate() >> consumes. Every key the pipeline reads is
declared here, so C<Genesis::Config> refuses an undeclared key by name as the
configuration loads, for every command rather than only for the pipeline ones.

The block declares C<enabled>, which is the gate and defaults to false, the
C<provider> hash, which is optional even once the gate is on and whose keys
L</_provider_options_schema> supplies, and C<name>, which is the pipeline's
own label in its provider and falls back to the deployment type.

The C<provider> block itself defaults to an empty hash so that the type's own
default still applies when the operator writes no provider block at all. A
section that is enabled with no provider block is therefore a manual pipeline
rather than no pipeline.

C<pipeline.provider.output_layout> is C<single> or C<multiple>, and it
appears in the merged schema only for a provider that declares the
C<multi_file_output> capability. It decides the override file's name: the
single form is C<.genesis/pipeline-overrides-E<lt>providerE<gt>.yml>, and
the multiple form is one file per emitted output, named by that output's
base name without its extension. The name follows the effective choice
and not the capability.

The block also declares C<source_control>, which is what the pipeline needs
to know about the repository, in three tiers. C<remote>, C<uri>, and
C<repository> are derived from git with an explicit override; C<control_branch>,
C<pr_prefix>, and C<control_requires_pr> are defaulted; and C<auth> and
C<identity> are required wherever an automation has to clone and commit
unattended, which is what L</_automated_provider_configured> decides. Two
things take no key at all. The deployment root is a fact of the checkout,
read from the git prefix, and the branch a command runs from is runtime
state, so it is checked rather than configured. L</_source_control> resolves
the tiers.

Four more blocks complete the section. C<shuttle> is the object store behind
every deployment's request queue and its C<_ran> event, and it is required
wherever an automation has to do the work unattended, which is again what
L</_automated_provider_configured> decides. Its C<backend> is C<s3> or C<gcs>
and never a directory, because a directory on one worker cannot trigger
across pipelines, and its C<bucket> is required beside it. The C<region>,
C<endpoint>, and C<auth> keys are optional, and the resource C<image> and
C<image_tag> carry defaults.

C<vault> is the vault a pipeline task writes exodus through. Its C<url> is
required, and C<namespace>, C<auth>, and C<options> are optional. It is
required under an automated provider for the same reason the shuttle is,
because a task nobody is watching cannot be asked where to write.

C<locker> is the locker the two deploy locks use. The block declares the
locker and its credentials and says nothing about either lock, so how a
pipeline takes them is settled where the pipeline is compiled rather than
here. Its C<url> is required, C<username>, C<password>, and C<ca_cert> are
optional, and C<skip_ssl_validation> defaults to false. It is required under
an automated provider as well.

C<notifications> is optional under every provider. Its C<style> is the
repository default rendering and defaults to C<default>, and C<slack> and
C<email> carry whatever entries the notifier reads. An environment overrides
the style through its own C<genesis.pipeline.notifications> block, which
L</_pipeline_env_keys_schema> declares.

The section also carries C<pipeline.name>, which is the pipeline's label
in its provider and nothing more. It composes no branch, since the branch
is the deployment slug, so it is deliberately not validated as a git ref
component and keeps whatever character set its provider allows.

C<pipeline.recreate_on_deploy> is C<never>, C<redeploy-only>, or
C<always>, defaulting to C<never>. It and C<pipeline.provider.group_commits>
are repository-wide and refused per environment, because a key that
changes how a deployment progresses has to be uniform or the earlier
environments stop rehearsing the later ones.

B<Returns:> A hash reference.

=head2 _current_config_schema

    my $schema = $top->_current_config_schema();

Returns the configuration schema for the version this repository holds on
disk, which is L</_repo_config_schema> for version 3 and

It is built afresh on every call rather than read back off the

=head2 _provider_options_schema

    my $schema = $top->_provider_options_schema();

Returns the schema for C<pipeline.provider>, which is the C<type> key
every provider shares with the configured provider's own
C<provider_options_schema> merged over it.

The per-provider key table is therefore derived from the provider classes
rather than hand-listed beside them, and a key no fragment declares is
refused by name. The C<manual> provider has no class and so no fragment,
so a provider key written beside C<type: manual> is refused with no
exception. A provider class that omits its fragment is a bug at load.

The enum for C<type> is built from
C<< Genesis::CI::Compiler::PipelineProvider->known_providers >>, so the
schema and every class lookup read one list and cannot spell a provider
two ways, and the type defaults to C<manual>. The configured type is read
straight off the loaded values, because this builds the schema that
validation is about to run against and there is no validated value yet.

=item *

=back

=head2 _source_control

    my $sc = $top->_source_control();

Returns the resolved source-control values as a hash reference, whose keys
are C<remote>, C<uri>, C<repository>, C<control_branch>, and C<pr_prefix>.
Precedence is explicit over derived over default.

The remote is the control branch's configured upstream, else C<origin>
where it exists, and otherwise refused by name; it is never the first
C<git remote>, which is alphabetical order. The repository is the GitHub
C<owner/repo> the remote's URL carries, github.com or GitHub Enterprise
alike, and any other host must name it explicitly. An empty C<pr_prefix>
is refused, because it would give the pull request branch the deployment
branch's own name, and an empty C<control_branch> is refused beside it,
because nothing can be read from a branch with no name. Every refusal exits
C<Genesis::Exit::CONFIG>.

The url is asked of git only where C<repository> was not configured, since
the repository is the one value derived from the url and asking costs a fork
on every command. So a configured repository is the only way C<uri> comes
back undef.

The answer is resolved once and kept, so the refusals land at configuration
load rather than at the first read.

B<Returns:> A hash reference of the five resolved values.

B<Errors:>

=over 4

=item *

C<"pipeline.source_control.pr_prefix must not be empty"> - raised when the
override is present and holds an empty string.

=item *

C<"pipeline.source_control.control_branch must not be empty"> - raised on
the same terms, because a branch with no name names nothing to read the
repository from.

=item *

C<"pipeline is enabled, but ... is not a git checkout"> - raised when the
deployment repository is not under git at all, which leaves the derivations
with nothing to read.

=item *

C<"pipeline.source_control.remote could not be derived"> - raised when the
control branch has no configured upstream and there is no remote named
C<origin>.

=item *

C<"pipeline.source_control.repository could not be derived"> - raised when
the remote's URL carries no GitHub C<owner/repo> pair and no override names
one. There is no exception under the manual provider.

=back

B<Examples:>

    my $sc = $top->_source_control;
    # returns {remote => 'origin', uri => 'git@github.com:team/bosh.git',
    #          repository => 'team/bosh', control_branch => 'control',
    #          pr_prefix => 'pr/'}

=head2 _github_owner_repo

    my $pair = _github_owner_repo($uri);

carries none. Both the https and the ssh forms parse, and GitHub Enterprise
parses the same way as github.com, because its URLs carry the pair in the
same shape and only the host differs. The host is what says GitHub: every
https URL on earth has two path segments, so a URL that names some other
forge answers C<undef> and its repository has to be configured by hand.

Plain function, not a method.

B<Parameters:>

=over 4

=item C<$uri>

The remote's fetch URL, in either form. An undefined or empty value answers
C<undef>.

=back

B<Returns:> The C<owner/repo> string, or C<undef>.

B<Examples:>

    my $pair = _github_owner_repo('git@github.com:team/bosh.git');
    # returns 'team/bosh'

    my $pair = _github_owner_repo('https://github.example.com/team/bosh');
    # returns 'team/bosh' -- GitHub Enterprise parses the same way

    my $pair = _github_owner_repo('https://git.example.com/team/bosh.git');
    # returns undef -- that host is not GitHub

=head2 _ref_component_errors

    my $why = _ref_component_errors($value);

Why a value cannot be a component of a git ref, or C<undef> where it can.

A value must match C<^[A-Za-z0-9][A-Za-z0-9._-]*$>, and three shapes that
the pattern admits but git then rejects are refused beside it: a trailing
dot, any C<..> sequence, and a C<.lock> suffix. The answer is a phrase that
reads on after a colon, so the caller writes the refusal and this says only
what is wrong with the value.

Plain function, not a method.

B<Parameters:>

=over 4

=item C<$value>

The candidate ref component. An undefined or empty value answers the
empty-value reason rather than passing.

=back

B<Returns:> A reason string, or C<undef> where the value is a well-formed
ref component.

B<Examples:>

    my $why = _ref_component_errors('us-east-prod');
    # returns undef -- that name composes a ref

    my $why = _ref_component_errors('bosh.lock');
    # returns 'it must not end in ".lock"'

    my $why = _ref_component_errors('-bosh');
    # returns 'it must match ^[A-Za-z0-9][A-Za-z0-9._-]*$'

=head2 _validate_slug_components

    $top->_validate_slug_components();

Refuses, at C<Genesis::Exit::CONFIG>, a C<deployment_type> or an
environment name that is not a git ref component.

The deployment branch is the deployment slug C<< <env>/<type> >>, so both
halves become ref components and neither is trusted over the other. A value
must match C<^[A-Za-z0-9][A-Za-z0-9._-]*$> and must not end in a dot or in
C<.lock> or contain C<..>, which is what L</_ref_component_errors> decides.
The refusal names the branch the value would have composed, because that is
what makes it obvious why a name that was fine before this release is not
fine now.

Both halves already reach vault through the exodus slug and BOSH through
the deployment name, so the check is narrow in practice and it catches a
value that was never safe in those places either.

The environment names are the ones the deployment root holds, read merged
through L</_merged_env_params>, and a file carrying no C<genesis.pipeline>
block is passed over, so a legacy C<ci.yml> beside the environments is not
read as one. It does not read C<pipeline.enabled> itself, because
L</_validate_pipeline_config> is its only caller and has already returned
where the section is off.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"The deployment type ... is not a git ref component"> - raised when
C<deployment_type> cannot compose a ref, naming the value, the reason, and
the branch C<< <env>/<type> >> it would have named for every environment.

=item *

C<"The environment name ... is not a git ref component"> - raised when an
environment of the pipeline cannot compose a ref, naming the environment,
the reason, and the branch it would have composed.

=back

B<Examples:>

    $top->_validate_slug_components;
    # returns 1 where the type and every environment name compose a ref

    $top->_validate_slug_components;
    # exits CONFIG (78) where .genesis/config says deployment_type: bosh.lock

=head2 _validate_one_exodus_mount

    $top->_validate_one_exodus_mount();

Refuses, at C<Genesis::Exit::CONFIG>, a pipeline whose environments resolve
C<genesis.exodus_mount> to more than one value, naming every mount and the
environments that resolved it.

The pipeline's applied record lives at
C<< <exodus mount>_pipelines/<type> >>, so two mounts would leave it with
no single home. The merged hierarchy makes a file the environments inherit
the natural place to set the mount once, and that is the remedy the refusal
carries.

Each environment is read merged through L</_merged_env_params> and one that
does not carry a C<genesis.pipeline> key at all is passed over, membership
being the key being there rather than what it holds. Where an environment
names no mount, the value resolved is the one the run time would answer,
which is C<genesis.secrets_mount> with C<exodus/> under it and C</secret/>
where that is unset too. An empty value is a mount rather than an absent
one, because C<< Genesis::Env::exodus_mount >> takes it as written, and two
mounts the run time tells apart have to be two mounts here as well. Every
resolved value is normalised to leading and trailing slashes before the
comparison, so two spellings of one mount are one mount. It does not read
C<pipeline.enabled> itself, because L</_validate_pipeline_config> is its only
caller and has already returned where the section is off.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Every environment of a pipeline must resolve one genesis.exodus_mount">
- raised when the environments of the pipeline resolve two or more mounts,
listing each mount with the environments that resolved it and carrying the
remedy of setting the mount once in a file they all inherit.

=back

B<Examples:>

    $top->_validate_one_exodus_mount;
    # returns 1 where every environment resolves /secret/exodus/

    $top->_validate_one_exodus_mount;
    # exits CONFIG (78) where qa resolves /secret/exodus/ and prod
    # resolves /other/exodus/

=head2 _pipeline_exodus_mount

    my $mount = $top->_pipeline_exodus_mount();

The one exodus mount the pipeline's environments share, which is what
L</applied_record_path> hangs the pipeline's own record under.

It is read from the first environment the pipeline names, through the merged
hierarchy, because L</_validate_one_exodus_mount> has already refused a
repository whose environments resolve the mount differently. The value comes
back normalised with a trailing slash, so a caller appends to it directly.
The answer is memoized, since it is the same for every read in a run.

B<Parameters:> None.

B<Returns:> The mount, as a string ending in a slash.

B<Errors:>

=over 4

=item *

C<"This repository has a pipeline but no environment to resolve
genesis.exodus_mount from, so the pipeline's own record has no address."> -
raised at C<Genesis::Exit::CONFIG> when the repository declares a pipeline
and names no environment, carrying the remedy of adding an environment file
or disabling the pipeline.

=back

B<Examples:>

    my $mount = $top->_pipeline_exodus_mount;
    # returns '/secret/exodus/' where the environments set no mount of
    # their own

=head2 _validate_pipeline_config

    $top->_validate_pipeline_config();

Runs the checks on the pipeline section that a declarative schema cannot
state. It is called from L</_validate_config> for every command, straight
after C<< Genesis::Config::validate >>, so that a repository meets the same
refusal in the same words whichever command loaded it.

A section that is off is left alone. Otherwise the checks run in this
order. Both halves of the deployment slug are checked as git ref components
by L</_validate_slug_components>, first, because they name the branches
everything else here is about. Then the source-control block is resolved,
which is where the derivations and their refusals are raised. Then the
configured provider's own programmatic check runs through
L</_validate_provider_config>, then the capability gates of
L</_validate_capability_gates>, then the manifest store and the kit floors
of L</_validate_manifest_store>, and then the one exodus mount of
L</_validate_one_exodus_mount>, which comes after the store because the
mount is where that store keeps the pipeline's applied record. Last, every
environment the deployment root holds has its C<genesis.pipeline> block
checked, read merged through L</_merged_env_params>. The refusals
themselves belong to L</_validate_slug_components>, to L</_source_control>,
to L</_validate_provider_config>, to L</_validate_capability_gates>, to
L</_validate_manifest_store>, to L</_validate_one_exodus_mount>, and to
L</_validate_env_pipeline_block>.

B<Returns:> 1.

=head2 _validate_provider_config

    $top->_validate_provider_config();

Runs the configured provider's own C<validate_config> and refuses at
C<Genesis::Exit::CONFIG> when it returns errors.

This is the programmatic half of the provider configuration contract, and
it is deliberately narrow: it states what a declaration cannot, such as
"one of these two keys is required". It runs after the generic validation,
so every key it reads has already been typed and defaulted, and it makes no
network call, because a load that dialled a provider would make every
command wait on that provider being up.

The provider is built from the C<pipeline.provider> block with the resolved
C<repository> alongside it, since under D102 the repository the pipeline
acts on lives in the source-control block rather than the provider block.
The check gathers every error string the provider returns, so the refusal
names the provider once and lists everything wrong with it. An entry that is
undefined or empty is dropped before that list is built, because a rule that
answered with nothing would otherwise print an empty bullet.

The provider's class is somebody else's code, so building it and running its
check are wrapped in an C<eval>. A rule that dies is reported as the same
refusal, naming the provider and carrying what it said, rather than reaching
the operator as a C<Carp> trace out of the middle of a configuration load.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Invalid configuration for the ... provider"> - raised when the
provider's C<validate_config> returns one or more error strings, which are
listed under it, one per line, and raised in the same words when the
provider's own code dies, with what it said as the single entry under it.

=item *

C<"Unknown CI provider type ..."> - raised by
L<Genesis::CI::Provider/provider_class> when no registry entry holds the
configured type. The schema's enum normally refuses that first.

=back

B<Examples:>

    $top->_validate_provider_config;
    # returns 1 where the provider is happy with its configuration

    $top->_validate_provider_config;
    # exits CONFIG (78) where pipeline.provider.type is concourse and
    # pipeline.provider.target is unset

=head2 _validate_capability_gates

    $top->_validate_capability_gates();

Refuses, at C<Genesis::Exit::CONFIG>, any configuration key whose provider
capability is false, naming both the key and the capability.

A capability is what a provider is able to do and a key is the operator's
choice inside that ability, so a key with no ability behind it cannot mean
anything. Four of the six capabilities gate a key:
C<optional_git_triggers> gates C<genesis.pipeline.manual>,
C<scheduled_jobs> gates C<genesis.pipeline.redeploy_cron>,
C<per_commit_runs> gates C<pipeline.provider.group_commits>, and
C<multi_file_output> gates C<pipeline.provider.output_layout>. The other two
are structural and gate nothing configurable.

A provider with no compiler class declares no capabilities and is left
alone, which is the manual provider and, until its own compiler lands, the
github-actions one. Every other provider has its declaration checked
against the six names through
L<Genesis::CI::Compiler::PipelineProvider/declared_capabilities> before any
gate reads it.

The two repository-wide keys are read for what the operator actually wrote,
through C<< Genesis::Config::is_set >> rather than C<< has >>, because a
value the schema filled from a provider's own default is nobody's choice
and cannot be what a refusal is about. The two per-environment keys are
read out of each environment's merged C<genesis.pipeline> block, where no
default is ever applied. Every gate that fires is gathered before the
refusal is raised.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Configuration validation failed for ..."> - raised when at least one
configured key is gated on a capability the provider does not declare. Each
one is listed under it, naming the key, the provider, and the capability,
and the environment as well where the key lives in an environment file.

=item *

C<"Failed to load CI provider ..."> - raised when the registry names a
compiler class whose file will not compile. The schema build normally meets
that first.

=item *

C<"CI provider ... declares the capabilities ..."> - raised through
L<Genesis::CI::Compiler::PipelineProvider/declared_capabilities> when the
provider class answers anything but exactly the six names, which is a bug
in that class rather than anything an operator wrote.

=back

B<Examples:>

    $top->_validate_capability_gates;
    # returns 1 where every configured key has its capability behind it

    $top->_validate_capability_gates;
    # exits CONFIG (78) where an environment sets genesis.pipeline.manual
    # under a provider that declares optional_git_triggers false

=head2 _validate_manifest_store

    $top->_validate_manifest_store();

Refuses, at C<Genesis::Exit::CONFIG>, a C<manifest_store> that is not
C<exodus>, and any environment whose effective Genesis floor is below
3.1.0. It does not read C<pipeline.enabled> itself, because
L</_validate_pipeline_config> is its only caller and has already returned
where the section is off, so everything below is said of a repository
whose pipeline is known to be on.

Under a pipeline the deploy must not be a git writer on a deployment
branch, because the propagation writer already advances it. The certified
commit and the applied, hold and proposed records live in exodus, so the
store cannot be anything else, and the refusal is permanent rather than a
limit the MVP lifts later.

The check sits here rather than in the compiler's validator, which is
where a deploy would never meet it. That gap is what let an environment on
an old kit keep both writers on the branch, because a kit whose Genesis
floor is below 3.1.0 is forced onto the repository store at run time
whatever the configuration says, since earlier versions cannot update the
exodus deployment audit data.

The floor compared is the effective one, which is the higher of the
repository's own C<minimum_version> and the environment's merged
C<genesis.min_version>, or C<genesis.minimum_version>, the same pair
C<< Genesis::Env::effective_minimum_version >> takes the maximum of.
Reading the environment's line alone would refuse a repository whose own
floor already lifts it, over a number no deploy would ever honour. Each
environment is read merged through L</_merged_env_params> and refused by
name, with the remedy of raising the kit's floor rather than changing the
store's value.

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"manifest_store: ... cannot be used under a pipeline"> - raised when the
repository's pipeline is enabled and its store is C<repository> or
C<hybrid>, naming the value that was configured.

=item *

C<"The environment ... uses a kit whose Genesis floor is below 3.1.0"> -
raised when an environment's effective floor, the higher of its own merged
C<genesis.min_version>, or C<genesis.minimum_version>, and the
repository's C<minimum_version>, is older than 3.1.0, naming the
environment and carrying the remedy.

=back

B<Examples:>

    $top->_validate_manifest_store;
    # returns 1 where the store is exodus and every kit floor is 3.1.0 or later

    $top->_validate_manifest_store;
    # exits CONFIG (78) where .genesis/config says manifest_store: hybrid

=head2 _merged_env_params

    my $params = $top->_merged_env_params('us-east-prod');

Returns an environment's merged parameters as a hash reference, loaded from
its file hierarchy with the nearer file winning. It is the load-time form of
the read every C<genesis.pipeline.*> key gets: an inherited key is absent
from the leaf file, so a leaf-only read answers wrongly and says nothing
about it.

The hierarchy comes from C<< Genesis::Env::relate_by_name >>, which is given
the deployment root as both of its bases, because with no other environment
to relate to every token of the name is unique. Files that are not there are
skipped, so the merge is over what the root actually holds, but a file that
is there and will not parse is refused rather than skipped: a key can live
anywhere in the hierarchy, so a file nobody can read is a key nobody can
see. No C<Genesis::Env> is built and no kit is needed, which is what lets
the check run as the configuration loads.

B<Parameters:>

=over 4

=item C<$env_name>

The environment's name, which is also the stem of its leaf file.

=back

B<Returns:> A hash reference of the merged parameters, empty where the
environment has no files at all.

B<Errors:>

=over 4

=item *

C<"An environment file could not be read as YAML."> - raised at
C<Genesis::Exit::CONFIG>, naming the file on the line below and carrying what
the parser said, when a file in the hierarchy is there and will not parse.

=back

B<Examples:>

    my $params = $top->_merged_env_params('us-east-prod');
    # returns the merge of us.yml, us-east.yml, and us-east-prod.yml,
    # with the nearest file winning

=head2 _env_file_names

    my @names = $top->_env_file_names();

Returns the environment names the deployment root holds, as the stems of its
top-level C<.yml> files, sorted. It is what the load can see without building
a C<Genesis::Env>, and it is enough for a check that only reads the merged
parameters.

B<Returns:> A sorted list of names, empty where the root holds no C<.yml>
files.

=head2 _validate_env_pipeline_block

    $top->_validate_env_pipeline_block('us-east-prod', $block);

Checks one environment's C<genesis.pipeline> block against
L</_pipeline_env_keys_schema>, and refuses it by name where it does not fit.

The block is validated through a throw-away in-memory C<Genesis::Config>, so
the types, the defaults, the required flags, and the unknown-key refusal are
the ones the repository configuration already gets and there is no second
validator to keep in step with the first. A block that is not a hash at all
is handed over as it stands, so the answer is the declaration's own refusal
rather than a Perl error. A bare string written where one of the three list
keys is declared is normalised to a one-element list first, because an
operator may still write a single entry, and nothing is split on the way,
since a crontab expression carries commas of its own.

Two shapes the declaration cannot state are checked beside it. A
C<track_dependencies> entry is a deployment type at this environment or an
C<< <env>/<type> >> pair elsewhere, and C<track_bosh_configs> is a boolean or
a list of config type names.

Those checks read the block as the operator wrote it, taken before the
validator runs. Each list key declares C<envsplit>, and C<Genesis::Config>
answers a value that is not a list by splitting it as though it came from the
environment, which turns a mapping into the address of a reference. A mapping
written where a list belongs is therefore refused outright, before any entry
of it is read.

A refusal the validator raises that carries no bullets to pick apart is
reported as it stands, so an C<eval> that failed never leaves the block
looking valid.

B<Parameters:>

=over 4

=item C<$env_name>

The environment the block belongs to, which the refusal names.

=item C<$block>

Hash reference of the merged C<genesis.pipeline> block.

=back

B<Returns:> 1.

B<Errors:>

=over 4

=item *

C<"Configuration validation failed for environment ..."> - raised at
C<Genesis::Exit::CONFIG> with one bullet per fault, which are the schema's
own refusals with their keys named as the environment file spells them, the
shape refusals above, and C<"genesis.pipeline.<key>: expected a list of
strings"> where a mapping was written in a list's place.

=back

B<Examples:>

    $top->_validate_env_pipeline_block('us-east-prod', {manual => 1});
    # returns 1

    $top->_validate_env_pipeline_block('us-east-prod', {manual => 'maybe'});
    # exits CONFIG: genesis.pipeline.manual: expected a boolean

=head2 _first_errors

    my @errors = _first_errors($@);

The bullet lines out of a caught C<< Genesis::Config::validate >> refusal.
That refusal arrives already formatted and wrapped to the terminal, so the
text is split on the bullet the formatter itself uses, each error is folded
back onto one line, and the heading above the first bullet is dropped. The
bullet is asked for rather than assumed, because which glyph it is depends on
what the terminal can render.

Each error's C<pipeline.> prefix is rewritten to C<genesis.pipeline.>, so the
key is named the way the environment file spells it rather than the way the
throw-away configuration was built.

Plain function, not a method.

B<Parameters:>

=over 4

=item C<$caught>

The caught text, normally C<$@>. An undefined or empty value answers an empty
list.

=back

B<Returns:> A list of one-line error strings, empty where the text carries no
bullet at all, which is the caller's cue to report the caught text as it
stands.

B<Examples:>

    my @errors = _first_errors($@);
    # returns ('genesis.pipeline.manual: expected a boolean, not maybe')
