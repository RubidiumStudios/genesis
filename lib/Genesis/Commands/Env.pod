=head1 NAME

Genesis::Commands::Env - Command handlers for Genesis environment lifecycle management

=head1 SYNOPSIS

  # Loaded automatically by bin/genesis command dispatch
  use Genesis::Commands::Env;

  # CLI invocations (scope: <env> is an environment name or .yml file):

  genesis <env> create [<options>]
  genesis <env> edit   [<options>]
  genesis <env> check  [<options>]
  genesis <env> manifest [<options>]
  genesis <env> deploy [<options>] [<reason>]
  genesis <env> terminate [<options>] [<reason>]
  genesis <env> do <action> [<addon-options-and-args>]
  genesis <env> check-secrets [<options>] [<paths...>]
  genesis <env> secrets [<options>] [<filters...>]
  genesis <env> add-secrets [<options>] [<paths...>]
  genesis <env> rotate-secrets [<options>] [<paths...>]
  genesis <env> remove-secrets [<options>] [<paths...>]
  genesis <env> env-shell [<options>]

=head1 DESCRIPTION

C<Genesis::Commands::Env> implements the command handlers that back the core
environment lifecycle CLI commands in C<bin/genesis>.  Each function in this
module is registered with C<define_command> in the Genesis binary and is
called directly with the parsed command-line arguments.

This module is procedural: there is no object constructor.  Each exported
subroutine receives positional arguments that correspond to CLI arguments
as described in each function's B<Parameters> section.

Options are accessed via the C<get_options> and C<has_option> helpers
from L<Genesis::Commands>.

=head1 FUNCTIONS

=head2 create($name)

  genesis <env> create [--kit <kit>] [--vault <vault>] [--root-ca-path <path>] [<options>]

Create a new Genesis deployment environment.  Prompts the user with
kit-supplied questions, writes the environment YAML file, and generates
all required secrets and certificates in Vault.

In a repository with a pipeline it also stages the file and commits it on
the branch the operator is standing on, which is the control branch or a
feature branch bound for a pull request.  It creates no branch and touches
no deployment branch.  The environment reaches its deployment branch when a
C<genesis propagate> run delivers the commit, and the branch itself is
created by C<genesis pipeline-apply>.

The branch it may run from is settled before the command starts, by the
branch class gate in L<Genesis::Commands>, which also brings the control
branch in from the remote.  So C<create> reads no branch of its own and
refreshes nothing.

B<Parameters:>

=over 4

=item C<$name>

Environment name string (e.g., C<us-east-prod>).  A C<.yml> suffix is
stripped automatically.  Exactly one argument is required.

=back

B<Options (via get_options):>

=over 4

=item C<--kit|-k>

Name (and optionally, version) of the Genesis Kit to use (e.g.,
C<shield/6.3.0>).  Defaults to the latest locally available version.
Use C<dev> to use the dev kit.

=item C<--vault>

The name of a C<safe> target (a Vault) to store newly generated credentials
in.  Overrides the vault specified in the deployment repository.  Use C<?>
to select a vault interactively.

=item C<--root-ca-path>

Vault path to a root CA certificate that will sign all generated certificates
that do not specify their own CA.

=item C<--create-env!>

For kits that allow but do not require C<create-env>-style deployment,
force or suppress C<create-env> mode.

=item C<--secrets-path|-P>

Override the default secrets path (C<secret/E<lt>env-nameE<gt>/E<lt>kitE<gt>>).

=item C<--secrets-mount>

Use an alternative base location other than C<secret/> for secrets.

=item C<--exodus-mount>

Use an alternative base path for exodus data.

=item C<--ci-mount>

Use an alternative base path for concourse-provided secrets.

=item C<--force|-f>

Create a new environment file even if one already exists.

=back

B<Returns:>

Nothing.  Prints a success message with the C<genesis deploy> command to
run next, then exits normally.

B<Errors:>

=over 4

=item C<"No environment name specified!">

Raised when C<$name> is empty after stripping the C<.yml> suffix.

=item C<"Unable to determine the correct version of the Genesis Kit to use.  Perhaps you should specify it with the `--kit` flag.">

Raised when no kit is found and no kit identifier was provided.

=item C<"No dev/ kit found in current working directory.  Did you forget to `genesis decompile-kit` first?">

Raised when C<--kit dev> is requested but no C<dev/> directory is present.

=item C<"Kit '$kit_id' not found in compiled kit cache.  Do you need to `genesis fetch-kit $kit_id`?">

Raised when the requested compiled kit version is not cached locally.
C<$kit_id> is the kit name and version string provided by the user.

=item C<"No CA certificate found in vault under '#C{%s}'">

Raised when C<--root-ca-path> is given but no valid x509 CA is found at
that Vault path.  C<%s> is the path supplied by the user.

=item C<"Failed to create environment $name">

Raised when C<< Genesis::Top->create_env >> returns a false value.
C<$name> is the environment name.

=item C<"--prior-env '%s' does not match any environment in this repository.">

Raised when C<--prior-env> names an environment that does not exist. Checked
against the repository's known environments before any pipeline metadata is
written, so a typo is caught rather than recorded as a predecessor that can
never deploy. C<%s> is the value supplied.

=item C<"There are staged changes in this repository, and this command makes a commit, so they would be swept into it:">

Raised by L</_assert_clean_index($git)> when the index holds a staged change
and the run will make a commit. The staged paths are listed after the
message, and the exit code is C<DATAERR>.

=back

B<Examples:>

  # Create a new BOSH environment using the latest bosh kit
  genesis my-env create --kit bosh/10.2.0
  # prints: Setting up new environment my-env based on kit bosh/10.2.0 ...

  # Create with an explicit vault target
  genesis my-env create --vault prod-vault
  # prints: New environment my-env provisioned!

=head2 create and the branch session

C<genesis new> opens no branch session and takes no switch lock, because a
session exists to leave a branch and come back and this command never
leaves one.  It writes the environment file and commits it on the branch the
operator stands on, unless C<--no-commit> is given, in which case it leaves
the file staged and makes no commit at all.  It tracks no branch on its git
handle either way, so nothing restores a branch when the process exits.

A second process holding the switch lock is therefore no obstacle to it,
and a lock file it never took is a lock file it never creates.

=head2 create and the pre-flight

Before it writes anything, C<genesis new> runs the same pre-flight helper a
branch session's C<begin> runs, C<< $git->preflight >>.  One cheap git
command either succeeds or fails, and its failure is classified as a
C<safe.directory> refusal, a missing committer identity, or a repository
with no commits, each of them named with the fix the operator has to apply.

Two of those three are what C<genesis new> actually meets.  In a repository
with a pipeline the C<safe.directory> shape never reaches the helper, because
the deployment root tests the checkout for itself before any command runs and
refuses with C<is not a git checkout>, which names no fix.

The command opens no session, so this is the only piece of a session's
entry it keeps.  Both callers run the one helper, so a broken repository
reads the same way whichever command met it first.

=head2 create and uncommitted work

C<genesis new> refuses to run when the index holds staged changes, naming
them, because it makes a commit and those changes would be swept into it.
It ignores an unstaged edit elsewhere in the working tree, because an
unstaged edit never enters the commit and refusing it would protect
nothing.

Under C<--no-commit> both checks are skipped. The option stages the
environment file deliberately and stops there, so there is no commit for a
staged change to be swept into.

This is the qualifier in the uncommitted-work invariant read the way it is
written. An operation that will switch branches asserts a clean tree and a
clean index, because its abort has to discard only what it wrote. This
command switches nothing and discards nothing, so it keeps today's
tolerance of local edits and checks the index alone.

=head2 edit($name)

  genesis <env> edit [--editor <cmd>] [--kit <kit>] [--manual!] [--ancestors!]

Open the environment file in your configured editor.  When the editor is
vi-based (C<vi>, C<vim>, C<mvim>, C<nvim>, C<gvim>) or C<emacs>, the kit's
C<MANUAL.md> and any existing ancestor YAML files are opened alongside the
environment file in a split-window layout.  VSCode (C<code>) opens all
files as separate tabs.

If the kit referenced by the environment file is not locally available,
the user is prompted to select an alternate local kit, download the
required version, or continue without a manual.

B<Parameters:>

=over 4

=item C<$name>

Environment name string.

=back

B<Options (via get_options):>

=over 4

=item C<--editor|-e>

Editor command to use.  Defaults to the C<EDITOR> environment variable, or
C<vim> if C<EDITOR> is not set.

=item C<--kit|-k>

Kit name and version to use when displaying the manual, in
C<name/version> format.

=item C<--manual!>

Include (or suppress with C<--no-manual>) the kit C<MANUAL.md> in the
editor split window.  Enabled by default for vi-based editors, emacs, and
VSCode.

=item C<--ancestors!>

Include (C<--ancestors>) all possible hierarchical ancestor YAML files in
the editor, even those that do not yet exist.  Suppress with
C<--no-ancestors> to open only the environment file.  By default, existing
ancestor files are opened.

=back

B<Returns:>

Nothing.  Prints a completion notice after the editor exits.

B<Errors:>

=over 4

=item C<"Cannot specify #Y{--manual} unless the editor is vi-based (vi,vim,mvim,nvim,gvim), vscode (code) or emacs: Pull request are welcome for other editors.">

Raised when C<--manual> is specified with an unsupported editor.

=item C<"Cannot specify #Y{--include-all-ancestors} unless the editor is vi-based (vi,vim,mvim,nvim,gvim) or vscode (code): Pull request are welcome for other editors.">

Raised when C<--ancestors> is specified with an unsupported editor.

=item C<"Failed to download Genesis Kit #C{$kitsig}">

Raised when the user chooses to download a kit but the download fails.
C<$kitsig> is the kit name and version string.

=item C<"Aborted by user">

Raised when the user declines to continue after warnings, or selects
C<abort> from the kit selection prompt.

=item C<"Failed to edit environment %s">

Raised when the editor exits with a non-zero exit code.  C<%s> is the
environment name.

=back

B<Examples:>

  # Edit with the default editor
  genesis my-env edit
  # prints: Editing environment file ~/deployments/my-env.yml

  # Edit without showing the manual
  genesis my-env edit --no-manual
  # prints: Editing environment file ~/deployments/my-env.yml

  # Edit with a specific editor
  genesis my-env edit --editor code
  # prints: Editing environment file ~/deployments/my-env.yml

=head2 check($name)

  genesis <env> check [--no-config] [--secrets!] [--manifest!] [--stemcells!]

Run preflight checks against the environment manifest, secrets, and
stemcell availability to verify that the environment can be successfully
deployed.

B<Parameters:>

=over 4

=item C<$name>

Environment name string.  Exactly one argument is required.

=back

B<Options (via get_options):>

=over 4

=item C<--no-config>

Skip cloud config tests.  Cannot be combined with the default
C<--manifest> check (requires C<--no-manifest>).

=item C<--secrets!>

Include or suppress secrets validation.  Disabled by default.

=item C<--manifest!>

Include or suppress manifest build and validation.  Enabled by default.

=item C<--stemcells!>

Include or suppress stemcell availability checks.  Disabled by default.

=back

B<Returns:>

Nothing.  Exits with code C<0> on success, or dies with a preflight-failed
message on any check failure.

B<Errors:>

=over 4

=item C<"Cannot specify --no-config without also specifying --no-manifest">

Raised when C<--no-config> is used but C<--manifest> is still enabled.

=item C<"\n[#M{%s}] #R{PREFLIGHT FAILED}">

Raised when one or more checks fail.  C<%s> is the environment name.

=back

B<Examples:>

  # Run all default checks
  genesis my-env check
  # prints: [my-env] All Checks Succeeded

  # Check only secrets, skip manifest and config
  genesis my-env check --no-manifest --no-config
  # prints: [my-env] All Checks Succeeded

=head2 manifest($name)

  genesis <env> manifest [--type <type>] [--subset <subset>] [--list]

Generate the BOSH deployment manifest for the environment and print it to
STDOUT.  If C<--list> is specified, print the valid manifest types and
subsets instead.

B<Parameters:>

=over 4

=item C<$name>

Environment name string.  Exactly one argument is required.

=back

B<Options (via get_options):>

=over 4

=item C<--list|-l>

List valid manifest types and subsets for this environment, then return.
All other options are ignored when C<--list> is specified.

=item C<--type|-t>

Manifest type to generate.  Defaults to C<deployment>.  Use C<--list> to
see valid types.

=item C<--subset|-s>

Subset of manifest content to return.  Defaults to the full manifest.  Use
C<--list> to see valid subsets.

=back

B<Returns:>

Returns C<1> when C<--list> is used.  Otherwise prints the manifest YAML
to STDOUT and does not return a meaningful value.

B<Errors:>

=over 4

=item C<"Unknown manifest type %s - use --list option to show valid types">

Raised when C<--type> specifies a type not supported by this environment's
manifest provider.  C<%s> is the requested type string.

=item C<"Unknown manifest subset %s - use --list option to show valid subsets">

Raised when C<--subset> specifies a subset not supported by this
environment's manifest provider.  C<%s> is the requested subset string.

=item C<"Manifest type %s is not supported by this environment">

Raised when the manifest provider does not implement the requested type
method.  C<%s> is the resolved type string.

=back

B<Examples:>

  # Print the default deployment manifest
  genesis my-env manifest
  # prints: (YAML manifest content to STDOUT)

  # List available types and subsets
  genesis my-env manifest --list
  # prints: Valid manifest types: ...

  # Print the unredacted manifest
  genesis my-env manifest --type unredacted
  # prints: (unredacted YAML manifest content to STDOUT)

=head2 deploy($env_name, $reason)

  genesis <env> deploy [<options>] [<reason>]

Deploy the environment to its BOSH director (or via C<create-env> for
bootstrap environments).  Before deploying, this function orchestrates
cloud config generation and upload, network claims locking, secrets
validation and repair, manifest validation, stemcell checks, and CPI
config management.  After a successful deploy it returns C<0>; on failure
it calls C<bail()>.

The deploy declares the C<DEPLOYED_STATE> branch class, so it makes no
branch switch of its own.  By the time this function runs, the gate in
L<Genesis::Commands> has opened a branch session, asserted a clean tree and
index, taken the switch lock, and stood the working tree where this run
deploys from, which is C<< <env>/<type> >> for a deploy of the tip and the
recorded commit itself, checked out detached, for one that resolved a
deployed commit; and the session puts the branch, the head, and the
directory back when the function returns.  That is why the status is
returned rather than exited with: an exit from here would leave the session
for its own last-resort net to find.

That session is handed to C<< $env->deploy >> as its C<session> option, so
L<Genesis::Env/_post_deploy(%opts)> is the one place that decides what a
dirty tree costs.  It finishes the session where the tree is clean, and
where it is not it names the modified files, discards them, restores the
branch, withholds the downstream cascade, and exits
C<Genesis::Exit::SOFTWARE> even though the deploy itself succeeded.  Putting
it there rather than here means no early return in this function can skip the
assertion, and the gate then finds a session already closed, on which its
own finish is a no-op.  The one path that does leave ahead of the assertion
is the dry run, which exits from inside
L<Genesis::Env/_post_deploy(%opts)> before any deployment has been made.
That exit never comes back here, so the gate's finish never runs and the
session is left open, and what closes it instead is the session's own
last-resort net, which aborts rather than finishes.  The net says so on
stderr, because the status the dry run left behind is zero.

The root is loaded once, where the gate stood the working tree, which is the
deployment branch for a deploy of the tip and the resolved commit, checked
out detached, for one that resolved a deployed commit.  It is never rebuilt
from C<.> partway through.  A root rebuilt after a checkout is a root built
out of whatever the checkout left behind, which is how a deploy came to
report a repository that is not there instead of the problem in front of it.

A repository that has applied a pipeline and since set C<pipeline.enabled>
to false has disowned a pipeline that is still live, still watching its
branches, and still deploying.  The deploy asks
L<Genesis::CI::Preflight/assert_not_disowned> about that before it reads
anything else, and where it is true it warns and carries on, because an
operator part way through tearing a pipeline down has a reason to be
deploying.  C<--yes> changes nothing about the warning.  Inside the
pipeline's own job the same state is a refusal, because nobody there reads a
warning.  The question is asked ahead of everything the pipeline block does,
since every read in that block is guarded on the key being true and the one
state this answers for is the key being false.

Everything else a pipeline deploy asks before it deploys is asked by
C<_deploy_preflight>, in one place, because the order is part of what the
answers mean: the refresh, the control check, the cleanliness of a tree the
gate did not switch, the deployment branch's own class, what the branch
carries once the one move that class allows has landed, and the predecessor
this environment names.  A branch merely behind its counterpart is
fast-forwarded, which is the one ref move a deploy makes and the one that
neither creates nor discards a commit.  Every other class refuses, so an
operator meets the branch they are deploying from before they meet a warning
about a deploy that is not going to happen.  The predecessor is read from the
merged environment hierarchy, with no kit loaded and nothing connected, and
its deployment record is read once and shared by every step that wants it.

The last refusal the pre-flight raises on its own judgment, once the
predecessor's record has been read and before it warns about anything, is
the question of whether a pipeline owns this deploy. Where the provider is
an automated one, the pipeline's own jobs take locks a deploy typed at a
terminal cannot take, so the two can run beside each other
and neither knows. L<Genesis::CI::Preflight/assert_provider_gate> refuses
that deploy, and C<--force> is the only way past it. At a terminal the flag
turns the refusal into an acknowledgement the operator types out in full,
which C<--yes> does not answer, and which names what to quiesce and says
that no event is written to wake the deployments reading this one. Outside a
terminal the refusal stands even with the flag. The pipeline's own job skips
the gate, and under the manual provider it is never met, the operator there
being the pipeline.

Once every gate has passed, the pre-flight says what this run is about, and
it says so before it warns about anything. A run that named C<--redeploy>
resolved a deployed commit, and the gate has already stood the working tree
on it, so the deploy names that commit and says it is redeploying what the
environment is running rather than the tip of its branch. Every warning after
it describes that tip, which is why the sentence comes first. A run that
resolved no commit is deploying the tip and says nothing here.

That resolved commit answers one other question earlier on. The pre-flight
asks whether it is reading the deployment branch at all, and a redeploy is
standing on a commit of that branch rather than on the branch name, because
the gate checked the commit out detached. It is reading the branch, so it
passes where a deploy the gate left on control refuses.

Then the pre-flight warns. The first warning is about the pipeline itself:
where control has changed the shape of an environment
since C<genesis pipeline-apply> last applied it, the deploy says which
environments changed and why, and names the apply that brings the pipeline
back into step. It warns rather than refuses, because a pipeline out of step
with control still deploys what the branch carries. It is said first, because
what is stale decides which environments and which branches the due-commits
warning after it is talking about.

Then the deploy says what control carries that has not reached this branch,
naming each commit and C<genesis propagate>, and where a pull request
already proposes one of them it says so from durable state rather than from
the GitHub API. Last of the three, it says where the branch itself differs
from the snapshot of the control commit its marker names, naming the files
that differ and deploying anyway.

A redeploy skips the two warnings that describe the branch tip, which are the
commits due to the environment and the branch having drifted from its
marker's snapshot, because it is not trying to ship the tip. It keeps the
provider gate and the stale-pipeline warning, because a redeploy under an
automated provider still takes work the pipeline owns, and a pipeline whose
definition has moved is stale whichever commit is being deployed. A
C<--redeploy> of an environment that has never deployed successfully resolves
no commit and deploys the tip, and such a run hears both warnings.

A run that resolved a deployed commit hands off to no propagate child either,
and it is the resolved commit that decides this, the same fact the paragraphs
above turn on. The pre-flight resolved it once and returns it, this function
writes whether it is there into the options it forwards, and
L<Genesis::Env/_spawn_propagate_child(%opts)> withholds the child on it. A run
that resolved a commit certifies nothing new, so there is nothing for a
downstream environment to receive and a child would walk the whole pipeline to
learn that. A C<--redeploy> that resolved no commit is deploying the tip and
hands off like the ordinary deploy it is. No Genesis command writes the
propagate request queue instead, because that queue belongs to the pipeline's
own deploy job.

Whether the BOSH deploy carries C<--recreate> is settled once, by
L</_recreate_wanted($top, $options)>, out of the operator's own flag and the
repository's C<pipeline.recreate_on_deploy>. It is settled below the guard
that refuses more than one of C<--fix>, C<--recreate>, and C<--dry-run>,
because that guard is about what the operator asked for and a repository
setting is not that, so a repository that always recreates can still be
asked what a deploy would do.

At a terminal the deploy then asks whether to go ahead past what is due, and
C<--yes> answers that question. Outside a terminal it warns and carries on,
because a deploy must not stop to ask where nobody can answer. A no there
stops a deploy that every gate above it has passed, so the question, rather
than the gate, is the last thing that can stop this deploy.

B<Parameters:>

=over 4

=item C<$env_name>

Environment name string.

=item C<$reason>

Optional free-text reason for the deployment.  Required when the
environment's policy specifies a minimum reason length.  Defaults to
C<'unknown'> if not provided and not required.

=back

B<Options (via get_options):>

=over 4

=item C<--dry-run|-n>

Build and validate the manifest without making changes to the BOSH director.

=item C<--yes|-y>

Suppress all interactive prompts; assume yes.

=item C<--reactions!>

Process reactions from the environment file after deployment (default: enabled).

=item C<--redact!>

Redact sensitive values from diff output (default: redact when not writing
to a live terminal).

=item C<--fix>

Recreate unresponsive VMs rather than raising an error.  Mutually exclusive
with C<--recreate> and C<--dry-run>.

=item C<--fix-releases>

Re-upload releases and replace corrupt or missing jobs and packages.

=item C<--fix-stemcells>

Re-upload stemcells and replace corrupt or missing ones.  Not applicable
to C<create-env> environments.

=item C<--fix-secrets>

Rotate problematic secrets (expired, invalid, or missing) before deploying.

=item C<--fix-checks|-F>

Shorthand for C<--fix-stemcells> and C<--fix-secrets>, as applicable.

=item C<--clear>

Clear the deployment cache before starting.  Required if a prior
deployment was interrupted and left cached files behind.

=item C<--recreate>

Recreate all VMs instead of applying only the changed configuration.  The
repository can ask for the same thing on every deploy, or on every redeploy,
through C<pipeline.recreate_on_deploy>, and a run the repository asked for
carries the flag whether or not the operator typed it.

=item C<--recreate-persistent-disks|--rpd>

Recreate all persistent disks even when the deployment is a no-op.

=item C<--skip-drain>

Skip drain scripts for specific instance groups.  May be specified
multiple times.

=item C<--canaries>

Override the default number of canary VMs per instance group.

=item C<--max-in-flight>

Override the default maximum number of VMs in flight per instance group.

=item C<--STATE-FILE-PATH>

Path to a state file to use for this deployment, overriding the one
fetched from exodus or C<.genesis/manifests>.

=item C<--force>

Deploy an environment whose pipeline runs under an automated provider, which
is otherwise refused. At a terminal the flag turns the refusal into a typed
acknowledgement, which C<--yes> does not suppress; outside a terminal the
refusal stands even with the flag.

=item C<--redeploy>

Deploys the environment's deployed commit, the commit recorded in its last
successful deployment, rather than the tip of its deployment branch.  The
commit is checked out detached inside the branch session and the deploy runs
against it, so the environment is redeployed as it is running.  The record
written afterwards names the same two hashes as the record it redeployed,
because the control commit comes from the deployed commit's own marker, so the
certified commit does not move.

=back

B<Returns:>

Nothing.  Exits with code C<0> on success.

B<Errors:>

=over 4

=item C<"Cannot deploy environment #C{%s} without a reason (minimum length is %d characters).\nPlease provide a reason after any options on the command line">

Raised when the environment's policy requires a reason but none was given,
or the given reason is shorter than the minimum.  The intended substitutions
are: C<%s> for the environment name and C<%d> for the minimum character count.

=item C<"The following options cannot be specified for #M{create-env}: %s">

Raised when C<--fix>, C<--dry-run>, or C<--fix-stemcells> are passed to a
C<create-env> environment.  C<%s> is the comma-separated list of invalid
options.

=item C<"\nCowardly refusing to clear deployment cache files in #C{%s} without user confirmation.\n\nUse the #Y{--clear} option to clear them, or run the command without the #Y{--yes} option in an interactive terminal to be prompted.">

Raised when cached deployment files exist and C<--yes> is specified in a
non-interactive terminal without C<--clear>.  C<%s> is the cache directory.

=item C<"Genesis kit #C{%s} does not support the IaaS type #C{%s} - you will need to use a different kit/version.">

Raised when the kit's C<supports> metadata list does not include the
environment's IaaS type.  The first C<%s> is the kit id; the second is the
IaaS type.

=item C<"Cannot provide the required CPI config: %s">

Raised when the CPI config check reports a fatal error.  C<%s> is the
error message from the check result.

=item C<"Could not update required CPI config: %s">

Raised when fixing the CPI config fails.  C<%s> is the error message from
the fix result.

=item C<"Network claims are currently locked -- cannot proceed with deployment!">

Raised when another deployment holds an active network claims lock on the
BOSH director.

=item C<"Network claims lock was lost since last checked (may have become stale and removed) -- cannot proceed with deployment!">

Raised when the network claims lock is lost between the cloud config upload
and the network map update steps.

=item C<"Error generating cloud config for diff: %s">

Raised when C<spruce merge> fails while preparing the cloud config for
comparison.  C<%s> is the error or output text.

=item C<"Error comparing cloud configs: %s">

Raised when C<spruce diff> fails while comparing old and new cloud configs.
C<%s> is the error text.

=item C<"Failed to upload cloud config %s to BOSH director: %s\n\nContent:\n%s">

Raised when C<bosh upload-config> fails.  The first C<%s> is the cloud
config name; the second is the error; the third is the cloud config YAML.

=item C<"\nCannot continue without a valid network map:\n\n%s">

Raised when the vault update for the network map fails.  C<%s> is the
error detail.

=item C<"Failed to fix secrets: %s">

Raised when the pre-deploy secrets repair step fails fatally.  C<%s> is
the error message.

=item C<"Cannot prompt user for confirmation of release version overrides - not in a controlling terminal.  Please specify #Y{-y|--yes} to bypass this prompt.">

Raised when release version overrides require confirmation but there is no
interactive terminal and C<--yes> was not specified.

=item C<"Failed to fix stemcells: %s">

Raised when the stemcell upload repair step fails fatally.  C<%s> is the
error message.

=item C<"Stemcell check failed: %s">

Raised when stemcells are missing or corrupt and C<--fix-stemcells> was
not specified.  C<%s> is the check result message.

=item C<"Preflight checks failed; deployment operation halted.">

Raised when one or more preflight checks fail and the deploy cannot
proceed.

=item C<"Aborted by user">

Raised when the user declines to clear the deployment cache during the
pre-deploy cache check (without C<--yes>).

=item C<"Aborted.">

Raised when the user declines the confirmation prompt shown before a
pipeline deploy proceeds. Distinct from C<"Aborted by user"> only in
wording; both mean the operator said no.

=item C<"Working tree has uncommitted changes.  Commit or stash them\nbefore deploying:\n%s">

Raised when a pipeline deploy that opens no branch session is attempted with
a dirty working tree, and the C<%s> is the list of modified tracked paths, as
L<Service::Git::Session/modified_paths_of($git)> reads it, so it is the list
the session itself would have named. The deploy records the commit it ran
from, so uncommitted changes would be deployed but not recorded, leaving the
audit trail describing something other than what shipped.

A deploy that does switch never reaches this, because the session's C<begin>
has already asserted the same thing in its own words. A deploy run from the
environment's own deployment branch never reaches it either, and that is
deliberate: the command is leaving no branch behind, so an operator may
deploy an edit in place while testing a change.

=item C<"Refusing to run #C{genesis %s}.  #C{GENESIS_PIPELINE_TASK} is set, ...">

Raised through L<Genesis::CI::Preflight/assert_not_disowned> when the applied
record stands while C<pipeline.enabled> reads false and the command is running
inside the pipeline's own job, and it exits C<CONFIG>, because a job never
deploys what its own configuration disowns.  Outside a job the same state is
a warning rather than a refusal, for the reason given above.  C<%s> is the
command the operator ran, and the refusal closes with
C<"Nothing was deployed.">

=item C<"Refusing to deploy.  Failed to reach #C{%s} to refresh the pipeline branches, ...">

Raised through L<Genesis::Top/fetch_pipeline_envs> when the remote cannot be
reached, and it exits C<TEMPFAIL> rather than a bare failure, because the
refresh is unconditional and a retry is what fixes it. The deploy reads a
due commit and a drift off the remote-tracking refs, and both answers are
worthless against refs nobody has moved, so it refuses before it reads.  The
refusal closes with C<"Nothing was deployed.">

=item C<"Refusing to deploy.  The control branch #C{%s} exists neither on #C{%s} nor locally, ...">

Raised through L<Genesis::CI::Preflight/require_control> when the control
branch is in neither the remote nor this clone, and it exits C<CONFIG>,
because the environment files live on control and a deploy that cannot read
the topology can decide nothing.  No command creates the branch, since cutting
the one that becomes the repository's source of truth is the operator's act.
The first C<%s> is the control branch and the second is the remote, and the
refusal closes with C<"Nothing was deployed.">

=item C<"Refusing to deploy.  The environment #C{%s} has no branch on #C{%s} or locally, ...">

=item C<"Refusing to deploy.  The local branch #C{%s} has no counterpart on #C{%s}, ...">

=item C<"Refusing to deploy.  The local branch #C{%s} shares no ancestor with #C{%s/%s}, ...">

=item C<"Refusing to deploy.  The branch #C{%s} is ahead of #C{%s/%s} by %s, ...">

=item C<"Refusing to deploy.  The branch #C{%s} has diverged from #C{%s/%s}, ...">

Raised through C<_deploy_branch_action>, each at C<DATAERR> and each closing
with C<"Nothing was deployed.">, for the four states of the deployment branch
a deploy cannot read: the environment has no branch at all, the branch exists
only here, it shares no ancestor with the remote's, or it is ahead of or
diverged from the remote's. Genesis deletes no branch on any of them, and
each names the remedy in the order it is to be run.

=item C<"Refusing to deploy.  The branch #C{%s} carries no repository, ...">

=item C<"Refusing to deploy.  The branch #C{%s} carries no repository as this clone holds it, ...">

Raised through C<_deploy_preflight>, at C<DATAERR> and closing the same way,
for the two states in which there is no deployment root on the branch to
read. The first is an environment nothing has been delivered to, which waits
for C<genesis propagate>. The second is a clone that has not pulled the
delivery, which waits for a fetch, and it is reached only where this run's
own refresh brought the delivery down after the gate had already decided not
to switch: a clone that was behind when the gate ran was brought forward by
it, since the deploy declares C<branch_fast_forward>.

=item C<"Cannot deploy #C{%s}: its pipeline predecessor #C{%s} has never been successfully deployed.">

Raised through C<_assert_prior_env_deployed> inside the pre-flight, at
C<DATAERR> and closing the same way, when the environment names a predecessor
that has never deployed.  C<--yes> does not override it.

=item C<"The #C{%s} pipeline owns deploys of this environment. ...">

Raised through L<Genesis::CI::Preflight/assert_provider_gate> inside the
pre-flight, at C<NOPERM> and closing with C<"Nothing was deployed.">, for a
deploy under an automated provider with no C<--force>, and again for a
C<--force> deploy with no controlling terminal. Where the operator is at a
terminal and types anything but the acknowledgement, the deploy exits
C<ABORTED> instead. C<--yes> answers no part of this.

=item C<"Aborted by user!">

Raised when the user declines an interactive prompt during cloud config
comparison or release version override confirmation.

=item C<"[#M{%s}] #R{Deployment Failed}">

Raised when the underlying C<< $env->deploy >> call returns false.  C<%s>
is the environment name.

=back

B<Examples:>

  # Deploy interactively
  genesis my-env deploy
  # prints: my-env/bosh deployed successfully.

  # Deploy non-interactively with auto-fix checks
  genesis my-env deploy --yes --fix-checks
  # prints: my-env/bosh deployed successfully.

  # Dry run to validate without changing anything
  genesis my-env deploy --dry-run
  # prints: (dry-run output; no changes made)

  # Deploy with a reason for audit purposes
  genesis my-env deploy "Quarterly patching cycle"
  # prints: my-env/bosh deployed successfully.

=head2 redeploy_wanted($top, $options)

  my $bool = redeploy_wanted($top);
  my $bool = redeploy_wanted($top, $options);

Answers whether the run in progress is a redeploy. A caller holding the
deploy's own options hash passes it as the second argument and the answer is
read from there; a caller with no options hash omits it and the answer is read
from the command line. Every part of Genesis that behaves differently on a
redeploy asks this, so the question has one answer rather than one per caller.

The options hash is what carries the answer to code with no command line to
ask. L<Genesis::Env> imports C<current_command> and C<known_commands> from
L<Genesis::Commands> and cannot call C<has_option> at all, so a deploy that
has read its own options hands the answer on rather than leaving it to be
asked again.

A run that has already resolved its target asks the target instead, which
C<_warn_about_the_tip> does and which C<deploy> does on behalf of everything
downstream of it. The two answers part company in one state, a C<--redeploy>
of an environment that has never deployed successfully, where the flag was
given, no commit was resolved, and the run deploys the tip.
L<Genesis::Commands/deployed_target> is the reader for that question.

It is the module's one exported name. Nothing imports it today, every caller
so far sitting in this module beside it, and it is on the list so that a
caller outside it has one name to ask rather than a second spelling of the
question.

L</deploy($env_name, $reason)> does not ask it. The deploy has a resolved
target by then and writes whether that target is there into the
C<redeploy> key of the options it forwards, so
L<Genesis::Env/_spawn_propagate_child(%opts)> and every other reader of that
key are answered by the commit the run resolved rather than by the flag it
was given.

Its one product caller today is L</_recreate_wanted($top, $options)>, which
asks it of that same options hash, so the repository's C<redeploy-only>
setting turns on the commit the run resolved as the hand-off does. The other
caller the design names is C<_propagate_after_deploy>, which M15 lands in this
module when the hand-off moves here.

B<Parameters:>

=over 4

=item C<$top>

The deployment repository. It comes first so that this reads like the other
questions the deploy asks of a run, and it is not read.

=item C<$options>

Optional. The command's own options, as C<get_options> answered them. Given,
it is where the answer comes from; omitted, the command line is asked.

=back

B<Returns:> 1 on a redeploy and 0 otherwise.

B<Errors:> none.

B<Examples:>

  redeploy_wanted($top);
  # Returns: 1 under `genesis qa deploy --redeploy`

  redeploy_wanted($top, {redeploy => 1, yes => 1});
  # Returns: 1, read from the hash rather than from the command line

  redeploy_wanted($top, {});
  # Returns: 0, an options hash with no redeploy key being an answer rather
  # than an absence

=head1 INTERNAL FUNCTIONS

These are internal to this module and may change without notice.

C<_assert_clean_index> serves the check C<create> makes before it commits.
C<_derive_deploy_reason> and C<_format_pipeline_reason> serve C<deploy>'s
reason line, and C<_prior_env_record> and C<_assert_prior_env_deployed>
together serve the invariant that a pipeline predecessor has been deployed
before anything downstream of it is: one of them reads the predecessor's
record and the other judges what it read. The rest each serve one step of a
deploy.

=head2 _assert_clean_index($git)

Refuses the command when the index holds a staged change, because C<create>
makes a commit and a commit takes everything the index already holds. The
refusal names every staged path, so the operator can see what would have
been swept in.

Only the index column of C<git status --porcelain> is read. A space in that
column means the change is unstaged and a question mark means the path is
untracked, and neither one reaches the commit, so neither one is in the
way. C<create> calls this only when it is going to commit, so C<--no-commit>
never reaches it at all.

B<Parameters:>

=over 4

=item C<$git>

A C<Service::Git> for the deployment repository.

=back

B<Returns:> A true value when the index is clean. It does not return when
the index is not.

B<Errors:>

=over 4

=item C<"There are staged changes in this repository, and this command makes a commit, so they would be swept into it:">

Raised when at least one path is staged. The staged paths follow the
message, one per line, and the remedy offered is to commit them, to unstage
them with C<git reset>, or to re-run with C<--no-commit>. The exit code is
C<DATAERR>, because staged work is something the operator has to act on
rather than something a re-run fixes.

=back

B<Examples:>

  _assert_clean_index($git);
  # returns 1 when nothing is staged

  _assert_clean_index($git);
  # exits 65 naming ops/pending.yml when that path is staged

=head2 _derive_deploy_reason($env, $git)

Works out a human-readable reason for a deploy by reading what changed in
git since the last successful deployment of this environment.

Three cases, in order:

=over 4

=item *

The branch head matches the last deployed commit, so nothing has changed and
the reason is simply that this is a redeploy of that commit.

=item *

There is a previous deployment, so the range examined is
C<last_deployed..branch_head>.

=item *

There is none, so the whole history to the branch head is examined.

=back

B<The history is scoped to files this environment depends on.> Without that
filter, a repository deploying several things from one env branch -- bosh and
vault, say -- would surface propagation markers belonging to a sibling
deployment, and report a reason describing work that had nothing to do with
the deploy in hand.

Every step is guarded: no vault, no branch head, or no matching commits each
yield C<undef> rather than an error. A deploy is not worth blocking over a
missing explanatory line.

B<Parameters:>

=over 4

=item C<$env>

The C<Genesis::Env> being deployed.

=item C<$git>

A C<Service::Git> for the deployment repository.

=back

B<Returns:> The reason string, or C<undef> when one cannot be derived.

B<Examples:>

  my $reason = _derive_deploy_reason($env, $git);
  # returns 'Redeploy of a1b2c3d' when nothing has changed

  my $reason = _derive_deploy_reason($env, $git);
  # returns undef when the environment has no vault, or the branch
  # has no head, or no control commits touched its files

=head2 _format_pipeline_reason($log_lines, $short_sha, $subject_of)

Turns a list of git log subjects into the reason text, by picking out the
propagation markers and reporting the commits they point at.

Only lines carrying a propagation marker count, and the marker is read with
L<Genesis::CI::Marker/in_text> rather than matched here. Those markers record
where a propagation came from, so the useful reason is the subject of the
I<control> commit, not of the propagation commit that carried it across.

The reader is anchored to the start of a line, which is what keeps a sha
named in passing from matching, so the commit's own sha has to come off the
front of a line before the marker is at the start of anything. Each line is
read as it arrived first and with that leading field removed second, so a
caller handing over a bare subject is answered rather than met with silence.
Both reads are anchored, so the second adds no way for a sha named in
passing to match.

Order is reversed on the way through: git log is newest-first, and a reason
listing several commits reads properly oldest-first.

The lookups are passed in rather than performed here, which is what makes the
function testable without a repository.

B<Parameters:>

=over 4

=item C<$log_lines>

Arrayref of log subject lines to scan, ordinarily in git's C<%H %s> shape,
which is what C<log_subjects> returns by default. A bare subject line is read
too. C<undef> is treated as empty.

=item C<$short_sha>

Callback abbreviating a sha. Accepted for symmetry with callers; the subject
lookup is what the result is built from.

=item C<$subject_of>

Callback returning the subject line of a given commit.

=back

B<Returns:> The subject alone when one control commit is found; a count
followed by an indented list when several are; C<undef> when none are.

B<Examples:>

  my $reason = _format_pipeline_reason($lines, $short, $subject);
  # returns 'Bump cf-deployment to 42.1.0'   (a single control commit)

  my $reason = _format_pipeline_reason($lines, $short, $subject);
  # returns "3 commits:\n  - Bump cf-deployment\n  - Add az4\n  - ..."

  my $reason = _format_pipeline_reason([], $short, $subject);
  # returns undef -- no propagation markers to report

=head2 _prior_env_record($env, $prior_name)

  my $record = _prior_env_record($bare, 'staging');

Reads the predecessor environment's exodus deployment records once and
answers the newest whose result is C<success> or C<post-failed>, which is the
newest deployment that actually reached the director.

Two readers want that record, the check below for the fact that the
predecessor deployed at all and the due-commits computation for the control
commit it certified, and both read it from here, so a deploy makes one read
of it rather than two.

B<A C<post-failed> result counts as deployed.> It means the BOSH deploy
itself succeeded and only a post-deploy step failed, so the environment is
running and is a legitimate predecessor. Treating it as a failure would block
a deploy that should proceed.

The read is of the deployment audits under the predecessor's own exodus base,
which is the set every reader of a certified commit goes through, and the
entries are read newest first by the compact timestamp each is named for.
The flat record beside them holds the same facts under other names and is the
staleness comparison's half.

Each entry is built as a C<Genesis::Env::Deployment> with C<from_storage>,
which is how C<Genesis::Env::DeploymentManager> reads the same set. A record
may predate the current schema by years, and one normalised by one reader and
read raw by another is a predecessor that has deployed by one reckoning and
never deployed by the other.

The vault read is wrapped in an C<eval>, so a predecessor whose history
cannot be read at all is answered the same way as one that never deployed,
and the check that reads this answer is where the refusal is worded.

B<Parameters:>

=over 4

=item C<$env>

An environment of the deployment being read from, which is the bare
environment the pre-flight builds. Its exodus mount and its deployment type
compose the path, and its vault makes the read.

=item C<$prior_name>

The predecessor environment's name, as C<genesis.pipeline.prior_env> gives
it. An empty or undefined name answers C<undef> without reading anything.

=back

B<Returns:> a hash reference of C<at>, the entry's timestamp; C<result>; and
C<git>, the entry's commit pair as a hash reference. C<undef> where the
predecessor has no such deployment, or none that can be read.

B<Errors:> none from the read itself. The vault read is inside the C<eval>, so
a history that cannot be read answers C<undef>. C<< $env->vault >>,
C<< $env->exodus_mount >>, and C<< $env->type >> are outside it, and a
repository with no reachable vault target dies through them.

B<Examples:>

  my $record = _prior_env_record($bare, 'lab');
  # Returns: {at => '20260917120000', result => 'success',
  #           git => {commit => '...', control_commit => '...'}}

  my $record = _prior_env_record($bare, '');
  # Returns: undef, with no vault read made

=head2 _assert_prior_env_deployed($env, $prior_name, $record)

Refuses the deploy when this environment's pipeline predecessor has never
deployed at all.

The point is to catch the ordering mistake early, with a message naming what
to do, rather than let a deploy proceed against a predecessor that was never
stood up. It is a hard invariant, which C<--yes> does not override.

It judges the record C<_prior_env_record> already read rather than reading
one of its own, and it asks nothing about which control commit the
predecessor certified. A predecessor that deployed and certified nothing
holds everything below it under D43, and the due-commits warning is where
that is said, so such a predecessor passes here.

B<Parameters:>

=over 4

=item C<$env>

The environment about to deploy, whose name the refusal carries.

=item C<$prior_name>

The predecessor environment's name.

=item C<$record>

What C<_prior_env_record> answered for that predecessor.

=back

B<Returns:> true when the predecessor has a record.

B<Errors:>

=over 4

=item *

C<"Cannot deploy #C{%s}: its pipeline predecessor #C{%s} has never been successfully deployed."> --
raised via C<bail()> at C<DATAERR>, followed by an instruction to deploy the
predecessor first and by C<"Nothing was deployed.">. The substitutions are
this environment's name and the predecessor's.

=back

B<Examples:>

  _assert_prior_env_deployed($bare, 'staging', $record);

  _assert_prior_env_deployed($bare, 'staging', undef);

=head2 _warn_stale_pipeline($top, $git)

=item C<$git>

=back

B<Returns:> how many environments it named, which is zero when nothing has

B<Errors:> none of its own. The read beneath it can die where the vault is

=head2 _warn_commits_due($env, $record)

  my $due = _warn_commits_due($env, $record);

Warns that control carries commits due to this environment and not yet on its
deployment branch, naming each one and C<genesis propagate>, which is the one
command that delivers them.

Where a pull request already proposes one of those commits, the warning says
so, and it says it from the environment's proposed record rather than from
the GitHub API, so a warning costs no API call and works with no token at
all.

Where an ancestor has certified no control commit, nothing is due at all,
because such an ancestor holds everything below it. The warning then names
that ancestor instead, and it takes the name from the reason the walk put on
the hold rather than reading the ancestor itself, so the two never disagree
about which one is holding things up. That arm asks for an empty pending
list as well as for the hold, since the sentence it prints says that nothing
is due and only an empty list makes that true.

Where the walk failed for this environment, it says that it could not tell
what is due and why, and it warns about nothing else, the rest of the record
being whatever the failure left behind. A reader that went straight to the
pending list would print the silence of a branch with nothing due over a
question nobody answered, which is the one wrong answer this warning can
give.

The due set is not computed here. It comes from the walk, which is the same
computation C<genesis propagate> delivers from, run read-only and narrowed to
this one environment, so the deploy and the propagate run cannot disagree
about what is due.

B<Parameters:>

=over 4

=item C<$env>

The environment being deployed, read bare. Its name, its deployment slug, and
its proposed record are what the warning says.

=item C<$record>

This environment's entry in the walk's record, whose C<pending> list is what
is due, whose C<held> list carries the holding ancestor's reason, and whose
C<error> is what the walk ran into where it could answer neither.

=back

B<Returns:> the due commits as an array reference, which is empty where
nothing is due, where an ancestor holds everything, and where the walk could
not tell.

B<Errors:> none of its own. Reading the proposed record can die where the
vault is unreachable, as any other read of that vault can.

B<Examples:>

  my $due = _warn_commits_due($env, $record);
  # names two commits and genesis propagate, and returns both

  my $due = _warn_commits_due($env, $record);
  # says lab holds everything below it, and returns []

  my $due = _warn_commits_due($env, {error => 'vault unreachable'});
  # says it could not tell what is due for qa, and returns []

=head2 _confirm_commits_due($env_name, $due, $options)

  _confirm_commits_due('qa', $due, $options);

Asks whether to deploy anyway when commits are due, and carries the deploy
past the question on a yes.

C<--yes> answers it, and so does the absence of a controlling terminal,
because a deploy must not stop to ask where nobody can answer. That is the
opposite of the provider gate's rule, and for the opposite reason: a deploy
past a due commit is something an operator may legitimately want, where a

It is a sub of its own so that its terminal half can be driven directly, no
spawned command having a terminal to answer from.

B<Parameters:>

=over 4

=item C<$env_name>

The environment the question names.

=item C<$due>

The due commits, as L</_warn_commits_due($env, $record)> answered them.
Nothing is asked where the list is empty.

=item C<$options>

The deploy's options, of which C<yes> is the only key read.

=back

B<Returns:> true, in every case where the deploy goes on.

B<Errors:> exits with C<Genesis::Exit::ABORTED> (130) on a no, saying that

B<Examples:>

  _confirm_commits_due('qa', $due, {yes => 1});

  _confirm_commits_due('qa', $due, {});

=head2 _warn_drifted($env, $git)

  my $drifted = _warn_drifted($top->load_env('qa'), $git);

Warns that the deployment branch differs from the snapshot of the control
commit its newest marker names, naming every file that differs, and lets the
deploy go ahead. A branch in that state carries a hand commit somebody pushed
to work around the pipeline, which is legal and temporary, and the deployment
record tells the two commits apart afterwards.

The comparison covers the environment's propagation set and nothing else,
because that set is what a delivery mirrors and a file outside it was never
the branch's to match. A branch carrying no marker anywhere has been
delivered nothing, so there is no snapshot to compare it against and this
says nothing rather than reading the whole branch as drift.

The set is read from the branch's own working tree, which is what
C<propagation_files> answers, so a member the hand commit deleted outright is
in no pathspec and its absence goes unnamed. Two kinds go quietly that way,
C<kit-overrides.yml> and the embedded C<.genesis/bin/genesis>; the rest
either stop the load or sit under a directory pathspec, where git reports the
deletion anyway.

It is the last of the pre-flight's warnings and it prints before the prompt
beside the due-commits warning, so an operator answering that prompt has
heard everything the pre-flight had to say.

The pre-flight loads the environment for this one read alone, every other
read it makes going through C<< Genesis::Env->bare >>. The load reads the
kit off the deployment branch and connects to nothing, and the deploy loads
the same environment a step later, so a kit that cannot be loaded stops the
deploy here rather than there with the same complaint.

B<Parameters:>

=over 4

=item C<$env>

The environment, loaded rather than bare, because the propagation set is
built from the kit as well as from the environment file and a bare
environment has no kit to ask. It answers the deployment branch's name and
the set.

=item C<$git>

The deploy's git handle, standing on that branch.

=back

B<Returns:> the files that differ as an array reference, empty when none do.

B<Examples:>

  my $drifted = _warn_drifted($top->load_env('qa'), $git);
  # Returns: ['envs/qa.yml'] having named the hand-edited file.  The paths
  # are git-root-relative, as propagation_files answers them, so they carry
  # the deployment root's prefix wherever the repository has one.

  my $drifted = _warn_drifted($top->load_env('qa'), $git);
  # Returns: [] and says nothing of a branch that mirrors its snapshot

=head2 _warn_about_the_tip($top, $name, $git, %what)

  my $tip = _warn_about_the_tip($top, 'qa', $git,
      bare => $bare, record => $due_record, target => $commit);

The one caller of the pre-flight's three warnings, and the one place that
decides which of them a redeploy skips.

A redeploy skips the two warnings that describe the branch tip, which are the
commits due to the environment and the branch having drifted from its
marker's snapshot, because it is not trying to ship the tip. It keeps the
provider gate and the stale-pipeline warning, because a redeploy under an
automated provider still takes work the pipeline owns, and a pipeline whose
definition has moved is stale whichever commit is being deployed. The gate is
not asked here at all; it is a refusal and it sits two steps above these
warnings.

What it reads is the resolved target rather than the flag. That is the same
answer the notice above it gave the operator, so the run cannot say it is
deploying the tip and then withhold what the tip carries. A C<--redeploy> of
an environment that has never deployed successfully resolves no commit and
deploys the tip, as every deploy did before the flag existed, and such a run
hears both warnings. The flag has its own reader in L</redeploy_wanted($top, $options)>,
which is what a caller with no resolved target to hand asks.

The environment the drifted warning reads is loaded here rather than by the
caller, so a redeploy pays for neither the load nor the warning it feeds.

Both lists come back rather than being swallowed. The prompt that sits beside
the due-commits warning reads the due list, and C<_deploy_preflight> carries
both lists in the hash it answers, so a wrapper that returned nothing would
take the prompt's input away.

B<Parameters:>

=over 4

=item C<$top>

The deployment repository, which the stale-pipeline warning reads and which
the drifted warning's environment is loaded from.

=item C<$name>

The environment's name, normalised, as the pre-flight derived it once for
everything below it.

=item C<$git>

The deploy's git handle, which two of the three warnings take.

=item C<%what>

C<bare>, the bare environment the due-commits warning names and reads the
proposed record through; C<record>, that environment's entry from the walk,
which is where the due list comes from; and C<target>, the commit this run
resolved, or C<undef> where it is deploying the tip.

=back

B<Returns:> a hash reference carrying C<due>, the control commits the
due-commits warning named, and C<drifted>, the files the branch differs from
its snapshot in. Both are empty array references where the warning found
nothing, and both are empty on a run that resolved a target, neither warning
having been asked.

B<Errors:> none of its own. Each warning fails as it fails when called
directly, and the environment load can stop a deploy whose kit cannot be
read, which is the load C<_deploy_preflight> would otherwise have made here.

B<Examples:>

  my $tip = _warn_about_the_tip($top, 'qa', $git,
      bare => $bare, record => $due_record, target => undef);
  # Returns: {due => [...], drifted => ['envs/qa.yml']} having printed all
  # three warnings

  my $tip = _warn_about_the_tip($top, 'qa', $git,
      bare => $bare, record => $due_record, target => 'a1b2c3d4');
  # Returns: {due => [], drifted => []} having printed the stale-pipeline
  # warning alone

=head2 _warn_about_the_version_served($env)

run just wrote are for a control commit other than the one the environment is

handle per repository root, so it is the gate's own handle and not a second

=item C<$env>

=head2 _deploy_branch_action($top, $env_name, $git)

  my $action = _deploy_branch_action($top, 'qa', $git);

Classifies the environment's deployment branch against the remote and
returns what the deploy should do with it, which is C<proceed> for a branch
in sync and C<fast-forward> for one that is behind. Every other state is a
refusal: a branch ahead of or diverged from the remote's, a local branch the
remote lacks, a local branch sharing no ancestor with the remote's, and an
environment with no branch anywhere. Genesis deletes nothing on any of them.

What the branch carries is not asked here. C<_deploy_preflight> asks it after
the fast-forward this classification ordered has landed, because a branch
behind a delivery holds the commit before it until then and an answer taken
first would be an answer about the wrong commit.

The fast-forward is the one ref move a deploy makes. It moves the local
branch toward its counterpart and neither creates nor discards a commit,
which is why a branch that is ahead or diverged is refused instead: resetting
a marker-only commit and refusing a hand commit by name belong to
C<genesis propagate>, and a deploy never discards a commit.

Two of the states need care. C<< $git->resolve_branch >> answers C<undef>
outright when neither the local branch nor the tracking ref exists, so that
case has no state at all and is read before anything reads one. And
C<resolve_branch> has no C<unrelated> state, because a branch sharing no
ancestor with the remote's counts commits both ways and reads as
C<diverged>; the ancestry question is therefore asked separately, through
the same test the propagate run's initial state uses, so the two commands
mean the same thing by it.

C<no-local> is classified with the two that deploy rather than refused.
Nothing reaches this sub in that state: the refresh two steps earlier
materialises a local ref the clone lacks from the tracking ref, which is what
the propagate run's own initial state says about the same state, and the
gate's switch would have created the ref in any case.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the deployment root.

=item C<$env_name>

The environment name, with any leading directories and C<.yml> suffix
already taken off, from which the branch is derived.

=item C<$git>

A C<Service::Git> for the repository.

=back

B<Returns:> a hash reference of C<action>, which is C<proceed> or
C<fast-forward>, and C<divergence>, which is what C<resolve_branch>
answered. It does not return on any of the four refusals.

B<Errors:>

=over 4

=item C<"Refusing to deploy.  The environment #C{%s} has no branch on #C{%s} or locally, ...">

Raised when neither the local branch nor the tracking ref exists, naming
C<genesis pipeline-apply> and then C<genesis propagate> as the remedy.

=item C<"Refusing to deploy.  The local branch #C{%s} has no counterpart on #C{%s}, ...">

Raised under D48 for a branch only this clone has, which is a legacy
checkout or a branch made by hand, since a deployment branch is derived from
control and never originates locally.

=item C<"Refusing to deploy.  The local branch #C{%s} shares no ancestor with #C{%s/%s}, ...">

Raised under D48 for a branch of the right name and an unrelated history,
from which a deploy would certify a commit that is not on the remote.

=item C<"Refusing to deploy.  The branch #C{%s} is ahead of #C{%s/%s} by %s, ...">

=item C<"Refusing to deploy.  The branch #C{%s} has diverged from #C{%s/%s}, standing %s ahead of it and %s behind, ...">

Raised for a branch ahead of or diverged from its counterpart, naming
C<genesis propagate>, which resets a marker-only commit and refuses a hand
commit by name. The two states read differently, so the verb comes off the
state rather than the state's own name standing in for one, and each count
carries its noun.

=back

Every one of them exits C<DATAERR> and closes with C<"Nothing was
deployed.">

B<Examples:>

  my $action = _deploy_branch_action($top, 'qa', $git);
  # Returns: {action => 'proceed', divergence => {state => 'in-sync', ...}}

  my $action = _deploy_branch_action($top, 'qa', $git);
  # exits 65 naming genesis propagate when qa/bosh is two commits ahead

=head2 _deploy_preflight($top, $env_name, $options)

  my $preflight = _deploy_preflight($top, 'qa', \%options);

Runs a pipeline deploy's pre-flight in order and answers what it settled.
The steps are the refresh of control and the deployment branches, the
control check, the cleanliness of a working tree the branch-class gate did
not switch, the classification of the deployment branch, the fast-forward
where that is the move its class allows, what the branch carries once the
move has landed, the predecessor this environment names, the provider gate,
the notice that says which commit this run is about, and then the warnings,
which are the stale-pipeline warning, the due-commits warning, and the
drifted warning, with the one prompt after all three.

The notice comes before every warning because each of them describes the
branch tip. A run that resolved a deployed commit names it and says it is
redeploying what the environment is running rather than the tip of its
branch; a run that resolved none is deploying the tip and says nothing here.

The gate sits after the predecessor's record and before the warnings, so it
is the last refusal the pre-flight raises on its own judgment. Every refusal
above it is one no acknowledgement can settle: an operator who types the
phrase past a branch carrying no repository still has nothing to deploy.
C<--force> is an answer to the gate's question alone, so the question is
asked once everything that is not negotiable has passed, and what follows it
is a warning rather than a refusal of ours. The operator can still stop the
deploy after it, by declining the prompt that sits beside the due-commits
warning, which exits C<ABORTED>. The gate is shared with the propagate run
and lives in L<Genesis::CI::Preflight/assert_provider_gate>; the deploy
gives it its own words for what the pipeline owns, its own closing sentence,
and the phrase the operator types.

The predecessor is read through the merged environment hierarchy, which is
what D79 asks of every C<genesis.pipeline.*> key the pre-flight reads, so a
predecessor named on a site file is seen. C<< Genesis::Env->bare >> runs the
name and file-existence checks and nothing else, so the read loads no kit and
connects to nothing. Its record is read once, by C<_prior_env_record>, and
handed to C<_assert_prior_env_deployed>, because the due-commits computation
wants the same record and a deploy should read it once. Reading it here,
rather than after the environment is loaded, is what lets a deploy that may
not proceed say so instead of reporting whatever the loading of that
environment ran into first.

The fast-forward is made only where the deploy is standing on the branch,
since C<pull_ff_only> merges into the branch the working tree holds and would
otherwise pull the deployment branch into control. Standing on the branch is
also what answers the question of what it carries, the gate having switched
onto it. A deploy not standing on the branch is one the gate declined to
switch: the root it read is control's, whatever the branch carries now, so
the commit it would record is not the commit it would deploy, and it is
refused.

A run that resolved a deployed commit is the exception, and it is an
exception to that premise rather than to the rule. The gate checked the
commit out detached, so the run is standing on the branch's own history at
the commit it was told to deploy, and the root it read is the branch's. What
it is not standing on is the branch name, so the question of what the branch
carries takes the resolved commit as an answer alongside the name, and the
fast-forward stays off it, a pull having no detached head to merge into.

Two states are refused there and they need different remedies. An
environment nothing has been delivered to is told to propagate. A clone
holding a branch whose delivery it has not pulled is told to fetch it,
because a propagation would find nothing due and the next deploy would
refuse the same way. The second is rare, since the gate brings a branch this
clone holds behind its counterpart forward before it switches, the deploy
declaring C<branch_fast_forward>; it is what is left when this run's own
refresh brought the delivery down after that decision was made.

It is one sub because the order is the point. Every gate runs before every
warning, so an operator meets a refusal before a warning about a deploy that
will not happen, and the divergence refusal prints where the refusal about
an undeployed predecessor would otherwise also apply.

The warnings then run in the order the design fixes, and C<_warn_stale_pipeline>
is the first of them. A pipeline that no longer matches control decides which
environments and which branches everything after it is talking about, so an
operator hears that before anything else the pre-flight has to say.

C<_warn_commits_due> follows it, and the one prompt C<--yes> answers sits
beside it. What is due comes from the walk that C<genesis propagate> delivers
from, run read-only and narrowed to this environment, so the two commands
read one computation and cannot disagree about what is due. The walk is
handed the deployment branch by name rather than the branch record
L<Genesis::CI::Preflight/initial_state> builds, because that stage resets and
fast-forwards the branches it classifies, which is no read for a deploy to
make, and the branch this deploy is about was resolved by the classification
four steps above.

C<_warn_drifted> is the last of the three, and the prompt follows it rather
than sitting between the two, because that prompt is the last place a deploy
can be stopped and an operator answering it should have heard every warning
first.

All three are called through C<_warn_about_the_tip>, which is the one place
that decides which of them a run skips. A redeploy skips the two warnings
that describe the branch tip, which are the commits due to the environment
and the branch having drifted from its marker's snapshot, because it is not
trying to ship the tip. It keeps the provider gate and the stale-pipeline
warning, because a redeploy under an automated provider still takes work the
pipeline owns, and a pipeline whose definition has moved is stale whichever
commit is being deployed. The walk that feeds the due-commits warning is
still made here, being the deploy's own read of durable state, and its answer
is handed to that caller.

The git handle comes from C<< Service::Git->new('.') >>, which memoises one
handle per repository root, so it is the same handle the gate used rather
than a second one onto the same working tree. The session is the gate's,
read through L<Genesis::Commands/branch_session>, and it is C<undef> where
the gate switched nothing.

Only a repository whose pipeline is enabled reaches this. The environment
name is normalised here, the way the gate normalises the same argument, and
the branch is derived once from it for everything below.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> the deploy loaded, on the tree the gate stood it on,
which is the deployment branch for a deploy of the tip and the recorded
commit, detached, for one that resolved a deployed commit.

=item C<$env_name>

The environment name as the operator gave it, which may be a path or carry a
C<.yml> suffix.

=item C<$options>

The deploy's own options, as C<get_options> answered them.

=back

B<Returns:> a hash reference carrying C<git>, the handle; C<branch>, the
deployment branch's name; C<session>, the gate's session or C<undef>;
C<action>, what the classification decided; C<bare>, the bare environment the
configuration reads were made through; C<target>, the deployed commit this
run resolved or C<undef> where it resolved none; C<prior>, the predecessor's
deployment record or C<undef>; C<due>, the control commits the warning named,
which is an empty array reference where nothing is due; and C<drifted>, the
files the branch differs from its snapshot in, which is an empty array
reference where it does not.

Both C<due> and C<drifted> are empty on a run that resolved a deployed
commit, because neither warning was asked. An empty list there says that the
question went unasked rather than that the answer was nothing, so a caller
that wants either fact about the tip of a redeploy's branch has to compute it
for itself.

B<Errors:>

=over 4

=item C<"Working tree has uncommitted changes.  Commit or stash them\nbefore deploying:\n%s">

Raised when the gate switched nothing, the operator is not standing on the
deployment branch, and the tree holds a modified tracked path. The paths are
listed as the session's own reader names them.

=item C<"Refusing to deploy.  The branch #C{%s} carries no repository, ...">

Raised at C<DATAERR> when nothing has been delivered to the environment on
either side, naming C<genesis pipeline-apply> and then C<genesis propagate>
as the remedy.

=item C<"Refusing to deploy.  The branch #C{%s} carries no repository as this clone holds it, and it stands %s behind #C{%s/%s}, ...">

Raised at C<DATAERR> when the delivery is on the remote and this clone has
not pulled it, naming the fetch that brings the branch up as the remedy.
Both refusals close with C<"Nothing was deployed.">

=item C<"Cannot deploy #C{%s}: its pipeline predecessor #C{%s} has never been successfully deployed.">

Raised at C<DATAERR> through C<_assert_prior_env_deployed> when the
environment names a predecessor that has no deployment record.

=item C<"The #C{%s} pipeline owns deploys of this environment. ...">

Raised at C<NOPERM> through L<Genesis::CI::Preflight/assert_provider_gate>
for a deploy under an automated provider without C<--force>, and again with
the flag but no controlling terminal. A terminal answer that is not the
acknowledgement exits C<ABORTED> instead.

=item C<"Aborted.  Nothing was deployed.">

Raised at C<ABORTED> through C<_confirm_commits_due> when an operator at a
terminal declines to deploy past the commits that are due.

=item C<"The walk answered no environment for #C{%s}.">

Raised as a bug when the walk, asked about this one environment, answers a
list with nothing in it. Carrying on would read as nothing being due.

=back

The refusals of the refresh, the control check, and the branch
classification are raised through the subs that own them and are documented
with C<deploy>.

B<Examples:>

  my $preflight = _deploy_preflight($top, 'qa', \%options);
  # Returns: {git => $git, branch => 'qa/bosh', session => $session,
  #           action => {action => 'proceed', ...}, bare => $bare,
  #           target => undef, prior => {at => '20260917120000', ...},
  #           due => [], drifted => []}

  my $preflight = _deploy_preflight($top, 'qa.yml', \%options);
  # exits 65 when qa/bosh exists nowhere, naming genesis pipeline-apply

=head2 _recreate_wanted($top, $options)

  $options{recreate} = _recreate_wanted($top, \%options);

Whether this run should pass C<--recreate> to the BOSH deploy, as C<1> or
C<0>. The operator's own C<--recreate> always wins, and this only adds the
flag where the repository asked for it through
L<Genesis::Top/recreate_on_deploy>. C<always> adds it to every deploy,
C<redeploy-only> to a run L</redeploy_wanted($top, $options)> calls a
redeploy, and C<never> to none. The repository's setting covers the CLI's
C<--redeploy> as well as the pipeline's own redeploy job, both being the same
code path, and a C<--redeploy> that resolved no commit is deploying the tip
and counts as an ordinary deploy here as it does everywhere else.

C<deploy> asks it once, below the guard that refuses more than one of
C<--fix>, C<--recreate>, and C<--dry-run>, and writes the answer back into
the options it forwards. The position is the point. That guard is about what
the operator asked for, and a repository setting is not that, so an answer
folded in above it would be read as a second thing the operator typed and a
repository set to C<always> would have every dry run in it refused.

B<Parameters:>

=over 4

=item C<$top>

The deployment repository, which is where the setting is read from.

=item C<$options>

The deploy's own options, as C<get_options> answered them, with the redeploy
question already written into them.

=back

B<Returns:> C<1> where the deploy should carry C<--recreate>, C<0> otherwise.

B<Examples:>

  _recreate_wanted($top, {recreate => 1});
  # returns 1 in any repository, the operator having asked for it

  _recreate_wanted($top, {redeploy => 0});
  # returns 1 where the repository says always, and 0 where it says
  # redeploy-only or never

=head2 _deploy_dryrun_cloud_config_warning($env, $cloud_config_name, $state)

  _deploy_dryrun_cloud_config_warning($env, 'lab.cf', 'outdated');

Warns that a dry run validates its manifest against the cloud config the
BOSH director already holds, because a dry run never uploads one.  Errors
from bosh about networks, vm types, disk types, vm extensions, or
availability zones follow from that, and the warning says so, so the
operator does not read them as a fault in the manifest.

B<Parameters:>

=over 4

=item C<$env>

The C<Genesis::Env> being deployed.  Its C<bosh> names the director in the
warning.

=item C<$cloud_config_name>

The name of the cloud config this deploy would have uploaded.

=item C<$state>

C<'outdated'> when the director holds a cloud config by that name and the
generated one differs from it, or C<'missing'> when the director holds no
cloud config by that name at all.

=back

B<Errors:>

=over 4

=item C<"Unknown cloud config state '%s' for a dry-run warning">

Raised (via C<bug()>) for any C<$state> other than C<'outdated'> or
C<'missing'>.

=back

B<Returns:> C<1>.

B<Examples:>

  _deploy_dryrun_cloud_config_warning($env, 'lab.cf', 'outdated');
  # warns that the director will validate against its current copy

  _deploy_dryrun_cloud_config_warning($env, 'lab.cf', 'missing');
  # warns that the director holds no such cloud config

=head2 _deploy_network_claims_lock($env, %opts)

  my $lock_held = _deploy_network_claims_lock($env, dryrun => 0, yes => 1);

Checks the network claims lock on the environment's BOSH director before the
deploy synthesizes its cloud config, and takes the lock for a real deploy.
The cloud config synthesis reads the network claims recorded in the
director's exodus data, and a real deploy rewrites them once the cloud
config is uploaded, so the lock is held from here until the claims are
submitted.

A dry run only reads the claims, so it never takes the lock and never clears
a stale one; it reports what it found and returns false.  A live lock stops a
real deploy, since two deploys cannot claim addresses at the same time, but
it only warns a dry run, which reads the claims and writes nothing.  The
warning says that another deploy holds the lock and that the claims being
read can change while the dry run reads them.  A stale lock is cleared before a real deploy acquires
its own: at once with C<--yes>, after a confirmed answer at a controlling
terminal, and otherwise not at all, in which case the deploy fails with a
message that says to rerun with C<--yes>, rather than waiting on a question
that a piped terminal cannot show.

B<Parameters:>

=over 4

=item C<$env>

The C<Genesis::Env> being deployed.  Its C<bosh> is the director holding
the network claims.

=item C<dryrun>

True for C<--dry-run>; the lock is checked but not taken.

=item C<yes>

True for C<--yes>; a stale lock is cleared without asking.

=back

B<Errors:>

=over 4

=item C<"Network claims are currently locked -- cannot proceed with deployment!">

Raised (via C<bail()>) when another process holds a live lock during a real
deploy.  A dry run warns instead and carries on.

=item C<"Aborted by user!">

Raised (via C<bail()>) when the operator declines to clear a stale lock.

=item C<"Network claims are locked with a stale lock: %s\n\nRerun with --yes to clear it, or run this command in a terminal to be asked.">

Raised (via C<bail()>) when a real deploy finds a stale lock outside a
controlling terminal without C<--yes>.

=back

B<Returns:> True when this process now holds the lock, false when it does
not (a dry run).

B<Examples:>

  my $lock_held = _deploy_network_claims_lock($env, dryrun => 1);
  # returns 0; the director was asked about the lock and nothing else

  my $lock_held = _deploy_network_claims_lock($env, dryrun => 1);
  # with another deploy holding the lock: warns that the claims may change,
  # then returns 0

  my $lock_held = _deploy_network_claims_lock($env, dryrun => 0, yes => 1);
  # returns 1; a stale lock was cleared and the lock is now ours

=head2 _deploy_confirm($question, %opts)

  _deploy_confirm("Upload the new cloud config? [y|n]", yes => $options{yes}, default => 1)
    or bail "Aborted by user!";

Answers a yes/no question on the deploy path.  With C<--yes> the answer is
yes and nothing is printed.  At a controlling terminal the question is put
to the operator.  Anywhere else, such as a deploy whose output is piped
through a filter, the deploy stops at once with a message naming the
question and saying to rerun with C<--yes> or in a terminal, since a
question written into a pipe is never seen and would wait forever.

B<Parameters:>

=over 4

=item C<$question>

The question, ending in C<[y|n]>.

=item C<yes>

True for C<--yes>.

=item C<default>

The answer an empty response at the terminal gives; defaults to yes.

=back

B<Errors:>

=over 4

=item C<"Cannot ask \"%s\" without a controlling terminal.\n\nRerun with --yes to answer yes, or run this command in a terminal to be asked.">

Raised (via C<bail()>) when there is neither C<--yes> nor a controlling
terminal.

=back

B<Returns:> C<1> for yes, C<0> for no.

B<Examples:>

  _deploy_confirm("Proceed? [y|n]", yes => 1);
  # returns 1 without printing anything

  _deploy_confirm("Proceed? [y|n]", yes => 0);
  # asks at a terminal; stops with a message when there is none

=head2 _deploy_release_network_claims_lock($env)

  _deploy_release_network_claims_lock($env);

Releases the network claims lock on the environment's BOSH director if this
process still holds it, reporting the release.  The deploy path calls this
on every exit from the cloud config check, including errors and signals, so
a lock is never left on the director for the next deploy to find stale.
C<INT>, C<TERM>, C<HUP>, and C<QUIT> are turned into errors while the lock
is held, which is what routes a cancelled deploy, a killed one, and an ssh
session that drops out from under a bastion through this release.  A
lock held by someone else, or already released when the claims were
submitted, is left alone.

B<Parameters:>

=over 4

=item C<$env>

The C<Genesis::Env> being deployed.

=back

B<Returns:> True when a lock was released, false otherwise.

B<Examples:>

  _deploy_release_network_claims_lock($env);
  # clears the lock this process took, or does nothing
