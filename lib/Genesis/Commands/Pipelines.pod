=head1 NAME

Genesis::Commands::Pipelines - Command handlers for Genesis CI/CD pipeline management

=head1 SYNOPSIS

  # Registered in bin/genesis via define_command:
  genesis embed
  genesis pipeline-apply [layout] [--target <fly-target>] [--dry-run] [--yes] [--paused] [--output-dir <dir>] [--debug-dir <dir>] [--skip-vault]
  genesis repipe [layout]   # deprecated; warns and delegates to pipeline-apply
  genesis graph  [layout] [--config ci.yml]
  genesis describe [layout]

=head1 DESCRIPTION

Provides operator-facing command handlers for Genesis CI/CD pipeline
management.  C<embed>, C<apply>, C<graph>, and C<describe> are run by a
Genesis operator to embed the Genesis binary, give the pipeline its shape
on the configured provider, visualize the pipeline dependency graph, or
display a human-readable pipeline description.
C<repipe> is the deprecated name for C<apply>, kept so an operator's habit
still works, and it warns before it delegates.

The legacy Concourse-facing pipeline task handlers
(C<ci_pipeline_deploy>, C<ci_show_changes>, C<ci_generate_cache>, and
C<ci_pipeline_run_errand>) have been retired.  Their commands remain
registered in F<bin/genesis> with a C<retired> property so a legacy
Concourse pipeline that shells to C<genesis ci-*> fails loudly at
dispatch time with a migration message; the earlier v3.1 semantics
that would have deployed based on C<VAULT_ROLE_ID>/C<VAULT_SECRET_ID>
plus C<CURRENT_ENV>/C<GIT_BRANCH>/C<WORKING_DIR>/C<OUT_DIR>/C<CACHE_DIR>
environment variables no longer applies.  See L<Genesis::Commands> for
the C<retired> mechanism.

=head2 Where C<propagate> starts each environment

C<propagate> runs in two stages.  L<Genesis::CI::Preflight> settles the
initial state first, which refreshes, checks control, refuses a branch with no
legitimate origin or a hand edit, resets a branch a re-run reproduces, and
fast-forwards a branch that is merely behind.  The walk then decides what to
deliver to each environment, and it starts from the newest marker on the
branch the pre-flight settled rather than from the environment's own name or
from the remote-tracking ref.

That branch is the deployment slug, and it is not behind its remote-tracking
ref, because the pre-flight has just seen to both.  So a delivery a teammate
published is already on the branch when the walk reads its marker, which is
what stops the walk delivering it a second time.  Under a dry run the
pre-flight moves nothing, and the record it leaves names the ref a real run
would have left the branch on, which is the ref the walk reads instead.

The branch the walk reads from is the branch it writes to.  It hands each
pending commit to the session's single writer, one delivery per control
commit, on the branch the pre-flight settled, so every delivery is committed
onto that branch and it is what gets pushed.  The environment's own name
stays what the marker records and what the operator reads.

Nothing stands between the two stages.  An environment the pre-flight has no
record for has no branch on either side, and the walk reports it as awaiting
C<genesis pipeline-apply> and carries on, writing nothing for it.  C<propagate>
used to offer to cut that branch itself, and the branch it cut carried the
environment's own name rather than the deployment slug, so the offer satisfied
nothing and left a ref standing exactly where the real branch has to go.
C<genesis pipeline-apply> is the command the design gives the job of cutting a
deployment branch, and it is the only one that does it.

=head1 FUNCTIONS

=head2 embed()

    genesis embed

Embeds the current Genesis binary into the deployment repository under
C<.genesis/>.  This ensures that all pipeline tasks use the same Genesis
version that was present when the pipeline was configured.

The binary to embed is taken from the C<GENESIS_CALLBACK_BIN> environment
variable, falling back to C<$0> (the currently executing Genesis binary).

Takes no arguments.  Prints usage and exits if any arguments are supplied.

B<Returns:> The return value of C<Genesis::Top-E<gt>embed>.

B<Examples:>

  # Embed the currently running genesis binary into the deployment repo
  genesis embed

=head2 apply([$layout])

    genesis pipeline-apply
    genesis pipeline-apply sandbox
    genesis pipeline-apply --target my-concourse --dry-run

Gives the pipeline its shape on every provider. It refuses when
C<pipeline.enabled> is false or absent, creates each missing deployment
branch, applies the branch protection, writes the applied record and each
environment's pipeline record, and sets the pipeline where the provider has
one. Under the C<manual> provider it does all of that except set a pipeline,
because deploys happen at the operator's terminal and there is no hosted
pipeline to set. With C<--dry-run> it reports every one of those steps and
writes nothing to the repository, the remote, or the vault, neither a branch,
nor a protection setting, nor a record.

C<genesis repipe> is the deprecated name for the same command, and it
warns and then delegates here.

It refuses before it reads anything else when C<pipeline.enabled> is false
or absent, because the command applies a configured pipeline and never
enables one.  That refusal reads C<.genesis/config> alone, so a repository
with no pipeline is turned away before a vault is asked for.

It then refuses a clone that does not carry the control branch, because the
apply records the commit it applied from and there would be no commit to
read. That refusal comes before any branch is created, so a run it turns away
has written nothing anywhere.

Where a pipeline is enabled, the branch stage runs first and under every
provider, because a deployment branch is what a delivery is written to
whether or not anything hosts a pipeline. It creates each missing branch as
an orphan named by the deployment slug, publishes it, and leaves a branch the
remote already carries where it is. The remote it asks and publishes to is
the one C<pipeline.source_control.remote> resolves to, and not whichever
remote git happens to list first, so a clone with two of them still writes
where the repository says its branches live.

With the branches in place the run asks the repository to protect them.
Control and every deployment branch are told to block force pushes and to
require linear history. A deployment branch is told to require a pull request
where its own C<genesis.pipeline.require_pr> is true, and control is told to
require one where C<pipeline.source_control.control_requires_pr> is true. A
pull request into a deployment branch may only be merged by rebase. That
merge method can only be asked for inside the rule that requires a pull
request, and that rule would stop a direct push, so a branch whose
C<require_pr> is false is given no pull request rule at all and can still be
pushed to directly. Nothing is lost there, because the force-push block and
the linear-history requirement stand on every branch either way, and the
marker that rebase-only protects can only be lost by squashing a pull
request, which a branch in no pull request mode does not have. Each branch
gets one ruleset named for it, so a re-run replaces rather than
accumulates. A user whose token cannot grant a setting is told which branch
and which settings, and the run carries on. A run that carries no
C<GITHUB_AUTH_TOKEN> skips the stage, names the variable, and carries on as
well.

With the branches protected the run records what it applied, which is the
control commit it read, the provider it applied, and the time. That record
goes to the pipeline's own address in exodus under every provider, because it
is what a later reader asks to tell an applied pipeline from one nobody has
applied. An C<--output-dir> run writes the compiled artifacts rather than
setting the pipeline, and it writes that record as any other run does. A dry
run reports the record it would write and writes none.

The same stage then walks the pipeline in order and works out each
environment's dependency set, which is the declared list and the exodus
paths of that environment's own manifest taken together. Each set is written
beside that environment's exodus record, and an environment that would not
render or would not load is warned about, wired from its declared list
alone, marked incomplete, and left behind rather than stopping the run.

Under C<--skip-vault> there is no vault to write it to, so the run warns,
names the record it left unwritten and the flag that stopped it, and carries
on. It does not refuse the apply, because the branch work and the compile are
both worth having without a vault.

The provider then comes from C<pipeline.provider.type>, and an absent type
reads as the C<manual> provider. The manual provider has no pipeline to set,
so the command says which stage it skipped and exits 0 with the branch work
behind it rather than refusing.
An automated provider is compiled from the C<pipeline> section of
C<.genesis/config>, which is the one configuration source, and the
compiled result is then set on the provider.
Concourse has its pipeline uploaded through the C<fly> CLI.  GitHub Actions
has its workflows written under C<.github/workflows/> for the operator to
commit.

B<Parameters:>

=over 4

=item C<$layout> (optional)

The pipeline layout to use.  It names the Concourse target where
C<--target> does not, and the pipeline's own name stands in where neither
of them is given.

=back

B<Options (via C<get_options>):>

=over 4

=item C<--target>

The Concourse C<fly> target to use.  Defaults to the layout name, and then
to the pipeline's own name, when not specified.

=item C<--dry-run>

Report the whole run and write nothing to the repository, the remote, or the
vault.  Every stage says what it would do and then stands aside, so the run
names each branch it would create or publish, each branch it would protect
and the settings it would send, the applied record it would write, and each
environment's record with the dependencies it counted.  No branch is cut, no
ruleset is sent, and no record is written.  The clone's remote-tracking refs
are still refreshed before any of that, because the preview reports what the
remote carries and a stale answer would name the wrong branches.  Under an
automated provider the compiled pipeline is printed as well, which is the
Concourse pipeline YAML or each GitHub Actions workflow file under its own
name.  C<--output-dir> and C<--debug-dir> are the one exception, and a run
given either of them fills that directory as it always would, since the
directory is one the operator named for the purpose rather than a store the
apply owns.

=item C<--output-dir>

Write the compiled artifacts and C<ast.json> to this directory and exit
without setting anything.  Given on its own, every stage before the compile
writes as it always does, so the run creates and publishes any deployment
branch the remote lacks, applies the protection, and records what it applied
before it writes a file.  Given together with C<--dry-run>, the preview wins
for the repository, the remote, and the vault, and this directory is written
even so.  Under the C<manual> provider nothing is written here at all,
whichever other flag it is given with, because the run exits before the
compile and there is no compiled artifact to write.

=item C<--debug-dir>

Dump the compiler's intermediates to this directory, and carry on.  The
directory is filled under C<--dry-run> as well, for the same reason
C<--output-dir> is, and it is left empty under the C<manual> provider for
the same reason C<--output-dir> is.

=item C<--yes>

Skip the interactive confirmation the provider would otherwise ask for.

=item C<--paused>

Leave the pipeline paused after applying it instead of unpausing it.

=item C<--skip-vault>

Build the repository handle without a vault connection, for compiling
where no vault is running.  The applied record is written to the vault, so
this flag leaves it unwritten and the run says so.

=back

B<Returns:> Nothing.  Exits 0 on success, and exits 0 early under
C<--dry-run> and C<--output-dir> alike.  An C<--output-dir> run given on its
own has the branch, protection, and record stages behind it rather than
skipped, and a dry run has reported all three and written none of them,
whether or not a directory flag was given with it.  Exits 0 under the
C<manual> provider, once those stages have run and the skipped stage has
been named.  Exits 86 when the provider's prerequisites are not met.

B<Errors:>

Calls C<bail()> with C<Genesis::Exit/CONFIG> when C<pipeline.enabled> is
false or absent, naming the key and saying that nothing was written.

Calls C<bail()> with C<Genesis::Exit/CONFIG> when the clone has no git remote
by the name C<pipeline.source_control.remote> resolves to, naming that remote,
because there is then nowhere to publish a deployment branch to.  The refusal
comes before the first branch is created, so no branch is left standing behind
it.

Calls C<bail()> with C<Genesis::Exit/CONFIG> when the control branch is not
in the clone, naming the branch and saying that no branch was created and no
record was written.  The apply records the commit it applied from, and git
answers an unresolvable ref with its own error text rather than failing, so a
run that carried on would write that text into the record.

Calls C<bail()> with C<"No vault specified or configured."> when no vault
is configured and C<--skip-vault> was not given.

Calls C<bail()> when the compiled pipeline has no name, and when the
provider is one this command cannot set.

B<Examples:>

  # Apply the pipeline the repository configures
  genesis pipeline-apply
  # Returns: exits 0 on success

  # Preview the whole run, writing nothing
  genesis pipeline-apply --dry-run
  # Prints: every branch, protection, and record it would write, and the
  # compiled pipeline where the provider has one

  # Apply to a named Concourse target
  genesis pipeline-apply --target prod-concourse
  # Returns: exits 0 on success

  # A repository that has not enabled a pipeline
  genesis pipeline-apply
  # Exits: Genesis::Exit::CONFIG, having written nothing

=head2 describe([$layout])

    genesis describe
    genesis describe sandbox

Parses the pipeline configuration and prints a human-readable description
of the environments and their pass/trigger relationships.

Where the repository configures a pipeline, the report opens with the
resolved source-control values, each beside the tier it came from, so an
override that has drifted away from what git says is visible rather than
silent.

B<Parameters:>

=over 4

=item C<$layout> (optional)

The pipeline layout to use.  Defaults to the layout inferred from the CI
config file when omitted.

=back

B<Options (via C<get_options>):>

=over 4

=item C<--config>

The option is still accepted, and nothing reads it any more.  The
description is built from the C<pipeline> section of C<.genesis/config>,
which is the one configuration source.

=back

B<Returns:> Prints the pipeline description to standard output.

B<Examples:>

  # Describe the default pipeline
  genesis describe

  # Describe a specific pipeline layout
  genesis describe sandbox

=head2 propagate

    genesis propagate
    genesis propagate --dry-run

Walks the control branch forward from every deployment branch's newest
marker and routes each control commit on its own, in control order, under
D34 and D36.

A branch that has never been delivered to carries no marker, and the walk
starts at the commit that introduced the environment instead, under D61.
That commit is routed, held, and delivered exactly as every commit after it
is, so a new environment receives its own history rather than one baseline
taken from control's tip.  There is no separate seeding step, and the run
cuts no branches: C<genesis pipeline-apply> is the one command that does.

The run takes no argument.  A run that is handed one is a usage error,
because the C<E<lt>envE<gt>> argument went with the cascade it scoped under
D36, and a commit held behind an ancestor is released by the next bare run
rather than by a run aimed at it.

The run may be started from any branch.  It switches to control inside its
own session under D65, walks from there, and puts the operator back on the
branch they were standing on, so nobody has to move before running it.  See
L</open_control_session>.

B<Options (via C<get_options>):>

=over 4

=item C<--dry-run>, C<-n>

Report what each environment would receive, per control commit, and write
nothing.

=item C<--yes>, C<-y>

Publish without asking.  The verified delta for every environment is shown
either way.  D83 returns the flag with this meaning, and it answers no
other question.

=item C<--force>

Propagate by hand under a pipeline that owns the work, which D95 makes the
one way past the provider gate.  At a terminal the operator is still asked
to confirm, and outside one the refusal stands.

=back

The three options above are the whole table.  C<--commit>, C<--no-push>,
and C<--no-fetch> are gone, because D44 withdrew the push switch and left
C<--dry-run> as the only preview, D40 removed the fetch switch once the
refresh became unconditional, and a caller-chosen source commit is the one
thing that let the pipeline's run and the operator's run differ.

B<Returns:> Nothing.  The run prints its report as it goes.

B<Examples:>

  # Walk control onto every deployment branch
  genesis propagate

  # Report what every environment would receive, and write nothing
  genesis propagate --dry-run

=head2 assert_not_disowned

    assert_not_disowned($top, $command);

Refuses a pipeline the configuration has disowned, under D64.

A repository disowns its pipeline when C<pipeline-apply> has left an applied
record while C<pipeline.enabled> reads false. The pipeline is still live,
still watching its branches, and still deploying, and the configuration no
longer admits that it exists, so every command that would act on it stops
here rather than acting beside it.

The check reads the record and not only the key, because a repository that
never had a pipeline has neither and is disowning nothing. Such a repository
falls through and meets the pre-flight, which has its own words for it.

The refusal names the applied record, the control commit it was applied
from, the time it was applied, and both remedies, which are to set
C<pipeline.enabled: true> again or to tear the pipeline down by hand.
Tearing it down has no command yet, and the message says so rather than
naming one that does not exist.

B<Parameters:>

=over 4

=item C<$top>

The repository, as a C<Genesis::Top>.

=item C<$command>

The command's own name, which the refusal spells back so the operator reads
the command they ran.

=back

B<Returns:> 1, where the pipeline is enabled or where no applied record
stands. It does not return otherwise.

B<Errors:>

Calls C<bail()> at C<Genesis::Exit/CONFIG> where an applied record stands
while C<pipeline.enabled> reads false.

B<Examples:>

  assert_not_disowned($top, 'propagate');
  # returns 1 where pipeline.enabled is true

  assert_not_disowned($top, 'propagate');
  # [FATAL] Refusing to run genesis propagate.  The pipeline is disabled
  #         in .genesis/config, but the applied record says pipeline-apply
  #         applied it from control@a1b2c3d at 2026-09-15 11:04:22 +0000

=head2 assert_provider_gate

    assert_provider_gate($top, $opts);

The propagate run's break-glass past the pipeline that owns it, under D95.

Under an automated provider the pipeline owns propagation. A hand run does
the pipeline's work while taking none of the pipeline's locks, so the
pipeline has no way to see that it is happening and the two can collide on a
director. A bare run is therefore refused at C<Genesis::Exit/NOPERM> before
it walks anything.

The gate behaves five ways. C<--force> at a controlling terminal turns the
refusal into a warning and the question "Proceed anyway?", and a no exits
C<Genesis::Exit/ABORTED>. Outside a terminal the refusal stands even with
the flag, because the acknowledgement cannot be given without one.
C<GENESIS_PIPELINE_TASK> skips the gate, because the pipeline's own job sets
it and nothing legitimate reaches the gate unattended. C<--dry-run> passes
with the warning and no question, because it writes nothing. And C<-y> never
answers the question, since D83 leaves it answering the publish confirmation
alone. The manual provider is silent, and so is a repository with no
pipeline at all.

B<Parameters:>

=over 4

=item C<$top>

The repository, as a C<Genesis::Top>, which is what the provider is read
from.

=item C<$opts>

The run's options, as C<get_options> answered them. C<force> and C<dry-run>
are the two the gate reads.

=back

B<Returns:> 1, where the gate is passed or does not apply. It does not
return otherwise.

B<Errors:>

=over 4

=item *

Calls C<bail()> at C<Genesis::Exit/NOPERM> for a bare run under an automated
provider, and again for a C<--force> run with no controlling terminal.

=item *

Calls C<bail()> at C<Genesis::Exit/ABORTED> where the operator answers no at
the terminal.

=back

B<Examples:>

  assert_provider_gate($top, {});
  # returns 1 under the manual provider

  assert_provider_gate($top, {'dry-run' => 1});
  # warns that this is the pipeline's work, asks nothing, returns 1

  assert_provider_gate($top, {});
  # [FATAL] The concourse pipeline owns propagation for this repository.
  #         Run it with --force at a terminal if you mean to.

=head2 open_control_session

    my $session = open_control_session($top, $git);

Begins the run's session and switches it to the control branch, under D65.
It asks nothing about the local control ref, because every caller reaches it
through C<Genesis::CI::Preflight::require_control>, which refuses each state
in which that ref could be missing.

The run no longer refuses to start off control.  C<finish> returns the
operator to the branch they stood on, exactly as a deploy that switches to
its own deployment branch already does, so where the operator was standing
stops mattering.  The session comes from the handle rather than being built
here, because the handle keeps one session per working tree and that is what
I9 asks for.

The clean-tree refusal that used to stand beside the branch refusal has
moved rather than gone.  It now lives in the session's own C<begin>, which
names the files it found, and it applies to a dry run as it does to a
writing one, because a dry run switches to control like any other run and
D65 puts the clean assertion on the switch.

B<Returns:> The open session, standing on control.

B<Examples:>

  my $session = open_control_session($top, $git);
  # ... the walk ...
  $session->finish;
  # the operator is back on the branch they ran this from

=head1 INTERNAL FUNCTIONS

=head2 INIT_FILE_BODY

The one line an init commit writes into its C<init> file. It names the
command that manages the branch, because an operator who meets the branch in
a fresh clone has nothing else there to read.

=head2 _apply_branch_protection

  my $missing = _apply_branch_protection($gh, $owner_repo,
    branches => \@specs);
  my $missing = _apply_branch_protection($gh, $owner_repo,
    branches => \@specs, dry_run => 1);

Asks the repository for the protection each branch was derived, sending one
ruleset per branch and naming it C<genesis-E<lt>branchE<gt>>. The name is what
a replace matches on, so a re-run replaces the ruleset it wrote last time
rather than adding another beside it, and an operator reading the repository's
settings can tell which rules Genesis owns.

A branch the token cannot protect is reported by name with the settings it
needed, and the run carries on, because a user without admin should still be
able to apply the pipeline and hand that list to whoever holds admin.

Nothing here derives a rule. The caller has already done that through
C<_protection_rules_for>, so this function takes the client, the pair, and
the branches it is to send and reads no environment of its own.

Under C<dry_run> it names each branch and the settings that branch would be
given, sends nothing, and reports nothing missing, because a repository that
was never asked has refused nothing.

B<Parameters:>

=over 4

=item C<$gh>

The C<Service::Github> client the rulesets are sent through.

=item C<$owner_repo>

The repository in C<owner/repo> form, which is the pair
C<pipeline.source_control.repository> resolves to.

=item C<%opts>

=over 4

=item C<branches>

An arrayref of specs, each a hashref with a C<branch> name and the C<rules>
arrayref that branch is to carry.

=item C<dry_run>

Whether C<--dry-run> was given, in which case each branch and the settings it
would be given are named and no ruleset is sent.

=back

=back

B<Returns:> A hashref of branch name to the arrayref of rule types that
branch could not be granted. It is empty where every branch was protected,
and empty under C<dry_run>, where none was asked for.

B<Errors:>

=over 4

=item *

C<"Missing owner/repo for set_ruleset"> and C<"Missing name for set_ruleset">
- raised via C<bail()> through C<Service::Github::set_ruleset>.

=item *

A branch the repository refused raises nothing. It is warned about by name,
with the reason the API gave and the settings it needed, and the run carries
on.

=back

B<Examples:>

  my $missing = _apply_branch_protection($gh, 'genesis/bosh-deployments',
    branches => [{branch => 'qa/bosh', rules => $rules}]);
  # returns {} once the branch carries its ruleset

  my $missing = _apply_branch_protection($gh, 'genesis/bosh-deployments',
    branches => [{branch => 'control', rules => $rules}]);
  # returns {control => ['non_fast_forward', 'required_linear_history']}
  # for a token without admin, having warned by name

  my $missing = _apply_branch_protection($gh, 'genesis/bosh-deployments',
    branches => [{branch => 'qa/bosh', rules => $rules}], dry_run => 1);
  # names qa/bosh and the rule types it would carry, and returns {}

=head2 _apply_init_branches

  my $report = _apply_init_branches($top, $git);
  my $report = _apply_init_branches($top, $git, dry_run => 1);

Creates and publishes the deployment branch for every environment in the
pipeline that has none, and leaves a branch the remote already carries where
it is. The branch is an orphan whose root commit adds a single C<init> file
under the subject C<Initialize E<lt>slugE<gt> branch [ci skip]>, so the
pipeline's git resource registers the head as a version and skips the commit.
The name is the deployment slug, so two deployment roots serving one
environment get a branch each rather than contending for one ref.

Every question and every write names the remote that
C<Genesis::Top/source_control_remote> answers with, which is what
C<pipeline.source_control.remote> resolves to. Reading whichever remote git
lists first would ask the wrong repository on a clone that has two, since git
lists them alphabetically rather than in the order they were added.

A clone with no remote by that name is refused before the first branch is
created, because every deployment branch lives on the remote and a run that
created one and then failed to publish it would leave an orphan standing in
the clone and every environment behind the first with nothing.

The refresh runs next, so what the remote carries is read from refs this run
brought down rather than from whatever the clone happened to hold.

Both the clone and the remote are asked whether the branch is there. A branch
the remote carries is standing and is not touched. A branch the clone holds
and the remote lacks is published rather than refused, since recreating it is
not allowed and leaving it would keep it from everybody else. Everything else
is created and then published.

Every publish goes through C<push_append_only>, so no stage here can rewrite
a branch the remote already carries.

Under C<dry_run> the clone and the remote are asked the same two questions
and the answers are reported under the same three headings, and nothing is
created and nothing is pushed. The refusals still stand, because a run that
cannot publish anywhere is worth saying so whether or not it meant to write.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the deployment root the command is running in. It
names the pipeline's environments and composes each deployment slug.

=item C<$git>

The C<Service::Git> for the repository, which is where the branches are
written and from which they are published.

=item C<%opts>

=over 4

=item C<dry_run>

Whether C<--dry-run> was given, in which case each branch is named under the
heading it would fall to and neither a branch nor a push is made.

=back

=back

B<Returns:> A hashref with three arrayrefs of branch names, which are
C<created>, C<published>, and C<standing>. Under C<dry_run> it is the same
three lists, naming what the run would have done rather than what it did.

B<Errors:>

=over 4

=item *

A refusal at C<CONFIG> when the clone has no git remote by the name
C<pipeline.source_control.remote> resolves to, naming that remote and saying
that there is nowhere to publish the deployment branches to and that no branch
was created. It is raised before anything is written.

=item *

A refusal at C<TEMPFAIL> from C<fetch_pipeline_envs> when the remote cannot be
reached, naming C<pipeline-apply> and saying that no branch was created and no
pipeline was set.

=item *

C<"ls-remote against %s failed"> from C<remote_branch_exists> when the remote
rejects the query.

=item *

Whatever C<create_orphan_branch> and C<push_append_only> raise, which is a
failed plumbing step, a push the remote rejected, or a refusal to rewrite
history on a branch that is append-only.

=back

B<Examples:>

  my $report = _apply_init_branches($top, Service::Git->new('.'));
  # returns {created => ['qa/bosh'], published => [], standing => ['prod/bosh']}

  my $report = _apply_init_branches($top, Service::Git->new('.'), dry_run => 1);
  # says it would create qa/bosh, cuts nothing, and returns the same report

=head2 _apply_records

  _apply_records($top, control_commit => $sha, provider => 'concourse');
  _apply_records($top, %facts, skip_vault => 1);
  _apply_records($top, %facts, dry_run => 1);

Writes what the apply learned to exodus.

The writes are split across two owners, because a deploy rewrites its own
environment's exodus record on every run and would clobber anything the apply
left beside it. The pipeline's own facts go to C<Genesis::Top>, through
C<applied_record>, and each environment's compiled facts go beside that
environment's own record. Neither this helper nor the command spells either
address, so the two writers cannot drift apart on where the facts live.

One pass over the topology follows the applied record. It loads each
environment, asks it for its dependency set, and writes that set and the
discovery mark beside the environment's own exodus record, in the order the
walk itself reads, so the report comes out top down.

An environment that will not load is answered the way one that will not
render is. It is warned about by name with the reason, its record is written
with the declared set alone and its discovery marked incomplete, and the
pass carries on to the next environment. A load failure costs the manifest
and nothing else, so the declared half is still read, and only the
discovered half goes missing.

Both that read and the record write go through a bare environment, which
resolves the whole of C<genesis.pipeline> and the record's own address on
the merged hierarchy with no kit. The record is written even so, because an
environment carrying none at all reads as one the apply never reached.

That bare read is itself guarded, because an environment whose files will
not merge at all refuses it and the record's address alike. Where even the
bare read fails, the warning says both reads failed and the pass moves on
with nothing recorded for that environment, which leaves it reading as an
environment no pipeline knows. A failure while recovering from a failure
still costs one environment rather than the whole run.

It runs under every provider, including the manual one, since the record says
what was applied rather than what was hosted. It runs on an C<--output-dir>
run too, which writes the compiled artifacts rather than setting the
pipeline, so that run records what it applied as any other run does.

Where C<dry_run> is true the whole stage is walked and nothing is written.
The pass loads each environment and works out its dependency set exactly as
the writing pass does, so a run that would mark an environment incomplete
says so, and the branch between the two is at the vault call alone. The
applied record is named in words rather than by its vault address, for the
reason the C<skip_vault> warning names it that way, which is that composing
the address is itself a read that a preview has no reason to make.

Where C<skip_vault> is true there is no vault to write to, so it warns,
names the record it left unwritten and the flag that stopped it, and answers
as though it had written one. That is a warning rather than a refusal,
because the operator asked for a run without a vault and the rest of the
apply still has work to do. The warning names the record in words rather than
by its vault address, since composing that address reads the repository's
exodus mount and refuses where there is no environment to read it from, which
would turn the stage that stands aside into the stage that stopped the run.

The control commit has to be a commit sha. C<apply> refuses a clone without
the control branch before this is reached, so anything else arriving here is
a fault between the two, and the record takes a sha or nothing at all.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the deployment root the command is running in, which
owns the pipeline's record and composes its address.

=item C<control_commit>

The commit the apply applied from, which is the tip of the control branch as
this run read it. It has to be a forty character hexadecimal sha.

=item C<provider>

The provider the repository is configured for, which is C<manual> where the
configuration names none.

=item C<skip_vault>

Whether C<--skip-vault> was given, in which case nothing is written and the
run says what it left unwritten.

=item C<dry_run>

Whether C<--dry-run> was given, in which case every record the stage would
write is named and none of them is written.

=back

B<Returns:> 1, whether it wrote the records, previewed them, or skipped them.

B<Errors:>

=over 4

=item *

C<< "_apply_records was given <value> as the control commit, which is not a
commit sha" >> - raised through C<Genesis::bug> when C<control_commit> is
absent, or is anything other than a forty character hexadecimal sha. The
value is put back on one line before it is named, because git's error text
arrives across several.

=item *

C<"Genesis::Top::applied_record was asked to write the applied record without
a value for any of control_commit, provider, or at"> - raised through
C<Genesis::bug> when neither option carries a value.

=item *

Whatever C<Genesis::Top::applied_record> raises from the vault, which is a
failed authentication or a failed write.

=item *

Whatever C<Genesis::Env::pipeline_record> raises from the vault on a
per-environment write, for the same two reasons. A failure to load an
environment is not among these, because it is warned about rather than
raised.

=back

B<Examples:>

  _apply_records($top,
    control_commit => $git->sha($top->control_branch),
    provider       => 'manual');
  # writes /secret/exodus/_pipelines/bosh, writes a pipeline subpath
  # beside each environment's exodus record, and returns 1

  _apply_records($top, %facts, skip_vault => 1);
  # writes nothing, warns that the record went unwritten, and returns 1

  _apply_records($top, %facts, dry_run => 1);
  # names the applied record and each environment's record with the
  # dependencies it counted, writes nothing, and returns 1

  _apply_records($top, control_commit => 'control', provider => 'manual');
  # raises a bug, because a branch name is not a commit sha

=head2 _compile_pipeline

  my $result = _compile_pipeline($top, $provider_type);

Compiles the pipeline from the C<pipeline> section of C<.genesis/config>,
which is the one configuration source.  Neither the C<.genesis/ci/>
directory nor a legacy C<ci.yml> is read, and a repository still carrying
either one is compiled as though it did not.  The provider type is the one
the caller read off C<pipeline.provider.type>, and the provider's own
command-line options are collected from C<get_options> and handed to the
compiler beside it.

Where C<--debug-dir> is given, the compiler's intermediates are written
there before the result is returned.

B<Parameters:>

=over 4

=item C<$top>

The repository handle to compile from.

=item C<$provider_type>

The provider to generate output for, such as C<concourse> or
C<github-actions>.

=back

B<Returns:> The compiler's result hash, with the collected provider
options added to it under C<provider_cli_opts>.

B<Errors:>

Calls C<bail()> through the compiler when the repository has no C<pipeline>
section to compile, and when the configuration it finds does not validate.

B<Examples:>

  my $result = _compile_pipeline($top, 'concourse');
  # $result->{output}{'pipeline.yml'} holds the generated pipeline

=head2 _describe_source_control

  _describe_source_control($top);

Prints the repository's source-control values, one to a line, each beside
the tier it resolved from.

The resolution belongs to C<< $top->source_control_resolved >>, which
settles what every value is and whether the operator wrote it, git answered
for it, or nobody set it at all.  This lays those rows out and nothing more.

The key column and the tier column are both sized from the rows, and the
tier is printed before the value rather than after it.  A remote URL is
routinely longer than what is left of an eighty-column line, and C<output>
wraps on whitespace, so whichever field comes last is the one that takes a
line of its own when the line runs long.  That has to be the value, because
a tier on a line with no key beside it says nothing at all.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the repository being described.

=back

B<Returns:> 1, having printed the block to standard output.

B<Errors:> None of its own.

B<Examples:>

  _describe_source_control($top);
  # Source control
  #   remote         derived origin
  #   uri            derived https://github.com/fivetwenty-io/lmelt.git
  #   repository     derived fivetwenty-io/lmelt
  #   control_branch default control
  #   pr_prefix      default pr/

Every key the block resolves is printed, so the report is five rows and
not two, and both column widths come from those rows.  A repository that
overrides one of them widens the tier column to hold C<explicit>.

=head2 _protection_rules_for

  my $rules = _protection_rules_for($top, $branch, control => 1);
  my $rules = _protection_rules_for($top, $branch, require_pr => 1);

Derives one branch's protection from state the repository has already
decided, so nothing is configured twice. The derivation is pure and asks the
API for nothing, which is what lets it be read without a repository.

Control and every deployment branch block force pushes and require linear
history, which is what makes the append-only rule enforceable rather than a
convention Genesis observes on its own side.

A deployment branch requires a pull request where C<require_pr> is true, and
it merges by rebase alone, so a merger never gets the chance to rewrite an
aggregate commit's message and lose its marker. Control requires a pull
request where C<pipeline.source_control.control_requires_pr> is true, whose
default is false, and it keeps squash or rebase at the merger's choice,
because a user's pull request into control carries no marker.

The merge method is a parameter of the pull request rule, and that rule type
requires a pull request before merging, so a deployment branch whose
C<require_pr> is false is given no pull request rule at all and goes on
taking direct pushes. Nothing is lost where it is off, because the force-push
block and the linear-history requirement stand on every branch either way,
and the marker that rebase-only protects can only be lost by squashing a pull
request, which a branch in no pull request mode does not have. Where someone
opens a pull request into such a branch by hand, the recovery that reads the
marker out of the pull request's body covers it.

No rule dismisses a stale approval anywhere. Review safety lives in the
mechanism instead, so an approval survives the rebuild a later run pushes.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the deployment root, which is read for
C<pipeline.source_control.control_requires_pr> and for nothing else.

=item C<$branch>

The branch the rules are for, which names the derivation rather than
changing it.

=item C<%opts>

=over 4

=item C<control>

True where the branch is control, which takes the control derivation rather
than the deployment one.

=item C<require_pr>

True where this deployment branch's own C<genesis.pipeline.require_pr> is
true, and it decides whether the branch is given a pull request rule at all.
The caller reads it off the pipeline topology, which is the same normalised
answer the compiled pipeline runs that environment by, so a file spelling the
key C<false> or C<no> reads as false here too. It is ignored under
C<control>.

=back

=back

B<Returns:> An arrayref of rule hashrefs, each with a C<type> and, for a
pull request rule, C<parameters>.

B<Errors:> None. The derivation reads configuration and composes a list.

B<Examples:>

  my $rules = _protection_rules_for($top, 'qa/bosh');
  # returns the force-push block and the linear-history requirement, and no
  # pull request rule, so the branch still takes direct pushes

  my $rules = _protection_rules_for($top, 'qa/bosh', require_pr => 1);
  # adds a pull request rule needing one review that merges by rebase alone

  my $rules = _protection_rules_for($top, 'control', control => 1);
  # returns the force-push block and the linear-history requirement, and
  # no pull request rule where control_requires_pr is false

=head2 _refuse_disabled_pipeline

  _refuse_disabled_pipeline();

Refuses when the repository declares no enabled pipeline, naming
C<pipeline.enabled>, telling the operator to set it on control and commit
it, and exiting C<Genesis::Exit/CONFIG>.  A false key and an absent block
are the same refusal, because the command applies a configured pipeline and
never enables one.

It reads C<.genesis/config> through a bare C<Genesis::Config> and builds
no C<Genesis::Top> of its own.  That is deliberate, and it is what puts
the refusal ahead of the vault.  The command's own repository handle,
built by C<_get_top> a line later, opens a vault connection, and a
repository with no pipeline has no reason to hold a vault it would then
be asked for.  The dispatch gate in L<Genesis::Commands> already holds a
handle built with C<no_vault>, so this is not the first read of the
repository, only the first one that could ask for a vault.

The read is raw.  It sees neither the schema defaults nor the environment
overrides that L<Genesis::Top/pipeline_enabled> applies, so the two agree
only while C<pipeline.enabled> defaults to false and declares no
environment variable, which is the case today.  A change to either side
of that has to be made in both places.

B<Parameters:> None.  The repository is the current directory, which is
where the command's own repository handle is built from.

B<Returns:> 1, where the pipeline is enabled.  It does not return
otherwise.

B<Errors:>

Calls C<bail()> with C<Genesis::Exit/CONFIG> when C<pipeline.enabled> is
false or absent.

B<Examples:>

  _refuse_disabled_pipeline();
  # returns 1 where .genesis/config carries pipeline.enabled: true

  _refuse_disabled_pipeline();
  # [FATAL] Refusing to apply.  pipeline.enabled is false or absent in
  #         .genesis/config, and pipeline-apply applies a configured
  #         pipeline and never enables one.
  #
  #         Set pipeline.enabled: true on control, commit it, then run
  #         genesis pipeline-apply again.  Nothing was written.

=head2 _resolve_propagation_base

  my ($sha, $depth) = _resolve_propagation_base($branch, $git, $control);

Finds the control-branch commit an environment branch was last brought
up to, so propagation knows what to diff against.

It reads the branch's own log first, looking for the most recent
C<[pipeline] control@E<lt>shaE<gt>> marker, and warns when that marker is
not the tip, since commits on top of it were made by hand. A branch
carrying no marker was spawned from control and never propagated to, so
the merge base with the control branch is used instead.

B<The control branch is passed in rather than assumed.> Its name is
configured per repository at C<pipeline.source_control.control_branch>,
every caller has already read it through
L<Genesis::Top/control_branch>, and taking a merge base against the
wrong branch would silently change what the diff is computed from.

B<Parameters:>

=over 4

=item C<$branch>

The environment branch to resolve a base for.

=item C<$git>

The C<Service::Git> handle to read through. Optional, and it defaults to
one opened on the current directory.

=item C<$control>

The repository's control branch, as its configuration names it.
Mandatory, and it has no default, because there is no name this sub
could fall back to that would be right for every repository.

=back

B<Returns:> Two values. The first is the control commit the branch was
last brought up to, spelled as fully as this repository can spell it. A
marker naming a commit this clone has never fetched comes back at the
width the marker wrote it, because a sha the repository cannot reach is
a sha it cannot expand. The second is a count only on the marker path,
where it is the number of commits standing on top of the newest marker,
and it is a literal zero on the merge-base path, where nothing is
counted. A branch that shares no history with control comes back as
C<undef> and zero.

B<Errors:> None, in that no input makes it die, and an unresolvable base
comes back as C<undef>. It does warn: where the newest marker is not the
tip, it says how many commits were made by hand on top of the last
propagation, because those commits are about to be diffed against
control.

B<Examples:>

  my ($sha, $depth) = _resolve_propagation_base('qa', $git, 'trunk');
  # returns the sha from qa's newest [pipeline] marker, and 0
  # returns the merge base with trunk, and 0, when qa has no marker
