=head1 NAME

Genesis::Commands::Repo - Command handlers for Genesis repository management

=head1 SYNOPSIS

  # Registered in bin/genesis via define_command:
  genesis repo-init [options] [<name>]      # alias: genesis init
  genesis secrets-provider [options] [<target>]
  genesis kit-provider [options]

  # Perl import (for testing or internal dispatch):
  use Genesis::Commands::Repo;
  Genesis::Commands::Repo::repo_init(@ARGV);
  Genesis::Commands::Repo::secrets_provider(@ARGV);
  Genesis::Commands::Repo::kit_provider(@ARGV);

=head1 DESCRIPTION

Implements the Genesis CLI commands that manage the repository lifecycle and
its provider configuration.  The three commands handled here correspond
directly to top-level genesis subcommands:

=over 4

=item C<genesis init>

Create a new Genesis deployment repository on disk, optionally installing or
linking a kit at the same time.

=item C<genesis secrets-provider>

Display or change the Vault/Safe target used by the current deployment
repository for secrets storage.

=item C<genesis kit-provider>

Display or change the kit provider (source from which kits are downloaded)
for the current deployment repository.

=back

Each function reads global command-line options via C<get_options> /
C<append_options> and then delegates persistence and resolution to
L<Genesis::Top>.

=head1 FUNCTIONS

=head2 repo_init

  genesis repo-init [options] [<name>]
  genesis init [options] [<name>]        # alias

Creates a new Genesis deployment repository named C<$name>.  Validates git
identity, creates the repository structure via L<Genesis::Top>, embeds the
genesis binary, sets up the chosen kit, initialises git, and commits the
initial state.

C<$name> is optional when C<--kit> or C<--link-dev-kit> is given, because the
name can be inferred from the kit name or the link target path.

B<The command is named C<repo-init>, not C<repo init>.> Genesis has no
subcommand support, so the grouping that a nested form would express is
carried in the hyphenated name instead. C<init> is registered as an alias, so
the older invocation keeps working -- and because aliases resolve to the
I<command>, both names dispatch here.

B<Three phases, in order.> The split is what keeps the command safe to
interrupt:

=over 4

=item 1. B<Validate> -- C<_repo_init_validate>

Parses options, checks combinations, gathers local state, runs the network
checks, prompts for anything missing, and prints the plan. Everything that
can refuse the request happens here, before anything is created.

=item 2. B<Execute> -- C<_repo_init_execute>

Does the work. No prompts, no user-input bails: a failure at this stage is an
unexpected error, not a rejected request.

=item 3. B<Report> -- C<_repo_init_report>

Summarises the outcome, or cleans up after a failed execution.

=back

B<Parameters:> None directly; the name is read from the positional arguments
and options from C<get_options>.

B<Options> (parsed from C<@_> via C<Genesis::Kit::Provider> and C<get_options>):

=over 4

=item C<--kit|-k> I<spec>

Kit to install.  Accepts a kit name, a C<name/version> specifier, or a path
to a locally compiled C<.tar.gz> kit archive.

=item C<--link-dev-kit|-L> I<path>

Symlink a local kit directory as C<./dev> inside the new repository.  Mutually
exclusive with C<--kit>.

=item C<--kits-path> I<dir>

Override the local kits cache directory (defaults to C<~/.genesis/kits>).
When specified, the directory is created if it does not already exist and is
used as the kit storage location for the new repository.

=item C<--vault> I<target>

The safe target to configure as the repository's secrets vault. When omitted
and running interactively, the validation phase offers to select one; when
declined, vault configuration is deferred and the plan says so.

=item C<--directory|-d> I<name>

Create the repository in a directory of this name, rather than one derived
from the repository name.

=item C<--no-commit>

Stage the initial state but do not commit it.

=item C<--reason> I<text>

Override the initial commit message.

=back

Genesis detects whether the target sits inside an existing Genesis
repository, and creates a subdirectory repo -- sharing the enclosing C<.git>
rather than nesting one -- when it does.

B<Returns:>

Does not return to the caller -- calls C<exit 0> on success.

B<Errors:>

Every refusal comes from the validation phase -- see
L</_repo_init_validate> for the full list. Errors are otherwise propagated
from L<Genesis::Top> (repository creation, kit download) and from
C<git init> / C<git commit>; if any step after directory creation fails, the
partially created repository is removed before the error is re-raised.

B<Examples:>

  # Create a repo named "my-env" with a kit from the default provider
  genesis repo-init --kit cf my-env
  # prints the plan, then: Initialized empty Genesis repository in my-env

  # Create a repo, linking a local dev kit; name inferred from link target
  genesis repo-init --link-dev-kit ~/src/cf-genesis-kit
  # prints: Initialized empty Genesis repository in cf-genesis-kit

  # Create a repo with an explicit name, no kit (empty ./dev directory created)
  genesis repo-init my-env
  # prints: Initialized empty Genesis repository in my-env

  # The alias still works
  genesis init my-env
  # prints the same; init resolves to repo-init

=head2 secrets_provider([$target])

  genesis secrets-provider [--interactive|-i] [--clear|-c] [<target>]

Displays the Vault/Safe secrets provider configured for the current deployment
repository.  When options are supplied, updates the configuration first, then
displays the new state.

Exactly one of C<$target>, C<--interactive>, or C<--clear> may be specified
at a time.

B<Parameters:>

=over 4

=item C<$target> (optional)

A Vault target alias or URL.  Sets the repository's secrets provider to this
target.

=back

B<Options> (read via C<get_options>):

=over 4

=item C<--interactive|-i>

Prompt the user interactively to select or configure the Vault target.

=item C<--clear|-c>

Remove the repository's secrets provider configuration, reverting to the
system-default safe target (legacy mode).

=back

B<Returns:>

Does not return to the caller -- calls C<exit 0> on success or C<exit 1>
when the provider update fails.

B<Errors:>

=over 4

=item C<"You can only specify one of target, -i|--interactive or -c|--clear">

More than one of the mutually exclusive options was supplied.

=back

Output is written directly to the terminal.  When a vault is configured, the
display includes the type, URL, local alias, and authentication status.  When
no vault is configured, a notice is shown that legacy mode is active.

B<Examples:>

  # Show the current secrets provider
  genesis secrets-provider
  # prints: Secrets provider for cf deployment at /path/to/repo:

  # Set the secrets provider to a named safe target
  genesis secrets-provider my-vault
  # prints: Secrets provider for cf deployment at /path/to/repo:

  # Interactively choose the secrets provider
  genesis secrets-provider --interactive
  # prints: (interactive vault selection prompt)

  # Remove the secrets provider configuration (revert to legacy mode)
  genesis secrets-provider --clear
  # prints: Not set - legacy mode enabled (will use current safe target on system)

=head2 kit_provider()

  genesis kit-provider [options]

Displays the kit provider currently configured for the deployment repository.
When provider options are supplied, updates the configuration first, then
displays the provider status and the list of available kits.

The C<--export-config> flag is mutually exclusive with all other flags; when
used, it emits the provider configuration as JSON and exits.

B<Options> (parsed via C<Genesis::Kit::Provider> and C<get_options>):

=over 4

=item C<--kit-provider> I<spec>

Set the kit provider to the given provider specifier string.

=item C<--default>

Set the kit provider to the Genesis Community default (C<genesis-community>).

=item C<--export-config>

Output the current kit provider configuration as a JSON object to stdout, then
exit.  Cannot be combined with any other option.

=item C<--verbose|-v>

Request verbose kit provider information when querying the provider.

=back

B<Returns:>

Exits C<0> after C<--export-config> or exits C<1> when the provider update
fails.  On the normal display path, returns to the caller after printing
the provider status and kit list.

B<Errors:>

=over 4

=item C<"Option #M{--export-config} cannot be used with any other options">

C<--export-config> was combined with at least one other option.

=item C<"$@"> (dynamic)

Any exception raised inside the C<eval> block that queries kit provider
information is re-thrown via C<bail()>.  The message content depends on
the underlying provider error.

=back

Errors encountered while changing the kit provider are printed and cause an
immediate C<exit 1>.  Errors from provider information lookup are propagated
via C<bail()>.

B<Examples:>

  # Show the current kit provider and available kits
  genesis kit-provider
  # prints: Type: genesis-community

  # Switch to the Genesis Community provider
  genesis kit-provider --default
  # prints: Type: genesis-community

  # Export the current kit provider configuration as JSON
  genesis kit-provider --export-config
  # prints: {"type":"genesis-community",...}

  # Set a custom provider and show verbose info
  genesis kit-provider --kit-provider my-github-org --verbose
  # prints: Type: my-github-org

=head1 INTERNAL FUNCTIONS

These are internal to this module and may change without notice.

=head2 _repo_init_validate

  _repo_init_validate();

Phase 1 of C<repo_init>: everything that can refuse the request, before
anything is created.

Runs in a deliberate order -- parse and derive first (fast, no side effects),
then invalid-combination checks, then local gathering, then the subdirectory
preflight, then destructive prerequisites, then the network checks, and only
then the prompts. Cheap rejections come before expensive ones, and nothing
touches the network until the request is known to be otherwise valid.

Derived values are stored back into the options hash under underscore-prefixed
keys (C<_name>, C<_target_path>, C<_kit_provider> and so on) for the execute
phase to read, and the phase ends by printing the plan it intends to carry
out.

B<Parameters:> None; reads C<get_options> and C<get_args>.

B<Returns:> 1 when validation passed.

B<Errors:>

=over 4

=item *

C<"Dev kit link target '%s' not found."> -- the C<--link-dev-kit> path does
not exist.

=item *

C<"Dev kit link target '%s' is not a valid kit (missing kit.yml)."> --
followed by a note that C<repo-init E<lt>nameE<gt>> without C<-l> is how you
ask for an empty dev kit. The distinction matters: pointing at the wrong
directory and wanting a fresh kit look identical otherwise.

=item *

C<"Dev kit link target '%s' has an unreadable kit.yml:\n%s"> -- the file
exists but could not be parsed.

=item *

C<"Dev kit link target '%s' has a kit.yml that is missing the required #C{name:} field.">

=item *

C<"You must specify a deployment name, a kit (-k), or a dev link target (-l)."> --
none of the three ways to determine a name was given.

=item *

C<"You can only specify one of kit (-k) or link to a kit (-l).">

=item *

C<"Configuring a CI provider requires the enclosing git repository to be on a branch named #C{%s}, but it is currently on #C{%s}."> --
followed by an instruction to switch branches. Raised when creating a
CI-enabled repository inside an existing one that is not on its control
branch, because the new repository's pipeline would otherwise be rooted on
whatever branch happened to be checked out.

=item *

C<"Cannot specify both --vault and --skip-vault.">

=item *

C<"Local compiled kit file '%s' not found."> -- the C<--kit> value looks like
a local archive path, but no such file exists.

=item *

C<"Kit '%s' not found or no versions available from %s."> and
C<"Kit '%s/%s' not found from %s."> -- the named kit, or that specific
version of it, is not available from the provider. These are the network
checks, and they run before any prompting.

=item *

C<"Could not initialize kit provider: %s">

=item *

C<"Cannot create repository: directory #C{%s} already exists. Use -f to force replacement."> --
raised only when non-interactive; interactively the operator is asked whether
to replace it.

=item *

C<"Cannot create a Genesis deployment repository inside an ..."> -- raised
when the target sits inside another repository in a way Genesis will not
nest.

=back

All are raised via C<bail()>.

B<Examples:>

  _repo_init_validate();
  # prints the plan and returns 1, or bails with the reason it cannot proceed

=head2 _repo_init_execute

  my $result = _repo_init_execute();

Phase 2 of C<repo_init>: does the work.

No prompts and no user-input bails -- validation has already settled what
should happen, so a failure here is an unexpected error rather than a rejected
request. Reads the underscore-prefixed values the validation phase derived.

B<Parameters:> None; reads C<get_options>.

B<Returns:> A result hashref describing what happened, including C<root>,
C<target_path>, C<parent_dir>, C<use_subdir>, and C<error> when something
failed.

B<Errors:> Most failures are reported through the C<error> key rather than
raised, so the caller can clean up the half-built repository. The exception
is the initial commit: if C<git commit> fails the repository exists but is
in a state no later step can reason about, so it bails naming the root.

B<Examples:>

  my $result = _repo_init_execute();
  # returns { root => '/path/to/my-env', use_subdir => 0, ... }

=head2 _repo_init_report

  _repo_init_report($result);

Phase 3 of C<repo_init>: reports the outcome, or cleans up after a failure.

B<The cleanup is why this phase exists separately.> On failure the partially
created directory is removed -- and in subdirectory mode, anything staged into
the enclosing repository's index is unstaged first, with the reset scoped by
pathspec to just what was staged. Without that, a failed init would leave the
parent repository's index dirty with files that no longer exist. Validation
having established the parent had no other pending changes is what makes the
reset safe.

B<Parameters:>

=over 4

=item C<$result>

The hashref from C<_repo_init_execute>.

=back

B<Returns:> Nothing on success; bails on a recorded error.

B<Errors:>

=over 4

=item *

C<"Failed to create Genesis repository at #C{%s}:\n%s"> -- raised via
C<bail()> after cleanup. The substitutions are the repository path and the
underlying error.

=back

B<Examples:>

  _repo_init_report(scalar _repo_init_execute());
  # prints the summary, or cleans up and bails

=head2 _find_enclosing_genesis_repo

  my $root = _find_enclosing_genesis_repo();

Walks up from the current directory looking for a Genesis repository.

Used to decide whether a new repository should be created as a subdirectory
of an existing one, sharing its C<.git>, rather than nesting a second
repository inside the first.

B<Parameters:> None.

B<Returns:> The absolute path of the enclosing repository root, or C<undef>
when there is none.

B<Examples:>

  my $root = _find_enclosing_genesis_repo();
  # returns '/home/me/deployments', or undef at the filesystem root

=head2 _select_vault_target

  my $vault = _select_vault_target();

Offers to configure a secrets vault, and runs the target picker if the
operator accepts.

Declining is a legitimate answer, not a failure: the repository is created
with vault configuration deferred, which the plan output says explicitly.

B<Parameters:> None.

B<Returns:> A C<Service::Vault::Remote>, or C<undef> when declined or when
selection failed.

B<Examples:>

  my $vault = _select_vault_target();
  # returns undef when the operator answers no

=head2 _create_ci_scaffold

  _create_ci_scaffold($top, %opts);

Writes the C<ci> section of the repository config during init.

Accepts a provider either as an object or as a bare type name, taking the
object's own C<config> when given one, so the same call works whether the
provider was selected interactively or defaulted.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the new repository.

=item C<%opts>

C<provider> (object or type string) and optionally C<root>.

=back

B<Returns:> Nothing; the config is written to disk.

B<Examples:>

  _create_ci_scaffold($top, provider => 'manual');
  # writes ci.enabled, ci.provider and ci.name, then saves
