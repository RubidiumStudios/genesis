=head1 NAME

Genesis::CI::Walk - the per-commit propagation walk and its record

=head1 SYNOPSIS

    use Genesis::CI::Walk;

    # What every environment should receive, computed and written nowhere.
    # The branches map is the pre-flight's own initial_state record, and
    # nothing routes for an environment the map does not name.
    my $record = Genesis::CI::Walk::plan($top, git => $git,
                                         branches => $initial->{branches});

    # Then, inside the run's session, one commit per control commit.
    for my $env_record (@{$record->{environments}}) {
      next unless @{$env_record->{pending}};
      $session->switch($env_record->{branch});
      Genesis::CI::Walk::deliver_pending(
        session => $session,
        env     => $top->load_env($env_record->{env}),
        record  => $env_record,
      );
    }

=head1 DESCRIPTION

The walk reads durable state and decides what each environment should
receive.  It reads control on the remote, each deployment branch's newest
marker, each environment's certified commit in exodus, the applied record,
and the hold record.  Every routing question is answered out of the tree at
the commit being routed rather than out of the tree on disk, which is what
keeps a report reproducible from the repository rather than from whatever the
operator happened to have checked out.  The topology and the environment files
are the exception, and they are read off control, which the run stands itself
on before it asks for a plan.

A deployment branch that has never been delivered to carries no marker and
shares no history with control, so there is nothing on it to walk from.  The
walk starts at the commit that introduced the environment instead, and that
commit is routed, delivered, and held exactly as every commit after it is.
There is no separate seeding step, and nothing here ever cuts a branch.

It writes nothing itself.  The caller delivers what the record marks pending,
one commit at a time, through the session's single writer, so the one thing
that touches a deployment branch stays in one place.

Each control commit that routes to an environment becomes exactly one commit
on its deployment branch, and it is routed on its own, in control
order.  Collapsing everything
outstanding into a single diff against control's tip made an urgent change to
one environment wait behind an unrelated earlier change to a shared file, and
routing per file would have split a commit whose files have to land together.
The middle of those two is what this module does.

=head1 FUNCTIONS

=head2 plan

    my $record = Genesis::CI::Walk::plan($top, git => $git,
                                         branches => $initial->{branches});
    my $record = Genesis::CI::Walk::plan($top, git => $git, scope => ['qa'],
                                         branches => $initial->{branches});

The run's canonical record, computed from durable state alone.

It reads the pipeline's applied record, walks the topology in the order
C<< Genesis::Top->pipeline_topology >> gives it, takes each branch's base
from L</walk_base>, and routes every control commit that stands after it.  A
branch that has been delivered to is walked from the newest marker it
carries, and one that has never been delivered to from the commit that
introduced the environment, so that commit is routed and held like any
other.  Nothing here writes, so C<genesis propagate --dry-run> and
C<genesis pipeline-status> render one record and can never disagree about
what a repository is holding.

An environment with no settled branch is recorded and passed over, since only
C<genesis pipeline-apply> cuts a deployment branch.  An environment that will
not load, or whose vault this run cannot read, is recorded with its reason in
C<error>, because one unreadable environment is not a reason to stop reading
the rest.  An environment whose deployment record carries no certified commit
is one the pipeline was never applied to, so it is held rather than walked
and nothing stands pending for it.  Its base is never read, since reading one
costs a walk of control over that environment's own file and an environment
this run will not walk has no use for the answer, so its C<merged> stays null
and its reading stays C<not-propagated>.

Each environment's ancestors are read once and asked of every commit it
routes, through L</hold_for>, so a commit whose files an ancestor has not yet
deployed is held, and so is every commit after it.  An ancestor outside the
scope is read all the same, because an environment named on its own is still
held by the one above it.

The gate is read once for each environment as well, through L</gate_state>
and L</released_gates>, over the range from that environment's own certified
commit to control's tip rather than over the commits the walk finds due.  A
branch already delivered up to a gate is walked from the gate itself, so a
gate read over the due commits alone would fall behind the base on the very
next run and stop holding anything, while the environment still waits for the
deploy that certifies it.

An environment that has certified nothing has no such commit to read from,
and its marker will not stand in for one, for the same reason: the first run
delivers up to the gate and leaves the marker on it, so the second run's
range would start at the gate and find no gate at all.  Its range starts
where its own walk starts on an unseeded branch, at the commit
L</_before_introduction> answers, so the gate stands until a certification
exists.

A propagation hold is applied through L</apply_hold> at the end of each
environment's walk, once what is due has been computed and before the record
is handed back, so the caller has nothing left to deliver to a held
environment and the preview still has what waits behind the hold to show.

Fields a later stage owns are present and null rather than absent, so a
renderer never has to ask whether a key exists.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> the run is standing in.

=item C<git>

Required.  The C<Service::Git> handle every reading is made through.

=item C<scope>

Optional.  An arrayref of environment names to plan.  The DAG order and each
environment's C<prior_env> and C<depth> come from the whole topology either
way, so an environment named on its own still reads its ancestor correctly.

=item C<branches>

Optional.  C<Genesis::CI::Preflight::initial_state>'s own C<branches> record,
keyed by environment name, each entry carrying the branch it settled and,
under a dry run, the ref a real run would have moved that branch to.  An
environment absent from it has no deployment branch on either side, so it is
recorded and passed over as awaiting C<genesis pipeline-apply> and nothing
routes for it.  A call that leaves the map out therefore routes nothing at
all.

The map is an option because the walk does not yet read the branch state for
itself.  L</walk_base> has taken the base out of it, and the rest goes once
C<read_durable_state> lands.

=item C<refreshed>

Optional, default 1.  Whether the remote-tracking refs this walk reads were
brought up to date before it ran.

=item C<provider>

Optional.  The pipeline provider that owns propagation here, defaulting to
the one the configuration names.

=back

B<Returns:> A hashref carrying C<pipeline>, which is the label the
configuration gives the pipeline or null where it names none, C<provider>,
C<control>, C<applied>, C<refreshed>, and C<environments>, the last being an
arrayref of per-environment records in DAG order.  Each of those carries C<env>, C<type>,
C<branch>, C<prior_env>, C<depth>, C<reading>, C<merged>, C<deployed>,
C<certified>, C<pending>, C<held>, C<proposed>, C<hold>, C<drifted>,
C<pr>, C<manual>,
C<divergence>, C<discovery>, C<error>, C<outcome>, and C<outcome_detail>.

B<Errors:> Raises a bug where no git handle is given, since every reading
below is made through one and a walk without it can answer nothing.

B<Examples:>

  my $record = Genesis::CI::Walk::plan($top, git => $git,
                                       branches => $initial->{branches});
  # returns a record whose environments arrayref is in DAG order, with
  # each environment's due commits under pending

=head2 introducing_commit

    my $e = Genesis::CI::Walk::introducing_commit($git, $control, 'qa.yml');

E, the control commit that added that environment's own file.

Control is linear, so the question has one answer, and the oldest commit that
added the file is it.  A file that was added, removed, and added again
belongs to the environment from the first of the three onward, so the oldest
add is what comes back rather than the newest.

The path is followed back through the renames it has been through, so a
repository that has moved its deployment root answers the commit that first
added the file rather than the restructure that moved it, and no routing
commit between the two falls outside the walk.  Rename detection is git's
similarity heuristic rather than a recorded fact, and only an exact match
counts here, which a move that changed nothing about the file's content
always is.  The threshold is exact rather than the default because git turns
copy detection on inside its own rename following and will not let a caller
turn it off, and environment files resemble one another closely enough that
a looser threshold reads a brand new one as a copy of the environment beside
it.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$control>

The control branch, or any commit on it.

=item C<$env_file>

The environment's own file, named relative to the git root.

=back

B<Returns:> The forty-character sha of the commit that added the file, or
undefined where control has never carried it.

B<Examples:>

  my $e = Genesis::CI::Walk::introducing_commit($git, $sha, 'prod.yml');
  # returns the sha of the commit whose subject is 'Add prod'

=head2 walk_base

    my ($base, $reading) = Genesis::CI::Walk::walk_base(
      git => $git, ref => $ref, control => $sha, env_file => 'qa.yml');

Where one environment's walk starts, and whether its branch has ever been
delivered to.

A branch that carries a marker is walked from it.  A branch that carries none
is an init-only orphan that shares no history with control, so there is
nothing on it for the marker walk to read, and the walk starts at the commit
that introduced the environment instead.  The base that comes back for such a
branch is the commit before that one, so that E itself is the first commit
routed and is holdable like any other.  Seeding from control's tip instead
would collapse every commit since the environment was added into one baseline
and skip all of their holds, and a new environment could then receive shared
files that nothing upstream had deployed.

The base and the branch's marker are two different facts.  Only the base
comes back as the base, and the reading beside it is what tells a caller
whether it may also read that base as the commit the branch has merged.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$ref>

The deployment branch's ref, which is the local one the pre-flight settled,
or under a dry run the ref a real run would have moved it to.

=item C<$control>

The control branch, or any commit on it, which is where E is looked for.

=item C<$env_file>

The environment's own file, named relative to the git root.

=back

B<Returns:> Two values, the commit to walk from and one of C<seeded> or
C<unseeded>.  The commit comes back undefined two ways.  One is a branch with
no marker whose environment was introduced on control's own first commit,
since there is no commit before that one to stand the walk on.  The other is
a branch with no marker whose environment control has never carried a file
for at all, so there is no introducing commit to stand it on either.  The
caller reads both the same way, as the whole of control.

B<Examples:>

  my ($base, $reading) = Genesis::CI::Walk::walk_base(
    git => $git, ref => 'refs/heads/bosh/qa',
    control => $sha, env_file => 'qa.yml');
  # returns ($marker, 'seeded') for a branch that has been delivered to

=head2 control_commits

    my @commits = Genesis::CI::Walk::control_commits($git, $control, $base);

The control commits after C<$base>, oldest first.

Control is linear, so first-parent order is control order, and reversing it
puts the oldest due commit first, which is the order a delivery has to make
them in.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$control>

The control branch, or any commit on it.

=item C<$base>

The commit to start after, which is normally the one the branch's newest
marker names.  Undefined means the whole of control, which is what
L</walk_base> answers for a branch with no marker whose environment was
introduced on control's own first commit.

=back

B<Returns:> A list of hashrefs, each with C<sha> and C<subject>, oldest
first, and an empty list where git could not read the range.

B<Examples:>

  my @due = Genesis::CI::Walk::control_commits($git, 'control', $marker);
  # returns ({sha => '...', subject => 'Tune qa'}, ...)

=head2 changed_set

    my ($triggering, $carried)
      = Genesis::CI::Walk::changed_set($git, $env, $commit);

One commit's changed files, filtered to the environment's propagation set as
that commit's own tree defines it, and split in two.

The set is read from the tree at the commit being delivered and never from
the working tree, because a restructure moves the prefix that defines it.  A
triggering path is one whose change means deploy me; a non-triggering path
has to be current on the deployment branch without its change meaning that.
What the split then decides is L</route_commit>'s to say.

A kind that is a directory stands for everything under it, so a commit that
touches the dev kit or a reaction script is matched by the directory the set
names rather than being read as a path the set has never heard of.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$env>

The environment whose set the commit is filtered against.

=item C<$commit>

The control commit whose changed files are being read.

=back

B<Returns:> Two arrayrefs, the triggering paths and the non-triggering ones,
each sorted, and two empty ones where git could not read the commit.

B<Errors:> Raises whatever reading the set at a commit raises, which is a
commit carrying no kit the environment declares, a tracked list escaping the
deployment root, and a read with no vault to lend.

B<Examples:>

  my ($files, $carried) = Genesis::CI::Walk::changed_set($git, $env, $sha);
  # returns (['qa.yml'], ['.genesis/config'])

=head2 route_commit

    my $routed = Genesis::CI::Walk::route_commit($git, $env, $commit);

Whether one control commit belongs to one environment, and what of it does.

Only triggering content routes a commit, under D68.  L</changed_set> makes
the split, and a commit whose content for this deployment falls wholly on the
non-triggering side is skipped exactly as one that touches nothing in the set
is, and it records no outcome, because the next delivery is a mirror and
carries that content with it.  That holds behind a hold as well as in front
of one, so a configuration change standing behind a held commit is not
reported as waiting on anything.  The non-triggering paths come back beside
the triggering ones so that the report can say a script or a configuration
change rode along.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$env>

The environment the commit is being routed to.

=item C<$commit>

The control commit under consideration.

=back

B<Returns:> A hashref carrying C<triggering> and C<carried>, each an arrayref
of sorted paths, or C<undef> where the commit has no triggering content for
this environment.

B<Errors:> Raises whatever reading the set at a commit raises, which is a
commit carrying no kit the environment declares, a tracked list escaping the
deployment root, and a read with no vault to lend.

B<Examples:>

  my $routed = Genesis::CI::Walk::route_commit($git, $env, $sha);
  # returns {triggering => ['qa.yml'], carried => ['.genesis/config']}

  my $quiet = Genesis::CI::Walk::route_commit($git, $env, $config_only);
  # returns undef, and the commit records nothing at all

=head2 undeployed_set

    my @paths
      = Genesis::CI::Walk::undeployed_set($git, $env, $certified, $upto);

Every file in the environment's propagation set that changed on control
between its certified commit and the commit under consideration.

An environment that has never certified a commit is holding everything below
it, so with no certified commit the answer is the whole set rather than the
empty list, and nothing here ever falls back to control's tip.

A range git will not resolve ends the run rather than answering an empty
list.  An environment can certify a commit this clone has never fetched, or
one a rewritten control no longer carries, and reading that as an ancestor
with nothing outstanding would drop the very hold the range was read for.

B<Parameters:>

=over 4

=item C<$git>

The handle to read through.

=item C<$env>

The environment whose set the diff is filtered against.

=item C<$certified>

The control commit that environment last deployed from, or undefined where it
has deployed nothing.

=item C<$upto>

The control commit the question is being asked about.

=back

B<Returns:> A list of git-root-relative paths, and an empty list where the
range resolved and nothing in the set changed across it.

B<Errors:> Raises a C<Genesis::CI::RunFailure> of the run-fatal kind, naming
the environment and the range, where git cannot resolve the range.  It also
raises whatever reading the set at a commit raises, for the reasons
L</changed_set> gives.

B<Examples:>

  my @held = Genesis::CI::Walk::undeployed_set($git, $env, undef, $sha);
  # returns the whole triggering set, because nothing is certified

=head2 overlap

    my @shared = Genesis::CI::Walk::overlap($files, $undeployed);

The files a commit and an ancestor's undeployed set have in common.

Only triggering paths reach it, under D68, because a hold exists to stop
unproven content moving downstream and a reaction script that takes effect at
the next deploy is not that.  Both lists arrive triggering already, the
commit's from L</route_commit> and the ancestor's from L</undeployed_set>, so
nothing is filtered here.  Without the rule a shared C<.genesis/config>
change would hold every descendant on the commit that touched it.

B<Parameters:>

=over 4

=item C<$files>

The triggering paths of the commit being routed.

=item C<$undeployed>

The triggering paths the ancestor holds or is about to hold.

=back

B<Returns:> The paths both lists name, in the order C<$files> gives them, and
an empty list where they share none.

B<Examples:>

  my @shared = Genesis::CI::Walk::overlap(['qa.yml', 'dev/'], ['dev/']);
  # returns ('dev/')

=head2 certified_for

    my $certified = Genesis::CI::Walk::certified_for($env);

That environment's certified commit, its deployed commit, and when it
deployed, or the reason there is none.

Three states have no certified commit and they are kept apart, because each
means something different to the environments below.  An environment whose
C<with_vault> fails is broken and the walk records it as failed.  One with a
readable deployment record carrying no C<git.control_commit> is one the
pipeline was never applied to.  And one with no successful deployment at all
has certified nothing.  Nothing here ever falls back to control's tip,
because that asserts a deploy that did not happen and empties the set that
holds the descendants.

B<Parameters:>

=over 4

=item C<$env>

The environment whose record is read.

=back

B<Returns:> A hashref carrying C<state>, which is one of C<certified>,
C<never-certified>, C<never-applied>, and C<unreadable>, with
C<control_commit>, C<commit>, and C<at> beside it where the state is
C<certified>, and C<error> where it is C<unreadable>.

B<Examples:>

  my $certified = Genesis::CI::Walk::certified_for($env);
  # returns {state => 'certified', control_commit => $sha, ...}

  my $fresh = Genesis::CI::Walk::certified_for($undeployed_env);
  # returns {state => 'never-certified'}

=head2 hold_for

    my $hold = Genesis::CI::Walk::hold_for(git => $git, commit => $sha,
                                           files => $files,
                                           ancestors => $ancestors,
                                           provider => 'manual');

The reason one commit is held for one environment, or undefined when nothing
holds it.

The ancestors are asked nearest first, so the reason names the one closest to
the environment.  An ancestor that has certified nothing holds everything
below it, whether or not its own branch already holds the files, and an
overlap with an ancestor's undeployed set holds the commit.  Where the
overlap is what holds it the reason also carries the ancestor's own state, so
that an operator is not left to infer it from another row.

B<Parameters:>

=over 4

=item C<git>

The handle to read the undeployed set through.

=item C<commit>

The control commit the question is being asked about.

=item C<files>

An arrayref of the commit's triggering paths for this environment.

=item C<ancestors>

An arrayref of the environment's ancestors, nearest first, each a hashref of
C<name>, C<env>, and the C<certified> record L</certified_for> answers.

=item C<provider>

The pipeline provider that owns propagation here.  Only an automated one lets
an ancestor's C<genesis.pipeline.manual> read as awaiting its trigger, since
the key is inert under the manual provider.

=back

B<Returns:> A hashref carrying C<reason> and C<ancestor>, with
C<ancestor_files> beside them for an overlap and C<ancestor_state> in both
cases, or undefined where no ancestor holds the commit.

B<Errors:> Raises whatever reading an ancestor's undeployed set raises, for
the reasons L</undeployed_set> gives.

B<Examples:>

  my $hold = Genesis::CI::Walk::hold_for(git => $git, commit => $sha,
                                         files => ['ops/shared.yml'],
                                         ancestors => $ancestors,
                                         provider => 'manual');
  # returns {reason => 'ancestor-overlap', ancestor => 'lab', ...}

=head2 gate_state

    my $gate = Genesis::CI::Walk::gate_state(git => $git, commit => $sha,
                                             certified => $certified,
                                             released => $released);

Whether the commit under consideration is a gate the environment has not yet
passed, or undefined where it is not.

A gate is a control commit carrying a C<Genesis-Stage> trailer, and it
constrains only what follows it, so it travels with the commits already ahead
of it and ends the delivery.  Three things release it.  The environment's own
certified commit reaching or passing it releases it, a later commit that
reverts it releases it with no deploy, and so does a C<Genesis-Release-Stage>
trailer naming it.  The trailer is read under the key
C<Genesis::CI::Marker> answers it by, which that module exports as C<STAGE>.

B<Parameters:>

=over 4

=item C<git>

The handle to read the trailer and the ancestry through.

=item C<commit>

The control commit the question is being asked about.

=item C<certified>

The control commit the environment last deployed from, or undefined where it
has deployed nothing.  A gate at or behind it has been passed.

=item C<released>

The hashref L</released_gates> answers, keyed on the full sha of every gate a
later commit has released.

=back

B<Returns:> A hashref carrying C<reason>, which is always C<gate-ahead>,
C<gate>, the gate's own commit, and C<gate_reason>, the trailer's text with
any C<hold:> prefix taken off it.  Undefined where the commit is no gate or
where the gate has been passed or released.

B<Examples:>

  my $gate = Genesis::CI::Walk::gate_state(git => $git, commit => $sha,
                                           certified => undef,
                                           released => {});
  # returns {reason => 'gate-ahead', gate => $sha, gate_reason => 'schema change'}

=head2 released_gates

    my $released = Genesis::CI::Walk::released_gates($git, @commits);

The gates any commit in the range has released, read once so that a release
sitting after a gate is visible while the walk is still at the gate.

It accepts git's own revert body line and the C<Genesis-Release-Stage>
trailer, which C<Genesis::CI::Marker> exports the key for as
C<RELEASE_STAGE>, and it resolves a short hash through C<rev-parse>, so a
trailer naming an unambiguous abbreviation releases the gate the full hash
names.

After is what it says and what it means.  A commit in the range that names
one at or after itself releases nothing, because a gate constrains what
follows it and a release standing in front of the gate would lift it before
it was ever set.  A name the range does not hold is a commit older than the
range, and the release is after that one by the same reading, so it stands.

B<Parameters:>

=over 4

=item C<$git>

The handle to read the messages and resolve the names through.

=item C<@commits>

The commits of the range, oldest first, each a hashref carrying C<sha>, as
L</control_commits> answers them.  The order is what says which of two
commits is the later, control being linear.

=back

B<Returns:> A hashref keyed on the full sha of every released gate.

B<Examples:>

  my $released = Genesis::CI::Walk::released_gates($git, @commits);
  # returns {$gate_sha => 1} where a later commit reverts the gate

=head2 hold_reason

    my $words = Genesis::CI::Walk::hold_reason($held);

One held commit's reason, in the form the design fixes.

The words are exact, so that C<genesis propagate>, its dry run, and the
routing column of C<genesis pipeline-status> can never disagree about one.
The overlap form carries the ancestor's own state and the never-certified
form carries no such clause, an environment that has never deployed being
already clear about why.  A commit held behind a gate reads C<< gate:
<reason> >> with the trailer's own text and no held prefix, because the gate
is a step somebody has to take rather than a state the pipeline works its own
way out of.  An ancestor this run could not read at all reads C<< held by
<ancestor>, which could not be read >>, since an ancestor nobody can read is
neither certified nor uncertified.  A commit standing behind one the run has
already held reads C<< held behind control@<sha> >>, naming that commit in
the marker's short form.  A commit stopped by the environment's own
propagation hold reads C<< held (<reason>) >> carrying the reason somebody
wrote on the hold record, rather than the word C<on-hold>, because what an
operator has to clear is that reason and not the state's own name.

B<Parameters:>

=over 4

=item C<$held>

One entry of an environment record's C<held> list.

=back

B<Returns:> The reason as one line of prose.

B<Examples:>

  my $words = Genesis::CI::Walk::hold_reason($held);
  # returns "held by lab (ops/shared.yml), lab awaiting deployment"

=head2 held_qualifier

    my $words = Genesis::CI::Walk::held_qualifier($env_record);

One environment's own held phrase, or undefined where nothing holds it.

It says what the environment waits for rather than why any one commit is
held.  An environment the pipeline was never applied to waits for that
command, one holding commits behind an ancestor waits for that ancestor to
certify the commit it has not deployed, and one holding commits behind a gate
waits on its own deployment of the gate, which is the commit the phrase then
names.

An environment with a propagation hold standing against it reads C<< held,
needs clearing (<reason>) >> ahead of any of those, because under D50 a hold
is a decision somebody made for a reason the pipeline cannot see and only a
person clears it, so it outranks whatever the commits underneath it happen to
be waiting for.

B<Parameters:>

=over 4

=item C<$record>

One environment's record, as L</plan> builds it.

=back

B<Returns:> The qualifier as one line of prose, or undefined.

B<Examples:>

  my $words = Genesis::CI::Walk::held_qualifier($env_record);
  # returns "held, awaiting deployment (lab at control@1a2b3c4)"

=head2 hold_detail

    my $words = Genesis::CI::Walk::hold_detail($env_record);

What the standing hold is holding, in the two wordings D56 fixes, or
undefined where no hold stands.

D56 makes a hold outrank idempotent, so an environment with one standing
never reads as though it were fine, and this is the line beside
L</held_qualifier> that says which of the two situations it is in.  Where
nothing is due behind the hold it reads that nothing is due now and that
anything becoming due stays blocked, and where something is it names how many
commits are blocked until the hold is released.

The count is of the commits the hold itself took, and not of everything held,
because a commit a gate or an ancestor had already stopped is reported under
that reason, and counting it here would name it twice and send an operator to
the wrong command.

B<Parameters:>

=over 4

=item C<$record>

One environment's record, as L</plan> builds it, after L</apply_hold> has run
over it.

=back

B<Returns:> The detail as one line of prose, or undefined where the record
carries no C<hold>.

B<Examples:>

  my $words = Genesis::CI::Walk::hold_detail($env_record);
  # returns "2 commits are blocked until this hold is released"

=head2 walk_env

    Genesis::CI::Walk::walk_env(git => $git, env => $env, record => $rec,
                                control => $sha, base => $marker,
                                hold_check => sub { undef });

One environment's walk, from its newest marker to control.

Each due commit is routed on its own, in control order, through
L</route_commit>, and a commit that routes nowhere records nothing whether it
stands in front of a hold or behind one.  The first hold ends the delivery
for that environment, because a mirror at any later commit would carry the
held one with it, and every routed commit after the hold is recorded as
C<behind-held-commit> so that no routed commit goes unnamed.

A gate ends the delivery the other way about.  It travels with the commits
already ahead of it, so a commit at or before the gate is delivered, and
every commit after it is held with the gate's own reason rather than behind
the commit in front of it, because the gate is the one thing an operator can
clear.

B<Parameters:>

=over 4

=item C<git>

The handle to read through.

=item C<env>

The environment being walked.

=item C<record>

That environment's record, which this appends to.

=item C<control>

The control commit the walk runs up to.

=item C<base>

The commit to start after, or undefined for the whole of control.

=item C<gate>

Optional.  The gate the environment has not passed, as L</gate_state> answers
it.  Every commit after it is held with its reason, and where it is undefined
nothing is gated.

=item C<hold_check>

A coderef called as C<< $hold_check->($commit, $files) >>, answering a
hashref where the commit is held and undefined where it is not.  L</plan>
passes one that asks the environment's ancestors through L</hold_for>.

=back

B<Returns:> The record it was given, with C<pending> and C<held> filled in.

B<Examples:>

  Genesis::CI::Walk::walk_env(git => $git, env => $env, record => $rec,
                              control => $sha, base => undef,
                              hold_check => sub { undef });
  # every due commit lands in $rec->{pending}, in control order

=head2 apply_hold

    Genesis::CI::Walk::apply_hold($env_record, $env->hold_record);

Stops delivery for a held environment and says why.

Under D50, while a propagation hold stands the run delivers nothing new to
that environment and opens or updates no pull request, in either mode, while
everything already on the deployment branch stays deployable.  The walk still
computes what is due, which is what lets C<genesis propagate --dry-run> show
what waits behind the hold.

Every pending commit moves into the record's C<held> list with the reason
C<on-hold> and the hold's own reason beside it, rather than being discarded,
so the preview and the report have something to list.  They go on the front
of that list, because everything the walk had already held stands after the
last commit that was still pending, and a report whose commits are out of
control order is one nobody can read against the log.

It runs at the end of each environment's walk inside L</plan>, once
L</walk_env> has computed what is due and before the caller reads the record,
so nothing downstream can deliver a commit the hold has taken.

B<Parameters:>

=over 4

=item C<$record>

One environment's record, as L</plan> builds it.

=item C<$hold>

That environment's hold record, as C<< Genesis::Env->hold_record >> answers
it, or undefined where no hold stands, in which case the record comes back
untouched.

=back

B<Returns:> The record it was given, with C<hold> set, C<pending> emptied,
and every entry that was pending moved to the front of C<held>.

B<Examples:>

  Genesis::CI::Walk::apply_hold($env_record, $env->hold_record);
  # $env_record->{pending} is now empty and $env_record->{hold} is set

=head2 deliver_pending

    Genesis::CI::Walk::deliver_pending(session => $session, env => $env,
                                       record => $env_record);

Hands each pending commit to the single writer, one commit at a time.

One control commit becomes one commit on the deployment branch, carrying the
marker that names it and mirroring the set as it stood at that commit.  The
writer asserts the snapshot invariant on the index before each commit, so the
assertion runs after every delivery rather than once at the end of the run.

The session has to be standing on the environment's deployment branch already,
because the writer commits where it finds itself.

B<Parameters:>

=over 4

=item C<session>

The run's open session, standing on the deployment branch.

=item C<env>

The environment being delivered to, which the writer reads its set through.

=item C<record>

That environment's record.  Each entry in C<pending> gains C<commit>,
C<delivered>, C<removed>, and C<overwrote>.

=item C<dry_run>

Optional.  Where it is true the writer reports what would land and what would
go and writes nothing at all.

=back

B<Returns:> The record it was given, with C<overwrote> collected across the
deliveries and C<merged> moved to the last control commit delivered.  A
preview moves nothing, so under C<dry_run> C<merged> stays where the branch's
own marker put it.

B<Errors:> Raises whatever the single writer raises, which is an empty
propagation set, a source commit holding none of it, and either index
assertion failing.

B<Examples:>

  Genesis::CI::Walk::deliver_pending(session => $session, env => $env,
                                     record => $env_record);
  # commits once per pending entry, newest last

=head2 walk_one

    Genesis::CI::Walk::walk_one(record => $env_record, deliver => $code);
    Genesis::CI::Walk::walk_one(session => $session, record => $env_record,
                                deliver => $code);

Walks and delivers to one environment, ending at that environment's own
error.

Under D96 and D60, an error confined to one environment ends that environment
and nothing else.  Its branch goes back to T so that nothing of a partial
delivery survives, it records C<failed> with the error it raised, and the run
walks on to the next environment.  The same call stands around the walk and
around the delivery, because under D78 a blueprint that raises while one
environment's fragments are enumerated belongs to the same class as a
delivery that died halfway.

A run-fatal or unsurvivable error is re-raised for the caller to abort the
whole run on, which L</is_run_fatal> is the reader for.

B<Parameters:>

=over 4

=item C<record>

One environment's record, as L</plan> builds it.  On a confined error it
gains C<error> and an C<outcome> of C<failed>, and its C<pending> list is
emptied.

=item C<deliver>

The code to run for this environment.  Anything it raises that is not
run-fatal ends this environment alone.

=item C<session>

Optional.  The run's open session, handed over only where something may have
been written, since that is what the branch is put back from.  It is asked
for C<< Service::Git::Session->discard >> and never for C<abort>, because an
abort would end the run and leave every environment below this one
unattempted.

=back

B<Returns:> The record it was given.

B<Errors:> Re-raises a run-fatal or unsurvivable error unchanged, so the
caller can abort the run on it.

B<Examples:>

  Genesis::CI::Walk::walk_one(session => $session, record => $env_record,
      deliver => sub {
          $session->switch($env_record->{branch});
          Genesis::CI::Walk::deliver_pending(session => $session,
              env => $env, record => $env_record);
      });
  # a delivery that dies halfway resets the branch and records failed

=head2 is_run_fatal

    my $bool = Genesis::CI::Walk::is_run_fatal($error);

Whether an error ends the run rather than the environment, under D82's two
classes.

Run-fatal is the writer's own failure, where nothing a caller could do
differently would have helped.  Unsurvivable is an error no environment
survives that a retry may fix, the remote being unreachable as the case.
Both end the run, and both are raised as C<Genesis::CI::RunFailure>, whose
two constructors bless one package and tell the two apart through the C<kind>
they set, so the kind is what is read here.  Everything else is confined to
the environment that raised it.

B<Parameters:>

=over 4

=item C<$error>

Whatever was raised.  Anything that is not a blessed C<Genesis::CI::RunFailure>
is not run-fatal.

=back

B<Returns:> 1 where the error ends the run, and 0 where it ends one
environment.

B<Examples:>

  Genesis::CI::Walk::is_run_fatal(Genesis::CI::RunFailure->fatal);        # 1
  Genesis::CI::Walk::is_run_fatal(Genesis::CI::RunFailure->unsurvivable); # 1
  Genesis::CI::Walk::is_run_fatal("the blueprint hook exited 1\n");       # 0

=head1 INTERNAL FUNCTIONS

=head2 _before_introduction

    my $since = Genesis::CI::Walk::_before_introduction($git, $control,
                                                        $env_file);

The commit a range starts after so that E, the commit that introduced the
environment's file, is the first commit in it.

An environment control has never carried a file for, and one whose file was
introduced on control's own first commit, both answer undefined, which
L</control_commits> reads as the whole of control.  A root commit has no
parent, and the whole of control is what the caller wants there, because
control's first commit is where E already is.

Two callers ask it.  L</walk_base> asks for a branch that carries no marker,
and L</plan> asks for an environment that has certified nothing, because a
gate range taken from that environment's marker instead would start at the
gate the last run delivered to and so find no gate at all.

B<Parameters:>

=over 4

=item C<$git>

The handle the range is read through.

=item C<$control>

The control commit the walk is reading against.

=item C<$env_file>

The environment's own file, git-prefixed.

=back

B<Returns:> The sha of the commit before E, or undefined where there is
none.

B<Examples:>

  Genesis::CI::Walk::_before_introduction($git, $sha, 'bosh/qa.yml');
  # the commit before the one that added bosh/qa.yml

=head2 _reading

    my $reading = Genesis::CI::Walk::_reading($marker, $deployed);

Which of the four readings describes a deployment branch.

A branch with no marker has been cut and never delivered to, which is
C<unseeded>.  A branch whose marker names the control commit the environment
last deployed from is C<deployed>, and one whose marker has moved past it is
C<pending-deploy>.  A branch whose deployment could not be read keeps
C<not-propagated>, because claiming either of the other two would be claiming
something no durable state said.

B<Parameters:>

=over 4

=item C<$marker>

The control commit the branch's newest marker names, or undefined.

=item C<$deployed>

The environment's last successful deployment as a hashref, or undefined.

=back

B<Returns:> One of the four readings, as a string.

B<Examples:>

  Genesis::CI::Walk::_reading(undef, undef);
  # returns 'unseeded'

=head2 _load_error

    my $reason = Genesis::CI::Walk::_load_error($err);

A short reason from a load that raised.

The record carries one line per environment, because the report prints it
beside the environment's name, while the raised text is several decorated
lines of which the first substantive one says what went wrong.

B<Parameters:>

=over 4

=item C<$err>

Whatever the failed load left in C<$@>.

=back

B<Returns:> The first substantive line, trimmed, or C<'unknown reason'>.

B<Examples:>

  Genesis::CI::Walk::_load_error("\nNo such environment 'qa'\n  at ...\n");
  # returns "No such environment 'qa'"
