=head1 NAME

Genesis::CI::Publish - the propagate run's third stage, one push per branch

=head1 SYNOPSIS

    use Genesis::CI::Publish;

    # Every branch the run committed to, pushed on its own, with each
    # push's result recorded as that branch's outcome.
    my $publish = Genesis::CI::Publish::publish_run(
        git     => $git,
        session => $session,
        remote  => 'origin',
        control => 'control',
        records => $record->{environments},
        specs   => [
            {branch => 'lab/bosh', kind => 'deployment', env => 'lab'},
        ],
        yes          => $opts->{yes},
        unsurvivable => sub {die "the remote answered nothing: $_[1] $_[0]\n"},
    );

    # A control that moved under the run refuses the whole publish, and the
    # sentence to refuse with comes back for the command to speak.
    bail({exitcode => TEMPFAIL}, '%s', $publish->{refused})
        if $publish->{refused};

=head1 DESCRIPTION

The walk decides what is due and the delivery writes it onto the deployment
branches in the local repository. Everything here is about getting what the
local repository now holds onto the remote, and saying, per environment, what
the remote made of it.

The push set is the deployment branches alone. Control is the run's input and
never its output, which is D30, so what this stage does with control is read
it once more before the first push. A marker is a bare sha with no ancestry
link to the deployment branch, so it means something only where the commit it
names can be fetched from the remote, and a control that moved under the run
leaves every marker the run wrote naming a commit computed from a tip that has
already moved. Such a run refuses before its first push, puts every branch it
committed to back where the remote has it, and hands the caller the sentence
to refuse with.

Everything the push would carry is shown before it goes, and the showing does
not wait on anyone being there to read it. A dry run followed by a real run
computes everything twice, and control or exodus can move between the two, so
the second run may deliver what the operator never previewed. This stage
computes once, verifies, shows, and asks. At a terminal the delta comes first
and the operator answers for it, and where there is no controlling terminal
the same delta goes to the log and the run goes on, so a pipeline job and a
propagate child print what an operator would have been shown. C<yes>
suppresses the ask and nothing else.

Each branch is pushed on its own. A rejection on one branch costs one
environment one run and nothing else, which is what D83 asks for, and no
push's result withholds another's, which is the third stage of D96. The
branches after a refused one go out regardless of where the refusal fell.

A push the remote refused is that environment's outcome and not a warning
printed beside a success. The record reads C<publish rejected> in the bare
word I8 fixes, with the moved ref standing beside it in the detail, because
the run's exit status and the report both match the whole of the outcome field
against seven words and a phrase written into it would match none of them.

The ref named in that detail is the one git printed in its own porcelain line,
rather than one composed here out of the branch the push asked for. Where a
teammate has moved a branch under the run, the two can differ, and the name
worth telling an operator is the one the remote actually refused.

A refused branch goes back to its remote state at once, through the session,
so the run ends with no local commit nobody else can see. It is the same reset
the abort runs over every branch a session committed to, so the two cannot
come to disagree about what putting a branch back means.

The commit axis of I8 is written here too. Every commit an environment
actually got onto the remote reads C<delivered>, and the commits of an
environment that was refused are left null, because they are delivered in no
sense the word carries.

=head1 FUNCTIONS

=head2 publish_run

    my $publish = Genesis::CI::Publish::publish_run(
        git     => $git,
        session => $session,
        remote  => 'origin',
        control => 'control',
        records => \@records,
        specs   => \@specs,
        yes     => $yes,
    );

Pushes every branch the run committed to, one branch per push, and records
each push's result as that branch's outcome.

Every branch's verified delta is shown before the first push goes out, and an
operator at a controlling terminal is then asked whether to publish. A run
that is declined pushes nothing and answers C<declined>, and the status such a
run exits with is the caller's to decide.

Control is re-checked against the remote before the first push, and a control
that is behind, ahead, or gone refuses the whole publish. Nothing is pushed,
every branch the run committed to goes back to where the remote has it, and
the refusal comes back on C<refused> as the sentence the caller speaks.

A branch the remote refused records C<publish rejected> with C<E<lt>refE<gt>
moved on R> beside it, is reset to its remote state at once, and the remaining
branches are pushed anyway. A branch that landed records nothing of its own,
because the walk has already written what the environment did, and its pending
commits each read C<delivered>.

A push the remote answered about on no ref at all is the remote being gone
rather than any branch's own quarrel with it, so nothing is recorded and the
C<unsurvivable> callback is invoked with git's own words instead. The
classifier that turns those words into a remedy lives beside the run, so the
caller raises the failure and this stage only says which reason to raise it
on.

B<A remote that refused every branch is not a remote that went away.> What
the stage reads is whether git named a ref, because a ref comes from git's
own porcelain line and a push that never reached the remote prints none.
Reading whether any ref landed instead would give a run whose every branch
was refused the answer an unreachable remote earns, and that is no corner
case now that the push set is the deployment branches alone, because a run
with one environment in it has a single ref to land.

No two branches are published together and none is read together. Every
deployment branch is an independent mirror at its own marker, routing
between environments reads the deployment records rather than another
branch, and a run that lands one branch and not another leaves a state in
which every marker is true and which the next run converges.

B<Parameters:>

=over 4

=item C<git>

The repository handle the push runs through.

=item C<session>

The open branch session, through which a refused branch is reset. A call
without one records the outcomes and resets nothing.

=item C<remote>

The remote to publish to, by name. It falls back to the repository's default
remote, and a repository with no remote at all publishes nothing.

=item C<control>

The control branch's name, which is the branch re-checked before the first
push. A call without one pushes without re-checking.

=item C<records>

An arrayref of the walk's per-environment records, which is where an outcome
is written. A spec whose environment is not among them is pushed and reported
and writes no outcome.

=item C<specs>

An arrayref of ref specs, in the order they should be pushed. Each carries
C<branch>, and may carry C<kind>, which is C<deployment> or C<pr>, and C<env>,
which names the record the outcome belongs to. Control is never among them. An
empty list publishes nothing.

=item C<yes>

Answers the ask without putting it, which is what C<--yes> passes. It leaves
the showing alone, so the delta is printed either way.

=item C<unsurvivable>

A callback invoked where git named no ref at all, with two arguments. The
first is git's reason, which is the short phrase from a porcelain line or the
whole of what git said where there was no such line, and the second is git's
standard error, which is where a hint naming the class of the failure lives
and which is the empty string where git wrote nothing there. It is expected
to raise, and the stage returns without recording anything if it does not.

=back

B<Returns:> A hashref carrying C<published> and C<rejected> as arrayrefs of
branch names, C<declined> as 0 or 1, and C<results> as the per-ref results the
push answered. A publish the control check refused carries C<refused> as well,
holding the sentence, with every other key left as it began. A publish the
operator declined carries C<declined> as 1 and every other key as it began.

B<Errors:> None of its own. A rejection is an outcome rather than a failure, a
control that moved is a sentence for the caller to refuse with, and the one
failure the stage meets is raised by the caller's own callback.

B<Examples:>

    publish_run(git => $git, specs => []);
    # returns the empty result and pushes nothing

    publish_run(git => $git, session => $session, remote => 'origin',
        control => 'control', records => \@records, specs => \@specs);
    # returns { published => ['lab/bosh'], rejected => ['prod/bosh'],
    #           declined => 0, results => [...] }
    #   where the remote had moved under prod

    publish_run(git => $git, session => $session, remote => 'origin',
        control => 'control', records => \@records, specs => \@specs);
    # returns { refused => 'Refusing to publish.  ...', published => [],
    #           rejected => [], declined => 0, results => [] }
    #   where a teammate pushed to control during the walk

=head2 confirm_publish

    my $go = Genesis::CI::Publish::confirm_publish(
        $git, 'origin', \@specs, yes => $yes,
    );

Shows every branch's verified delta and then asks whether to publish.

The showing is unconditional. At a terminal it comes before the ask, and where
there is no controlling terminal it goes to the log and the run proceeds, so a
pipeline job and a propagate child print the same delta an operator would have
seen. C<yes> suppresses the ask and nothing else, and it is read before the
terminal is consulted at all, so a flag that answers the question cannot also
decide whether the question's subject is printed.

B<Parameters:>

=over 4

=item C<$git>

The repository handle each delta is read through.

=item C<$remote>

The remote the push would go to, by name. It names the remote-tracking ref
each delta is measured against.

=item C<$specs>

An arrayref of the ref specs the push would be handed, in the order they would
go out. Each is shown on a line of its own.

=item C<yes>

Answers the ask without putting it. The showing happens either way.

=back

B<Returns:> 1 to publish, and 0 where the operator declined.

B<Errors:> None of its own. The delta reader and the prompt raise as they do
for every other caller, and a prompt that reaches the end of standard input
bails the way every other Genesis prompt does.

B<Examples:>

    confirm_publish($git, 'origin', \@specs, yes => 1);
    # prints every delta, asks nothing, and returns 1

    confirm_publish($git, 'origin', \@specs);
    # prints every delta and returns 1 where there is no terminal to ask at

=head2 publish_delta

    my $delta = Genesis::CI::Publish::publish_delta($git, 'origin', $spec);

What one branch's push would carry, read as the range from the
remote-tracking ref to the local branch.

The range is exactly what the push sends, so it is read from git rather than
recomposed from the walk's record, and a delta shown to an operator is
therefore the delta they get. A branch the remote does not hold yet has no
range to read and reports as new.

B<Parameters:>

=over 4

=item C<$git>

The repository handle the range and the diff are read through.

=item C<$remote>

The remote, by name, which names the remote-tracking ref the range starts at.

=item C<$spec>

One ref spec. It carries C<branch>, and a spec carrying C<delete> is a removal
rather than a range.

=back

B<Returns:> A hashref carrying C<commits> as the subjects in that range,
C<changed> and C<deleted> as file counts, and C<new_branch> where the remote
has no such branch yet. A removal reports C<removal> and nothing else.

B<Errors:> None of its own. The queries raise as they do for every other
caller.

B<Examples:>

    publish_delta($git, 'origin', {branch => 'lab/bosh'});
    # returns { new_branch => 0, commits => ['3f9a1c2 deliver an op'],
    #           changed => 1, deleted => 0 }

    publish_delta($git, 'origin', {branch => 'pr/qa/bosh', delete => 1});
    # returns { removal => 1 }

=head1 INTERNAL FUNCTIONS

=head2 _recheck_control

    my $refused = Genesis::CI::Publish::_recheck_control($git, 'control', 'origin');

Asks D30's in-sync question a second time, immediately before the first push.

The pre-flight asks it once, before the walk, and a walk takes long enough for
a teammate to push through the middle of it. A marker is a bare sha with no
ancestry link to the deployment branch, so control moving under the run is the
one condition that makes every delivery stale. The branch is fetched first, so
the answer is about what the remote holds now rather than about a tracking ref
nobody has refreshed since the run began.

Each of the six states the query answers with earns a refusal of its own, as
does control having gone from both sides, because the step that repairs one
repairs none of the others. Genesis never moves control, so every refusal
names the corrective step and leaves control where it was found. The sentence
is returned rather than printed, because the caller closes the session before
it speaks and a stage that printed for itself would speak first.

A fetch that could not reach the remote is passed over. The question asked
here is about control, and a remote that has gone away is D82's question,
which the push raises for itself, so a failed refresh leaves the reading to
the tracking ref and the push to say what it finds.

B<Parameters:>

=over 4

=item C<$git>

The repository handle the fetch and the query run through.

=item C<$control>

The control branch's name. An undefined or empty name skips the check.

=item C<$remote>

The remote to check against, by name.

=back

B<Returns:> C<undef> where control is in sync, which is the one state that lets
the push go out, and otherwise the sentence the caller refuses with.

B<Errors:> None of its own. The fetch and the query raise as they do for every
other caller.

B<Examples:>

    _recheck_control($git, 'control', 'origin');
    # returns undef, and the push goes out

    _recheck_control($git, 'control', 'origin');
    # returns 'Refusing to publish.  The control branch control is behind
    #   origin/control by 1 commit, so everything this run computed is
    #   stale.  ...' where a teammate pushed during the walk

=head2 _commits

    my $said = Genesis::CI::Publish::_commits(2);

The count of commits and its noun, so the verb around it reads.

A refusal that says "by 1 commits" is read past rather than read, so the number
governs the noun wherever a refusal names one.

B<Parameters:>

=over 4

=item C<$n>

How many commits. An undefined count reads as none.

=back

B<Returns:> The count and its noun, as one string.

B<Errors:> None.

B<Examples:>

    _commits(1);
    # returns '1 commit'

    _commits(3);
    # returns '3 commits'

=head2 _reset_publish_set

    my $put_back = Genesis::CI::Publish::_reset_publish_set($session);

Puts every branch the run committed to back where the remote has it.

A branch carrying a commit the remote has never seen is the illegal initial
state D96 names, and a run that refuses before its first push must not leave
one behind. The set is the session's own, which is the set an abort resets, so
a refusal here and an abort put back exactly the same work. Control is not in
it, because I2 keeps committed work on control whole.

B<Parameters:>

=over 4

=item C<$session>

The open branch session, which both answers the set and does the resetting. A
call without one resets nothing.

=back

B<Returns:> How many branches were put back.

B<Errors:> The session's own reset raises where git refuses it.

B<Examples:>

    _reset_publish_set($session);
    # returns 2, having put lab/bosh and qa/bosh back at their remote state

    _reset_publish_set(undef);
    # returns 0

=head2 _spec_for

    my $spec = Genesis::CI::Publish::_spec_for(\@specs, 'lab/bosh');

The ref spec a push result belongs to.

The push answers one result per ref and the result carries the branch it was
asked for, so the spec is found by that name rather than by position, and a
push that answered in some other order is read correctly anyway.

B<Parameters:>

=over 4

=item C<$specs>

An arrayref of the specs the push was handed.

=item C<$branch>

The branch a result names.

=back

B<Returns:> The spec, or an empty hashref where no spec carries that branch.

B<Errors:> None.

B<Examples:>

    _spec_for([{branch => 'lab/bosh', env => 'lab'}], 'lab/bosh');
    # returns { branch => 'lab/bosh', env => 'lab' }

    _spec_for([], 'lab/bosh');
    # returns {}

=head2 _record_for

    my $rec = Genesis::CI::Publish::_record_for(\@records, 'lab');

The walk's record for an environment.

B<Parameters:>

=over 4

=item C<$records>

An arrayref of the walk's per-environment records.

=item C<$env>

The environment's name, or undefined for a spec that belongs to no
environment, such as the control branch.

=back

B<Returns:> The record, or C<undef> where there is none.

B<Errors:> None.

B<Examples:>

    _record_for([{env => 'lab'}], 'lab');
    # returns { env => 'lab' }

    _record_for([{env => 'lab'}], undef);
    # returns undef

=head2 _mark_delivered

    Genesis::CI::Publish::_mark_delivered($record);

Writes the commit axis of I8 for an environment that published.

The report's per-commit word defaults to C<delivered>, and the publish is what
the enum names as the writer of it, so the word is written here for every
commit an environment actually got onto the remote. A refused environment's
commits are left null.

B<Parameters:>

=over 4

=item C<$rec>

One environment's record, or C<undef>, which is a no-op.

=back

B<Returns:> Nothing.

B<Errors:> None.

B<Examples:>

    _mark_delivered({pending => [{subject => 'tune lab'}]});
    # leaves outcome delivered on the pending commit

    _mark_delivered(undef);
    # does nothing
