=head1 NAME

Genesis::CI::Propagation - the pull request half of pipeline propagation

=head1 SYNOPSIS

    use Genesis::CI::Propagation;

    # The commit a propagation is written with, and nothing else.  Nothing
    # here is public: what is left is what other test files still reach for
    # by name.

=head1 DESCRIPTION

C<Genesis::CI::Propagation> holds what is left of the module that used to
execute pipeline propagation, which is the commit a delivery onto a branch
was written with and nothing more.

Everything else it held has gone.  C<propagate_envs> applied a target list to
a real git working tree in one loop that recorded the first error and stopped,
which left every environment after that one neither attempted nor reported,
and its C<no_push> master switch went with the flag it served.  What replaced
it is a walk: C<Genesis::CI::Walk::plan> visits every environment and answers
it commit by commit against durable state, C<Genesis::CI::Walk::walk_one>
confines an error to the environment that raised it, C<Service::Git::Session>
is the one writer, and the publish pushes each branch on its own.

The direct path went with that loop, because a delivery onto an environment's
own branch is what the walk and the single writer now do.  The pull request
path has gone the same way: L<Genesis::CI::PullRequest> owns the aggregate
commit, the pull request, and the proposed record, and the arm and the
per-file lines that used to stand here went with it.  So did the body a
proposal was opened with and the dispatch that opened or updated it.  A title
and a body that name the control commits being proposed are what
L<Genesis::CI::PullRequest/title_for> and
L<Genesis::CI::PullRequest/aggregate_message> compose, and
L<Genesis::CI::PullRequest/sync_pull_request> is the one place that sends
them.  The idempotent re-run check for a rolling
C<pr/E<lt>envE<gt>/E<lt>typeE<gt>> branch went with them as well.  It read the
branch's newest marker and compared it with the commit being propagated, and
D48 replaced that with the marker walk on both branches and a comparison of
the two trees, which is L<Genesis::CI::PullRequest/settled>.  What is left is
what other test files still reach for by name, and retiring the module
outright would take them with it.

=head1 DESIGN CONSIDERATIONS

=head2 Why this is a module and not part of the pipelines command

Propagation began inside C<Genesis::Commands::Pipelines> and was extracted
here because two callers needed the same execution path, which were the
C<genesis propagate> command and the Manual provider's auto-trigger at the
end of a deploy.  Leaving the logic in a command module would have meant the
provider either shelling out to a command or keeping a second copy.

The rolling-branch decision, which is whether an existing pull request
already carries the change, was the part most likely to be wrong and the
hardest to observe in a live pipeline run.  Separating it from command
dispatch is what allowed it to be exercised directly in tests, and it is the
reason this module outlived the loop it was extracted with.  That decision
now belongs to L<Genesis::CI::PullRequest/settled>, which is asked once the
single writer has built the aggregate, so the comparison is between two trees
rather than between two guesses about them.


=head1 INTERNAL FUNCTIONS

These are internal to the implementation.  They may change without notice
and should not be called directly.

=head2 _apply_propagation_commit

  _apply_propagation_commit($git, $env_name, $control_sha, $control_short, $detail);

Checks the changed files out of the control commit, removes the deleted ones,
and commits under the subject L<Genesis::CI::Marker/build> renders.

The subject is not cosmetic.  It is the branch's only record of the control
commit it carries, and L<Genesis::CI::Marker/newest> is what reads it back,
so the format lives in that module rather than here.

B<Returns:> nothing.

B<Examples:>

  _apply_propagation_commit($git, 'staging', $sha, 'a1b2c3d', $detail);
  # no return value; commits "[pipeline] control@a1b2c3d -> staging"

=head1 LIMITATIONS

=head2 GitHub-only for PR-based propagation

PR creation, lookup, and update go through C<Service::Github> only.
GitLab, Bitbucket, and Gitea are not supported.  When a target has
C<require_pr =E<gt> 1>, the caller must supply a C<Service::Github>
instance and the C<owner_repo> resolves to a GitHub C<owner/name>
slug.  Adding another forge would require a parallel
C<Service::E<lt>ForgeE<gt>> with the same C<open_prs / create_pr /
update_pr> surface, plus a dispatch layer in front of
L<Genesis::CI::PullRequest/sync_pull_request>.

=head2 Single-repo working tree only

These helpers assume the C<Service::Git> instance points at a single working
tree where every environment's branch can be checked out, which is the
Manual mode shape and the shape the session is keyed on.

The Concourse mode shape, which is one git workspace per environment branch
provided as a separate job input, is B<not yet wired>.  When that work lands,
callers will resolve workspace paths by convention or through environment
variables and reach these helpers once per environment, each with a git
handle of its own.

=head2 Fast-forward-only push for C<pr/E<lt>envE<gt>> branches

When the count=1 case appends a new commit to an existing
C<pr/E<lt>envE<gt>> branch, the push is a plain
C<git push origin pr/E<lt>envE<gt>>.  If the remote has commits
that the local branch does not (non-fast-forward), the push fails
and that environment records the failure as its own outcome.

The cherry-pick + force-push recovery path (rebuild
C<pr/E<lt>envE<gt>> locally from C<E<lt>envE<gt>>, cherry-pick the
remote's pending commits, append the new propagation, force-push)
is B<deferred>.  In practice the walk's ancestor hold prevents the
non-fast-forward case, because a fresh propagation reaching
C<pr/E<lt>envE<gt>> touches files disjoint from anything already queued on
the branch.  If real-world usage
proves the case reachable, the recovery path will be added; until
then, the failure is caught and surfaced rather than papered over.

=head2 Manifest store under C<require_pr> is broken

When an env has C<require_pr =E<gt> 1>, propagation creates the
rolling C<pr/E<lt>envE<gt>> branch instead of pushing to
C<E<lt>envE<gt>>.  This breaks the post-deploy manifest writer
for C<manifest_store=repository> and C<manifest_store=hybrid>,
which expect to push the rendered manifest to C<E<lt>envE<gt>>.

C<manifest_store=exodus> is unaffected (writes to vault, not git).

No resolution is settled yet.  Until one is, configure
C<manifest_store=exodus> on envs with C<require_pr =E<gt> 1>.
