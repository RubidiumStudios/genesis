=head1 NAME

Genesis::Hook::CpiConfig - Hook implementation for generating BOSH CPI configs

=head1 SYNOPSIS

    package Genesis::Hook::CpiConfig::my_kit;
    use parent 'Genesis::Hook::CpiConfig';

    sub perform {
        my ($self) = @_;

        my $properties = $self->gather_properties(
            'datacenter',
            'datastore',
            '!password@credentials.vcenter_password',
        );

        my $config = $self->build_cpi_config_for_iaas(
            vsphere => $properties,
        );

        $self->done($config);
    }

    1;

=head1 DESCRIPTION

C<Genesis::Hook::CpiConfig> is the base class for Genesis kit hooks that
generate BOSH CPI (Cloud Provider Interface) configurations. It extends
C<Genesis::Hook> with infrastructure specific to CPI config generation:
property lookup and resolution from environment manifests and OCFP
configuration, secret entombment into CredHub, and construction of the CPI
config data structure.

Kit authors subclass this class and implement C<perform>. The C<perform>
method should call C<gather_properties> to resolve CPI property values,
C<build_cpi_config_for_iaas> to assemble the BOSH CPI config structure, and
finally C<done> to signal completion and deliver the result to Genesis.

The hook lifecycle follows the standard C<Genesis::Hook> pattern. See
L<Genesis::Hook> for inherited methods including C<init>, C<perform>,
C<completed>, C<env>, C<iaas>, C<features>, C<want_feature>, and BOSH
integration helpers.

=head1 PROPERTY MAPPING

A kit's property map is a translation table between two vocabularies that
do not agree, and most of its behaviour follows from which side of that
translation a given part belongs to.

    !pve_host@host>pve.host
     |______||__| |_______|
        |      |      `-- CPI vocabulary: what the release's job spec calls it
        |      `--------- operator vocabulary, superseded spelling
        `---------------- operator vocabulary, current spelling

In full, a descriptor is:

    [!]key[@alt1,alt2][:default|?][>path]

     !            marks the property secret
     key          primary lookup name
     @alt1,alt2   further lookup names, tried in order after key
     :default     value to use when no lookup finds one
     ?            optional; omit from the output entirely instead
     >path        where the value lands in the emitted properties

Every part except C<key> is optional. C<:default> and C<?> are mutually
exclusive. Omitting C<< >path >> makes the output path the same as C<key>.

The B<operator vocabulary> is flat, Genesis-namespaced, and chosen by the
kit author as their contract with whoever writes the environment file. The
B<CPI vocabulary> is whatever the CPI release declares, frequently nested,
and not Genesis's to choose.

C<< > >> exists only where the two disagree. C<access_key_id> needs no
C<< > >> because the operator and the AWS CPI happen to use the same word;
C<< http_endpoint>metadata_options.http_endpoint >> needs one because the
CPI namespaces it and an operator should not have to type that.

=head2 What each part means, and who supplies it

=over 4

=item C<key>

I<What does the operator call this?> Written by the kit author; read by the
environment and OCFP lookups. It is the stable, operator-facing identifier,
and by convention it is flat.

=item C<@alts>

I<What did we used to call it?> Written by the kit author, almost always
because a name changed and existing environments still use the old one.
Tried in order after C<key>.

=item C<:default>

I<What if the operator says nothing?> The kit author's opinion. Decoded as
JSON when it parses as such, so C<["bosh"]> arrives as an array rather than
a string.

=item C<?>

I<Is it required?> Marks the property genuinely optional: absent from the
output entirely rather than present and empty, which is a distinction the
CPI can act on.

=item C<!>

I<Must this stay out of the manifest?> Routes the value through CredHub
entombment, leaving a C<(( reference ))> behind.

=item C<< >path >>

I<What does the CPI call this?> The only part Genesis does not choose. It
is dictated by the CPI release's job spec, and changing a CPI can change
it.

=back

=head2 Where values come from

Resolved in strict precedence order, stopping at the first hit:

=over 4

=item 1.

C<bosh-configs.cpi.E<lt>key|altE<gt>> in the environment file -- the operator.

=item 2.

C<cpi.E<lt>iaasE<gt>.E<lt>key|altE<gt>> in the OCFP configuration.

=item 3.

The descriptor's C<:default> -- the kit author.

=back

B<Every operator name is tried before any platform name.> The two sources
are not consulted per name in step, which would let a platform value under
the primary key beat an operator value under an C<@alt> -- silently
overriding an operator who used the older spelling, which is the one thing
an alt must not do.

B<Presence decides, not definedness.> Within the operator's namespace the
first name that B<exists> settles the question, whatever it holds. A key
set to null is therefore how an operator discards a value the platform put
in the OCFP configuration and falls back to what the kit declares -- so a
null on the name the operator wrote is not rescued by an alt they did not.
A C<defined>-based test would quietly remove that mechanism.

A non-optional property found nowhere takes its C<:default>, which is the
empty string when the descriptor declares none. That is fatal only for a
C<!> secret, which cannot be entombed empty; see L</_entomb_if_needed>.

=head2 A dot means different things on each side

On the B<lookup> side a dot is a nested lookup: C<struct_lookup> descends
C<bosh-configs.cpi.E<lt>keyE<gt>>, so a dotted key reads a nested value
from the environment file.

On the B<output> side a dot is structure. The resolved pairs are collected
flat and handed to C<Genesis::unflatten>, which splits on dots to build the
nesting the CPI expects:

    {pve.host, pve.user, agent.mbus, flat_key}
      => {pve => {host, user}, agent => {mbus}, flat_key}

So dots in C<< >path >> are not decoration and cannot simply be removed --
they are the only way to emit a nested CPI property.

Where a literal dot is wanted in an output key rather than nesting,
C<unflatten> treats C<~> as an escape: C<a~b> yields the single key
C<a.b>, and C<p.q~r> yields C<p> containing the single key C<q.r>.

That escape is B<not> available on the input side. C<Genesis::flatten> does
not escape a literal C<~> on the way in, so C<unflatten> turns it into a dot
on the way out and a key written C<we~ird> returns as
C<we.ird>. Rather than build on a mechanism that does not round-trip, an
operator key holding a literal dot -- C<"pve.host": value> -- is refused,
with the nested spelling offered instead.

=head2 How an operator addresses a property

C<bosh-configs.cpi> is flattened to its leaves, and each leaf is classified
once against two sets -- the map's source keys (with their C<@alts>) and the
map's output paths:

=over 4

=item *

A leaf matching a source key or an C<@alt> resolves that mapped property.

=item *

A leaf matching a mapped C<< >path >> B<also> resolves that mapped
property. It is not passthrough.

=item *

A leaf matching neither passes through to the CPI config untouched.

=back

Both spellings are routes into the same property, with identical
entombment, defaults and optionality. The second rule is not a convenience:
for C<< !pve_host@host>pve.host >>, an operator writing C<pve: {host:
E<lt>secretE<gt>}> must have that entombed. Routing a mapped path to
passthrough instead would mean C<!> never applies -- it lives on the
descriptor -- and the secret would ship in cleartext.

Because every route is equivalent, a property may be addressed B<exactly
once>. Its source key, any of its C<@alts>, and its C<< >path >> are three
spellings of one thing, so setting any two of them together is fatal --
key with path, key with alt, or alt with path alike. The ambiguity is
precisely what the rule removes, and it does not become less ambiguous for
being spelled with an alt.

The error names the two leaves that collided rather than the key and the
path, since which pair of routes was used varies and a message that assumed
one pair would misdescribe the other two.

The path form exists so that a nested block carrying both modelled and
unmodelled properties need not be split across two spellings:

    pve:
      host: x          # mapped
      unknown: y       # passthrough -- the block justifies the path form

Where that justification is absent -- every leaf under the same parent
resolves to a mapped property -- the operator has taken on the exposure
below and gained nothing, so a warning names the key that would have done
instead. Granularity is same-parent: the most local rule, and the easiest
to explain.

B<The exposure, stated:> if a CPI renames a property and the kit's map
follows, a leaf using the B<path> form silently becomes a passthrough at a
dead address. The value stops reaching the property, the default takes
over, and nothing errors -- because "meant the mapped path, which moved" is
indistinguishable from "wants a passthrough here". The key form has no such
exposure, as the map absorbs the rename. This is the same bargain
passthrough already offers, which is why it is a warning rather than a
refusal.

=head2 Constraints and traps in the descriptor grammar

=over 4

=item *

C<key> may not contain C<@>, C<:>, C<?> or C<< > >>. It B<may> contain a
dot, which makes it a nested lookup as above.

=item *

C<@alts> may not contain C<:>, C<?> or C<< > >>, but C<@> B<is> accepted
inside it. That asymmetry with C<key> is incidental rather than designed.

=item *

C<:default> may not contain C<< > >>, and this fails silently rather than
loudly: C<< key:a>b >> parses as default C<a> and path C<b> with no error.
A default holding a URL or comparison containing C<< > >> will be
misparsed.

=item *

With no C<< > >>, the output path defaults to C<key>, so a dotted key is
simultaneously a nested lookup and a nested output.

=back

=head2 Where the results go

Resolved non-secret values become the flattened C<%config>, which is
unflattened into the C<properties> of a single entry in C<cpis>, and from
there into the director's CPI config.

Secret values are replaced in that structure by a C<(( path ))> reference,
with the value itself collected into C<credhub_secrets> and committed to
the director's CredHub under C<bosh-configs.cpi.credhub_base>, or under
C<< <credhub base>genesis-entombed/ >> when that is not set.

The entombed secret's name is Genesis's own bookkeeping and belongs to
neither vocabulary. It is currently derived from the CPI-side path, which
couples Genesis's records to a name the CPI owns; see
L</cpi_entombment_path_for> for the consequences.

=head1 INTERNAL METHODS

These are internal to the implementation and may change without notice.

=head2 _parse_property

    my $spec = $hook->_parse_property($descriptor);

Splits one property descriptor into its parts. Pure: performs no lookups
and touches no state.

B<Parameters:>

=over 4

=item C<$descriptor>

A descriptor string in the grammar described under L</PROPERTY MAPPING>.

=back

B<Returns:> A hash reference with the keys:

=over 4

=item C<key>

The primary lookup name -- the operator-facing spelling.

=item C<alts>

Array reference of alternate lookup names, in the order they were
declared. Empty when none were given.

=item C<lookups>

C<key> followed by C<alts>, which is the order they are consulted in.
Provided so callers do not rebuild it, and so the set of names a map
consumes is available without reassembling it from two fields.

=item C<default>

The declared default, verbatim. JSON decoding happens at resolution
time, not here, so a default of C<["bosh"]> is still a string at this
point.

=item C<optional>

C<1> when the descriptor ended in C<?>, else C<0>.

=item C<secret>

C<1> when the descriptor began with C<!>, else C<0>.

=item C<path>

Where the value lands in the emitted properties -- the C<< > >> side, or
C<key> when the two vocabularies agree.

=back

B<Errors:>

Dies with C<"Invalid CPI config property specification '%s' in kit
cpi-config hook (expected [!]key[@alt][:default|?][>path])"> when the
descriptor does not parse. The message repeats the grammar because the
descriptor comes from a kit's C<cpi-config> hook, so its author is the
one who has to correct it.

B<Examples:>

    $hook->_parse_property('region');
    # { key => 'region', alts => [], lookups => ['region'], default => '',
    #   optional => 0, secret => 0, path => 'region' }

    $hook->_parse_property('!host@addr:def>a.b.c');
    # { key => 'host', alts => ['addr'], lookups => ['host','addr'],
    #   default => 'def', optional => 0, secret => 1, path => 'a.b.c' }

=head2 _resolve

    my ($value, $found) = $hook->_resolve($spec, $routed_leaf);

Finds the value for one property spec.

Consults B<every> name the operator might have used before B<any> name
the platform might have used. Doing it the other way -- both sources per
name -- lets an OCFP value under the primary beat an operator value under
an C<@alt>, so an operator still using an older spelling is silently
overridden by the platform default. Preventing that is what an C<@alt> is
for.

The operator side reads through C<lookup_entombed_self>, so a
C<(( vault ))> reference in the environment file arrives already entombed.
The platform side reads C<ocfp_config_lookup> and JSON-decodes when it
can, falling back to the raw string.

B<Parameters:>

=over 4

=item C<$spec>

A spec from L</_parse_property>.

=item C<$routed_leaf>

Optional. When the operator addressed the property by its CPI path rather
than by its key, the leaf where the value sits. Given, only that leaf is
consulted on the operator side; omitted, the spec's names are swept in
order.

=back

B<Returns:> C<($value, $found)>. C<$found> reports whether anything
B<stopped the search>, not whether there is a usable value: a key that
exists settles the question whatever it holds, which is what makes an
explicit null able to discard an OCFP value. Callers wanting "is there a
value" must test C<defined($value)>, not C<$found>.

B<Errors:>

None. An unresolvable property is reported as not found.

B<Examples:>

    $hook->_resolve($spec);              # sweep the spec's own names
    $hook->_resolve($spec, 'pve.host');  # the operator used the CPI path

=head2 _entomb_if_needed

    my $value = $hook->_entomb_if_needed($spec, $value);

Applies the entombment rule to one resolved value, in this order:

=over 4

=item 1.

A value already matching C<((...))> is returned untouched, B<regardless of
C<!>>. Entombment has happened upstream, and doing it again would store a
reference to a reference.

=item 2.

Without C<!>, the value is returned as-is.

=item 3.

An undefined or empty value B<dies>. An empty secret cannot be stored, and
failing here names the property; left alone it surfaces much later as a
missing CredHub value, naming a path instead.

=item 4.

Otherwise the value is entombed via L</cpi_entombment_path_for>, recorded
in C<credhub_secrets>, and replaced by its C<(( reference ))>.

=back

C<!> exists chiefly for values drawn from the B<OCFP config>, which lives
in vault and can hold credentials and certificates: there is no other way
to place one in custom CredHub entombment. An operator value overriding
such a property is entombed too, so that the same property does not land
in CredHub or in the clear depending on which source supplied it.

B<Parameters:>

=over 4

=item C<$spec>

A spec from L</_parse_property>; only C<secret>, C<key> and C<path> are
consulted.

=item C<$value>

The resolved value.

=back

B<Returns:> The value to emit -- unchanged, or a C<(( reference ))>.

B<Errors:>

Dies with C<"Cannot entomb CPI property #C{%s}: no value was found for it
in #C{bosh-configs.cpi} or the OCFP config, and an empty secret cannot be
stored."> when a C<!> property resolves to undef or the empty string.

B<Examples:>

    $hook->_entomb_if_needed($spec, 's3cr3t');
    # '((/cpi-config/properties/cpi-config-property--api_key--a1b2c3d4))'

    $hook->_entomb_if_needed($spec, '((genesis-entombed/x--y--abc12345))');
    # unchanged -- already a reference

=head1 METHODS

=head2 init

    my $hook = Genesis::Hook::CpiConfig->init(%opts);

Constructs and returns a new C<Genesis::Hook::CpiConfig> object. Delegates
to the parent class for base initialization, then initializes two internal
stores: C<cpi_config> (empty hashref) and C<credhub_secrets> (empty
hashref).

B<Parameters:>

=over 4

=item C<%ops>

Key-value pairs passed through to C<Genesis::Hook>'s C<init>. The C<env> key
is required. See L<Genesis::Hook/init> for the full list of accepted options.

=back

B<Returns:> A blessed C<Genesis::Hook::CpiConfig> object (or subclass).

B<Examples:>

    my $hook = Genesis::Hook::CpiConfig->init(env => $env);
    # Returns: a blessed Genesis::Hook::CpiConfig object

=head2 done

    $hook->done($config, $error);
    $hook->done(undef, $error_message);
    $hook->done($config);

Signals that CPI config generation is complete. When C<$config> is a
defined, truthy value, it is serialized to a temporary YAML file and the
YAML string is stored as the hook's content. When C<$config> is false or
undefined, the content is set to C<undef>. An optional C<$error> string
records any error that occurred during generation. Sets the internal
C<complete> flag to C<1>.

Modifies the object in-place.

B<Parameters:>

=over 4

=item C<$config>

A data structure (hashref) representing the CPI config to serialize to YAML,
or C<undef> / a false value to indicate that no config was produced.

=item C<$error>

B<(optional)> An error message string to record. Stored as C<undef> if not
provided.

=back

B<Returns:> C<1> (the value of the C<complete> flag after being set).

B<Examples:>

    # Signal success with a config structure
    $self->done($cpi_config_hashref);
    # Returns: 1

    # Signal that generation produced no config
    $self->done(undef, "IaaS not supported for this environment");
    # Returns: 1

=head2 results

    my $hashref          = $hook->results;
    my ($content, $secrets, $error) = $hook->results;

Returns the results of CPI config generation after C<done> has been called.
Returns early with an empty/undefined value if the hook has not yet
completed.

In scalar context, returns a hashref with three keys: C<content> (the
generated YAML string, or C<undef>), C<credhub_secrets> (a hashref mapping
CredHub credential names to their values), and C<error> (an error message
string, or C<undef>).

In list context, returns the three values directly in the order
C<(content, credhub_secrets, error)>.

B<Returns:>

In scalar context: a hashref with keys C<content>, C<credhub_secrets>, and
C<error>, or C<undef> if the hook has not completed.

In list context: C<($content, $credhub_secrets, $error)>, or an empty list
if the hook has not completed.

B<Examples:>

    $hook->done($config);

    # Scalar context
    my $r = $hook->results;
    print $r->{content};
    # Returns: { content => '...yaml...', credhub_secrets => {...}, error => undef }

    # List context
    my ($yaml, $secrets, $err) = $hook->results;
    # Returns: ('...yaml...', { '/path/cred--key--abc1234' => 'value' }, undef)

    # Before done() is called
    my $r = $hook->results;
    # Returns: undef (scalar context) or () (list context)

=head2 build_cpi_config_for_iaas

    my $config = $hook->build_cpi_config_for_iaas(%configs);

Builds a BOSH CPI config data structure for the environment's IaaS type.
C<%configs> is a dispatch table mapping IaaS type strings (e.g., C<'aws'>,
C<'vsphere'>) to either a properties hashref or a code reference that
returns one. Only the entry matching the environment's current IaaS is used.
If the current IaaS is not present in C<%configs>, the method terminates
with an error.

B<Parameters:>

=over 4

=item C<%configs>

A hash mapping IaaS type strings to CPI properties. Values may be either a
hashref of CPI properties or a C<CODE> reference that, when called with no
arguments, returns a hashref of CPI properties.

=back

B<Returns:> A hashref suitable for passing to C<done>, structured as:

    {
        cpis => [
            {
                name       => $env->cpi_name,
                type       => $iaas,
                properties => \%properties,
            }
        ],
    }

B<Errors:>

=over 4

=item *

C<"Unsupported IaaS: %s"> -- raised via C<bail()> if the environment's IaaS
type is not a key in C<%configs>. C<%s> is replaced with the IaaS type
string.

=back

B<Examples:>

    my $config = $hook->build_cpi_config_for_iaas(
        aws     => { region => 'us-east-1', default_key_name => 'bosh' },
        vsphere => sub { { datacenter => $hook->env->lookup('params.datacenter') } },
    );
    # Returns: { cpis => [{ name => 'aws_cpi', type => 'aws', properties => {...} }] }

    $self->done($config);
    # Returns: 1

=head2 gather_properties

    my $properties = $hook->gather_properties(@properties);

Resolves a list of CPI property descriptors into a flat hashref of values
suitable for use as the C<properties> key in a CPI config structure. Each
descriptor is a string in a mini-language that controls where to look up the
value, what default to use, and where to place it in the output.

B<Property descriptor syntax:>

    [!]property_name[@alt1,alt2][:default_value|?][>config_path]

=over 4

=item C<property_name>

The primary lookup key. Used to search C<bosh-configs.cpi.E<lt>keyE<gt>> in
the environment manifest, and C<cpi.E<lt>iaasE<gt>.E<lt>keyE<gt>> in the
OCFP configuration. Also used as the output key in the returned hashref
unless C<< > >> is specified.

=item C<!>

Marks the property as a secret. The resolved value is entombed in CredHub
via C<cpi_entombment_path_for>, the original value is stored in the hook's
C<credhub_secrets> store, and the property's value in the output is replaced
with the CredHub reference C<(( path ))>.

=item C<@alt1,alt2,...>

Alternative lookup keys tried in order if C<property_name> is not found.
Multiple alternatives are comma-separated.

=item C<:default_value>

A default value to use if the property is not found via any lookup. The
default is parsed as JSON if possible; otherwise used verbatim. Use C<true>,
C<false>, and C<null> for their JSON/YAML equivalents. Quoted strings are
parsed as JSON strings.

=item C<?>

Makes the property optional. If not found via any lookup, the property is
omitted from the output entirely (no error, no default).

=item C<< >config_path >>

Overrides the output key in the returned hashref. Useful for nested
properties using dot-notation (e.g., C<< connection_options.connect_timeout >>).

=back

B<Resolution is a single pass.> The operator's C<bosh-configs.cpi> is read
once, flattened to leaves, and each leaf is classified exactly once -- as a
route into a mapped property, or as passthrough. Every property is then
resolved and emitted once, from one manifest, under one ruleset. See
L</How an operator addresses a property> for the classification, and
L</Where values come from> for the precedence within a resolution.

That partition is the whole of the method's logic. It replaces an earlier
arrangement in which the operator's namespace was read B<twice> -- once
through C<lookup> against the merged, evaluated manifest for the declared
properties, and again through C<lookup_unevaled> against the raw
environment files for anything left over. A single operator setting was not
merely read twice but resolved into two different values from two different
manifests, both of which could reach the output: a C<!> secret could be
re-emitted in cleartext beside the CredHub reference meant to replace it,
and a spruce operator could reach the director as a literal, where it is
parsed as a BOSH variable reference and fails every deployment against that
director.

Operator values are read through C<lookup_entombed_self>, so a C<(( vault
))> reference in the environment file -- explicit or implicit, at any depth
-- arrives already entombed. This is what retired the hand-rolled vault
regex that scanned only scalars, and with it the limitation that a vault
reference nested inside a hash or array reached the CPI config
un-entombed.

The resulting flat hash is passed through C<unflatten> to produce a nested
structure when dot-notation config paths are used. Leaf-level flattening
also means passthrough no longer hands whole subtrees through by reference,
which previously let C<unflatten> alias the environment's own parameters
into the emitted config -- so building a CPI config rewrote the
environment's view of itself.

B<Parameters:>

=over 4

=item C<@properties>

A list of property descriptor strings as described above.

=back

B<Returns:> A hashref of resolved CPI property values, unflattened into a
nested structure.

B<Errors:>

=over 4

=item *

C<"Invalid CPI config property specification '%s' in kit cpi-config hook
(expected [!]key[@alt][:default|?][>path])"> -- raised via C<bail()> when a
descriptor does not parse against the syntax above.  The message repeats the
grammar, since the descriptor comes from a kit's C<cpi-config> hook and its
author is the one who has to correct it.

=item *

C<"Cannot set %s in bosh-configs.cpi: a quoted key holding a literal dot is
not supported -- nest it instead."> -- raised via C<bail()> when an operator
key contains a literal dot, detected as a C<~> in the flattened leaf. The
message offers the nested spelling, which is the supported form.

=item *

C<"CPI property %s is set more than one way in bosh-configs.cpi: %s and %s
both address it -- set only one."> -- raised via C<bail()> when one property
is addressed twice, by any two of its source key, its C<@alts>, and its
C<< >path >>. The second and third C<%s> are the two colliding leaves, in
sorted order so the message does not vary with hash ordering.

=item *

C<"Cannot entomb CPI property %s: ..."> -- raised via C<bail()> from
L</_entomb_if_needed> when a C<!> property resolves to nothing and no
default supplies one, since an empty secret cannot be stored. This is the
error the dead C<"Missing default for CPI config value"> bail was meant to
catch and never could: C<:default> defaults to the empty string, so the
value was always defined by the time that test ran, and the failure instead
surfaced much later as C<"N missing secret values"> -- naming a CredHub path
rather than the property, after the config had already been built.

=back

B<Warnings:> a modelled property addressed by its C<< >path >> where no
unmodelled leaf shares its parent warns, naming the source key that would
have avoided the rename exposure. See L</How an operator addresses a
property>.

B<Examples:>

    my $props = $hook->gather_properties(
        'datacenter',                        # required, from env or OCFP
        'datastore:default-datastore',       # optional with default
        'timeout?',                          # omitted if not set
        '!vcenter_password',                 # secret: entombed in CredHub
        'clusters@vsphere_clusters:[]',      # alternate lookup with default
        'ntp>global.ntp',                    # placed at properties.global.ntp
    );
    # Returns: { datacenter => '...', datastore => '...', global => { ntp => [...] }, ... }

=head2 cpi_entombment_path_for

    my $credhub_path = $hook->cpi_entombment_path_for($path, $value);

Computes a deterministic CredHub credential path for a CPI config property
value. The result is of the form:

    $prefix . 'cpi-config-property--' . $flattened . '--' . $sha1

where C<$prefix> is taken from C<< $self->{credhub_prefix} >> if set,
otherwise from C<< $env->cpi_credhub_base >>; C<$flattened> is C<$path>
with every character outside C<[A-Za-z0-9_-]> replaced by an underscore;
and C<$sha1> is the first 8 hex characters of the SHA-1 digest of the
string C<"cpi-config-property--$path--$value">, built from the B<original>
path rather than the flattened one.

The flattening exists because BOSH resolves a C<(( name.subkey ))>
reference by splitting it on the first dot. A credential whose name
contains a dot is therefore asked for under a truncated name, and the
director gets a 404 -- which fails every read of the affected config, not
just the one property. Array indices need the same treatment, since an
output path may address an array element such as C<< nics[0].ip >>. See
L</PROPERTY MAPPING> for why an output path carries these characters in
the first place.

Because the digest covers the unflattened path, two paths that flatten
alike -- C<pve.host> and C<pve_host> -- still receive distinct entries. A
path already within C<[A-Za-z0-9_-]> is returned unchanged, so introducing
the flattening moved only entries that were already unusable.

This method is used internally by C<gather_properties> to generate stable,
unique CredHub paths for secret values. The result is the same for a given
combination of path and value, making it safe to call idempotently.

B<Parameters:>

=over 4

=item C<$path>

The output path the property occupies in the emitted CPI config -- the
C<< > >> side of a descriptor, or the property name where no C<< > >> was
given. Note this is the CPI-side address rather than the operator-facing
key; see L</PROPERTY MAPPING>.

=item C<$value>

The secret value. Incorporated into the SHA-1 hash to produce a unique path
per distinct value.

=back

B<Returns:> A CredHub credential path string of the form
C<"${prefix}cpi-config-property--$flattened--$sha1">.

B<Errors:>

None. Every input yields a path; a C<$path> consisting entirely of
characters outside C<[A-Za-z0-9_-]> flattens to a run of underscores and
is still distinguished by its digest.

B<Examples:>

    $hook->cpi_entombment_path_for('vcenter_password', 's3cr3t');
    # Returns: '/bosh/cpi-config-property--vcenter_password--a1b2c3d4'

    $hook->cpi_entombment_path_for('pve.host', 'pve.example.com');
    # Returns: '/bosh/cpi-config-property--pve_host--e5f6a7b8'

B<Limitations:>

The entombed name is Genesis's own bookkeeping, but is derived from the
CPI-side path rather than the operator-facing key. A CPI release that
renames one of its nested properties therefore renames the corresponding
CredHub entry, orphaning the old one and entombing afresh on the next
deploy.

The name is also what an operator is shown when a secret is missing --
C<Genesis::Env> extracts it from between the C<--> delimiters for that
message -- so the reported name is the flattened CPI-side path rather than
the name they set in their environment file.
