=head1 NAME

Genesis::Commands - Command infrastructure and dispatch for Genesis CLI

=head1 SYNOPSIS

  # In bin/genesis -- register a command
  use Genesis::Commands;

  define_command('deploy',
    {
      summary        => 'Deploy a Genesis environment',
      scope          => 'env',
      function_group => ENVIRONMENT,
      option_group   => ENV_OPTIONS,
      options        => [
        'dry-run|n' => 'Perform a dry run without deploying',
      ],
    }
  );

  # From within a command implementation
  my %opts = %{get_options()};
  my @args = get_args();
  bail "need an environment name" unless @args;

  # CLI invocation (from the shell)
  genesis deploy my-env
  genesis --help
  genesis deploy --help-full

=head1 DESCRIPTION

C<Genesis::Commands> is the procedural backbone of the Genesis CLI.  It
provides command registration, option parsing, dispatch, help generation,
and pre-flight validation.  All functions are exported into the caller's
namespace via C<@EXPORT>.

The module maintains several package-level data structures that track the
currently active command and its parsed state:

=over 4

=item C<$COMMAND>

The canonical name of the active command (e.g., C<deploy>), set during
C<prepare_command>.

=item C<$CALLED>

The alias or name actually typed by the user (e.g., C<dep> if the user
typed an alias), set during C<prepare_command>.

=item C<%RUN>

A dispatch table mapping command names to the closures that execute them.
Populated by C<define_command>.

=item C<%PROPS>

A property hash mapping command names to their registered metadata
(scope, option group, aliases, summary, description, options, etc.).
Populated by C<define_command>.

=item C<%GENESIS_COMMANDS>

Maps every known name (canonical and aliases) to the canonical command
name.  Populated by C<define_command>.

=item C<@COMMANDS>

An ordered list of canonical command names in registration order.
Populated by C<define_command>.

=back

=head1 CONSTANTS

B<Function-Group Constants>

The following constants are hash references used as the C<function_group>
property in C<define_command>.  Each carries C<order>, C<module>, and
C<label> keys that drive help output grouping and default dispatch module
resolution.

=over 4

=item C<ENVIRONMENT>

Order 0.  Module C<Env>.  Label C<Environment Management>.

=item C<BOSH>

Order 1.  Module C<Bosh>.  Label C<BOSH Actions>.

=item C<INFO>

Order 2.  Module C<Info>.  Label C<Informative>.

=item C<REPOSITORY>

Order 3.  Module C<Repo>.  Label C<Repository Management>.

=item C<KIT>

Order 4.  Module C<Kit>.  Label C<Kit Management>.

=item C<PIPELINE>

Order 5.  Module C<Pipelines>.  Label C<Pipeline Management>.

=item C<GENESIS>

Order 6.  Module C<Core>.  Label C<Genesis Management>.  This is the
default function group for commands that do not specify one.

=item C<UTILITY>

Order -1.  Module C<Utility>.  Label C<Script Callback Helper>.

=item C<DEPRECATED>

Order -2.  Module C<Deprecated>.  Label C<Deprecated>.

=item C<DEV>

Order -3.  Module C<Core>.  Label C<Development>.

=item C<WIP>

Order -4.  Module C<Wip>.  Label C<Work in Progress>.

=back

Commands with a negative order are hidden from the default help output and
only appear when C<--all> is passed.

B<Option-Group Constants>

Each constant represents a tier of global options that the command opts
into.  Higher tiers are supersets of lower ones.

=over 4

=item C<BLANK_OPTIONS> (0)

No global options.  The command receives no pre-defined options from the
global option set.

=item C<BASE_OPTIONS> (1)

Includes help flags (C<--help>, C<--help-full>, C<--helpful>, C<--globals>),
logging and verbosity flags (C<--color>, C<--log>, C<--quiet>, C<--debug>,
C<--trace>, C<--show-stack>).  This is the default for commands that do
not specify C<option_group>.

=item C<REPO_OPTIONS> (2)

Extends C<BASE_OPTIONS> with C<--cwd|-C> (effective working directory).
Appropriate for commands that operate on a Genesis deployment repository.

=item C<ENV_OPTIONS> (3)

Extends C<REPO_OPTIONS> with C<--bosh-env|-e>, C<--config|-c>, and
C<--cpi>.  Appropriate for commands that target a specific environment and
may interact with a BOSH director.

=back

B<Branch-Class Constants>

Each constant is the value of the C<branch_class> property in
C<define_command>, and the two are the only legal values it takes.

=over 4

=item C<PRE_DEPLOY> (C<'pre-deploy'>)

The command changes what will be delivered, so it belongs on the control
branch or on a permitted feature branch.

=item C<DEPLOYED_STATE> (C<'deployed-state'>)

The command operates on what an environment is running, so it belongs on
that environment's deployment branch.

=back

B<The Deployed-Commit Help Sentence>

=over 4

=item C<DEPLOYED_TARGET_HELP>

The single help sentence printed by both C<--redeploy> and C<--as-deployed>.
The two flags select the same thing, the environment's deployed commit, so
they describe it in one place and cannot drift apart. Like the branch-class
constants above it is not exported, and every registration in F<bin/genesis>
names it in full as C<Genesis::Commands::DEPLOYED_TARGET_HELP>.

=back

=head2 Branch classes

Every pipeline-aware command declares one branch class at its registration,
beside its scope and its function group. The class is one of two constants
this module defines, C<PRE_DEPLOY> and C<DEPLOYED_STATE>. Neither is
exported, so a registration names the one it wants in full, as
C<Genesis::Commands::PRE_DEPLOY>, which is what every registration in
F<bin/genesis> does. The value is read back from
C<command_properties($cmd)-E<gt>{branch_class}>.

    define_command("propagate", {
        ...
        branch_class  => Genesis::Commands::PRE_DEPLOY,
        branch_target => 'control',
    });

A pre-deploy command changes what will be delivered, so it runs on the
control branch or on a permitted feature branch and refuses elsewhere. A
deployed-state command operates on what an environment is running, so it
switches to that environment's deployment branch inside a session. A
command that declares no class is not gated at all.

C<branch_target> is optional and is declared by C<propagate> alone. It says
that the command switches to control inside the session it already holds,
so the gate leaves it where it stands.

C<commits> is optional and is declared by C<create> alone. It says that the
command makes a commit on control, which is what decides whether a
repository requiring a pull request into control refuses the command there.
Most pre-deploy commands commit nothing: C<pipeline-apply> writes to the
provider, C<pipeline-status> and C<pipeline-describe> only read, and the
secrets commands write to the vault. C<pipeline-apply> is the command that
applies the protection the key derives, so a refusal that caught it would
leave an operator no way to turn the protection on.

The same property drives the marker the help listing prints beside each
command, so the listing and the refusal always agree.

=head2 The deployed-state switch

A command whose registration declares C<DEPLOYED_STATE> is run inside a
branch session that has already switched to the environment's deployment
branch, C<< <env>/<type> >>. The command therefore reads and renders what
was delivered rather than what is coming, and it writes no git of its own.

The session is opened by the gate, not by the command, so that every
deployed-state command switches the same way and takes the same switch
lock. The gate runs the command inside that session and closes it where the
command returns, so an ordinary run is back on the operator's own branch
before the process exits. A command that refuses exits with its own code,
and the session's own last-resort net puts the working tree back.

The branch the session stands on is the deployment branch's tip. D87 has a
deployed-state command default to the commit the environment last deployed,
and M14 supplies that commit through C<deployed_target>; until it does, the
tip is what is read.

A command already standing on the branch it would switch to opens no session
and takes no switch lock, because a session exists to leave a branch and come
back and there is nothing here to leave. So a deploy run from the
environment's own branch tolerates an edit in place, which is how an operator
tests a change without committing it first.

An environment with no deployment branch is not switched at all. That is
every environment between C<genesis new> and its first deploy, and the
command runs where it stands and reports in its own words that there is
nothing deployed to read.

Each of those three arms says which one it took, in one line, before the
command runs. A command reading the deployment branch and a command reading
whatever the operator is standing on answer different questions, and the
answer alone does not say which was asked. The line states the fact and
nothing more; refusing on any of the three states belongs to each command's
own classification of it. The arm an operator meets by accident is the first,
since standing on a deployment branch is an easy state to arrive at and a
deploy of the working tree as it stands reads no differently from any other
until something in it was not meant to ship.

A branch that C<genesis pipeline-apply> cut and no C<genesis propagate> run
has delivered to is not switched onto either. It carries its init file and
nothing else, so there is no repository on it to read, and a command switched
onto it would be looking at a tree with no configuration in it and would say
so rather than saying what was really wrong. The question asked is whether
the branch carries the deployment root's own C<.genesis/config>, because
every delivery mirrors that file and nothing else on the branch is
guaranteed. C<branch_carries_repository> is where that question is asked,
and the command asks it again where it classifies the branch for itself. The
gate only declines to switch, and a command that went on to read whatever the
operator was standing on would deploy or report from the wrong place
entirely.

Two states answer that question the same way and are not alike at all. An
environment nothing has been delivered to waits for a propagation. A clone
nobody has pulled since the apply cut the branch holds the init commit while
the remote holds every delivery, and it waits only for the branch to be
brought forward.

So the gate fast-forwards a branch this clone holds behind its
remote-tracking ref, before it asks what the branch carries and before it
switches, for a command whose registration declares C<branch_fast_forward>
and for no other. That is C<genesis deploy> today. The branch is the working
tree a command reads, and the checkout stands that tree on the commit the
local ref names, so a command that acts on the branch needs it current, while
a command that only reads it has no business moving a ref. The move is made
on the one state that promises a fast-forward, so it creates and discards
nothing, and nothing is fetched, because the refresh is its own step under
D40.

Where no move is made, the line the gate prints names how far behind its
counterpart the branch stands, so an operator of C<genesis info> or the
C<bosh> subcommands reads why what they are looking at is not the delivered
branch.

C<branch_session> answers the session the gate opened for this command, or
C<undef> where it opened none. A command reads it rather than asking the git
handle for a session, because C<< $git->session >> builds a fresh one on a
handle that never opened any, and a fresh session answers
C<finish_if_clean> false for a tree that is perfectly clean.

=head1 FUNCTIONS

=head2 define_command

  define_command($name, \%props, $fn);
  define_command($name, \%props);
  define_command($name, $fn);
  define_command($name);

Registers a Genesis CLI command.  This is the primary entry point for
adding commands to the dispatch table.

B<Parameters:>

=over 4

=item C<$name>

The canonical command name (e.g., C<'deploy'>).  Hyphens are acceptable
and are translated to underscores when resolving the default function name.

=item C<\%props>

Optional hashref of command properties.  Recognized keys:

=over 4

=item C<summary> - One-line description shown in C<genesis --help> output.

=item C<description> - Full description shown in command-specific help.

=item C<usage> - Usage string shown in command-specific help.

=item C<scope> - Execution context.  A string (C<'any'>, C<'env'>,
C<'repo'>, C<'kit'>, C<'empty'>, C<'pipeline'>) or an arrayref of scope
fragments for conditional scoping.  Defaults to C<'any'>.

=item C<no_vault> - Boolean.  When true, sets C<GENESIS_NO_VAULT=1> in the
environment before running the command.  Defaults to C<0>.

=item C<function_group> - One of the function-group constants
(C<ENVIRONMENT>, C<BOSH>, etc.).  Controls help grouping and default
dispatch module resolution.  Defaults to C<GENESIS>.

=item C<option_group> - One of the option-group constants
(C<BLANK_OPTIONS>, C<BASE_OPTIONS>, C<REPO_OPTIONS>, C<ENV_OPTIONS>).
Controls which global options are available.  Defaults to C<BASE_OPTIONS>.

=item C<option_passthrough> - Boolean.  When true, unknown options are
passed through to the command rather than causing an error.  Defaults to
C<0>.

=item C<branch_class> - The branch class the command belongs to, either
C<PRE_DEPLOY> or C<DEPLOYED_STATE>.  It drives both the refusal off a
forbidden branch and the marker the help listing prints, so the two can
never disagree.  Defaults to C<undef>, which leaves the command ungated.

=item C<branch_target> - The branch the command switches to inside its own
session, declared only alongside a C<branch_class>.  C<propagate> is the
one command that declares it, and C<'control'> is the one value it may
take, because that is the only target the gate compares against.  Defaults
to C<undef>.

=item C<commits> - Boolean.  True where the command makes a commit on the
control branch, which C<create> alone declares.  It decides whether the
C<control_requires_pr> refusal applies, because D45 is about a commit that
cannot reach control through a pull request and most pre-deploy commands
make none.  It is declared only alongside C<branch_class =E<gt> PRE_DEPLOY>,
since that is the one gate that reads it.  Defaults to C<undef>.

=item C<branch_fast_forward> - Boolean.  True where the gate may bring the
environment's deployment branch up to its remote-tracking ref before it
switches onto it, which C<deploy> alone declares.  A clone that has not
pulled holds the branch where C<genesis pipeline-apply> cut it, and the
checkout stands the working tree on the commit the local ref names, so a
command that acts on the branch needs it brought forward first while a
command that reads it has no business moving anything.  It is declared only
alongside C<branch_class =E<gt> DEPLOYED_STATE>, since that is the one gate
that reads it.  Defaults to false.

=item C<option_require_order> - Boolean.  When true, option parsing stops
at the first non-option argument.  Defaults to false.

=item C<options> - Arrayref of Getopt::Long-style option specifications
and their descriptions, interleaved: C<[$spec, $desc, $spec, $desc, ...]>.

=item C<deprecated_options> - Arrayref of deprecated option specifications.

=item C<arguments> - Arrayref of positional argument specifications and
descriptions for help output.

=item C<variables> - Arrayref of environment variable specifications and
descriptions for help output.

=item C<alias> - A single alias string for the command.

=item C<aliases> - Arrayref of alias strings for the command.

=item C<deprecated> - If set, the command is flagged as deprecated.  The
value may be a replacement command name string to include in the warning.
The command still runs after the warning is emitted.  Mutually exclusive
with C<retired>.

=item C<retired> - If set, the command is registered so C<has_command>
still recognizes it and dispatch bails with a targeted retirement
message, but the command is hidden from the default C<genesis help>
catalog.  It is re-surfaced under C<genesis help --all>, parallel to
commands in the DEPRECATED function group.  The value may be a scalar
message or a hashref of the form C<{message =E<gt> "..."}>; the message
is included in the bail output.  Use for commands that must not execute
under this Genesis version (e.g., pipeline tasks that would produce a
silent-but-wrong deploy if the pipeline has not been migrated first).
Mutually exclusive with C<deprecated>; declaring both causes
C<define_command> to bail with a bug diagnostic.

=item C<extended_usage> - A coderef returning extended usage text appended
to command-specific help.

=back

=item C<$fn>

Optional.  Either a coderef to call directly, or a fully qualified
function name string (e.g., C<'Genesis::Commands::Env::deploy'>).  When
omitted, the function name is derived from the C<function_group>'s module
and the command name with hyphens replaced by underscores.

=back

B<Returns:> Nothing.

B<Errors:>

=over 4

=item C<"Command %s declares both retired and deprecated; use retired alone once the command no longer runs.">

Raised via C<bug> when a single C<define_command> call supplies both
the C<retired> and C<deprecated> properties.  The two are mutually
exclusive -- C<retired>'s refuse-to-run always trumps C<deprecated>'s
warn-and-run, so declaring both leaves the intent ambiguous.  Remove
C<deprecated> once the command has been retired.

=item C<"Command %s declares the branch class %s; the only classes are pre-deploy and deployed-state.">

Raised via C<bug> when C<branch_class> is set to anything but
C<PRE_DEPLOY> or C<DEPLOYED_STATE>.  A misspelled class would gate
nothing and say nothing, which is the failure a single declaration
exists to rule out.

=item C<"Command %s declares that it commits on control without the pre-deploy branch class.">

Raised via C<bug> when C<commits> is true and C<branch_class> is anything
but C<PRE_DEPLOY>.  Only the pre-deploy assertion asks whether a command
commits on control, so the attribute anywhere else is read by nobody and
reads as though the command had been exempted from the
C<control_requires_pr> refusal when it was never subject to it.

=item C<"Command %s declares that it fast-forwards its deployment branch without the deployed-state branch class.">

Raised via C<bug> when C<branch_fast_forward> is true and C<branch_class> is
anything but C<DEPLOYED_STATE>.  Only the deployed-state gate asks whether a
command may move the branch, so the attribute anywhere else is read by nobody
and reads as though the command moved a ref it never touches.

=item C<"Command %s declares a branch target without a branch class.">

Raised via C<bug> when C<branch_target> is set and C<branch_class> is
not.  A target names where an already-classed command takes itself, so
it means nothing on its own.

=item C<"Command %s declares the branch target %s; the only target is control.">

Raised via C<bug> when C<branch_target> is set to anything but
C<'control'>.  A target the gate never compares against would exempt the
command from nothing while reading as though it had, which is the same
failure the class check rules out.

=back

B<Examples:>

  # Minimal - function resolved from function_group module
  define_command('status', {
    summary        => 'Show environment status',
    function_group => ENVIRONMENT,
    scope          => 'env',
  });
  # Returns: (nothing)

  # Explicit function name
  define_command('my-cmd', {}, 'Genesis::Commands::Utility::my_cmd');
  # Returns: (nothing)

  # With an alias and option group
  define_command('deploy', {
    alias        => 'dep',
    scope        => 'env',
    option_group => ENV_OPTIONS,
    options      => [
      'dry-run|n' => 'Perform a dry run without deploying',
    ],
  });
  # Returns: (nothing)

=head2 commands

Returns the ordered list of all registered canonical command names, in

B<Returns:> A list of command name strings.

B<Examples:>

  my @cmds = commands();
  # Returns: ('status', 'deploy', 'check', ...)

=head2 current_command

  my $name = current_command();

Returns the canonical name of the currently active command as set by
C<prepare_command>.  Returns C<undef> if no command has been prepared.

B<Returns:> The canonical command name string, or C<undef>.

B<Examples:>

  my $cmd = current_command();
  # Returns: 'deploy'

=head2 current_command_alias

  my $alias = current_command_alias();

Returns the name the user actually invoked, which may be a registered
alias rather than the canonical command name.  Set by C<prepare_command>.

B<Returns:> The invoked command name or alias string, or C<undef>.

B<Examples:>

  # User typed: genesis dep
  my $alias = current_command_alias();
  # Returns: 'dep'

=head2 known_commands

  my @canonical = known_commands();

Returns a list of the canonical command names -- those where the key equals
the value in C<%GENESIS_COMMANDS>.  Aliases resolve to their canonical
target and are excluded from this list.

B<Returns:> A list of canonical command name strings.

B<Examples:>

  my @names = known_commands();
  # Returns: ('status', 'deploy', 'check', ...)  -- aliases omitted

=head2 prepare_command

  prepare_command($called_name, @args);

Sets up the active command by recording the invoked name, resolving it to
the canonical command name, parsing command-line options from C<@args>,
and configuring the logging subsystem.

B<Parameters:>

=over 4

=item C<$called_name>

The command name as typed by the user (canonical or alias).

=item C<@args>

Remaining command-line arguments after the command name.

=back

B<Returns:> C<1> on success.

B<Examples:>

  prepare_command('dep', '--dry-run', 'my-env');
  # Returns: 1
  # Sets $COMMAND = 'deploy', $CALLED = 'dep'
  # Parses --dry-run into %COMMAND_OPTIONS
  # Remaining 'my-env' goes into @COMMAND_ARGS

=head2 run_command

  run_command();

Dispatches execution to the closure registered for the current command.
If the command has a C<retired> property, C<run_command> bails with the
retirement message and never invokes the function.  Otherwise, prints
a deprecation warning if the command has a C<deprecated> property, then
runs the two gates that stand in front of every command, which between them
call the registered function with C<@COMMAND_ARGS>, and exits on the status
that function chose.

Two gates stand between the dispatch and the function.
C<_gate_pipeline_on_legacy_ci_yml> refuses a pipeline command in a
repository still carrying a legacy F<ci.yml>, and it either bails or
returns.  C<_gate_branch_class> is handed the function rather than
returning to it, because a deployed-state command is run inside a branch
session that the gate opens and closes around it.  The function is
therefore called from inside the branch gate on every path, and
C<run_command> calls it nowhere itself.

A command declaring C<DEPLOYED_STATE> returns the status it should exit
with instead of exiting on it, because an exit from inside the session
leaves the session open behind it and the branch is then put back by the
session's last-resort net rather than by its C<finish>.  C<run_command>
exits on what such a function returned, after the gate has closed the
session.  Every other command exits zero on a normal return, as it always
has, since nothing outside the class promises a status at all.

If the current command has no registered handler, prints an error via
C<command_help> and exits with status 1.

B<Returns:> Does not return -- calls C<exit> on success, with the status a
C<DEPLOYED_STATE> function returned, and with zero for every other command.

B<Errors:>

=over 4

=item C<"The %s command has been retired and cannot be run.%s">

Raised via C<bail> when the current command has a C<retired> property.
The first C<%s> is the canonical command name; the second is the
retirement message from the property value (blank if the property was
set to a true scalar with no message), preceded by two newlines.  See
C<retired> under L</define_command> for how commands opt in.

=back

B<Examples:>

  prepare_command('deploy', 'my-env');
  run_command();
  # Calls Genesis::Commands::Env::deploy('my-env') and exits 0

=head2 has_command

  my $bool = has_command($cmd);

Returns true if C<$cmd> is a known command or alias, false otherwise.

B<Parameters:>

=over 4

=item C<$cmd>

Command name or alias to look up.

=back

B<Returns:> C<1> if found, empty string (C<''>) otherwise.

B<Examples:>

  has_command('deploy');
  # Returns: 1 (if registered)

  has_command('dep');
  # Returns: 1 (aliases also match)

  has_command('nosuchcmd');
  # Returns: '' (empty string)

=head2 is_equivalent_command

  my $bool = is_equivalent_command($cmd1, $cmd2);

Returns true if both C<$cmd1> and C<$cmd2> resolve to the same canonical
command name.  Useful for checking whether an alias or alternate spelling
refers to the same command.

B<Parameters:>

=over 4

=item C<$cmd1>

First command name or alias.

=item C<$cmd2>

Second command name or alias.

=back

B<Returns:> C<1> if equivalent, empty string otherwise.

B<Examples:>

  is_equivalent_command('dep', 'deploy');
  # Returns: 1  (if 'dep' is an alias for 'deploy')

  is_equivalent_command('deploy', 'check');
  # Returns: ''

=head2 equivalent_commands

  my @names = equivalent_commands($cmd);
  my $aref  = equivalent_commands($cmd);

Returns all names (canonical and aliases) that resolve to the same
canonical command as C<$cmd>.

B<Parameters:>

=over 4

=item C<$cmd>

Any command name or alias.

=back

B<Returns:> In list context, a list of all equivalent names.  In scalar
context, an arrayref of the same names.  Returns an empty list (or empty
arrayref) if C<$cmd> is not a known command.

B<Examples:>

  my @all = equivalent_commands('dep');
  # Returns: ('deploy', 'dep')  -- all names that map to the same command

  my $ref = equivalent_commands('unknown');
  # Returns: []

=head2 command_properties

  my $props = command_properties();
  my $props = command_properties($name);

Returns the properties hashref for a command.  When called with no
argument (or with an empty string), returns the properties for the
currently active command.  When called with a command name or alias,
resolves it and returns that command's properties.

B<Parameters:>

=over 4

=item C<$name>

Optional.  A command name or alias.  Defaults to the active command.

=back

B<Returns:> A hashref of command properties as registered by
C<define_command>.

B<Errors:>

=over 4

=item C<"No active or given command -- cannot return command_properties">

Thrown via C<bug()> if no command name is given and no command is
currently active.

=back

B<Examples:>

  my $props = command_properties();
  # Returns: { summary => '...', scope => 'env', ... }

  my $props = command_properties('deploy');
  # Returns: { summary => '...', scope => 'env', ... }

=head2 branch_session

  my $session = Genesis::Commands::branch_session();

Returns the branch session the deployed-state gate opened for this command,
or C<undef> where it opened none.

A command reads the session through this rather than through
C<< $git->session >>, because that builds a fresh session on a handle that
never opened one, and a fresh session answers C<finish_if_clean> false for a
tree that is perfectly clean, so a command could not tell the gate's session
apart from one it had just made itself.

C<undef> means the gate opened no session, which is a command outside the
pipeline surface, a pre-deploy command, or a deployed-state command whose
environment has no deployment branch it can read.

B<Returns:> the C<Service::Git::Session> the gate opened, or C<undef>.

B<Examples:>

  my $session = Genesis::Commands::branch_session();
  # Returns: the session `genesis qa deploy` is running inside

  my $session = Genesis::Commands::branch_session();
  # Returns: undef, in `genesis version`

=head2 branch_carries_repository

  my $yes = Genesis::Commands::branch_carries_repository($top, $git, $branch);

Answers whether a deployment branch holds the deployment root, which is
asked by looking for the root's own C<.genesis/config> on the branch. Every
delivery mirrors that file and nothing else on the branch is guaranteed, so
a branch that answers false is one C<genesis pipeline-apply> cut and no
C<genesis propagate> run has delivered to, or one this clone has not pulled
the delivery of.

The gate asks before it switches, so a command is not left looking at a tree
with no configuration in it. C<genesis deploy> asks again in its pre-flight,
after the fast-forward its classification ordered, because a deploy the gate
left standing on control would otherwise deploy from wherever the operator
happened to be and certify a commit no propagation routed anywhere. One
function answers both, since two readings of one question are two chances to
disagree about which branches are deployable.

What the branch holds is read off the local ref where there is one, and off
the remote-tracking ref otherwise, which is how the switch chooses too. The
local ref rather than the tracking ref, because a checkout takes the working
tree to the commit the local ref names and the tree is what a command then
reads: answered off the tracking ref, a branch this clone holds at the init
commit would pass, and the command would be stood on an empty tree by an
answer saying it had a repository on it. A clone that has not pulled is
brought forward before the question is asked rather than answered around,
and only for a command that declares C<branch_fast_forward>. This function
writes nothing and fetches nothing.

The deployment root is named as a path under the git root, and both paths are
resolved through C<Cwd::realpath> before they are compared, so a root
reached through a symlink is not mistaken for one outside the repository.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> for the deployment root being asked about.

=item C<$git>

A C<Service::Git> for the repository holding that root.

=item C<$branch>

The deployment branch to read, as C<< <env>/<type> >>.

=back

B<Returns:> 1 when the ref it reads carries the deployment root's
C<.genesis/config>, and 0 when it does not.

B<Errors:>

=over 4

=item C<"The deployment root ... is not inside the repository at ...">

Raised when the deployment root resolves to a directory outside the git
root, so there is no path on the branch to read it from. That is a defect
rather than something an operator did, so it is said outright rather than
answered as a branch carrying nothing.

=back

B<Examples:>

  Genesis::Commands::branch_carries_repository($top, $git, 'qa/bosh');
  # Returns: 1 for a branch a propagate run has delivered to

  Genesis::Commands::branch_carries_repository($top, $git, 'qa/bosh');
  # Returns: 0 for a branch still holding the init commit alone

=head2 deployed_target

  my $commit = Genesis::Commands::deployed_target($name, $top);

Returns the commit this run targets, or C<undef> when the run targets the tip
of the deployment branch. A command declares its default target at
registration with C<default_target>, which is C<tip> unless it says
C<deployed>, and either C<--redeploy> or C<--as-deployed> selects the
deployed commit regardless. When a flag is given while the repository's
pipeline is not enabled, this bails with C<Genesis::Exit::CONFIG>, because
the branch session that makes a detached checkout safe opens only under a
pipeline. The branch-class gate is the one caller, and it asks before it
switches, so no command resolves its own target.

It takes the environment's name and the deployment root rather than a
C<Genesis::Env>, because the gate asks this of every classified command and
C<genesis new> names an environment whose file it is about to write. An
environment built above the question, merely so the flags could be read,
would refuse that run over a missing file that is missing exactly as
intended, so the reader of the deployed record builds its own below the
question instead.

Neither this nor C<DEPLOYED_TARGET_HELP> is exported. The gate is the only
caller and every registration in F<bin/genesis> names the constant in full,
so an export would put two names in every importer's namespace that nothing
reads.

B<Parameters:>

=over 4

=item C<$name>

The environment name, with any leading directories and any C<.yml> or
C<.yaml> suffix already stripped by the caller.

=item C<$top>

The C<Genesis::Top> for the deployment root the command is running in.

=back

B<Returns:> the commit the run targets, or C<undef> where it targets the tip
of the deployment branch, which is every run that named neither flag and
every command whose registration declares no C<deployed> default.

B<Errors:>

=over 4

=item C<"Refusing to target the deployed commit for ...">

Raised via C<bail> at C<Genesis::Exit::CONFIG> when either flag is given in
a repository whose pipeline is not enabled. Without a pipeline there is no
branch session to assert the tree clean, to hold the switch lock, or to put
the operator back on the branch they started from, so the run is refused
rather than left detached in a tree nobody asserted.

=back

B<Examples:>

  Genesis::Commands::deployed_target('qa', $top);
  # Returns: undef, in `genesis qa deploy` with no flag

  Genesis::Commands::deployed_target('qa', $top);
  # Exits CONFIG, in `genesis qa deploy --redeploy` with the pipeline off

=head2 has_scope

  my $bool = has_scope(@scopes);

Returns true if any of the requested C<@scopes> apply to the current
command given its registered scope specification and current option values.

The command's C<scope> property (set in C<define_command>) may be a simple
string or an arrayref of scope fragments.  Simple string scopes are matched
directly.  Array scope fragments allow conditional scoping based on the
current parsed options: each fragment is a two-element arrayref of
C<[$conditions, $scopes]>, where conditions are option expressions
(C<opt_name>, C<!opt_name>, C<opt_name=value>, C<!opt_name=value>) and
scopes is a string or arrayref of scope names.  B<All> conditions in a
fragment must hold for that fragment to apply.

Fragments are OR'd, not first-match-wins.  Every fragment is considered:
a fragment whose conditions hold but whose scopes do not include any
requested scope does not stop the search -- evaluation continues to the
next fragment.  A bare string fragment is unconditional and behaves the
same wherever it appears in the list; it is not a fallback that applies
only when no other fragment matched.

So given C<scope =E<gt> [['--foo' =E<gt> 'env'], 'repo']> with C<--foo>
set, C<has_scope('repo')> returns true: the first fragment's conditions
hold but do not cover C<'repo'>, so the bare C<'repo'> fragment is still
reached.

B<Parameters:>

=over 4

=item C<@scopes>

One or more scope name strings to test.  Valid values are C<'env'>,
C<'repo'>, C<'kit'>, C<'empty'>, C<'pipeline'>, and C<'any'>.

=back

B<Returns:> C<1> if any requested scope matches, C<undef> otherwise.

B<Errors:>

=over 4

=item C<"Incorrectly defined scope for command $COMMAND">

Thrown via C<bug()> when an array scope fragment does not have exactly
two elements.

=back

B<Examples:>

  # In a command registered with scope => 'env'
  has_scope('env');
  # Returns: 1

  has_scope('repo');
  # Returns: undef

  # In a command registered with scope => 'any'
  has_scope('pipeline');
  # Returns: undef  ('any' excludes pipeline)

B<Limitations:> Multiple C<@scopes> are combined with I<any> semantics
only -- the call is true when at least one applies.  There is no way to
express other combinations through the argument list; compose them at the
call site instead:

=over 4

=item all of

C<has_scope('a') && has_scope('b')>

=item none of

C<!has_scope('a', 'b')>

=item not all of

C<!(has_scope('a') && has_scope('b'))>

=back

"At least one scope other than these" has no equivalent composition and
would need a change here.

Option conditions compare literal values only.  Regex and relational
comparisons are not supported.

=head2 check_embedded_genesis

Checks whether the current deployment repository contains an embedded

=head2 check_prereqs

  check_prereqs();

Validates that all external tools required by Genesis are installed and
meet minimum version requirements.  Also checks required Perl modules and
enforces directory scope constraints for the current command.

Checks the following external tools:

=over 4

=item perl E<gt>= 5.20.0

=item curl E<gt>= 7.30.0

=item git E<gt>= 2.34.1

The version Ubuntu jammy ships, jammy being the lowest supported image.
Declared for every Genesis command rather than only for the ones that lean
on recent git, so there is one requirement to keep true rather than one per
command, and so an image whose git has regressed is refused here.

=item jq E<gt>= 1.6

=item spruce E<gt>= 1.28.0

=item safe E<gt>= 1.6.1

=item a secrets engine: vault E<gt>= 1.9.0, I<or> bao E<gt>= 2.6.0 when
safe E<gt>= 1.20.0

Either engine satisfies Genesis, because safe drives both. OpenBao is only
accepted alongside safe 1.20.0 or newer, which is the release that learned
to drive it; on an older safe a C<bao> on the PATH is reported as unusable
rather than accepted, since accepting it would move the failure into
C<safe local> where the cause is much harder to see.

Vault is preferred when both are installed, matching safe's own resolution
order.

=item openssl E<gt>= 1.1.1

=item credhub E<gt>= 2.7.0

=item bosh E<gt>= 6.4.4

=back

Checks the following Perl modules:

=over 4

=item MIME::Base64 E<gt>= 3.14

=item IO::Uncompress::Gunzip E<gt>= 2.064

=item IO::Compress::Gzip E<gt>= 2.064

=item Archive::Tar E<gt>= 1.96

=back

=over 4

=item Commands with C<repo> or C<env> scope must be run in a Genesis deployment repo.

=item Commands with C<kit> scope must be run in a Genesis kit repo.

=item Commands with C<kit_or_dev> scope must be in a kit repo or a deployment repo with a C<dev/> directory.

=item Commands with C<empty> scope must NOT be in a deployment or kit repo.

The check runs at most once per process (tracked with a static variable).
It is skipped entirely when C<GENESIS_IS_HELPING_YOU> is set.

B<Returns:> C<1> if prerequisites pass.

B<Errors:>

=over 4

=item C<"check_prereqs called before command selected">

Thrown via C<bug()> if called before C<prepare_command> has been called.

Thrown via C<bail()> with exit code C<86> if any prerequisite check fails.
The message lists all failures encountered.  C<86> is the code the kit and
provider prerequisite checks already use, and it tells a caller that the
environment is what has to be fixed.

=back

B<Examples:>

  # Returns: 1  (all prerequisites met)

=item C<--trace> maps to C<TRACE>.

=item C<--debug> maps to C<DEBUG>.

=item Default is C<INFO>.

=back

Sets C<$ENV{GENESIS_DEBUG}> and C<$ENV{GENESIS_TRACE}> when the resolved
level meets or exceeds C<DEBUG> or C<TRACE> respectively.

B<Returns:> Nothing.

=head2 check_version

  my $err = check_version($name, $min, $cmd, $regex, $url, $path_src);
  my $err = check_version($name, $min, '', $version, $path, $url);
  my $err = check_version(\%opts, $name, $min, $cmd, $regex, $url);

Checks whether a tool meets a minimum version requirement.

Not exported.  Called internally by C<check_prereqs>.

When C<$cmd> is provided (non-empty string), runs it to obtain a version
string, extracts the version with C<$regex>, and finds the tool path
with C<type -p>.  When C<$cmd> is empty, uses the pre-supplied
C<$version> and C<$path>.

In development mode (C<GENESIS_DEV_MODE> set) a version string containing
C<'development'> is accepted unconditionally.

A version beginning C<dev> -- what a tool built from source reports, such as
C<safe vdev/E<lt>branchE<gt>/E<lt>shaE<gt>> -- carries no ordinal to compare
against.  By default such a build is accepted, treating the minimum as a
floor a source build is assumed to clear.  A caller that knows which release
a dev build must postdate passes C<dev_version>, and the comparison is made
against that instead of skipped, so raising C<$min> past it stops qualifying
dev builds rather than passing them silently.

B<Parameters:>

=over 4

=item C<\%opts>

Optional, and may appear in any position; several are merged.  Recognises
C<dev_version>, the release to read a C<dev> version as.

=item C<$name>

Human-readable tool name (e.g., C<'curl'>).

=item C<$min>

Minimum acceptable version string (e.g., C<'7.30.0'>).

=item C<$cmd>

Shell command to run to get the version output, or empty string.

=item C<@remainder>

When C<$cmd> is non-empty: C<($regex, $url, $path_src)>.

When C<$cmd> is empty: C<($version, $path, $url)>.

=back

B<Returns:> C<undef> on success, or an error message string on failure.

B<Examples:>

  my $err = check_version('curl', '7.30.0',
    'curl --version 2>/dev/null | head -n1',
    qr(^curl\s+(\S+)));
  # Returns: undef  (if curl meets the minimum version)
  # Returns: "curl v7.29.0 is installed at /usr/bin/curl, ..."  (if too old)

  my $err = check_version({dev_version => '1.20.1'}, 'safe', '1.6.1',
    'safe -v 2>&1', qr(safe v(\S+)));
  # `safe vdev/perf-improvements/d6a138d` is compared as 1.20.1
  # Returns: undef  (1.20.1 clears the 1.6.1 minimum)

=head2 check_secrets_engine

  my @errors = check_secrets_engine();

Checks that a secrets engine safe can drive is installed and new enough.

  check_secrets_engine();
  # Returns: a string naming the missing vault and the too-old safe,
  #          when neither engine is usable

=head2 _safe_drives_openbao

  my $ok = _safe_drives_openbao();

Reports whether the installed safe is new enough to drive OpenBao.

OpenBao support arrived in safe 1.20.0. Below that, safe shells out to
C<vault> unconditionally, so a C<bao> on the PATH is of no use to Genesis
however new it is.

A safe built from source reports C<safe vdevE<sol>E<lt>branchE<gt>E<sol>E<lt>shaE<gt>>,
which has no ordinal to compare and would otherwise read as older than every
release -- denying OpenBao to the people most likely to be building safe in
order to work on it.  Such a build is read as 1.20.1, the first release that
could have produced one carrying OpenBao support.  It is mapped rather than
waved through, so raising the minimum past 1.20.1 correctly stops qualifying
dev builds.

B<Returns:> 1 when safe is 1.20.0 or newer, 0 otherwise -- including when
safe is absent or its version cannot be parsed, since neither case can be
shown to support OpenBao.

B<Examples:>

  _safe_drives_openbao();
  # Returns: 1  (safe v1.20.0)

  _safe_drives_openbao();
  # Returns: 0  (safe v1.9.0, which predates engine selection)

  _safe_drives_openbao();
  # Returns: 1  (safe vdev/perf-improvements/d6a138d, read as 1.20.1)

=head2 _gate_context

  my ($top, $git) = _gate_context();

Loads the C<Genesis::Top> and the C<Service::Git> handle for the current
directory, once, and answers every later caller in that directory with the
same pair.

Both gates that run in front of a command ask the same two questions of the
same directory.  Loading a C<Top> is not free of consequence -- it names
C<GENESIS_ROOT>, C<GENESIS_TARGET_VAULT> and C<SAFE_TARGET> in the
environment, and the memo behind C<Service::Vault> answers every later
caller with whatever the first load chose -- so loading it twice for the
four commands that meet both gates announces one thing twice.

The answer is kept per directory rather than per process, so a caller that
runs a gate against one repository and then against another gets each
repository's own answer.

Each load has its own C<eval>. A directory that is no repository at all
still yields whatever C<Top> the first gate can refuse from, and the git
handle bails on its own where there is no repository root, so a failure
there hands back C<undef> and the branch-class gate stands aside rather
than speaking before the command's own refusal.

A directory is only a stable key while the tree in it holds still, and the
deployed-state switch moves it.  C<_gate_deployed_state> checks out the
environment's branch in this same process, so the repository configuration
and the environment files under that directory become another branch's, and
a C<Top> kept from before the switch would answer for the branch the
operator stood on.  C<_reset_gate_context> drops what is kept, and
C<_gate_deployed_state> calls it on both sides of the command, once after
the switch and once after the session restores.

B<Returns:> the C<Genesis::Top> and the C<Service::Git> handle, either of
which may be C<undef>.

B<Examples:>

  my ($top, $git) = _gate_context();
  # Returns: (Genesis::Top, Service::Git)

  my ($top, $git) = _gate_context();
  # Returns: (undef, undef)  (the directory is no deployment root)

=head2 _reset_gate_context

  _reset_gate_context();

Drops every pair C<_gate_context> is keeping, so the next caller loads the
directory as it now is.

It is called where the tree under a directory changes beneath the memo,
which today is the deployed-state switch and nothing else.  Clearing every
directory rather than the one that moved costs a reload the next caller was
going to pay for anyway, and it spares this function from having to know
which directory the switch moved.

B<Returns:> nothing.

B<Examples:>

  $session->switch($branch);
  _reset_gate_context();
  # the next _gate_context() reads the environment's branch

=head2 _gate_pipeline_on_legacy_ci_yml

  _gate_pipeline_on_legacy_ci_yml();

Blocks pipeline commands in a repository still carrying a legacy F<ci.yml>,
bailing with migration instructions at C<Genesis::Exit::CONFIG>.

Returns early -- allowing the command through -- in three cases: the command
is not in the C<Pipelines> group; it has no repo or env scope, so there is no
C<Genesis::Top> to inspect (C<help>, C<version>, C<ping>); or the C<Top> could
not be loaded at all.

That last case is deliberate.  A repository too broken to load is reported by
whatever the command does next, which will say something more useful than a
migration notice.

B<Returns:> nothing.  Bails when the gate applies.

B<Errors:>

=over 4

=item C<"This repository still has a legacy CI configuration at ci.yml...">

The full message names the values to carry across from the C<pipeline:>
block, which are the provider, the git URI, the branch, the pipeline name
and the vault URL, and it says to write them into the C<pipeline:> block of
F<.genesis/config>, which declares every one of them.  The bail exits
C<Genesis::Exit::CONFIG>.

=back

B<Examples:>

  _gate_pipeline_on_legacy_ci_yml();
  # no return value; bails if a legacy ci.yml blocks a pipeline command

=head2 _gate_branch_class

  my @out = _gate_branch_class($fn);

Enforces the branch class a command declared at its registration, running in
C<run_command> just after the legacy F<ci.yml> gate, and runs the command's
own function.

The class lives at the registration so that one declaration drives both the
help marker and the refusal, which is why the enforcement sits here rather
than inside each command.  A C<pre-deploy> command is handed to
C<Genesis::BranchClass::assert_pre_deploy>, which refreshes the control
branch from the remote and then refuses a derived branch at
C<Genesis::Exit::DATAERR>.  A C<deployed-state> command is handed to
C<_gate_deployed_state>, which opens the session the command reads inside
rather than refusing anything.

The refresh is passed along as C<< refresh => 0 >> for the two commands that
make no network call of their own.  C<pipeline-status> says so with
C<--no-refresh>, which it alone declares.  C<pipeline-describe> resolves the
repository's own configuration out of files, so it holds no ref a refresh
could make current, and a fetch would refuse offline what the command can
always answer from disk.  Both are read here, where the options and the
command name are, rather than in the assertion, which has no business knowing
which command declared what.

The two names sit in the gate for now.  D81 would rather a registration
declared that it needs no refresh, the way it declares its class, and the
step that gives registrations such an attribute moves these names onto it,
M17 for C<pipeline-status>.

Whether the command commits on control goes down as C<< commits => ... >>,
read straight off the registration. The C<control_requires_pr> refusal is
asked of that rather than of the class, and M17's attribute pattern absorbs
the declaration later the way it absorbs the two refresh exemptions above.

The name a command is about to add goes down with it as C<< adding => ... >>.
C<genesis new> takes that name as its first argument, and a feature branch
named for it could never stand beside the deployment branch the name will
need, so the gate reads the argument here and the predicate compares it
there.

Runs the function where it stands -- gating nothing -- in five cases: the
command declares no class; it declares C<branch_target =E<gt> 'control'>,
which C<propagate> does because it switches to control inside its own
session; it has no repo or env scope, so there is no C<Genesis::Top> to
read; the C<Top> or the git handle could not be loaded; or the repository
has no pipeline enabled, where every command behaves as it always has.

The target is read before anything is loaded.  Loading a C<Genesis::Top>
names the deployment root and the vault target in the environment, and a
command this gate never gates should not be handed those on its way past.

The C<Top> and the git handle both come from C<_gate_context>, which the
legacy F<ci.yml> gate reads too, so the four commands that meet both gates
are loaded once.

B<Parameters:>

=over 4

=item C<$fn>

The command's own function, as a code reference taking no arguments.  Every
path through the gate calls it exactly once, except a pre-deploy refusal,
which bails before it is reached.

=back

B<Returns:> whatever C<$fn> returned.

B<Errors:>

=over 4

=item The refusals belong to C<Genesis::BranchClass::assert_pre_deploy>.

This function raises none of its own.  The branch refusal names the branch,
the class it belongs to or the condition it failed, and the checkout,
rebase, or rename that fixes it, and it exits C<Genesis::Exit::DATAERR>.  A
remote that cannot be reached for the refresh exits
C<Genesis::Exit::TEMPFAIL>.

=back

B<Examples:>

  _gate_branch_class(sub {$RUN{$COMMAND}(@COMMAND_ARGS)});
  # runs the command, or bails first when a pre-deploy command stands on
  # a deployment, pull request, or artifacts branch, on a feature branch
  # that does not descend from control's tip, or on one named for an
  # environment

=head2 _gate_deployed_state

  my @out = _gate_deployed_state($top, $git, $fn);

Runs a deployed-state command inside a branch session standing on the
deployment branch of the environment the command was given, which is
C<< <env>/<type> >>.

The switch lives here rather than inside each command, so that every
deployed-state command reaches the same branch by the same path and takes
the same switch lock.  The branch holds exactly what was delivered, and the
kit's hooks need a working tree, which is why the command reads a checkout
rather than a tree object.

B<The branch's tip is what the session stands on.>  D87 has C<info> and the
C<bosh> subcommands default to the commit the environment last deployed,
which is the exodus C<git.commit>, and a tip may carry a delivery that has
not deployed.  M14 supplies that commit through C<deployed_target>, and
until it lands the tip is read in its place.

The environment name is taken from the first command argument, with any
leading directories and any C<.yml> or C<.yaml> suffix removed, because an
operator may name an environment by its path.  A command called with no
argument at all switches nothing and runs where it stands, so the command
raises its own usage error rather than meeting a bug report about an
undefined name.

A command already standing on the branch it would switch to is not switched
either, and it opens no session at all.  It says so in one C<info> line
before it runs, the way the two arms below do, and that line calls the branch
by name rather than calling it a deployment branch, because the phrase belongs
to the pre-deploy refusal this class must never meet and a row reads this
arm's output for its absence.  D80 makes the trigger the switch
rather than the class, so a command that is already where it would be going
takes no switch lock and asserts no cleanliness, since a session exists to
leave a branch and come back and there is nothing here to leave.  That is
what lets an operator edit a file on the deployment branch and deploy it in
place, which is the qualifier I3 carries.

An environment whose deployment branch does not exist is not switched
either.  Both the local branch and the remote-tracking one are asked about,
because git's own checkout makes a local branch out of one it has only
fetched.  Where neither is there the command runs where it stands, which is
what every environment between C<genesis new> and its first deploy needs:
C<info> then prints its own sentence about there being no record of a
deployment, rather than a refusal about a commit rewritten on the remote.

A branch that carries no repository is not switched onto.  C<pipeline-apply>
cuts a deployment branch as an orphan whose root commit adds one init file,
and until a propagate run delivers to it there is nothing on it a command can
read.  Switching onto it left the command loading a root out of a tree with
no configuration in it and reporting a repository that is not there, so the
branch is asked for the deployment root's C<.genesis/config>, and where it
does not carry it the session closes without having moved anything and the
command runs where it stands.

All three of those arms print one C<info> line naming the branch and why it
was not switched to, before the command runs.  The line is a statement and not a
refusal: whether either state should stop a command is each command's own
question, and the deploy's classification of it answers differently from
C<info>'s.

The deployment root is compared against the git root with both paths
resolved, because a root reached through a symlink, or named as F</var>
where git answers F</private/var>, is one directory under two spellings and
a comparison of the spellings would ask the branch for its C<.genesis/config>
at the repository root instead.  That answers "carries no repository" for a
branch that carries it, and the command then runs unswitched with nothing
saying why.  A deployment root genuinely outside the repository is a defect
rather than an operator error, so it bails.

That question is asked after C<begin> and not before it.  It runs a git
command of its own, and C<begin> is where the pre-flight classifies the
failures a git command otherwise hides, so asking first would answer a
repository git declines to trust with the listing's complaint instead of the
pre-flight's sentence.

The session opened here is kept in C<$BRANCH_SESSION> and read back through
C<branch_session>, so a command reaches the gate's own session rather than
building a second one on the same handle.  It is cleared where the session
closes.

The session closes here, where the function returns, and nothing about it
is left to an exit hook.  C<begin> hangs the session's own last-resort net
on C<END>, so a hook registered after it runs second and finds the session
already aborted, and a C<bail> out of C<END> replaces the status the command
chose with 1.  A command that refuses therefore exits with its own code and
the net puts the working tree back, which is the job the net exists for.

B<Parameters:>

=over 4

=item C<$top>

The C<Genesis::Top> the gate loaded, read for the control branch the
session is told never to reset and for the deployment branch to stand on.

=item C<$git>

The C<Service::Git> handle on the working tree, which hands out the one
session that tree may have open.

=item C<$fn>

The command's own function, as a code reference taking no arguments.  Every
path calls it exactly once, inside the session where there is one to open.

=back

B<Returns:> whatever C<$fn> returned.

B<Errors:> this function raises none of its own, and four things it calls
can end the command before it runs.  C<begin> refuses a session opened
while another is still open, refuses a working tree carrying tracked or
staged changes, and runs C<preflight>, which refuses a repository with no
commits, no committed identity, or an ownership git declines to trust.
C<switch> refuses at C<Genesis::Exit::TEMPFAIL> where another process holds
the switch lock.  C<ls_tree>, which is what asks the branch whether it
carries a repository, refuses at C<Genesis::Exit::DATAERR> where git cannot
resolve the ref.  This function itself bails in one case, which is a
deployment root that resolves to somewhere outside the repository, because
there is then no path on the branch to read it from.

B<Examples:>

  _gate_deployed_state($top, $git, $fn);
  # `genesis qa info` reads qa/bosh and is returned to control

  _gate_deployed_state($top, $git, $fn);
  # `genesis staging info` runs where it stands, because staging has
  # never been delivered and has no branch to read

  _gate_deployed_state($top, $git, $fn);
  # `genesis qa deploy` runs where it stands, because qa/bosh was cut by
  # pipeline-apply and carries no repository to read yet

  _gate_deployed_state($top, $git, $fn);
  # `genesis qa deploy` run from qa/bosh opens no session at all, so the
  # operator's uncommitted edit is deployed rather than refused

=head2 _parse_two_pass

  my $ok = _parse_two_pass($args, \@specs, $order);

Parses options for a command that declares a fixed-arity option, such as
C<--set E<lt>keyE<gt> E<lt>valueE<gt>>.

B<Getopt::Long refuses any C<{n}> arity specification while bundling.>
The check is on the configured bundling flag alone; it never inspects the
option's name, although only a single-letter option can appear in a
bundle and so only that case is genuinely ambiguous.  A long-form option
taking a counted pair is therefore rejected despite being unambiguous.

Two passes work around it without giving up either feature:

=over 4

=item 1.

Bundling off, C<pass_through> on, with every specification.  The arity
options are legal here and are consumed; anything unrecognised --
notably clustered short flags like C<-qT> -- is left in the array.

=item 2.

Bundling on, arity specifications withheld so the guard has nothing to
object to, C<no_pass_through> so an unknown option is still an error.
This pass claims the clusters the first one skipped.

=back

The result is that C<--set a 1 --set b 2> and C<-qT> both parse in the
same invocation, C<--> still terminates, and positionals survive for the
command to read.  An arity option cannot be abbreviated, because the
first pass runs with C<no_auto_abbrev>.

Engaged only when a command declares an arity specification; every other
command takes the original single-pass route unchanged.

B<Parameters:>

=over 4

=item C<$args>

The argument array, consumed in place.

=item C<\@specs>

All option specifications, base and command.

=item C<$order>

C<require_order> or C<permute>, matching the command's declaration.

=back

B<Returns:> True when both passes succeeded.

B<Errors:> None directly.  Parsing warnings are collected by the caller,
which reports them through C<command_usage>.

B<Examples:>

  _parse_two_pass(\@args, [@base_spec, @opts_spec], 'permute');
  # '--set a 1 -qT' => set => ['a','1'], quiet => 1, trace => 1
