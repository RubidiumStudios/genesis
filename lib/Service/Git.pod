=head1 NAME

Service::Git - Git operations for a deployment repository

=head1 SYNOPSIS

  use Service::Git;

  # One instance per repository, whatever path you name inside it
  my $git = Service::Git->new('.');
  my $git = Service::Git->new($path, track_branch => 1);

  # Branches
  $git->checkout('staging') if $git->branch_exists('staging');
  $git->create_branch('prod', 'control');
  $git->restore_branch;

  # Queries
  my $sha   = $git->sha('HEAD', short => 1);
  my $clean = $git->is_clean;
  my $diff  = $git->diff_files($from, $to, @paths);

  # Working tree
  $git->checkout_file($sha, 'ops/thing.yml');
  $git->commit('[pipeline] control@abc1234 -> staging (pulled)', @files);

  # Remotes
  my ($self, $result) = $git->fetch_branches(\@branches);
  my $pushed = $git->push(@branches);

=head1 DESCRIPTION

C<Service::Git> wraps the git commands Genesis needs to manage a deployment
repository: branch handling for the pipeline model, structured diffs for
propagation, and the remote operations that move branches between a working
copy and its origin.

It is deliberately thin. Each method is one git invocation and a little
parsing; nothing here caches file content or models the repository beyond
what git itself reports. What it does add is the handful of decisions that
would otherwise be repeated at every call site -- which failures are fatal,
which are ordinary answers, and how paths are spelled.

=head2 One instance per repository

C<new> is a flyweight: it resolves the git top-level for whatever path it is
given, and returns the existing instance when one already exists for that
root. Two callers naming different subdirectories of the same repository get
the same object.

That matters because instances carry mutable state -- the branch to restore,
the branch-existence cache, the resolved default remote. Independent objects
for one repository would each track a different "original" branch and undo
each other's work.

=head2 Two path spellings

Git reports paths relative to the B<git root>. Genesis works in a deployment
repository that may sit in a subdirectory of it, and speaks to operators in
paths relative to that B<deployment root>.

C<prefix> is the offset between them, and C<prefixed> / C<unprefixed> convert
between the two. Getting this wrong does not error: a pathspec in the wrong
spelling simply matches nothing, and a diff comes back empty as though there
were no changes.

=head2 Branch tracking

With C<< track_branch => 1 >>, the branch checked out at construction is
remembered and restored -- explicitly via C<restore_branch>, or at process
exit via C<DESTROY>. Commands that check out an environment branch to do
their work use this so an operator is not left somewhere unexpected.

Because the instance is a flyweight held for the process lifetime, C<DESTROY>
fires during global destruction rather than when a caller drops its
reference.

=head1 METHODS

=head2 new

  my $git = Service::Git->new;
  my $git = Service::Git->new($path);
  my $git = Service::Git->new($path, track_branch => 1);

Returns the C<Service::Git> for the repository containing C<$path>, creating
it on first call and returning the existing instance thereafter.

Requesting C<track_branch> on a repository that already has an untracked
instance upgrades that instance in place rather than creating a second one,
recording the current branch as the one to restore.

B<Parameters:>

=over 4

=item C<$path>

Any path inside the repository. Defaults to the current directory.

=item C<%opts>

=over 4

=item C<track_branch>

Remember the current branch and restore it on C<restore_branch> or at process
exit.

=back

=back

B<Returns:> The C<Service::Git> instance for that repository.

B<Errors:>

=over 4

=item *

C<"Not a git repository: %s"> -- raised via C<bail()> when C<$path> is not
under git control. C<%s> is the path given.

=back

B<Examples:>

  my $git = Service::Git->new('.');
  # returns the instance for the repository containing the cwd

  my $a = Service::Git->new('repo/bosh');
  my $b = Service::Git->new('repo/vault');
  # returns the same object for both -- one repository, one instance

=head2 create

  my $git = Service::Git->create($path);
  my $git = Service::Git->create($path, initial_branch => 'control');

Initialises a git repository at C<$path> and returns an instance for it.

When C<initial_branch> is given, the branch is set with
C<git symbolic-ref> rather than C<git init -b>, because the latter requires
git 2.28 or newer and this must work against older installations.

B<Parameters:>

=over 4

=item C<$path>

Where to initialise. Defaults to the current directory.

=item C<%opts>

C<initial_branch> as above; any other options are passed to C<new>.

=back

B<Returns:> The C<Service::Git> instance for the new repository.

B<Errors:>

=over 4

=item *

C<"Failed to initialize git in %s"> -- raised via C<run>'s C<onfailure> when
C<git init> fails.

=back

B<Examples:>

  my $git = Service::Git->create($dir, initial_branch => 'control');
  # returns an instance whose HEAD points at refs/heads/control

=head2 DESTROY

Restores the tracked branch at process exit.

Only acts when C<track_branch> was requested and the branch has actually
changed. Working-tree changes are discarded first -- a checkout would fail
against a dirty tree, and leaving the operator on the wrong branch is the
worse outcome.

Both commands run in pass/fail mode: this runs during global destruction,
where dying achieves nothing useful.

B<Returns:> Nothing.

=head2 is_ancestor

  my $bool = $git->is_ancestor($maybe_ancestor, $descendant);

Whether the first ref is reachable from the second. A ref is its own

B<Parameters:>

=over 4

=item C<$maybe_ancestor>

The ref that might be behind.

=item C<$descendant>

The ref that might be ahead.

=back

B<Returns:> 1 or 0. Returns 0 rather than erroring when either argument is

B<Examples:>

  # returns 1 -- a commit is its own ancestor

=head2 is_clean

  my $bool = $git->is_clean;

Whether the working tree has no modified, staged or conflicted files.

B<Untracked files do not count as dirty.> The question this answers is
whether it is safe to switch branches, and untracked files survive a
checkout untouched. Use C<status> when you need to see them.

B<Parameters:> None.

B<Returns:> 1 when clean, 0 otherwise.

B<Examples:>

  my $bool = $git->is_clean;
  # returns 1 even with untracked files present

=head2 status

  my $unclean = $git->status;
  my $unclean = $git->status(@pathspecs);

The working tree's state as a hashref of path to two-character porcelain
status code.

Unlike C<is_clean>, this B<does> include untracked files, reported as C<??>.
Callers wanting only tracked changes should filter them out.

B<Parameters:>

=over 4

=item C<@pathspecs>

Optional paths to limit the report to, relative to the git root -- so pass
them through C<prefixed> if they are deployment-relative.

=back

B<Returns:> A hashref keyed by path. Empty when nothing is reported.

B<Examples:>

  my $unclean = $git->status;
  # returns { 'ops/thing.yml' => ' M', 'scratch.txt' => '??' }

  my $unclean = $git->status($git->prefixed('ops/thing.yml'));
  # returns only that path's state, or {} when it is unchanged

B<Errors:>

=head2 diff_files

  my $diff = $git->diff_files($from, $to);
  my $diff = $git->diff_files($from, $to, @pathspecs);

A structured diff between two refs.

Renames are reported three ways at once, deliberately: the old path appears
in C<deleted>, the new one in C<changed>, and the pair in C<renamed>. A
caller copying C<changed> and removing C<deleted> therefore handles a rename
correctly without knowing it was one, while a caller that cares can consult
C<renamed>.

B<Parameters:>

=over 4

=item C<$from>, C<$to>

The refs to compare.

=item C<@pathspecs>

Optional paths to limit the diff to, relative to the git root.

=back

B<Returns:> A hashref with keys C<changed> (added, modified or type-changed),
C<deleted>, C<renamed> (old path to new), and C<all> (changed plus deleted).

B<Examples:>

  my $diff = $git->diff_files('staging', $sha, @paths);
  # returns { changed => ['ops/new.yml'], deleted => [],
  #           renamed => {}, all => ['ops/new.yml'] }

  # A rename from a.yml to b.yml:
  my $diff = $git->diff_files($from, $to);
  # returns { changed => ['b.yml'], deleted => ['a.yml'],
  #           renamed => { 'a.yml' => 'b.yml' }, all => ['b.yml','a.yml'] }

=head2 diff_names

  my @files = $git->diff_names($from, $to);
  my @files = $git->diff_names($from, $to, @pathspecs);

The names of files that differ between two refs, without classification.

B<Parameters:>

=over 4

=item C<$from>, C<$to>

The refs to compare.

=item C<@pathspecs>

Optional git-root-relative paths.

=back

B<Returns:> The list of changed paths. Empty when identical.

B<Examples:>

=head2 log_subjects

  my @lines = $git->log_subjects($branch);
  my @lines = $git->log_subjects($branch, limit => 50, paths => \@paths);

Commit lines for a branch, newest first.

The C<paths> filter is what makes this usable in a repository deploying more

B<Parameters:>

=over 4

=item C<$branch>

The branch or revision range to log.

=item C<%opts>

=item C<format>

A git format string. Defaults to C<'%H %s'> -- sha and subject.

=item C<paths>

Arrayref of git-root-relative paths; only commits touching them are returned.

=back

=back

B<Returns:> The formatted lines, newest first. Empty when nothing matches.

B<Examples:>

  # returns just that commit's subject

=head2 cherry_pick

=back

=head2 fetch_branches

  $git->fetch_branches(\@names);
  my ($self, $result) = $git->fetch_branches(\@names, $remote);

Fetches several branches in one git invocation.

B<One invocation, so credentials are prompted once> regardless of how many
branches are listed. Fetching them individually turns a ten-branch refresh
into ten prompts.

The currently checked-out branch is skipped: git refuses to update an active
branch through a refspec, and including it would fail the whole fetch.

B<Failures are classified rather than merely reported.> In list context the
result distinguishes a network problem from an authentication problem from
anything else, so a caller can tell an operator which one they are looking
at. Scalar context returns C<$self> alone, which is what earlier callers
expect.

Outside a controlling terminal, C<GIT_TERMINAL_PROMPT=0> is set so a missing
credential fails immediately instead of hanging on a prompt nobody can
answer.

B<Parameters:>

=over 4

=item C<\@names>

The branches to fetch.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> In scalar context, C<$self>. In list context,
C<($self, \%result)>, where the hashref carries C<ok> (1 on success or
no-op, 0 on a real failure), C<kind> (C<success>, C<network>, C<auth> or
C<unknown>), and C<err> (git's stderr, only when C<ok> is 0).

B<Examples:>

  my ($git, $r) = $git->fetch_branches(['staging', 'prod']);
  # returns ($self, { ok => 1, kind => 'success' })

  my ($git, $r) = $git->fetch_branches(\@branches);
  # returns ($self, { ok => 0, kind => 'auth', err => '...' })
  # when credentials are missing

  $git->fetch_branches([]);
  # returns $self -- nothing to fetch is a success, not a failure

=head2 push

  my $results = $git->push(@branches);
  my $results = $git->push($remote, @branches);

Pushes branches, reporting the outcome per branch.

B<The remote argument is detected, not declared.> If the first argument is
not a known local branch, it is taken to be a remote name. A branch whose
name collides with a remote's would therefore be misread -- in practice
branches are not named C<origin>.

Each branch is pushed separately and a failure does not stop the rest, so a
partial push is reported rather than aborted midway.

B<Parameters:>

=over 4

=item C<@args>

An optional leading remote name followed by the branches to push. The two are
not distinguished by position but by lookup: the first element is treated as
a remote only when C<branch_exists> says it is not a local branch. Passing
branches alone is the common case.

=back

B<Returns:> A hashref of branch name to 1 or 0. Empty hashref when no remote
is configured.

B<Examples:>

  my $results = $git->push('staging', 'prod');
  # returns { staging => 1, prod => 1 }

  my $results = $git->push(@branches);
  # returns { staging => 1, prod => 0 } when only prod was rejected

=head2 prefixed

  my @git_paths = $git->prefixed(@repo_paths);

Converts deployment-root-relative paths to git-root-relative ones, which is
the spelling every pathspec argument in this class expects.

B<Parameters:>

=over 4

=item C<@paths>

Paths relative to the deployment root.

=back

B<Returns:> The converted paths. Unchanged when the prefix is empty.

B<Examples:>

=head2 unprefixed

  my @user_paths = $git->unprefixed(@git_paths);

The inverse of C<prefixed>, for showing paths to an operator.

Paths that do not start with the prefix are returned untouched rather than
mangled, so a path from outside the deployment root stays recognisable
instead of being silently truncated.

B<Parameters:>

=over 4

=item C<@paths>

Paths relative to the git root.

=back

B<Returns:> The converted paths. Unchanged when the prefix is empty or does
not match.

B<Examples:>

  my @user_paths = $git->unprefixed('bosh/ops/thing.yml');
  # returns ('ops/thing.yml') when the prefix is 'bosh/'

  my @user_paths = $git->unprefixed('vault/ops/other.yml');
  # returns ('vault/ops/other.yml') -- outside this deployment, left alone
