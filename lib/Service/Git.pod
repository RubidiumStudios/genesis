=head1 NAME

Service::Git - Git operations for a deployment repository

=head1 SYNOPSIS

  use Service::Git;

  # One instance per repository, whatever path you name inside it
  my $git = Service::Git->new('.');

  # Branches, through the session and nowhere else
  my $session = $git->session(control => 'control');
  $session->begin;
  $git->create_branch('prod', 'control');
  $session->switch('prod');
  $session->finish;

  # Queries
  my $sha   = $git->sha('HEAD', short => 1);
  my $clean = $git->is_clean;
  my $diff  = $git->diff_files($from, $to, @paths);

  # Working tree
  $git->checkout_file($sha, 'ops/thing.yml');
  $git->commit('[pipeline] control@abc1234 -> staging (pulled)', @files);

  # Remotes
  my ($self, $result) = $git->fetch_branches(\@branches);
  my $pushed = $git->push(@branches);

=head1 DESCRIPTION

C<Service::Git> wraps the git commands Genesis needs to manage a deployment
repository: branch handling for the pipeline model, structured diffs for
propagation, and the remote operations that move branches between a working
copy and its origin.

It is deliberately thin. Each method is one git invocation and a little
parsing; nothing here caches file content or models the repository beyond
what git itself reports. What it does add is the handful of decisions that
would otherwise be repeated at every call site -- which failures are fatal,
which are ordinary answers, and how paths are spelled.

=head2 One instance per repository

C<new> is a flyweight: it resolves the git top-level for whatever path it is
given, and returns the existing instance when one already exists for that
root. Two callers naming different subdirectories of the same repository get
the same object.

That matters because instances carry mutable state -- the branch-existence
cache, the resolved default remote, and the one branch session. Independent
objects for one repository would each hold a session of their own, and two
sessions in one working tree is exactly what I9 forbids.

=head2 Two path spellings

Git reports paths relative to the B<git root>. Genesis works in a deployment
repository that may sit in a subdirectory of it, and speaks to operators in
paths relative to that B<deployment root>.

C<prefix> is the offset between them, and C<prefixed> / C<unprefixed> convert
between the two. Getting this wrong does not error: a pathspec in the wrong
spelling simply matches nothing, and a diff comes back empty as though there
were no changes.

=head2 One door onto a branch change

C<checkout> and C<checkout_detached> are reached through
L<Service::Git::Session> and nowhere else, and a call from outside a session
dies saying so. That is not a style rule. The session is what records where
the operator was, takes the lock that stops a second process switching
underneath them, and puts the working tree back on every exit path, and a
branch change outside one has none of that.

C<reset_working_tree> is gone as well. Discarding a working tree is what
C<< $session->abort >> is for, and it does more than that method could: it
names the files before it throws them away, it reaches the index as well as
the tree, and it puts every branch the session moved back where the remote
has it.

The C<track_branch> option and C<restore_branch> are gone with it. The branch
a command returns to is recorded by C<< $session->begin >> on the session
itself, rather than stamped onto the shared handle by whichever caller
happened to ask first. C<DESTROY> restores nothing either: the last-resort net
for a command that exits partway through belongs to the session, which
registers it through C<at_exit>.

C<checkout_one_way> is the one exception, and a temporary one. The deploy
moves onto the environment branch and means to stay there, and the post-deploy
block moves onto control and hands off to a child command that expects to find
it there. A session would put both back. Those three call sites come through
C<checkout_one_way> until the steps that own them decide what returning should
mean.

=head1 METHODS

=head2 new

  my $git = Service::Git->new;
  my $git = Service::Git->new($path);

Returns the C<Service::Git> for the repository containing C<$path>, creating
it on first call and returning the existing instance thereafter.

It tracks no branch. The branch a command returns to is recorded by
C<< $session->begin >>, on the session, so the first caller to ask can no
longer stamp the branch it happened to be on onto the handle that every other
caller shares.

Also calls L</provision_ci_credentials>, so a process that constructs a
C<Service::Git> can perform remote operations with credentials supplied
through the environment. A no-op when none are set, which is every local
run.

B<Parameters:>

=over 4

=item C<$path>

Any path inside the repository. Defaults to the current directory.

=item C<%opts>

Accepted and unused. It is kept so that C<create> can hand its own options
along without knowing which of them C<new> reads.

=back

B<Returns:> The C<Service::Git> instance for that repository.

B<Errors:>

=over 4

=item *

C<< "Git refuses to work in %s because it is owned by another user." >> --
exits C<CONFIG> when git declines the working tree under C<safe.directory>,
and names C<git config --global --add safe.directory> as the fix. Raised
through L</_refuse_dubious_ownership>, which C<preflight> raises it through
too, so an operator meets the same words wherever the condition is met.

=item *

C<"Not a git repository: %s"> -- raised via C<bail()> when C<$path> is not
under git control. C<%s> is the path given.

=back

B<Examples:>

  my $git = Service::Git->new('.');
  # returns the instance for the repository containing the cwd

  my $a = Service::Git->new('repo/bosh');
  my $b = Service::Git->new('repo/vault');
  # returns the same object for both -- one repository, one instance

=head2 create

  my $git = Service::Git->create($path);
  my $git = Service::Git->create($path, initial_branch => 'control');

Initialises a git repository at C<$path> and returns an instance for it.

When C<initial_branch> is given, the branch is set with
C<git symbolic-ref> rather than C<git init -b>, because the latter requires
git 2.28 or newer and this must work against older installations.

B<Parameters:>

=over 4

=item C<$path>

Where to initialise. Defaults to the current directory.

=item C<%opts>

C<initial_branch> as above; any other options are passed to C<new>.

=back

B<Returns:> The C<Service::Git> instance for the new repository.

B<Errors:>

=over 4

=item *

C<"Failed to initialize git in %s"> -- raised via C<run>'s C<onfailure> when
C<git init> fails.

=back

B<Examples:>

  my $git = Service::Git->create($dir, initial_branch => 'control');
  # returns an instance whose HEAD points at refs/heads/control

=head2 DESTROY

Only fires at global destruction, because the instance table holds a strong
reference to every handle for the life of the process, so a caller that drops
its own reference never brings the refcount to zero.

It drops the handle's session and evicts the handle's entry from the instance
table, so that a handle released by any other route leaves no stale entry
behind for a later C<new> to answer with.

No branch is restored here. That safety net has moved to the session, which
registers a last-resort abort through C<at_exit> instead. A net in C<DESTROY>
fires too late to be useful, because C<bail> exits when it is not inside an
C<eval>, Perl runs C<END> before global destruction, and the order after that
is undefined.

B<Returns:> Nothing.

=head2 root

  my $path = $git->root;

The absolute path of the git top-level directory.

B<Parameters:> None.

B<Returns:> The git root path.

B<Examples:>

  my $path = $git->root;
  # returns '/home/me/deployments'

=head2 prefix

  my $prefix = $git->prefix;

The offset from the git root to the directory the instance was created in,
as git reports it -- with a trailing slash, or empty when they are the same.

B<Parameters:> None.

B<Returns:> The prefix string, possibly empty.

B<Examples:>

  my $prefix = $git->prefix;
  # returns 'bosh/' for a deployment repo inside a larger git repository

  my $prefix = $git->prefix;
  # returns '' when the deployment repo is the git root

=head2 git_dir

  my $dir = $git->git_dir;

The absolute path of this working tree's git directory, as
C<git rev-parse --absolute-git-dir> reports it. For an ordinary clone this is
C<< <root>/.git >>; for a linked working tree it resolves under
C<< .git/worktrees/<name>/ >>, which is what makes anything written there
per working tree rather than per repository.

Resolved once and remembered, since it cannot change while the handle lives.

B<Parameters:> None.

B<Returns:> The absolute git directory path.

B<Errors:>

=over 4

=item *

C<< "Unable to resolve the git directory of %s" >> -- raised when git answers
nothing. C<%s> is the working tree root.

=back

B<Examples:>

  my $dir = $git->git_dir;
  # returns '/home/me/deployments/.git'

  my $dir = $git->git_dir;
  # returns '/home/me/deployments/.git/worktrees/feature' in a linked
  # working tree, so a lock written there is that working tree's alone

=head2 session

  my $session = $git->session(control => $top->control_branch);

The one branch session for this handle, built on the first ask and returned
unchanged afterwards. Every branch change Genesis makes goes through it.

The session is keyed on the handle rather than on the repository, which is what
makes sessions sequential within a working tree and independent between two of
them. A caller holding handles for two working trees holds one session on each
at the same time, while a second C<begin> on one handle is refused.

The session is returned closed. Nothing is read from the repository and
nothing is written to it until C<< $session->begin >> runs. See
L<Service::Git::Session>.

B<Parameters:>

=over 4

=item C<%opts>

Options, handed straight to the session's constructor. C<control> names the
branch a later abort never resets.

=back

B<Returns:> The session for this handle.

B<Examples:>

  my $session = $git->session(control => $top->control_branch);
  # returns the session, closed

  my $same = $git->session;
  # returns the same object, since the handle keeps one

=head2 current_branch

  my $branch = $git->current_branch;

The name of the branch at HEAD.

B<Parameters:> None.

B<Returns:> The branch name. On a detached HEAD git reports C<HEAD>, and that
is what comes back.

B<Examples:>

  my $branch = $git->current_branch;
  # returns 'staging'

=head2 checkout

  $session->switch($branch);   # this is how you get here

Checks a branch out. It runs from the repository root, because the branch
being checked out may not carry the directory you are standing in, and returns
you to that directory only when the checkout kept it.

It is reached through C<< $session->switch >> and nowhere else, and a call
from outside a session dies saying so. That is not a style rule: the session
is what records where you were, takes the lock that stops a second process
switching underneath you, and puts the working tree back on every exit path,
and a checkout outside one has none of that.

C<restore_branch> and the C<track_branch> option are gone. The branch a
command returns to is recorded by C<< $session->begin >> on the session
itself, rather than stamped onto the shared handle by whichever caller asked
first.

B<Parameters:>

=over 4

=item C<$branch>

The branch to switch to.

=back

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

C<"A branch checkout was attempted outside a branch session in %s."> --
raised via C<bail()> where no session is open. C<%s> is the repository root.

=item *

C<"Unable to enter git root %s: %s"> -- raised where the repository root
cannot be entered.

=item *

C<"Failed to checkout '%s'"> -- raised via C<run>'s C<onfailure>. C<%s> is
the branch name.

=back

B<Examples:>

  $session->switch('staging');
  # returns $self, with HEAD now on staging

  $git->checkout('staging');
  # raises, naming the repository, because no session is open

=head2 checkout_detached

  $git->checkout_detached($sha);

Stands on a commit, leaving HEAD detached rather than on a branch.

It is kept apart from C<checkout> because the two are different operations
with different consequences. One puts us on a branch that a later commit
moves, and this one leaves HEAD attached to nothing, which is only ever safe
inside a branch session that restores on every exit path. C<Service::Git::Session>
is its caller, and C<switch> takes this path where its target is a commit
rather than a branch.

Like C<checkout> it runs from the repository root, because the commit being
stood on may not carry the directory we are standing in, and it returns to
that directory only where the checkout kept it.

B<Parameters:>

=over 4

=item C<$commit>

The commit to stand on.

=back

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

C<"A detached checkout was attempted outside a branch session in %s."> --
raised via C<bail()> where no session is open. C<%s> is the repository root.

=item *

C<"Unable to enter git root %s: %s"> -- raised where the repository root
cannot be entered.

=item *

C<"Failed to check out '%s'"> -- raised via C<run>'s C<onfailure>. C<%s> is
the commit.

=back

B<Examples:>

  $git->checkout_detached($sha);
  # returns $self, with HEAD detached at that commit

  $git->checkout_detached('0000000000000000000000000000000000000000');
  # raises, naming the commit, where the repository does not have it

=head2 checkout_one_way

  $git->checkout_one_way($branch);

Checks a branch out and leaves you there. It is C<checkout> with the guard
lifted for the length of the call, and it is temporary.

Two call sites move onto a branch and mean to stay on it. The deploy switches
to the environment branch and deploys from there, and the post-deploy block
moves onto control and hands off to a child command that expects to find it
there. A session would put both back, which is the opposite of what they
mean, so they come through here until the steps that own them decide what
returning should mean. Nothing else may use it, and a test names the two.

There was a third, on the deploy's C<--pull> path, and it went with the flag
when the refresh became unconditional.

B<Parameters:>

=over 4

=item C<$branch>

The branch to switch to and stay on.

=back

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

C<"Failed to checkout '%s'"> -- raised via C<run>'s C<onfailure>. C<%s> is
the branch name.

=back

B<Examples:>

  $git->checkout_one_way('staging');
  # returns $self, standing on staging, with nothing arranged to come back

=head2 create_branch

  $git->create_branch($name);

Creates a branch, at C<$ref> when given and at HEAD otherwise. Does not check

B<Parameters:>

=over 4

=item C<$name>

The branch to create.

=item C<$ref>

Where to start it. Defaults to HEAD.

=back

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

C<"Failed to create branch '%s'"> -- raised via C<run>'s C<onfailure>,

=back

B<Examples:>

  # returns $self; prod now exists at control's tip

=head2 set_branch_ref

  $git->set_branch_ref($branch, $ref);

Forces one local branch ref to another ref. This is the write the design
admits in two cases and no others, which are the pre-flight's reset of a
branch whose only local commits are ones a re-run reproduces, and the
session's abort of a branch it committed to. Nothing else may call it, and in
particular nothing may call it for the control branch, whose committed work is
never discarded.

B<Parameters:>

=over 4

=item C<$branch>

The local branch to move.

=item C<$ref>

Where to move it to, which the two callers spell as a remote-tracking ref or
as a commit.

=back

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

A refusal at C<SOFTWARE> when the branch is the one this working tree is on,
since the ref and the tree would then disagree. The caller switches away
first. It is a defect rather than an operator's mistake, because the two
callers the design admits both know where they are standing and nothing an
operator types reaches it.

=item *

C<"Failed to move '%s' to '%s'"> -- raised via C<run>'s C<onfailure> when git
cannot resolve the ref or cannot write the branch.

=back

B<Examples:>

  $git->set_branch_ref('qa/bosh', 'refs/remotes/origin/qa/bosh');
  # returns $self; qa/bosh now stands where origin/qa/bosh stands

=head2 is_ancestor

  my $bool = $git->is_ancestor($maybe_ancestor, $descendant);

Whether the first ref is reachable from the second. A ref is its own

B<Parameters:>

=over 4

=item C<$maybe_ancestor>

The ref that might be behind.

=item C<$descendant>

The ref that might be ahead.

=back

B<Returns:> 1 or 0. Returns 0 rather than erroring when either argument is

B<Examples:>

=head2 is_clean

  my $bool = $git->is_clean;

Whether the working tree has no modified, staged or conflicted files.

B<Untracked files do not count as dirty.> The question this answers is
whether it is safe to switch branches, and untracked files survive a
checkout untouched. Use C<status> when you need to see them.

B<Parameters:> None.

B<Returns:> 1 when clean, 0 otherwise.

B<Examples:>

  my $bool = $git->is_clean;
  # returns 1 even with untracked files present

=head2 preflight

  $git->preflight;

Asks git one cheap question and classifies the answer, so that three common
failures name their cause and their fix instead of surfacing later as a failed
checkout or a failed commit.

The three are a working tree git refuses under C<safe.directory>, a process
with no committer identity, and a repository with no commits. The first two
exit C<CONFIG>, because the environment is misconfigured; the third exits
C<DATAERR>, because the repository's state is the input.

The identity is asked for separately from the head, because a repository that
has commits answers C<rev-parse> happily and only fails at the commit itself.
An identity supplied through C<GIT_COMMITTER_*> or C<GIT_AUTHOR_*> counts, so
a CI task that carries one in its environment passes.

Returns the handle, so it chains. The branch session calls it in C<begin>, and
C<genesis new>, which opens no session, calls it directly; they share this one
helper rather than each classifying its own failures.

B<Parameters:> None.

B<Returns:> C<$self>.

B<Errors:>

=over 4

=item *

C<< "Git refuses to work in %s because it is owned by another user." >> --
exits C<CONFIG>, and names C<git config --global --add safe.directory> as the
fix.

=item *

C<< "The repository at %s has no commits, so there is no branch to leave and
nothing to come back to." >> -- exits C<DATAERR>, and names C<git commit> as
the fix.

=item *

C<< "This process has no committer identity, so git cannot record a commit in
%s." >> -- exits C<CONFIG>, and names both C<git config user.name> and
C<git config user.email> as the fix.

=back

B<Examples:>

  my $ready = $git->preflight;
  # returns $self, so the session's begin chains straight on

  $git->preflight;
  # exits CONFIG naming the safe.directory command, where the working tree
  # is owned by another user

=head2 status

  my $unclean = $git->status;

The working tree's state as a hashref of path to two-character porcelain
status code.

Unlike C<is_clean>, this B<does> include untracked files, reported as C<??>.
Callers wanting only tracked changes should filter them out.

B<Parameters:>

=over 4

=item C<@pathspecs>

Optional paths to limit the report to, relative to the git root -- so pass
them through C<prefixed> if they are deployment-relative.

=back

B<Returns:> A hashref keyed by path. Empty when nothing is reported.

B<Examples:>

  my $unclean = $git->status;
  # returns { 'ops/thing.yml' => ' M', 'scratch.txt' => '??' }

  my $unclean = $git->status($git->prefixed('ops/thing.yml'));
  # returns only that path's state, or {} when it is unchanged

=head2 diff_files

  my $diff = $git->diff_files($from, $to);
  my $diff = $git->diff_files($from, $to, @pathspecs);

A structured diff between two refs.

Renames are reported three ways at once, deliberately: the old path appears
in C<deleted>, the new one in C<changed>, and the pair in C<renamed>. A
caller copying C<changed> and removing C<deleted> therefore handles a rename
correctly without knowing it was one, while a caller that cares can consult
C<renamed>.

B<Parameters:>

=over 4

=item C<$from>, C<$to>

The refs to compare.

=item C<@pathspecs>

Optional paths to limit the diff to, relative to the git root.

=back

B<Returns:> A hashref with keys C<changed> (added, modified or type-changed),
C<deleted>, C<renamed> (old path to new), and C<all> (changed plus deleted).

B<Examples:>

  my $diff = $git->diff_files('staging', $sha, @paths);
  # returns { changed => ['ops/new.yml'], deleted => [],
  #           renamed => {}, all => ['ops/new.yml'] }

  # A rename from a.yml to b.yml:
  my $diff = $git->diff_files($from, $to);
  # returns { changed => ['b.yml'], deleted => ['a.yml'],
  #           renamed => { 'a.yml' => 'b.yml' }, all => ['b.yml','a.yml'] }

=head2 diff_names

  my @files = $git->diff_names($from, $to);
  my @files = $git->diff_names($from, $to, @pathspecs);

The names of files that differ between two refs, without classification.

B<Parameters:>

=over 4

=item C<$from>, C<$to>

The refs to compare.

=item C<@pathspecs>

Optional git-root-relative paths.

=back

B<Returns:> The list of changed paths. Empty when identical.

B<Errors:>

=over 4

=item *

C<< "Cannot diff <from> against <to> in <root>" >> - raised with the
C<Genesis::Exit::DATAERR> exit code when git cannot take the diff, because a
ref names nothing the local repository holds. A caller that compared an
empty list against a known set would read it as "nothing changed", so the
refusal is raised here rather than handed on as a clean answer.

=back

B<Examples:>

  my @files = $git->diff_names('HEAD~1', 'HEAD');
  # returns ('ops/thing.yml')

=head2 ls_files

  my @paths = $git->ls_files;
  my @paths = $git->ls_files(@pathspecs);

Lists what the index holds, git-root-relative, optionally scoped to pathspecs.

The index and not the working tree, which is the difference every caller here
cares about. The mirror of C<< $session->apply_files >> asks what the branch
holds before it writes anything, and the postcondition check asks what the
index holds once it has written, and a reader that walked the working tree
would answer both questions with the operator's untracked files thrown in.

The paths come back relative to the repository root whatever directory the
caller is standing in, and a pathspec is read against that root too. The
listing is read NUL-separated, so a path holding a byte outside ASCII comes
back as itself rather than quoted and octal-escaped.

B<Parameters:>

=over 4

=item C<@pathspecs>

Optional pathspecs to scope the listing to. With none, the whole index is
listed.

=back

B<Returns:> The list of paths, in git's own order.

B<Errors:>

=over 4

=item *

C<< "Cannot read the index of %s" >> -- raised where git refuses the read,
quoting what git said. It exits C<DATAERR>. The status is read rather than
dropped because git writes its complaint where the paths would be, and a
caller that took those lines for index paths would hand them to C<rm>, which
fails on a pathspec matching nothing and loses every genuine removal.

=back

B<Examples:>

  my @paths = $git->ls_files;
  # returns ('bosh/.genesis/config', 'bosh/ops/thing.yml', 'bosh/qa.yml')

  my @paths = $git->ls_files('bosh/ops');
  # returns ('bosh/ops/thing.yml')

=head2 log_subjects

  my @lines   = $git->log_subjects($branch);
  my @lines   = $git->log_subjects($branch, limit => 50, paths => \@paths);
  my @records = $git->log_subjects($branch, body => 1);

Commit lines for a branch, newest first, or whole commit messages when
C<body> is set.

The C<paths> filter is what makes this usable in a repository deploying more
than one thing from a single branch: without it, the history returned
includes commits belonging to sibling deployments.

The C<body> walk is what makes a squash merge readable.  A squash keeps the
merger's title as the subject and moves the merged message into the body, so
a propagation marker on such a commit is invisible to a walk over subject
lines.  L<Genesis::CI::Marker/newest> is its caller.

B<Parameters:>

=over 4

=item C<$branch>

The branch or revision range to log.

=item C<%opts>

=over 4

=item C<limit>

Maximum number of commits.

=item C<format>

A git format string. Defaults to C<'%H %s'> -- sha and subject -- or to
C<'%H\x1f%B'> when C<body> is set.

The two options are not meant to be combined. A custom format given
alongside C<body> is used as it stands, with only the record separator
appended, so unless it puts a unit separator between the sha and the
message every record comes back with the whole formatted string in C<sha>
and an empty C<message>, and nothing warns. A caller that wants records
passes C<body> alone.

=item C<paths>

Arrayref of git-root-relative paths; only commits touching them are returned.

=item C<body>

Return one hashref per commit rather than one line, carrying the whole
message.

=back

=back

B<Returns:> Without C<body>, the formatted lines, newest first.  With
C<body>, a list of hashrefs of C<sha> and C<message>, newest first.  Empty
when nothing matches, either way.

B<Examples:>

  my @lines = $git->log_subjects('staging', limit => 5);
  # returns ('a1b2c3d... Bump kit version', ...)

  my ($subject) = $git->log_subjects($sha, limit => 1, format => '%s');
  # returns just that commit's subject

  my @records = $git->log_subjects('qa/bosh', body => 1, limit => 1);
  # returns ({sha => 'a1b2c3d...', message => "Merge pull request #7\n\n..."})

=head2 resolve_branch

  my $div = $git->resolve_branch($branch);
  my $div = $git->resolve_branch($branch, remote => 'upstream');
  my $div = $git->resolve_branch($branch, unverifiable => 1);

Reports how the local branch stands against its remote-tracking ref, as one
hashref:

  { state => 'in-sync', ahead => 0, behind => 0, unverifiable => 0 }

C<state> is one of C<in-sync>, C<ahead>, C<behind>, C<diverged>, C<no-local>,
and C<no-remote>. The first four come from the two counts that
C<git rev-list --left-right --count> reports, where C<ahead> counts the
commits the local branch has that the tracking ref lacks and C<behind> counts
the other way. C<no-remote> means the branch is local only, and C<no-local>
means the tracking ref alone has it. When neither ref exists the whole record
is C<undef>, because no state describes a branch that is nowhere.

C<unverifiable> is a flag and not a state. It rides on every answer a caller
asks for without refreshing first, so a report can say that its counts rest on
a tracking ref nobody brought up to date.

The query reads refs alone. It never fetches and never contacts the remote,
because the refresh is its own step and an answer that moved refs on its way
past could not be asked twice about one moment. A caller that wants the remote
consulted refreshes through L</fetch_branches> and then asks this.

Both halves are read through L</_ref_exists>, which answers about the ref it
is handed and about nothing else. L</branch_exists> would answer about a tag
of the same name as readily, and it remembers what it answered, so a handle
that asked before a refresh would go on reporting C<no-local> after one. The
counts are taken against C<refs/heads>, so a local half that read a tag would
name a head that is not there and turn this into a bail.

B<Parameters:>

=over 4

=item C<$branch>

The branch to report on, spelled the way a deployment branch is spelled and
with no C<refs/> prefix.

=item C<remote>

The remote whose tracking refs the branch is measured against. It defaults to
L</default_remote>, and where the repository has no remote at all every branch
it holds reads C<no-remote>.

=item C<unverifiable>

Set this where the caller did not refresh before asking, and the flag comes
back on the answer. It changes neither the state nor either count.

=back

B<Returns:> A hashref carrying C<state>, C<ahead>, C<behind>, and
C<unverifiable>, or C<undef> where neither the local branch nor the tracking
ref exists.

B<Errors:>

=over 4

=item C<< "Failed to compare '%s' with '%s/%s'" >>

Raised where C<git rev-list> fails on two refs that both exist, which is a
repository git cannot read rather than a state this reports.

=item C<"Failed to fetch #C{%s} from #C{%s}: %s">

Raised when the remote confirmed the branch but the refresh that followed
failed, carrying git's stderr or the classified kind, so a caller never
reads a failed refresh as a branch it now has.

=back

B<Examples:>

  my $div = $git->resolve_branch('qa/bosh');
  # returns {state => 'in-sync', ahead => 0, behind => 0, unverifiable => 0}

  my $div = $git->resolve_branch('qa/bosh');
  # returns {state => 'diverged', ahead => 2, behind => 1, unverifiable => 0}

  my $div = $git->resolve_branch('qa/bosh', unverifiable => 1);
  # the same state and the same counts, read off a ref nobody refreshed

  my $div = $git->resolve_branch('nowhere/bosh');
  # returns undef, because no state describes a branch that is nowhere

=head2 fetch_branches

  my ($git, $result) = $git->fetch_branches(\@branches);
  my ($git, $result) = $git->fetch_branches(\@branches, $remote);

Refreshes the named branches in one round trip, reporting which of them the
remote actually has and which local refs it had to create. A branch already
present locally updates its remote-tracking ref alone, so an unpushed local
commit survives the refresh. A branch the clone lacks is materialised
locally from the remote, and that creation is reported in C<created>.

This is the only refresh, and it takes one name as readily as many, because
the forced single-branch helper that wrote C<refs/heads/E<lt>branchE<gt>>
for any name it was handed has been removed, since it overwrote exactly the
local commits the multi-branch path protects.

B<No branch is skipped for being checked out.> The control branch is
usually the one the working tree stands on, and a refresh that left it out
was how a run came to source from whatever the clone already held. The
branch this clone stands on takes the tracking refspec instead, so git is
never asked to write the ref C<HEAD> points at, which it refuses outright
and which would fail the whole fetch. That holds for an unborn branch too,
which is the one checked-out branch C<git for-each-ref> does not list, so
the branch C<HEAD> names is read separately and never treated as one this
clone lacks.

B<One name asked for twice is one branch.> A caller assembling the control
branch and the deployment branches into one list need not check whether
control is already in it. A duplicate is dropped before the probe, so it is
reported once and its refspec appears once.

B<What the result reports is read back off the refs.> The probe and the
fetch are two round trips, so what the remote had when it was asked is not
what the refs hold once the fetch is done. Both namespaces are read again
afterwards, and C<fetched> and C<created> are assembled from what is
actually here rather than from what the probe saw. C<git fetch --porcelain>
would answer the same question in one call, and it arrived above the git
floor this tree declares, so the refresh re-reads instead.

B<Nothing here prunes.> The local-only commit query of
C<Genesis::CI::Preflight> reads the remote-tracking refs to say what a
branch holds that no remote has, and a prune deletes the very refs that
answer it. A branch a teammate deleted on the remote therefore stays in
this clone, with its tracking ref, and the commits it alone holds are still
listed.

B<The remote is asked before it is fetched from.> A refspec naming a branch
the remote lacks aborts the entire fetch -- git reports
C<couldn't find remote ref> and updates nothing, so a single absent branch
would leave every other branch in the list unrefreshed. An C<ls-remote>
probe resolves the set first, and only branches the remote confirms are
fetched. The rest come back in C<absent>, which is a report and not an
error.

B<Absence on the remote says nothing about local state.> A branch may exist
locally and nowhere else -- C<pipeline-prepare> creates env branches before
anything pushes them. So a branch listed in C<absent> leaves the branch
cache untouched, and C<branch_exists> continues to answer for it from local
refs. Only branches actually fetched are recorded as known-to-exist.

B<Callers use C<absent> to decide whether a branch may be created.> Local
absence alone is not grounds: the clone may simply be fresh or stale, and
creating a branch that already exists on the remote forks it from the real
history. C<absent> is the authoritative answer to "does this branch exist
anywhere". See C<Genesis::Env::prepare_branch>, which will not create a
branch the remote already has.

B<One invocation, so credentials are prompted once> regardless of how many
branches are listed. Fetching them individually turns a ten-branch refresh
into ten prompts. The probe adds one round trip, not one per branch.

Probe patterns are fully qualified (C<refs/heads/qa>, not C<qa>) because
C<ls-remote> matches the tail of a ref: a bare C<qa> also matches
C<refs/heads/team/qa>.

B<Failures are classified rather than merely reported.> In list context the
result distinguishes a network problem from an authentication problem from
anything else, so a caller can tell an operator which one they are looking
at. Both stages are classified the same way. Scalar context returns C<$self>
alone, which is what earlier callers expect.

Outside a controlling terminal, C<GIT_TERMINAL_PROMPT=0> is set on both the
probe and the fetch, so a missing credential fails immediately instead of
hanging on a prompt nobody can answer.

B<Parameters:>

=over 4

=item C<\@names>

The branches to fetch. Repeated names are collapsed.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> In scalar context, C<$self>. In list context,
C<($self, \%result)>, where the hashref carries C<ok> (1 on success or
no-op, 0 on a real failure), C<kind> (C<success>, C<network>, C<auth> or
C<unknown>), C<fetched> and C<absent> (arrayrefs partitioning the requested
names by what the remote had), C<created> (the subset of C<fetched> whose
local ref this refresh wrote for the first time), and C<err> (git's stderr,
only when C<ok> is 0).

C<fetched> and C<created> mean something only where C<ok> is 1. A fetch
carrying several refspecs can write some of them and then fail, and the
failure path reports both lists empty rather than working out which ones
landed, so a caller composes an event line out of a refresh that succeeded
and never out of one that did not. C<absent> is read before the fetch and
is reported either way.

B<Errors:> Transport failures never raise. They are returned as
C<ok =E<gt> 0> with a C<kind>, and a branch the remote does not have is
returned in C<absent>; callers that want a hard failure --
C<Genesis::Top::fetch_pipeline_envs> -- raise on the classified result
themselves. One condition does raise, and it is local rather than remote:
where C<git for-each-ref> cannot enumerate a namespace this refresh
reads, the local branches before the fetch or either namespace after it,
the refresh bails naming that namespace, the repository, and git's
stderr. A silently empty read of the local branches would make every
name look locally absent and take the forced refspec onto C<refs/heads>,
which is the overwrite this method exists to prevent, and a silently
empty read after the fetch would report a working refresh as having
fetched nothing.

B<Examples:>

  my ($git, $r) = $git->fetch_branches(['staging', 'prod']);
  # returns ($self, { ok => 1, kind => 'success',
  #                   fetched => ['staging','prod'],
  #                   created => [], absent => [] })

  my ($git, $r) = $git->fetch_branches(['staging', 'brand-new']);
  # returns ($self, { ok => 1, kind => 'success',
  #                   fetched => ['staging'], created => [],
  #                   absent => ['brand-new'] })
  # staging is still refreshed -- the absent branch does not poison it

  my ($git, $r) = $git->fetch_branches(['control', 'qa/bosh']);
  # returns created => ['qa/bosh'] where this clone had no local qa/bosh
  # and the remote did

  my ($git, $r) = $git->fetch_branches(\@branches);
  # returns ($self, { ok => 0, kind => 'auth', err => '...',
  #                   fetched => [], created => [], absent => [] })
  # when credentials are missing

  $git->fetch_branches([]);
  # returns $self -- nothing to fetch is a success, not a failure

  my $bool = Service::Git->is_inside_work_tree($dir);
  # returns false rather than bailing, unlike new()

=head1 FUNCTIONS

These are plain functions rather than methods -- credentials are a
property of the process, not of any one repository instance.

=head2 CI credentials

A CI task receives git credentials as environment variables, which git
itself cannot use: a private key has to exist as a file with restrictive
permissions, and a password has to be answerable when git prompts for it.
These functions bridge that gap.

They exist because the retired C<ci-*> task commands used to do this work
before handing off to Genesis. With those gone, a pipeline task invoking
the plain CLI has no configured git credentials, so every fetch and push
fails.

=head2 Why HOME is left alone

The retired task commands pointed C<HOME> at a temporary directory and
wrote C<~/.ssh/> beneath it. That was safe when the command owned the
whole process. It is not safe here: the same process resolves
C<~/.saferc> and C<~/.genesis>, so relocating C<HOME> would break vault
and repository configuration. Everything below is expressed through
git's own environment variables instead, touching neither C<HOME> nor
the repository's config.

=head2 provision_ci_credentials

  Service::Git::provision_ci_credentials();

Makes environment-supplied git credentials usable, then returns. Called
automatically by L</new>, so callers rarely invoke it directly.

When C<GIT_AUTHOR_NAME> or C<GIT_AUTHOR_EMAIL> is set, mirrors it to the
corresponding C<GIT_COMMITTER_*> variable unless that is already set. Git
requires both identities, and a CI container rarely has C<user.name> or
C<user.email> configured, so without this every commit fails with
"Please tell me who you are".

B<Everything else happens only when the environment carries transport
credentials> -- that is, when C<GIT_PRIVATE_KEY> or C<GIT_USERNAME> is
set, which in practice means a CI task and nothing else. A repository
with no remote, or one whose operator authenticates through a credential
helper, an ssh agent, or an interactive prompt, is left exactly as
configured.

That restraint is deliberate. Suppressing prompts unconditionally would
turn a local workflow that asks for a password into one that fails
outright whenever the operator's credential helper missed.

Having established that it is answering prompts itself, sets
C<GIT_TERMINAL_PROMPT> to C<0> and defaults C<GIT_ASKPASS> to
F</bin/false>, so git fails visibly rather than blocking forever on a
prompt no one can answer. A CI task has no terminal, which turns an
interactive prompt into an indefinite hang. Both are set with C<//=>, so
a caller that has already chosen values keeps them.

When C<GIT_PRIVATE_KEY> is set, writes the key to a private temporary
directory at mode C<0600> alongside an ssh config selecting it, and
points C<GIT_SSH_COMMAND> at that config.

When C<GIT_USERNAME> is set, writes an askpass helper and points
C<GIT_ASKPASS> at it. The helper reads C<GIT_USERNAME> and
C<GIT_PASSWORD> from its own environment rather than having them baked
into the script, so a password containing shell metacharacters is neither
mangled nor written to disk.

Idempotent: the temporary directory is created once per process and
subsequent calls return immediately. The directory is removed when the
process exits.

Does nothing beyond identity mirroring when neither C<GIT_PRIVATE_KEY>
nor C<GIT_USERNAME> is present, which is every local run -- including a
freshly initialised repository with no remote at all.

B<Errors:>

=over 4

=item C<"Cannot write git ssh key: %s">

Bails when the key file cannot be created, carrying the system error.

=item C<"Cannot write git ssh config: %s">

Bails when the ssh config cannot be created.

=item C<"Cannot write git askpass helper: %s">

Bails when the askpass helper cannot be created.

All three are fatal rather than warnings: continuing would leave git
without the credentials it was told to use, and the resulting failure
would surface far from its cause as an authentication error.

=back

B<Examples:>

  # In a CI task, with the pipeline supplying credentials:
  #   GIT_PRIVATE_KEY=... genesis <env> deploy -SFy
  Service::Git::provision_ci_credentials();
  # $ENV{GIT_SSH_COMMAND} is now "ssh -F /tmp/genesis-git-creds.XXXX/ssh_config"

  # Locally, or against a repository with no remote:
  Service::Git::provision_ci_credentials();
  # nothing is written and no git behaviour changes

=head2 reset_ci_credentials

  Service::Git::reset_ci_credentials();

Discards the record of provisioned credentials so the next
L</provision_ci_credentials> call materialises them again. Intended for
tests that need to exercise several credential shapes in one process;
production code has no reason to call it.

Releasing the temporary directory also deletes it, so any path previously
published in C<GIT_SSH_COMMAND> or C<GIT_ASKPASS> becomes invalid.

B<Errors:>

None.

B<Examples:>

  local %ENV = (%ENV);
  $ENV{GIT_USERNAME} = 'ci-bot';
  Service::Git::reset_ci_credentials();
  Service::Git::provision_ci_credentials();

=head1 INTERNAL FUNCTIONS

=head2 _refuse_dubious_ownership

  _refuse_dubious_ownership($said, $path);

Raises the C<safe.directory> refusal when git's own words name that condition,
and returns quietly when they do not.

Shared by L</new> and L</preflight>, because a working tree git declines is
refused while the handle is being built as readily as at the pre-flight, and
an operator who meets the condition twice should meet the same message, the
same fix, and the same exit code both times. A caller hands over whatever git
said and carries on with its own classification when this returns.

Matching is on git's message text, which is not a stable interface. An
unrecognised wording falls through to the caller's own refusal, so a missed
pattern degrades to a less helpful message rather than a wrong one.

B<Parameters:>

=over 4

=item C<$said>

What git said, standard error and standard output folded together. C<undef>
is treated as no match.

=item C<$path>

The working tree to name, and to name in the C<safe.directory> command the
message prints. Both callers hand over the path as git resolves it, so an
operator who meets this refusal twice is handed the same command both times,
and git compares a C<safe.directory> entry against the resolved path anyway.

=back

B<Returns:> Nothing, and only where git said nothing of the kind.

B<Errors:>

=over 4

=item *

C<< "Git refuses to work in %s because it is owned by another user." >> --
exits C<CONFIG>. C<%s> is C<$path>, which is also what the C<git config
--global --add safe.directory> line names.

=back

B<Examples:>

  _refuse_dubious_ownership('fatal: detected dubious ownership', '/repo');
  # exits CONFIG naming /repo and the command that adds the exception

  _refuse_dubious_ownership('fatal: Needed a single revision', '/repo');
  # returns, leaving the caller to classify an empty repository

=head2 _classify_remote_error

  my $kind = _classify_remote_error($stderr);

Buckets a git transport error into C<network>, C<auth> or C<unknown>.

Shared by the probe and fetch stages of L</fetch_branches> so the two cannot
drift into classifying the same failure differently -- the operator-facing
advice ("you are offline" versus "fix your credentials") depends on it.

Matching is on git's stderr text, which is not a stable interface. An
unrecognised message lands in C<unknown>, which callers surface verbatim, so
a missed pattern degrades to a less helpful message rather than a wrong one.

B<Parameters:>

=over 4

=item C<$stderr>

Git's stderr. C<undef> is treated as empty.

=back

B<Returns:> One of C<network>, C<auth>, C<unknown>.

B<Errors:> None. Every input yields a bucket.

B<Examples:>

  _classify_remote_error('fatal: Could not resolve host: github.com');
  # returns 'network'

  _classify_remote_error('fatal: Authentication failed for ...');
  # returns 'auth'

  _classify_remote_error(undef);
  # returns 'unknown'

=head2 _ref_exists

  my $bool = $git->_ref_exists('refs/remotes/origin/qa/bosh');

Whether a fully qualified ref is in this repository.

It asks C<git show-ref --verify>, which answers about the ref it is handed and
about nothing else. L</branch_exists> cannot answer this question, because it
runs C<git rev-parse --verify> on a short name, and that name resolves a tag or
a sha as readily as a branch while reaching no remote-tracking ref at all.
L</resolve_branch> asks this one about both of the refs it compares, where
every part of that looseness would give a wrong answer.

B<Parameters:>

=over 4

=item C<$ref>

The ref to look for, fully qualified. A short name is not resolved here, so
C<qa/bosh> reads false however many refs of that name the repository holds.

=back

B<Returns:> C<1> where the ref is here and C<0> where it is not.

B<Errors:> None. Git's own complaint is suppressed, and a ref that is not here
is an answer rather than a failure.

B<Examples:>

  $git->_ref_exists('refs/remotes/origin/qa/bosh');
  # returns 1 once the refresh has written the tracking ref

  $git->_ref_exists('qa/bosh');
  # returns 0, because the name is not fully qualified

=head2 _ref_names

  my $heads = $git->_ref_names('refs/heads/', \%opts);
  my $track = $git->_ref_names('refs/remotes/origin/', \%opts);

The short names under one ref namespace, as a hashref of name to C<1>.

One read rather than one probe per name. L</fetch_branches> asks about every
branch it was given twice, once to decide which refspec each of them takes and
once to see what the fetch actually left behind, so a probe per name would turn
a ten-branch refresh into thirty subprocesses.

How many components the name is stripped of is worked out from the prefix, so
C<refs/heads/> answers C<qa/bosh> and C<refs/remotes/origin/> answers the same
name rather than C<origin/qa/bosh>.

B<Parameters:>

=over 4

=item C<$prefix>

The namespace to list, with its trailing slash.

=item C<\%opts>

The options handed to C<run>, which carry the repository directory and, outside
a controlling terminal, C<GIT_TERMINAL_PROMPT>. Defaults to this handle's own
root where it is omitted.

=back

B<Returns:> A hashref keyed by short name, empty where the namespace holds
nothing.

B<Errors:> Bails when C<git for-each-ref> fails, naming the namespace, the
repository, and git's stderr. A failure is not allowed to read as an empty
namespace, because L</fetch_branches> would then take every branch for one this
clone lacks and force a write onto each of them.

B<Examples:>

  $git->_ref_names('refs/heads/');
  # returns { control => 1, 'qa/bosh' => 1 }

  $git->_ref_names('refs/remotes/origin/');
  # returns { control => 1 }, with the remote's name already stripped

=head2 _checked_out_branch

  my $branch = $git->_checked_out_branch;

The branch C<HEAD> points at, whether or not it has a commit on it yet.

L</current_branch> cannot answer this. It runs C<git rev-parse --abbrev-ref
HEAD>, which fails on an unborn branch and prints the literal string C<HEAD>,
so a fresh orphan checkout reads as though it were standing on a branch of that
name. C<git symbolic-ref> names the branch in that state, and it says nothing at
all on a detached C<HEAD>, which is what tells the two cases apart.

L</fetch_branches> asks it because git refuses to fetch into the ref C<HEAD>
points at, and an unborn branch is the one checked-out branch
C<git for-each-ref> does not list, so without this reader the refresh would
force a write git declines and lose the whole fetch with it.

B<Parameters:> None.

B<Returns:> The branch name, or C<undef> on a detached C<HEAD>.

B<Errors:> None. A detached C<HEAD> is an answer rather than a failure.

B<Examples:>

  $git->_checked_out_branch;
  # returns 'control' on an ordinary checkout, and 'newbranch' on a
  # `git checkout --orphan newbranch` that has committed nothing

  $git->_checked_out_branch;
  # returns undef where HEAD names a commit rather than a branch

=head2 _provision_ssh_key

Writes C<GIT_PRIVATE_KEY> to F<key> at mode C<0600> in the supplied
directory, writes an ssh config selecting it with C<IdentityFile> and
C<IdentitiesOnly>, and sets C<GIT_SSH_COMMAND>.

The config disables C<StrictHostKeyChecking> and discards
C<UserKnownHostsFile>, because a CI worker is ephemeral and has no
known_hosts to check against -- the key is the authentication.

B<Errors:> as documented under L</provision_ci_credentials>.

B<Examples:>

  Service::Git::_provision_ssh_key('/tmp/genesis-git-creds.ab12cd');

=head2 _provision_askpass

Writes an executable askpass helper into the supplied directory and sets
C<GIT_ASKPASS>. Git invokes the helper with the prompt text as its only
argument and reads one line from stdout; the helper answers a C<Username>
prompt with C<GIT_USERNAME> and anything else with C<GIT_PASSWORD>.

B<Errors:> as documented under L</provision_ci_credentials>.

B<Examples:>

  Service::Git::_provision_askpass('/tmp/genesis-git-creds.ab12cd');
  # $ENV{GIT_ASKPASS} now answers git's credential prompts

=head1 LIMITATIONS

=over 4

=item Credentials are process-wide, not per-repository

C<provision_ci_credentials> sets environment variables, so one set of
credentials applies to every repository this process touches. A task
operating on two repositories with different credentials is not
supported. No current caller does that.

=item The askpass helper answers any non-username prompt with the password

Git prompts for more than usernames and passwords -- an ssh key
passphrase, for instance. The helper cannot distinguish those, so it
answers with C<GIT_PASSWORD>. Harmless in practice, since a pipeline
supplies either a passphraseless key or a username/password pair, but it
would misbehave with an encrypted key.

=item Host key verification is disabled for ssh

Deliberate, and appropriate for an ephemeral CI worker, but it means an
ssh connection is not protected against a substituted host. A long-lived
worker with a managed known_hosts would be better served by leaving
C<GIT_SSH_COMMAND> unset and configuring ssh normally.

=item Provisioning happens on construction, not on demand

L</new> calls it, so a process that never constructs a C<Service::Git>
never provisions credentials even if the environment carries them. That
matches current usage, where every remote operation goes through this
class.

=item Presence of credentials is the only signal that this is CI

There is no explicit "running under CI" flag; C<GIT_PRIVATE_KEY> or
C<GIT_USERNAME> being set is taken to mean the caller wants Genesis to
answer git's credential prompts. An operator who exports those variables
for their own reasons would also get the prompt suppression, and would
see a failure where they expected to be asked. Setting C<GIT_ASKPASS> or
C<GIT_TERMINAL_PROMPT> explicitly opts back out, since both are applied
only when unset.

=back
