=head1 NAME

Service::Git - Git operations for a deployment repository

=head1 SYNOPSIS

  use Service::Git;

  # One instance per repository, whatever path you name inside it
  my $git = Service::Git->new('.');
  my $git = Service::Git->new($path, track_branch => 1);

  # Branches
  $git->checkout('staging') if $git->branch_exists('staging');
  $git->create_branch('prod', 'control');
  $git->restore_branch;

  # Queries
  my $sha   = $git->sha('HEAD', short => 1);
  my $clean = $git->is_clean;
  my $diff  = $git->diff_files($from, $to, @paths);

  # Working tree
  $git->checkout_file($sha, 'ops/thing.yml');
  $git->commit('[pipeline] control@abc1234 -> staging (pulled)', @files);

  # Remotes
  my ($self, $result) = $git->fetch_branches(\@branches);
  my $pushed = $git->push(@branches);

=head1 DESCRIPTION

C<Service::Git> wraps the git commands Genesis needs to manage a deployment
repository: branch handling for the pipeline model, structured diffs for
propagation, and the remote operations that move branches between a working
copy and its origin.

It is deliberately thin. Each method is one git invocation and a little
parsing; nothing here caches file content or models the repository beyond
what git itself reports. What it does add is the handful of decisions that
would otherwise be repeated at every call site -- which failures are fatal,
which are ordinary answers, and how paths are spelled.

=head2 One instance per repository

C<new> is a flyweight: it resolves the git top-level for whatever path it is
given, and returns the existing instance when one already exists for that
root. Two callers naming different subdirectories of the same repository get
the same object.

That matters because instances carry mutable state -- the branch to restore,
the branch-existence cache, the resolved default remote. Independent objects
for one repository would each track a different "original" branch and undo
each other's work.

=head2 Two path spellings

Git reports paths relative to the B<git root>. Genesis works in a deployment
repository that may sit in a subdirectory of it, and speaks to operators in
paths relative to that B<deployment root>.

C<prefix> is the offset between them, and C<prefixed> / C<unprefixed> convert
between the two. Getting this wrong does not error: a pathspec in the wrong
spelling simply matches nothing, and a diff comes back empty as though there
were no changes.

=head2 Branch tracking

With C<< track_branch => 1 >>, the branch checked out at construction is
remembered and restored -- explicitly via C<restore_branch>, or at process
exit via C<DESTROY>. Commands that check out an environment branch to do
their work use this so an operator is not left somewhere unexpected.

Because the instance is a flyweight held for the process lifetime, C<DESTROY>
fires during global destruction rather than when a caller drops its
reference.

=head1 METHODS

=head2 new

  my $git = Service::Git->new;
  my $git = Service::Git->new($path);
  my $git = Service::Git->new($path, track_branch => 1);

Returns the C<Service::Git> for the repository containing C<$path>, creating
it on first call and returning the existing instance thereafter.

Requesting C<track_branch> on a repository that already has an untracked
instance upgrades that instance in place rather than creating a second one,
recording the current branch as the one to restore.

Also calls L</provision_ci_credentials>, so a process that constructs a
C<Service::Git> can perform remote operations with credentials supplied
through the environment. A no-op when none are set, which is every local
run.

B<Parameters:>

=over 4

=item C<$path>

Any path inside the repository. Defaults to the current directory.

=item C<%opts>

=over 4

=item C<track_branch>

Remember the current branch and restore it on C<restore_branch> or at process
exit.

=back

=back

B<Returns:> The C<Service::Git> instance for that repository.

B<Errors:>

=over 4

=item *

C<"Not a git repository: %s"> -- raised via C<bail()> when C<$path> is not
under git control. C<%s> is the path given.

=back

B<Examples:>

  my $git = Service::Git->new('.');
  # returns the instance for the repository containing the cwd

  my $a = Service::Git->new('repo/bosh');
  my $b = Service::Git->new('repo/vault');
  # returns the same object for both -- one repository, one instance

=head2 create

  my $git = Service::Git->create($path);
  my $git = Service::Git->create($path, initial_branch => 'control');

Initialises a git repository at C<$path> and returns an instance for it.

When C<initial_branch> is given, the branch is set with
C<git symbolic-ref> rather than C<git init -b>, because the latter requires
git 2.28 or newer and this must work against older installations.

B<Parameters:>

=over 4

=item C<$path>

Where to initialise. Defaults to the current directory.

=item C<%opts>

C<initial_branch> as above; any other options are passed to C<new>.

=back

B<Returns:> The C<Service::Git> instance for the new repository.

B<Errors:>

=over 4

=item *

C<"Failed to initialize git in %s"> -- raised via C<run>'s C<onfailure> when
C<git init> fails.

=back

B<Examples:>

  my $git = Service::Git->create($dir, initial_branch => 'control');
  # returns an instance whose HEAD points at refs/heads/control

=head2 DESTROY

Restores the tracked branch at process exit.

Only acts when C<track_branch> was requested and the branch has actually
changed. Working-tree changes are discarded first -- a checkout would fail
against a dirty tree, and leaving the operator on the wrong branch is the
worse outcome.

Both commands run in pass/fail mode: this runs during global destruction,
where dying achieves nothing useful.

B<Returns:> Nothing.

=head2 is_ancestor

  my $bool = $git->is_ancestor($maybe_ancestor, $descendant);

B<Parameters:>

=over 4

=item C<$maybe_ancestor>

The ref that might be behind.

=head2 is_clean

  my $bool = $git->is_clean;

Whether the working tree has no modified, staged or conflicted files.

B<Untracked files do not count as dirty.> The question this answers is
whether it is safe to switch branches, and untracked files survive a
checkout untouched. Use C<status> when you need to see them.

B<Parameters:> None.

B<Returns:> 1 when clean, 0 otherwise.

B<Examples:>

  # returns 1 even with untracked files present

=head2 status

  my $unclean = $git->status;
  my $unclean = $git->status(@pathspecs);

The working tree's state as a hashref of path to two-character porcelain
status code.

Unlike C<is_clean>, this B<does> include untracked files, reported as C<??>.
Callers wanting only tracked changes should filter them out.

B<Parameters:>

=over 4

=item C<@pathspecs>

Optional paths to limit the report to, relative to the git root -- so pass
them through C<prefixed> if they are deployment-relative.

=back

B<Returns:> A hashref keyed by path. Empty when nothing is reported.

B<Examples:>

  # returns { 'ops/thing.yml' => ' M', 'scratch.txt' => '??' }

  # returns only that path's state, or {} when it is unchanged

=head2 diff_files

  my $diff = $git->diff_files($from, $to);
  my $diff = $git->diff_files($from, $to, @pathspecs);

A structured diff between two refs.

Renames are reported three ways at once, deliberately: the old path appears
in C<deleted>, the new one in C<changed>, and the pair in C<renamed>. A
caller copying C<changed> and removing C<deleted> therefore handles a rename
correctly without knowing it was one, while a caller that cares can consult
C<renamed>.

B<Parameters:>

=over 4

=item C<$from>, C<$to>

The refs to compare.

=item C<@pathspecs>

Optional paths to limit the diff to, relative to the git root.

=back

B<Returns:> A hashref with keys C<changed> (added, modified or type-changed),
C<deleted>, C<renamed> (old path to new), and C<all> (changed plus deleted).

B<Examples:>

  my $diff = $git->diff_files('staging', $sha, @paths);
  # returns { changed => ['ops/new.yml'], deleted => [],
  #           renamed => {}, all => ['ops/new.yml'] }

  # A rename from a.yml to b.yml:
  my $diff = $git->diff_files($from, $to);
  # returns { changed => ['b.yml'], deleted => ['a.yml'],
  #           renamed => { 'a.yml' => 'b.yml' }, all => ['b.yml','a.yml'] }

=head2 diff_names

  my @files = $git->diff_names($from, $to);

=head2 resolve_branch

  my $where = $git->resolve_branch($branch);
  my $where = $git->resolve_branch($branch, $remote);
  my $where = $git->resolve_branch({offline => 1}, $branch);

Locates a branch, fetching it when only the remote has it. Returns
C<local>, C<fetched>, C<absent> or C<unverifiable>.

B<A branch missing from this clone is not a branch that does not exist.>
The clone may be fresh or stale -- in CI it is always fresh, holding only
the control branch. Creating the branch in that case forks it from the real
one: the new branch starts at the wrong commit, and the first push either is
rejected as a non-fast-forward or, if forced, destroys the deployment anchor
propagation depends on. So the remote is the authority, and B<only C<absent>
licenses a caller to create the branch>.

B<An unreachable remote is not absence.> The probe raises rather than
returning C<absent>, because degrading to "assume it does not exist" is
exactly the mistake this guards against -- it would create branches whenever
the network is down. A caller that wants to proceed offline must decide that
explicitly; it cannot get there by accident.

A repository with no remote configured has no authority to consult, so local
absence is the whole truth and C<absent> is returned without a probe.

B<C<offline> withholds the answer instead of guessing.> Working offline is a
legitimate reason not to contact the remote, but it is not a reason to
assume the branch does not exist. C<offline> therefore yields
C<unverifiable> -- distinct from C<absent> precisely so a caller cannot
treat "we did not look" as "there is nothing there". Callers reconcile the
branches they already have and report the rest as skipped. A branch already
present locally still resolves to C<local> offline, since nothing needs
confirming.

B<Parameters:>

=over 4

=item C<\%opts>

Optional leading hashref. C<offline> suppresses the remote probe, yielding
C<unverifiable> for any branch not already local.

=item C<$branch>

The branch to locate.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> C<local> when the branch is already in this clone (the remote is
not consulted); C<fetched> when the remote had it and it has now been
fetched into a local ref; C<absent> when it exists neither here nor on the
remote, or when no remote is configured; C<unverifiable> under C<offline>
when the branch is not already local.

B<Errors:>

=over 4

=item C<"ls-remote against #C{%s} failed: %s">

Raised via C<remote_branch_exists> when the remote cannot be reached or
authenticated against. Deliberately not caught: see above.

=item C<"Failed to fetch '%s' from '%s'">

Raised via C<fetch_branch> when the remote confirmed the branch but the
fetch itself failed.

=back

B<Examples:>

  my $where = $git->resolve_branch('staging');
  # returns 'local' -- already here, no round trip

  my $where = $git->resolve_branch('staging');
  # returns 'fetched' -- the remote had it; refs/heads/staging now exists

  if ($git->resolve_branch('brand-new') eq 'absent') {
      $git->create_branch('brand-new');   # the only safe path to a create
  }

  my $where = $git->resolve_branch({offline => 1}, 'brand-new');
  # returns 'unverifiable' -- reconcile what is here, skip the rest

=head2 delete_remote_branch

  $git->delete_remote_branch($branch);
  $git->delete_remote_branch($branch, $remote);

Deletes a branch on the remote.

B<Parameters:>

=over 4

=item C<$branch>

The branch to delete.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> C<$self>. No-op when no remote is configured.

B<Errors:>

=over 4

=item *

C<"Failed to delete remote branch #C{%s} on #C{%s}: %s"> -- raised via
C<bail()> carrying git's message.

=back

B<Examples:>

  $git->delete_remote_branch('old-env');
  # returns $self

=head2 fetch_branch

  $git->fetch_branch($branch);
  $git->fetch_branch($branch, $remote);

Fetches one branch into the matching local ref.

Uses a forced refspec, so the local ref is created or overwritten regardless
of fast-forward status. That is safe for the branches this is used on --
propagation branches are written once and never rebased -- and would not be
for a branch someone commits to locally.

B<Parameters:>

=over 4

=item C<$branch>

The branch to fetch.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> C<$self>. No-op when no remote is configured.

B<Errors:>

=over 4

=item *

C<"Failed to fetch '%s' from '%s'"> -- raised via C<run>'s C<onfailure>.

=back

B<Examples:>

  $git->fetch_branch('staging');
  # returns $self; refs/heads/staging now matches the remote

=head2 fetch_branches

  $git->fetch_branches(\@names);
  my ($self, $result) = $git->fetch_branches(\@names, $remote);

Fetches several branches in one git invocation, reporting which of them the
remote actually has.

B<The remote is asked before it is fetched from.> A refspec naming a branch
the remote lacks aborts the entire fetch -- git reports
C<couldn't find remote ref> and updates nothing, so a single absent branch
would leave every other branch in the list unrefreshed. An C<ls-remote>
probe resolves the set first, and only branches the remote confirms are
fetched. The rest come back in C<absent>, which is a report and not an
error.

B<Absence on the remote says nothing about local state.> A branch may exist
locally and nowhere else -- C<pipeline-prepare> creates env branches before
anything pushes them. So a branch listed in C<absent> leaves the branch
cache untouched, and C<branch_exists> continues to answer for it from local
refs. Only branches actually fetched are recorded as known-to-exist.

B<Callers use C<absent> to decide whether a branch may be created.> Local
absence alone is not grounds: the clone may simply be fresh or stale, and
creating a branch that already exists on the remote forks it from the real
history. C<absent> is the authoritative answer to "does this branch exist
anywhere". See C<Genesis::Env::prepare_branch>, which will not create a
branch the remote already has.

B<One invocation, so credentials are prompted once> regardless of how many
branches are listed. Fetching them individually turns a ten-branch refresh
into ten prompts. The probe adds one round trip, not one per branch.

Probe patterns are fully qualified (C<refs/heads/qa>, not C<qa>) because
C<ls-remote> matches the tail of a ref: a bare C<qa> also matches
C<refs/heads/team/qa>.

The currently checked-out branch is skipped: git refuses to update an active
branch through a refspec, and including it would fail the whole fetch.

B<Failures are classified rather than merely reported.> In list context the
result distinguishes a network problem from an authentication problem from
anything else, so a caller can tell an operator which one they are looking
at. Both stages are classified the same way. Scalar context returns C<$self>
alone, which is what earlier callers expect.

Outside a controlling terminal, C<GIT_TERMINAL_PROMPT=0> is set on both the
probe and the fetch, so a missing credential fails immediately instead of
hanging on a prompt nobody can answer.

B<Parameters:>

=over 4

=item C<\@names>

The branches to fetch.

=item C<$remote>

Defaults to C<default_remote>.

=back

B<Returns:> In scalar context, C<$self>. In list context,
C<($self, \%result)>, where the hashref carries C<ok> (1 on success or
no-op, 0 on a real failure), C<kind> (C<success>, C<network>, C<auth> or
C<unknown>), C<fetched> and C<absent> (arrayrefs partitioning the requested
names by what the remote had), and C<err> (git's stderr, only when C<ok> is
0).

B<Errors:> Never raises. Transport failures are returned as C<ok =E<gt> 0>
with a C<kind>; a branch the remote does not have is returned in C<absent>.
Callers that want a hard failure -- C<Genesis::Top::fetch_pipeline_envs> --
raise on the classified result themselves.

B<Examples:>

  my ($git, $r) = $git->fetch_branches(['staging', 'prod']);
  # returns ($self, { ok => 1, kind => 'success',
  #                   fetched => ['staging','prod'], absent => [] })

  my ($git, $r) = $git->fetch_branches(['staging', 'brand-new']);
  # returns ($self, { ok => 1, kind => 'success',
  #                   fetched => ['staging'], absent => ['brand-new'] })
  # staging is still refreshed -- the absent branch does not poison it

  my ($git, $r) = $git->fetch_branches(\@branches);
  # returns ($self, { ok => 0, kind => 'auth', err => '...' })
  # when credentials are missing

  $git->fetch_branches([]);
  # returns $self -- nothing to fetch is a success, not a failure

=head2 push

  my $results = $git->push(@branches);
  my $results = $git->push($remote, @branches);

Pushes branches, reporting the outcome per branch.

B<The remote argument is detected, not declared.> If the first argument is
not a known local branch, it is taken to be a remote name. A branch whose
name collides with a remote's would therefore be misread -- in practice
branches are not named C<origin>.

Each branch is pushed separately and a failure does not stop the rest, so a
partial push is reported rather than aborted midway.

B<Parameters:>

=over 4

=item C<@args>

An optional leading remote name followed by the branches to push. The two are
not distinguished by position but by lookup: the first element is treated as
a remote only when C<branch_exists> says it is not a local branch. Passing
branches alone is the common case.

=back

B<Returns:> A hashref of branch name to 1 or 0. Empty hashref when no remote
is configured.

B<Examples:>

  my $results = $git->push('staging', 'prod');
  # returns { staging => 1, prod => 1 }

  my $results = $git->push(@branches);
  # returns { staging => 1, prod => 0 } when only prod was rejected

=head1 FUNCTIONS

These are plain functions rather than methods -- credentials are a
property of the process, not of any one repository instance.

=head2 CI credentials

A CI task receives git credentials as environment variables, which git
itself cannot use: a private key has to exist as a file with restrictive
permissions, and a password has to be answerable when git prompts for it.
These functions bridge that gap.

They exist because the retired C<ci-*> task commands used to do this work
before handing off to Genesis. With those gone, a pipeline task invoking
the plain CLI has no configured git credentials, so every fetch and push
fails.

=head2 Why HOME is left alone

The retired task commands pointed C<HOME> at a temporary directory and
wrote C<~/.ssh/> beneath it. That was safe when the command owned the
whole process. It is not safe here: the same process resolves
C<~/.saferc> and C<~/.genesis>, so relocating C<HOME> would break vault
and repository configuration. Everything below is expressed through
git's own environment variables instead, touching neither C<HOME> nor
the repository's config.

=head2 provision_ci_credentials

  Service::Git::provision_ci_credentials();

Makes environment-supplied git credentials usable, then returns. Called
automatically by L</new>, so callers rarely invoke it directly.

When C<GIT_AUTHOR_NAME> or C<GIT_AUTHOR_EMAIL> is set, mirrors it to the
corresponding C<GIT_COMMITTER_*> variable unless that is already set. Git
requires both identities, and a CI container rarely has C<user.name> or
C<user.email> configured, so without this every commit fails with
"Please tell me who you are".

B<Everything else happens only when the environment carries transport
credentials> -- that is, when C<GIT_PRIVATE_KEY> or C<GIT_USERNAME> is
set, which in practice means a CI task and nothing else. A repository
with no remote, or one whose operator authenticates through a credential
helper, an ssh agent, or an interactive prompt, is left exactly as
configured.

That restraint is deliberate. Suppressing prompts unconditionally would
turn a local workflow that asks for a password into one that fails
outright whenever the operator's credential helper missed.

Having established that it is answering prompts itself, sets
C<GIT_TERMINAL_PROMPT> to C<0> and defaults C<GIT_ASKPASS> to
F</bin/false>, so git fails visibly rather than blocking forever on a
prompt no one can answer. A CI task has no terminal, which turns an
interactive prompt into an indefinite hang. Both are set with C<//=>, so
a caller that has already chosen values keeps them.

When C<GIT_PRIVATE_KEY> is set, writes the key to a private temporary
directory at mode C<0600> alongside an ssh config selecting it, and
points C<GIT_SSH_COMMAND> at that config.

When C<GIT_USERNAME> is set, writes an askpass helper and points
C<GIT_ASKPASS> at it. The helper reads C<GIT_USERNAME> and
C<GIT_PASSWORD> from its own environment rather than having them baked
into the script, so a password containing shell metacharacters is neither
mangled nor written to disk.

Idempotent: the temporary directory is created once per process and
subsequent calls return immediately. The directory is removed when the
process exits.

Does nothing beyond identity mirroring when neither C<GIT_PRIVATE_KEY>
nor C<GIT_USERNAME> is present, which is every local run -- including a
freshly initialised repository with no remote at all.

B<Errors:>

=over 4

=item C<"Cannot write git ssh key: %s">

Bails when the key file cannot be created, carrying the system error.

=item C<"Cannot write git ssh config: %s">

Bails when the ssh config cannot be created.

=item C<"Cannot write git askpass helper: %s">

Bails when the askpass helper cannot be created.

All three are fatal rather than warnings: continuing would leave git
without the credentials it was told to use, and the resulting failure
would surface far from its cause as an authentication error.

=back

B<Examples:>

  # In a CI task, with the pipeline supplying credentials:
  #   GIT_PRIVATE_KEY=... genesis <env> deploy -SFy
  Service::Git::provision_ci_credentials();
  # $ENV{GIT_SSH_COMMAND} is now "ssh -F /tmp/genesis-git-creds.XXXX/ssh_config"

  # Locally, or against a repository with no remote:
  Service::Git::provision_ci_credentials();
  # nothing is written and no git behaviour changes

=head2 reset_ci_credentials

  Service::Git::reset_ci_credentials();

Discards the record of provisioned credentials so the next
L</provision_ci_credentials> call materialises them again. Intended for
tests that need to exercise several credential shapes in one process;
production code has no reason to call it.

Releasing the temporary directory also deletes it, so any path previously
published in C<GIT_SSH_COMMAND> or C<GIT_ASKPASS> becomes invalid.

B<Errors:>

None.

B<Examples:>

  local %ENV = (%ENV);
  $ENV{GIT_USERNAME} = 'ci-bot';
  Service::Git::reset_ci_credentials();
  Service::Git::provision_ci_credentials();

=head1 INTERNAL FUNCTIONS

=head2 _classify_remote_error

  my $kind = _classify_remote_error($stderr);

Buckets a git transport error into C<network>, C<auth> or C<unknown>.

Shared by the probe and fetch stages of L</fetch_branches> so the two cannot
drift into classifying the same failure differently -- the operator-facing
advice ("you are offline" versus "fix your credentials") depends on it.

Matching is on git's stderr text, which is not a stable interface. An
unrecognised message lands in C<unknown>, which callers surface verbatim, so
a missed pattern degrades to a less helpful message rather than a wrong one.

B<Parameters:>

=over 4

=item C<$stderr>

Git's stderr. C<undef> is treated as empty.

=back

B<Returns:> One of C<network>, C<auth>, C<unknown>.

B<Errors:> None. Every input yields a bucket.

B<Examples:>

  _classify_remote_error('fatal: Could not resolve host: github.com');
  # returns 'network'

  _classify_remote_error('fatal: Authentication failed for ...');
  # returns 'auth'

  _classify_remote_error(undef);
  # returns 'unknown'

=head2 _provision_ssh_key

Writes C<GIT_PRIVATE_KEY> to F<key> at mode C<0600> in the supplied
directory, writes an ssh config selecting it with C<IdentityFile> and
C<IdentitiesOnly>, and sets C<GIT_SSH_COMMAND>.

The config disables C<StrictHostKeyChecking> and discards
C<UserKnownHostsFile>, because a CI worker is ephemeral and has no
known_hosts to check against -- the key is the authentication.

B<Errors:> as documented under L</provision_ci_credentials>.

B<Examples:>

  Service::Git::_provision_ssh_key('/tmp/genesis-git-creds.ab12cd');

=head2 _provision_askpass

Writes an executable askpass helper into the supplied directory and sets
C<GIT_ASKPASS>. Git invokes the helper with the prompt text as its only
argument and reads one line from stdout; the helper answers a C<Username>
prompt with C<GIT_USERNAME> and anything else with C<GIT_PASSWORD>.

B<Errors:> as documented under L</provision_ci_credentials>.

B<Examples:>

  Service::Git::_provision_askpass('/tmp/genesis-git-creds.ab12cd');
  # $ENV{GIT_ASKPASS} now answers git's credential prompts

=head1 LIMITATIONS

=over 4

=item Credentials are process-wide, not per-repository

C<provision_ci_credentials> sets environment variables, so one set of
credentials applies to every repository this process touches. A task
operating on two repositories with different credentials is not
supported. No current caller does that.

=item The askpass helper answers any non-username prompt with the password

Git prompts for more than usernames and passwords -- an ssh key
passphrase, for instance. The helper cannot distinguish those, so it
answers with C<GIT_PASSWORD>. Harmless in practice, since a pipeline
supplies either a passphraseless key or a username/password pair, but it
would misbehave with an encrypted key.

=item Host key verification is disabled for ssh

Deliberate, and appropriate for an ephemeral CI worker, but it means an
ssh connection is not protected against a substituted host. A long-lived
worker with a managed known_hosts would be better served by leaving
C<GIT_SSH_COMMAND> unset and configuring ssh normally.

=item Provisioning happens on construction, not on demand

L</new> calls it, so a process that never constructs a C<Service::Git>
never provisions credentials even if the environment carries them. That
matches current usage, where every remote operation goes through this
class.

=item Presence of credentials is the only signal that this is CI

There is no explicit "running under CI" flag; C<GIT_PRIVATE_KEY> or
C<GIT_USERNAME> being set is taken to mean the caller wants Genesis to
answer git's credential prompts. An operator who exports those variables
for their own reasons would also get the prompt suppression, and would
see a failure where they expected to be asked. Setting C<GIT_ASKPASS> or
C<GIT_TERMINAL_PROMPT> explicitly opts back out, since both are applied
only when unset.

=back
